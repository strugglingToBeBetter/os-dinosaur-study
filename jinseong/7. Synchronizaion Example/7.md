# 7.1 Classic Problems of Synchronization

동기화 알고리즘이 제대로 동작하는지 검증할 때 반복적으로 사용되는 대표적인 문제들이다.

교재에서는 전통적으로 **semaphore**를 이용해서 해결 방법을 설명하지만, binary semaphore가 사용되는 부분은 실제 구현에서 **mutex lock**으로 대체할 수도 있다.

---

## 7.1.1 The Bounded-Buffer Problem

### 개념

Producer가 데이터를 만들어 **크기가 제한된 버퍼**에 넣고, Consumer가 그 데이터를 꺼내 사용하는 문제다.

```text
Producer
   ↓
┌───────────────┐
│   Buffer N개   │
└───────────────┘
   ↓
Consumer
```

문제는 Producer와 Consumer가 동시에 버퍼를 수정한다는 것이다.

따라서 다음 두 종류의 동기화가 필요하다.

| 목적                              | Semaphore |
| --------------------------------- | --------- |
| 버퍼 자체의 동시 접근 방지        | `mutex`   |
| 빈 공간의 개수 관리               | `empty`   |
| 데이터가 들어 있는 공간 개수 관리 | `full`    |

초기 상태는 다음과 같다.

```c
mutex = 1
empty = n
full  = 0
```

버퍼가 `n`칸이면 처음에는 모든 칸이 비어 있으므로 `empty=n`, 아직 데이터가 없으므로 `full=0`이다.

---

### Producer 동작

Producer는 먼저 데이터를 하나 만든다.

그 다음:

```text
wait(empty)
    ↓
빈 공간이 있는지 확인

wait(mutex)
    ↓
버퍼 독점

버퍼에 데이터 삽입

signal(mutex)
    ↓
버퍼 해제

signal(full)
    ↓
사용 가능한 데이터 +1
```

즉 개념적으로는 다음과 같다.

```c
produce item

wait(empty)
wait(mutex)

insert item

signal(mutex)
signal(full)
```

---

### Consumer 동작

Consumer는 반대로 움직인다.

```text
wait(full)
    ↓
꺼낼 데이터가 있는지 확인

wait(mutex)
    ↓
버퍼 독점

데이터 제거

signal(mutex)
    ↓
버퍼 해제

signal(empty)
    ↓
빈 공간 +1

consume item
```

```c
wait(full)
wait(mutex)

remove item

signal(mutex)
signal(empty)

consume item
```

---

### 왜 semaphore가 두 종류 필요한가?

`mutex`만 있으면 **동시에 버퍼를 변경하는 문제**는 막을 수 있다.

하지만 다음은 해결하지 못한다.

```text
Buffer가 가득 찼는데 Producer가 또 넣음
Buffer가 비었는데 Consumer가 꺼냄
```

그래서

```text
mutex → 누가 버퍼를 사용할 수 있는가
empty/full → 지금 버퍼 상태가 어떠한가
```

를 각각 관리한다.

### 핵심

```text
mutex = Mutual Exclusion
empty/full = Resource Counting
```

> **[추가 설명] 중요한 순서**
>
> Producer가 `mutex`를 먼저 잡은 뒤 `empty`를 기다리게 만들면 버퍼가 가득 찬 경우 Producer가 mutex를 쥔 채 잠들 수 있다. 그러면 Consumer도 버퍼를 비울 수 없어 deadlock으로 이어질 수 있다.
>
> 그래서 **자원이 있는지 먼저 확인 → mutex 획득** 순서가 중요하다.

# 7.1.2 The Readers–Writers Problem

## 개념

하나의 공유 데이터베이스를 여러 프로세스가 사용한다고 하자.

프로세스를 두 종류로 구분한다.

```text
Reader
→ 데이터 읽기만 수행

Writer
→ 데이터를 변경
```

Reader끼리는 동시에 실행되어도 문제가 없다.

```text
Reader A ─┐
Reader B ─┼→ Database    가능
Reader C ─┘
```

하지만 Writer가 등장하면 상황이 달라진다.

```text
Writer + Reader → 위험
Writer + Writer → 위험
```

따라서 Writer는 반드시 **exclusive access**를 가져야 한다.

---

## 두 가지 Readers-Writers 문제

### First Readers-Writers Problem

이미 Writer가 데이터 사용 권한을 획득한 경우가 아니라면 **Reader를 기다리게 해서는 안 된다.**

예를 들어:

```text
Reader 실행 중

Writer 도착 → 기다림
Reader 추가 도착 → 읽기 허용
Reader 추가 도착 → 읽기 허용
```

Reader를 우선하는 성격이다.

문제는 Reader가 계속 들어오면 Writer가 영원히 실행되지 못할 수 있다는 것이다.

```text
Writer Starvation
```

---

### Second Readers-Writers Problem

Writer가 기다리기 시작하면 가능한 한 빨리 Writer가 실행되어야 한다.

즉 Writer가 대기 중이라면 새로운 Reader의 진입을 막는다.

```text
Writer waiting
→ 새로운 Reader 진입 금지
```

이번에는 반대로 Reader가 starvation을 겪을 수 있다.

따라서

```text
First problem
→ Writer starvation 가능

Second problem
→ Reader starvation 가능
```

이다.

---

## First Readers-Writers Problem의 해결

공유 데이터는 다음과 같다.

```c
semaphore rw_mutex = 1;
semaphore mutex = 1;
int read_count = 0;
```

각 변수의 역할은 매우 중요하다.

| 변수         | 역할                                  |
| ------------ | ------------------------------------- |
| `rw_mutex`   | Writer와 Reader 집단 사이의 배타 접근 |
| `mutex`      | `read_count` 수정 보호                |
| `read_count` | 현재 읽고 있는 Reader 수              |

---

## Writer

Writer는 매우 단순하다.

```text
wait(rw_mutex)

write

signal(rw_mutex)
```

즉 Writer 하나가 들어가면 다른 Writer뿐 아니라 Reader도 들어갈 수 없다.

---

## Reader

Reader가 들어올 때 먼저 `read_count`를 증가시킨다.

```text
wait(mutex)
read_count++

if read_count == 1
    wait(rw_mutex)

signal(mutex)
```

여기서 핵심은 **첫 번째 Reader만 `rw_mutex`를 잡는다는 것**이다.

```text
Reader1
read_count = 1
→ rw_mutex 획득

Reader2
read_count = 2
→ rw_mutex 획득 안 함

Reader3
read_count = 3
→ rw_mutex 획득 안 함
```

따라서 Reader 여러 명이 동시에 읽을 수 있다.

---

읽기가 끝나면:

```text
wait(mutex)
read_count--

if read_count == 0
    signal(rw_mutex)

signal(mutex)
```

마지막 Reader가 나갈 때만 `rw_mutex`를 해제한다.

결국 Writer 입장에서는 Reader 집단 전체가 하나의 사용자처럼 보인다.

```text
       ┌ Reader 1
       ├ Reader 2
Writer │ Reader 3
       └ Reader 4
       ↑
   rw_mutex 하나
```

---

### Writer가 실행 중인데 Reader n명이 도착하면?

교재에서 짚는 세부 사항이다.

Writer가 `rw_mutex`를 보유한 상황에서 여러 Reader가 도착하면 첫 번째 Reader는 `rw_mutex`에서 막힌다.

그 Reader가 `mutex`도 잡고 있기 때문에 나머지 Reader들은 `mutex`에서 기다린다.

```text
Writer
 └─ rw_mutex 보유

Reader1
 └─ rw_mutex 기다림
    + mutex 보유

Reader2 ┐
Reader3 ├→ mutex 대기
Reader4 ┘
```

Writer가 `signal(rw_mutex)`를 수행한 뒤에는 기다리던 Reader 집단이나 다른 Writer 중 누가 먼저 실행될지는 **scheduler가 결정**한다.

---

# Reader-Writer Lock

이 문제를 일반화해서 운영체제와 라이브러리들은 **reader-writer lock**을 제공하기도 한다.

Lock 획득 모드가 두 가지다.

```text
Read Lock
→ 여러 스레드 동시 획득 가능

Write Lock
→ 단 하나의 스레드만 획득 가능
```

Reader-writer lock은 특히 다음 상황에서 효과적이다.

1. 어떤 작업이 읽기이고 어떤 작업이 쓰기인지 명확하게 구분할 수 있을 때
2. Writer보다 Reader가 훨씬 많을 때

Reader-writer lock 자체가 일반 mutex보다 관리 비용이 더 들 수 있지만, 여러 Reader가 동시에 접근할 수 있어서 **read-heavy workload에서는 동시성이 증가한다.**

# 7.1.3 The Dining-Philosophers Problem

## 개념

5명의 철학자가 원형 테이블에 앉아 있다.

```text
       P0

   P4      P1

   P3      P2
```

철학자 사이마다 젓가락 하나가 있다.

철학자가 밥을 먹으려면

```text
왼쪽 젓가락 + 오른쪽 젓가락
```

두 개를 모두 가져야 한다.

철학자는

```text
Thinking
   ↓
Hungry
   ↓
Eating
   ↓
Thinking
```

을 반복한다.

이 문제는 단순한 식사 문제가 아니라

> **여러 프로세스가 여러 개의 자원을 동시에 획득해야 하는 상황**

을 나타낸다.

---

## 7.1.3.1 Semaphore Solution

각 젓가락을 binary semaphore로 표현한다.

```text
chopstick[0] = 1
chopstick[1] = 1
...
chopstick[4] = 1
```

철학자 `i`는

```c
wait(left)
wait(right)

eat

signal(left)
signal(right)
```

형태로 행동한다.

이 방법은 **옆자리 철학자가 동시에 식사하는 것**은 방지한다.

하지만 심각한 문제가 있다.

---

## Deadlock 발생

5명이 동시에 배고파져 모두 왼쪽 젓가락을 잡았다고 하자.

```text
P0 → 왼쪽 획득
P1 → 왼쪽 획득
P2 → 왼쪽 획득
P3 → 왼쪽 획득
P4 → 왼쪽 획득
```

모든 철학자는 이제 오른쪽 젓가락을 기다린다.

그런데 그 오른쪽 젓가락은 옆 철학자가 가지고 있다.

```text
P0 waits P1
P1 waits P2
P2 waits P3
P3 waits P4
P4 waits P0
```

누구도 젓가락을 내려놓지 않는다.

즉 **Deadlock**이다.

---

## 교재가 제시하는 해결 방법

### 방법 1. 최대 4명만 테이블에 앉도록 제한

5명이 모두 자원 하나씩을 선점하는 상황 자체를 제거한다.

### 방법 2. 두 젓가락을 모두 사용할 수 있을 때만 가져가기

두 자원의 획득 여부를 하나의 critical section에서 검사한다.

```text
둘 다 있음 → 획득
하나라도 없음 → 아무것도 획득하지 않고 기다림
```

### 방법 3. 비대칭적 획득

```text
홀수 철학자
left → right

짝수 철학자
right → left
```

모든 철학자가 동일한 순환 대기를 만드는 것을 막는다.

---

## Deadlock-free ≠ Starvation-free

여기 매우 중요하다.

```text
Deadlock 없음
≠
모든 프로세스가 언젠가는 반드시 실행됨
```

Deadlock을 제거해도 특정 철학자가 계속 젓가락을 얻지 못한다면 **starvation**이 발생할 수 있다.

---

# 7.1.3.2 Monitor Solution

Monitor를 이용하면 **두 젓가락이 모두 사용 가능할 때만 철학자를 EATING 상태로 전환**할 수 있다.

철학자 상태를 세 가지로 정의한다.

```text
THINKING
HUNGRY
EATING
```

```c
state[5]
```

각 철학자마다 condition variable도 하나 둔다.

```c
self[5]
```

철학자 `i`가 먹을 수 있는 조건은:

```text
i가 HUNGRY

AND

왼쪽 철학자 != EATING

AND

오른쪽 철학자 != EATING
```

이다.

---

## pickup(i)

철학자가 배고파지면:

```text
state[i] = HUNGRY

test(i)

먹을 수 없다면
→ self[i]에서 wait
```

`test(i)`가 양쪽 철학자가 먹고 있지 않은지 확인한다.

조건을 만족하면:

```text
state[i] = EATING
signal(self[i])
```

한다.

---

## putdown(i)

식사를 끝내면:

```text
state[i] = THINKING
```

그리고 중요한 동작을 한다.

```text
왼쪽 이웃 test()
오른쪽 이웃 test()
```

즉 내가 젓가락을 놓았으므로 **나 때문에 먹지 못하던 이웃이 이제 먹을 수 있는지 검사**한다.

---

## Monitor 해결법의 특성

이 방법은

```text
인접한 두 철학자 동시 식사 방지
Deadlock 방지
```

를 보장한다.

하지만 교재는 여기서도 **starvation 가능성까지 제거된 것은 아니다**라고 강조한다.

---

# 7.2 Synchronization within the Kernel

지금까지는 추상적인 synchronization 문제였다면 이제 실제 운영체제의 kernel이 동기화를 어떻게 처리하는지 본다.

교재에서는 대표적으로

```text
Windows
Linux
```

를 비교한다.

---

# 7.2.1 Synchronization in Windows

Windows는 **multithreaded kernel**이며 멀티프로세서와 real-time application을 지원한다.

## Single Processor

단일 프로세서에서 Kernel이 어떤 global resource를 접근하는데 interrupt handler도 같은 자원을 사용할 가능성이 있다면 해당 interrupt를 잠시 mask한다.

```text
Kernel global resource 사용
       ↓
관련 interrupt disable
       ↓
critical operation
       ↓
interrupt enable
```

CPU가 하나이므로 interrupt를 막으면 경쟁자가 사실상 실행될 수 없다.

---

## Multiprocessor

CPU가 여러 개라면 한 CPU에서 interrupt를 막아도 다른 CPU가 실행될 수 있다.

따라서 Windows는 **spinlock**을 사용한다.

```text
CPU 0 → lock 보유

CPU 1 → spin
CPU 2 → spin
```

단, spinlock은 **아주 짧은 코드 영역**에만 사용한다.

또한 효율성을 위해 Windows kernel은 **spinlock을 보유한 thread가 preempt되지 않도록 한다.**

---

# Dispatcher Objects

Kernel 외부의 thread synchronization을 위해 Windows는 **dispatcher object**를 제공한다.

대표적으로:

| Dispatcher Object | 역할                      |
| ----------------- | ------------------------- |
| Mutex             | Mutual exclusion          |
| Semaphore         | 자원 개수 제어            |
| Event             | 조건 발생 통지            |
| Timer             | 일정 시간이 지났음을 통지 |

Event는 condition variable과 유사한 역할을 한다.

---

## Signaled / Nonsignaled State

Dispatcher object는 두 가지 상태를 가진다.

```text
Signaled
→ 사용 가능

Nonsignaled
→ 사용 불가능
```

Thread가 nonsignaled object를 얻으려고 하면:

```text
Ready
 ↓
Waiting
```

으로 바뀌고 해당 object의 waiting queue에 들어간다.

Object가 signaled가 되면 Kernel이 waiting thread를 깨운다.

---

### Mutex

Mutex는 한 thread만 소유할 수 있으므로 일반적으로 waiting queue에서 **한 thread**가 ready 상태로 이동한다.

### Event

Event는 조건 발생을 알리는 것이므로 **여러 waiting thread를 동시에 깨울 수 있다.**

---

# Windows Critical-Section Object

Windows에는 더 가벼운 **critical-section object**도 있다.

이는 user-mode mutex다.

경쟁이 없으면 kernel에 진입하지 않고 획득/해제가 가능하다.

Multiprocessor에서는 처음에는 짧게 spin한다.

```text
Lock 시도
 ↓
잠깐 spin
 ↓
곧 해제됨 → lock 획득
```

하지만 너무 오래 기다리면:

```text
kernel mutex 생성
→ CPU 양보
→ sleep
```

한다.

왜 효율적인가?

실제 프로그램에서는 lock contention이 없는 경우가 많다.

따라서 대부분의 경우:

```text
User Mode에서 처리
→ System call / kernel 전환 없음
```

이 되어 비용을 절감할 수 있다.

---

# 7.2.2 Synchronization in Linux

Linux 2.6 이전 kernel은 **nonpreemptive kernel**이었다.

즉 kernel mode에서 실행 중인 task를 다른 task가 강제로 뺏을 수 없었다.

현재 Linux kernel은 **fully preemptive**이므로 kernel mode에서도 조건을 만족하면 task가 preempt될 수 있다.

따라서 synchronization이 더욱 중요하다.

---

## Atomic Integer

Linux가 제공하는 가장 단순한 synchronization 도구 중 하나가 `atomic_t`이다.

예를 들어:

```c
atomic_t counter;
```

다음과 같은 연산을 atomic하게 수행할 수 있다.

```text
set
add
subtract
increment
read
```

예:

```c
atomic_inc(&counter);
```

의 전체 연산이 중간에 다른 thread에 의해 끼어들어 깨지지 않는다.

### 왜 사용하는가?

단순 counter처럼 변수 하나만 atomic하게 변경하면 되는 경우

```text
lock 획득
→ 수정
→ lock 해제
```

보다 비용이 적다.

그러나 여러 변수를 동시에 보호해야 한다면 `atomic_t`만으로 부족하다.

---

# Linux Mutex

Critical section에 들어가기 전:

```c
mutex_lock()
```

나온 후:

```c
mutex_unlock()
```

한다.

Mutex를 이미 다른 task가 가지고 있다면 요청한 task는 **sleep 상태**에 들어간다.

Lock이 해제되면 다시 깨어난다.

---

# Linux Spinlock

SMP 환경에서 짧은 critical section을 보호하는 기본적인 수단이다.

```text
CPU A → lock 보유
CPU B → 계속 확인하며 spin
```

Lock이 매우 짧게 유지된다면 context switch보다 spin이 더 싸다.

---

## Single CPU에서는?

CPU가 하나인데 spin을 하면 문제가 있다.

```text
Task A lock 보유

Task B spin
→ CPU 하나를 계속 사용

Task A 실행 못 함
→ lock을 풀 수 없음
```

그래서 single processor에서는 spinlock 대신 **kernel preemption을 disable**한다.

교재의 비교는 다음과 같다.

| Single Processor          | Multiple Processors |
| ------------------------- | ------------------- |
| Disable kernel preemption | Acquire spinlock    |
| Enable kernel preemption  | Release spinlock    |

---

# Linux Lock은 Nonrecursive

Linux kernel의 mutex와 spinlock은 **nonrecursive**이다.

```text
Thread A
lock(L)

lock(L)   ← 같은 lock 다시 획득
```

하면 두 번째 획득에서 자기 자신이 가진 lock을 기다리게 될 수 있다.

따라서 반드시 먼저 release해야 한다.

---

# `preempt_count`

Linux는 task마다 현재 얼마나 많은 lock을 보유하고 있는지를 나타내는 `preempt_count`를 관리한다.

```text
lock 획득
→ preempt_count++

lock 해제
→ preempt_count--
```

```text
preempt_count > 0
→ 현재 lock 보유
→ kernel preemption 불가

preempt_count == 0
→ 다른 조건도 만족한다면 preemption 가능
```

또한 Linux는

```text
preempt_disable()
preempt_enable()
```

을 제공한다.

---

## 어떤 lock을 언제 사용하는가?

```text
매우 짧음
→ spinlock / preemption disable

오래 걸릴 수 있음
→ mutex / semaphore
```

Spin 상태에서 오래 기다리면 CPU 시간이 낭비되기 때문이다.

---

# 7.3 POSIX Synchronization

7.2가 **kernel 내부** synchronization이라면 POSIX는 일반 application programmer가 사용하는 **user-level API**다.

주로 UNIX, Linux, macOS 환경에서 사용된다.

핵심은 세 가지다.

```text
Mutex
Semaphore
Condition Variable
```

---

# 7.3.1 POSIX Mutex Locks

Pthreads에서 가장 기본적인 synchronization 수단이다.

자료형은:

```c
pthread_mutex_t
```

초기화:

```c
pthread_mutex_init(&mutex, NULL);
```

`NULL`은 기본 속성을 사용한다는 의미다.

---

Critical section은 다음과 같이 보호한다.

```c
pthread_mutex_lock(&mutex);

/* critical section */

pthread_mutex_unlock(&mutex);
```

다른 thread가 mutex를 가지고 있으면 `pthread_mutex_lock()`을 호출한 thread는 기다린다.

소유자가 unlock하면 다시 획득할 수 있게 된다.

POSIX mutex 함수들은 정상 동작하면 `0`, 오류가 있으면 nonzero error code를 반환한다.

---

# 7.3.2 POSIX Semaphores

POSIX에서는 두 형태의 semaphore를 다룬다.

```text
Named Semaphore
Unnamed Semaphore
```

핵심적인 semaphore 동작은 동일하지만 **어떻게 생성하고 공유하느냐**가 다르다.

---

# 7.3.2.1 POSIX Named Semaphores

이름을 가진 semaphore다.

```c
sem_open(...)
```

으로 생성한다.

개념적으로:

```text
"SEM"이라는 이름의 semaphore
```

를 만든다.

초깃값을 `1`로 두면 binary semaphore처럼 사용할 수 있다.

가장 큰 장점은 **서로 관계가 없는 프로세스도 동일한 이름만 알면 같은 semaphore를 사용할 수 있다는 것**이다.

```text
Process A ─┐
           │ "SEM"
Process B ─┼──→ 동일 Semaphore
           │
Process C ─┘
```

Semaphore operation은:

```text
wait()   → sem_wait()
signal() → sem_post()
```

이다.

Linux와 macOS 모두 POSIX named semaphore를 지원한다고 교재는 설명한다.

---

# 7.3.2.2 POSIX Unnamed Semaphores

이름이 없는 semaphore다.

```c
sem_init(&sem, sharing_flag, initial_value);
```

세 매개변수는:

```text
1. semaphore pointer
2. 공유 범위
3. 초기값
```

이다.

예:

```c
sem_init(&sem, 0, 1);
```

여기서 두 번째 인자 `0`은

```text
이 semaphore를 만든 Process 내부의 thread들끼리 공유
```

한다는 의미다.

Nonzero를 사용하면 별도 프로세스 사이에서도 사용할 수 있는데, 이 경우 **shared memory 영역에 semaphore가 위치해야 한다.**

사용 방법은 동일하다.

```c
sem_wait(&sem);

/* critical section */

sem_post(&sem);
```

---

## Named vs Unnamed

|                         | Named        | Unnamed            |
| ----------------------- | ------------ | ------------------ |
| 식별                    | 이름         | 메모리 객체        |
| 생성                    | `sem_open()` | `sem_init()`       |
| 관련 없는 프로세스 공유 | 쉬움         | Shared memory 필요 |
| wait                    | `sem_wait()` | `sem_wait()`       |
| signal                  | `sem_post()` | `sem_post()`       |

---

# 7.3.3 POSIX Condition Variables

Condition variable은 단순히

```text
"지금 lock을 얻을 수 있나?"
```

가 아니라

```text
"내가 원하는 조건이 만족됐나?"
```

를 기다리는 도구다.

C에는 Java의 monitor 같은 언어 기능이 없기 때문에 POSIX에서는 **condition variable + mutex**를 함께 사용한다.

---

## 생성

```c
pthread_mutex_t mutex;
pthread_cond_t cond_var;
```

그리고 각각 초기화한다.

---

## 조건 기다리기

예를 들어:

```text
a == b가 될 때까지 기다린다.
```

면 개념적으로:

```c
pthread_mutex_lock(&mutex);

while (a != b)
    pthread_cond_wait(&cond_var, &mutex);

pthread_mutex_unlock(&mutex);
```

이다.

여기서 가장 중요한 것이 `pthread_cond_wait()`다.

호출하면:

```text
1. mutex를 놓는다.
2. condition variable에서 기다린다.
```

다른 thread가 lock을 얻어 `a`, `b`를 변경할 수 있어야 하기 때문이다.

---

## 왜 mutex를 놓아야 하는가?

만약:

```text
Thread A
mutex 보유
↓
a != b
↓
그대로 기다림
```

이면 다른 thread가 mutex를 얻지 못한다.

```text
Thread B
a = b로 변경해야 함
↓
mutex 필요
↓
Thread A가 가지고 있음
```

Deadlock과 비슷한 상황이 된다.

따라서 condition wait은 기다릴 때 mutex를 놓는다.

---

## Signal

다른 thread가 상태를 변경했다면:

```c
pthread_mutex_lock(&mutex);

a = b;

pthread_cond_signal(&cond_var);

pthread_mutex_unlock(&mutex);
```

한다.

중요한 점:

> `pthread_cond_signal()` 자체가 mutex를 해제하는 것은 아니다.

```text
signal
→ 기다리는 thread에게 알려줌

unlock
→ 실제 mutex 해제
```

이다.

Signal을 받은 thread는 lock을 다시 획득한 뒤 `pthread_cond_wait()`에서 돌아온다.

---

## 왜 `if`가 아니라 `while`인가?

조건을 다시 검사해야 하기 때문이다.

```c
while (a != b)
    wait();
```

Signal을 받았다고 해서 내가 실행되는 순간에도 반드시 조건이 참이라는 보장이 있다고 가정하면 안 된다.

따라서 깨어난 뒤 다시 검사한다.

---

# 7.4 Synchronization in Java

Java는 처음부터 thread synchronization 지원을 언어 수준에서 제공했다.

교재에서는 네 가지를 다룬다.

```text
Java Monitor
ReentrantLock
Semaphore
Condition Variable
```

---

# 7.4.1 Java Monitors

Java의 모든 object에는 **하나의 intrinsic lock**이 연결되어 있다.

Method에 `synchronized`를 붙이면 해당 object의 lock을 획득해야 method를 실행할 수 있다.

```java
public synchronized void insert(...) {
}
```

---

## Lock 획득

Thread A가 synchronized method를 실행하고 있으면 object lock을 가지고 있다.

그동안 Thread B가 같은 object의 synchronized method를 호출하면:

```text
Thread B
→ lock 없음
→ Entry Set에서 대기
```

한다.

---

# Entry Set

Entry set은

> **Object lock을 획득하기 위해 기다리는 thread들의 집합**

이다.

```text
Thread A → Object Lock 소유

Thread B ┐
Thread C ├→ Entry Set
Thread D ┘
```

Thread A가 method를 빠져나오면 lock이 풀리고 Entry Set 중 하나가 lock을 얻는다.

Java specification은 어떤 thread가 선택될지 특정 순서를 보장하지 않는다.

교재는 실제 JVM에서는 흔히 FIFO 형태로 구현되기도 한다고 설명한다.

---

# Block Synchronization

Method 전체가 critical section일 필요는 없다.

예:

```java
public void method() {

    // 일반 코드

    synchronized(this) {
        // critical section
    }

    // 일반 코드
}
```

이렇게 하면 **lock scope**를 줄일 수 있다.

Lock을 오래 보유할수록 다른 thread의 대기 시간이 늘어나므로 공유 데이터를 실제로 다루는 부분만 보호하는 것이 더 효율적일 수 있다.

---

# Wait Set

Java object에는 Entry Set 외에도 **Wait Set**이 있다.

```text
Entry Set
→ Lock을 얻고 싶어서 기다림

Wait Set
→ 특정 조건이 충족되길 기다림
```

이 차이를 반드시 구분해야 한다.

---

# `wait()`

Synchronized method 내부에서 조건을 만족하지 못하면 `wait()`을 호출할 수 있다.

`wait()`을 호출하면:

```text
1. Object lock 해제
2. Thread 상태 → blocked
3. Thread → Wait Set
```

으로 이동한다.

예를 들어 bounded buffer가 가득 찼다면 Producer는 wait한다.

```text
Producer
→ insert()
→ Buffer Full
→ wait()
→ lock 해제

Consumer
→ lock 획득
→ remove()
```

Consumer가 데이터를 하나 꺼내야 Producer가 다시 작업할 수 있기 때문이다.

---

# `notify()`

Consumer가 공간을 하나 만들면 `notify()`를 호출할 수 있다.

`notify()`는:

```text
Wait Set에서 thread 하나 선택
      ↓
Entry Set으로 이동
      ↓
blocked → runnable
```

시킨다.

하지만 여기서 굉장히 중요한 점이 있다.

> `notify()`를 호출했다고 바로 상대 thread가 실행되는 것이 아니다.

현재 Consumer가 여전히 object lock을 가지고 있다.

```text
Consumer
notify()
↓
Producer → Entry Set

Consumer synchronized method 종료
↓
lock 해제

Producer
↓
lock 다시 경쟁
↓
획득
↓
wait() 다음부터 실행
```

한다.

---

## Bounded Buffer에서의 동작

Producer:

```text
buffer full
→ wait()

공간 있음
→ insert
→ notify()
```

Consumer:

```text
buffer empty
→ wait()

데이터 있음
→ remove
→ notify()
```

여기 역시 조건은 `while`을 이용해 검사한다.

---

# 7.4.2 Reentrant Locks

Java 1.5 이후 API에는 `ReentrantLock`이 추가되었다.

기본 목적은 `synchronized`와 비슷하다.

```text
한 Thread만 critical section 진입
```

하지만 더 많은 기능을 제공한다.

예를 들어 **fairness 옵션**을 사용하면 오래 기다린 thread를 우선하도록 설정할 수 있다.

---

## Reentrant란?

Thread가 이미 lock을 가지고 있는 상태에서 같은 lock을 다시 획득할 수 있다.

```text
Thread A
lock()
  ↓
  함수 호출
    ↓
    lock()   ← 같은 Thread이므로 가능
```

그래서 이름이 **ReentrantLock**이다.

---

## 사용 방식

```java
lock.lock();

try {
    // critical section
}
finally {
    lock.unlock();
}
```

`finally`가 중요한 이유는 critical section 안에서 exception이 발생해도 lock을 반드시 해제하기 위해서다.

---

## 왜 `lock()`은 try 바깥인가?

교재가 꽤 세세하게 짚는 부분이다.

다음처럼 하면 안 된다.

```java
try {
    lock.lock();
}
finally {
    lock.unlock();
}
```

`lock()` 자체에서 unchecked exception이 발생해서 lock을 획득하지 못했는데도 `finally`가 실행되면 `unlock()`을 호출한다.

그러면 `IllegalMonitorStateException`이 발생하면서 원래 오류가 가려질 수 있다.

그래서:

```java
lock.lock();

try {
   ...
}
finally {
   lock.unlock();
}
```

구조를 사용한다.

---

# ReentrantReadWriteLock

일반 ReentrantLock은 Reader끼리도 동시에 들어가지 못한다.

Read-heavy application에서는 너무 보수적이다.

그래서 Java는:

```text
ReentrantReadWriteLock
```

도 제공한다.

```text
Read lock
→ 여러 Thread 가능

Write lock
→ 하나만 가능
```

7.1.2의 Readers-Writers Problem을 API 형태로 제공하는 셈이다.

---

# 7.4.3 Semaphores

Java에도 counting semaphore가 있다.

```java
new Semaphore(value)
```

교재에서는 초기값으로 음수도 허용한다고 설명한다.

Permit 획득:

```java
sem.acquire();
```

반환:

```java
sem.release();
```

`acquire()` 중 thread가 interrupt되면 `InterruptedException`이 발생할 수 있다.

Mutual exclusion 용도라면 permit을 1로 설정할 수 있다.

```text
Semaphore(1)
→ binary semaphore처럼 사용
```

---

# 7.4.4 Condition Variables

Java의 `wait()` / `notify()`에도 한계가 있다.

Object 하나에는 기본적으로 **하나의 unnamed wait set**이 있다.

따라서 thread가 `notify()`로 깨어났을 때

```text
"왜 내가 깨어났지?"
```

에 대한 정보를 직접적으로 알 수 없다.

그래서 Java의 `ReentrantLock`은 여러 Condition을 생성할 수 있게 한다.

---

## Condition 생성

```java
Lock lock = new ReentrantLock();
Condition condition = lock.newCondition();
```

Condition에는:

```text
await()
signal()
```

을 사용한다.

Monitor의

```text
wait()
signal()
```

과 비슷하다.

---

## 여러 조건을 분리할 수 있다는 장점

예를 들어 Thread가 5개 있고 순서대로 실행해야 한다고 하자.

```text
Thread 0
Thread 1
Thread 2
Thread 3
Thread 4
```

각 thread마다 Condition을 만들 수 있다.

```java
Condition[] conditions = new Condition[5];
```

Thread 2 차례가 아니면:

```text
conditions[2].await()
```

한다.

Thread 1이 일을 끝냈다면:

```text
turn = 2
conditions[2].signal()
```

처럼 **정확히 원하는 조건을 기다리는 thread를 깨울 수 있다.**

---

## `await()`의 특징

`await()` 역시 condition wait이므로 associated `ReentrantLock`을 놓는다.

```text
await()
→ lock release
→ wait
```

Signal을 받은 뒤 다시 lock을 획득해야 실행할 수 있다.

`signal()`도 lock을 해제하지 않는다.

```text
signal()
→ condition 통지

unlock()
→ 실제 lock 해제
```

이다.

따라서 ReentrantLock을 사용한다면 method에 `synchronized`를 추가로 붙일 필요는 없다.

---

# 7.5 Alternative Approaches

Multicore CPU가 증가하면서 application의 concurrency가 커졌다.

문제는 thread가 많아질수록:

```text
Race Condition
Deadlock
Lock Contention
Lock 관리 복잡도
```

도 증가한다는 것이다.

그래서 전통적인

```text
Mutex
Semaphore
Monitor
```

이외의 접근 방식도 연구되고 있다.

---

# 7.5.1 Transactional Memory

## 개념

Database의 transaction 개념을 memory synchronization에 적용한다.

**Memory transaction**은 여러 memory read/write operation을 하나의 atomic operation처럼 취급한다.

```text
Transaction 시작

Read
Write
Read
Write

모두 성공
→ Commit

중간 문제 발생
→ Abort
→ Rollback
```

---

## 기존 방식

```text
lock()

shared data 수정

unlock()
```

이다.

Thread가 많아질수록 lock contention과 deadlock 위험이 증가한다.

---

## Transactional Memory 방식

개념적으로:

```text
atomic {
    shared data 수정
}
```

이라고 선언한다.

그러면 programmer가 lock을 직접 관리하는 것이 아니라 **transactional memory system이 atomicity를 보장한다.**

장점은:

```text
Lock 직접 관리 감소
Deadlock 제거 가능
동시에 실행할 수 있는 작업 자동 판단 가능
```

이다.

특히 여러 thread가 동일 데이터를 read만 한다면 transactional system이 이를 병렬로 실행하도록 판단할 수 있다.

---

# Software Transactional Memory — STM

특수 hardware 없이 software로 구현한다.

Compiler가 transaction 영역에 instrumentation code를 넣는다.

이 코드가

```text
어떤 접근이 동시에 가능한지
어떤 부분에 실제 synchronization이 필요한지
```

를 관리한다.

장점:

```text
특수 hardware 불필요
```

단점:

```text
추가 instrumentation
→ overhead
```

이다.

---

# Hardware Transactional Memory — HTM

Hardware가 직접 지원한다.

주로:

```text
CPU Cache Hierarchy
Cache Coherency Protocol
```

을 이용해 여러 processor cache의 shared data conflict를 감지한다.

장점은 별도의 instrumentation이 필요 없어 STM보다 overhead가 작을 수 있다는 점이다.

대신 CPU cache와 coherency protocol 자체가 transactional memory를 지원해야 한다.

---

# 7.5.2 OpenMP

OpenMP는 shared-memory parallel programming을 지원한다.

4장에서 나온:

```c
#pragma omp parallel
```

뒤의 영역은 parallel region이 된다.

Thread 생성과 관리를 programmer가 직접 하지 않고 OpenMP runtime이 관리한다.

---

## Critical Section

OpenMP에서는:

```c
#pragma omp critical
{
    // critical section
}
```

로 critical section을 만들 수 있다.

예를 들어:

```c
counter += value;
```

를 여러 thread가 동시에 수행하면 race condition이 생길 수 있다.

이를:

```c
#pragma omp critical
{
    counter += value;
}
```

로 보호한다.

동작은 사실상 mutex/binary semaphore와 유사하다.

```text
Thread 하나만 진입

다른 Thread
→ 대기
```

한다.

여러 critical section에는 별도의 이름을 지정해서 같은 이름끼리 mutual exclusion을 적용할 수도 있다.

---

## 장단점

장점:

```text
직접 mutex를 생성하고 관리하는 것보다 사용하기 쉬움
```

단점:

```text
어디에 race condition이 발생하는지는
여전히 programmer가 찾아야 함
```

그리고 critical section 여러 개를 잘못 사용하면 **deadlock도 여전히 가능하다.**

즉 OpenMP가 concurrency bug를 자동으로 전부 제거해 주는 것은 아니다.

# 7.5.3 Functional Programming Languages

C, C++, Java, C# 같은 언어는 주로 **imperative / procedural language**다.

이들 언어의 특징은 상태가 변한다는 것이다.

```text
x = 1
x = 2
x = 3
```

즉 mutable state가 있다.

Race condition의 근본적인 원인도 여러 thread가 **mutable shared state를 동시에 변경하기 때문**이다.

---

## Functional Programming

Functional language에서는 핵심적으로 **immutable state**를 강조한다.

한 번 값이 정해지면 바뀌지 않는 방식이다.

```text
Shared mutable state가 없음
           ↓
동시에 수정할 대상이 줄어듦
           ↓
Race condition 문제가 크게 감소
```

따라서 교재는 functional paradigm에서는 이 장에서 다룬 많은 synchronization 문제가 애초에 발생하지 않는다고 설명한다.

대표적인 언어로:

```text
Erlang
Scala
```

를 언급한다.

Erlang은 concurrency와 parallel system 개발 지원으로 주목받았고, Scala는 functional programming과 object-oriented programming을 함께 지원한다.

# Chapter 7 핵심 요약

### 1. Mutex와 Semaphore를 구분해야 한다

```text
Mutex
→ "누가 들어갈 수 있는가"

Semaphore
→ "몇 개를 사용할 수 있는가"
```

Bounded buffer에서 이 차이가 명확하다.

```text
mutex → buffer 접근 보호
empty/full → buffer 개수 관리
```

### 2. Condition Variable은 Lock이 아니다

Condition variable은:

```text
조건이 만족될 때까지 기다리는 기능
```

이다.

따라서 대부분:

```text
Mutex + Condition Variable
```

형태로 사용된다.

### 3. `wait()`은 Lock을 놓는다

POSIX와 Java 모두 핵심 원리가 같다.

```text
Lock 획득
→ 조건 검사
→ 조건 불충족
→ wait
→ Lock release
→ Sleep
→ signal
→ Lock 재획득
→ 조건 재검사
```

### 4. Signal은 Lock Release가 아니다

```text
signal / notify
→ 기다리는 Thread 깨우기

unlock
→ Lock 해제
```

서로 다른 작업이다.

### 5. Deadlock-free가 Starvation-free를 의미하지 않는다

Dining Philosophers에서 가장 잘 드러난다.

```text
Deadlock 없음
≠
모든 Thread가 공정하게 실행됨
```

# 면접 포인트

### Q. Mutex와 Semaphore의 차이는?

**Mutex는 critical section의 mutual exclusion을 위한 소유권 기반 lock이고, semaphore는 정수 값을 이용해 사용 가능한 자원의 개수를 관리합니다.** Binary semaphore는 mutex와 유사하게 사용할 수 있지만 개념적인 목적과 소유권 특성이 다릅니다.

---

### Q. Condition Variable을 사용할 때 왜 Mutex가 필요한가?

조건을 검사하는 순간과 wait에 진입하는 과정에서 다른 thread가 공유 상태를 변경하면 race condition이 발생할 수 있기 때문이다.

따라서:

```text
Mutex 획득
→ 조건 검사
→ wait하면서 Mutex 해제
```

가 하나의 synchronization 과정으로 이루어진다.

---

### Q. `wait()`과 `notify()`에서 가장 중요한 점은?

`wait()`은 **현재 보유한 object lock을 놓고 Wait Set으로 들어간다.**

반대로 `notify()`는 waiting thread를 바로 실행시키는 것이 아니다.

```text
Wait Set
→ Entry Set
```

으로 옮길 뿐이며, notifier가 lock을 해제한 이후 다시 lock을 획득해야 실행될 수 있다.

---

### Q. Spinlock과 Mutex를 언제 사용하나?

```text
Critical Section이 매우 짧음
+ Multiprocessor
→ Spinlock

기다리는 시간이 길 수 있음
→ Mutex / Semaphore
```

Spinlock은 context switch가 없다는 장점이 있지만 오래 기다리면 CPU를 낭비한다.

---

### Q. Readers-Writers Problem에서 Reader는 왜 여러 명 들어갈 수 있나?

Reader는 데이터를 변경하지 않기 때문에 여러 Reader의 동시 접근이 서로에게 영향을 주지 않는다.

Writer는 데이터를 변경하므로:

```text
Writer ↔ Writer
Writer ↔ Reader
```

사이에는 mutual exclusion이 필요하다.

---

### Q. Java의 Entry Set과 Wait Set 차이는?

```text
Entry Set
→ Object Lock을 기다림

Wait Set
→ 특정 조건이 만족되기를 기다림
```

`notify()`된 thread는 Wait Set에서 Entry Set으로 이동하고, 다시 lock 경쟁을 해야 한다.

---

### Q. Linux single-core에서 spinlock을 쓰지 않는 이유는?

CPU가 하나라면 lock을 기다리며 spin하는 동안 **lock을 가진 task가 CPU를 사용할 수 없기 때문**이다.

그래서 single-core에서는:

```text
spinlock
대신
kernel preemption disable
```

방식을 사용할 수 있다.

---

### Q. `synchronized`와 `ReentrantLock` 차이는?

둘 다 mutual exclusion을 제공하지만 `ReentrantLock`은 명시적인 `lock()/unlock()` API를 사용하며 **fairness 설정, 여러 Condition 연결 등의 더 세밀한 기능**을 제공한다.

---

### Q. Transactional Memory가 나온 이유는?

Core와 thread 수가 많아질수록 직접 lock을 설계하는 것이 복잡해지고 lock contention과 deadlock 가능성도 증가한다.

Transactional memory는:

```text
atomic {
    shared data operation
}
```

처럼 programmer가 작업 범위를 지정하면 시스템이 atomicity와 conflict 처리를 담당하도록 하려는 접근이다.
