# 3.5 IPC in Shared-Memory Systems

## 3.5.1 공유 메모리의 개념

**공유 메모리(Shared Memory)**는 서로 독립된 주소 공간을 가진 프로세스들이 특정 메모리 영역을 공동으로 사용할 수 있도록 하는 IPC 방식이다.

원칙적으로 운영체제는 프로세스가 다른 프로세스의 메모리에 접근하지 못하도록 보호한다.

```text
Process A 주소 공간      Process B 주소 공간
┌──────────────┐        ┌──────────────┐
│ A의 데이터   │        │ B의 데이터   │
└──────────────┘        └──────────────┘

기본적으로 서로 접근할 수 없음
```

공유 메모리를 사용하면 운영체제가 특정 메모리 영역을 두 프로세스의 주소 공간에 연결한다.

```text
Process A                 Process B
┌──────────────┐         ┌──────────────┐
│ 일반 메모리  │         │ 일반 메모리  │
├──────────────┤         ├──────────────┤
│ 공유 메모리  │◀───────▶│ 공유 메모리  │
└──────────────┘         └──────────────┘
```

두 프로세스는 공유 영역에 데이터를 읽고 쓰면서 정보를 교환한다.

---

## 3.5.2 공유 메모리의 동작

공유 메모리는 일반적으로 다음 순서로 사용한다.

1. 한 프로세스가 공유 메모리 영역을 생성한다.
2. 다른 프로세스가 해당 영역을 자신의 주소 공간에 연결한다.
3. 프로세스들이 공유 영역을 읽고 쓴다.
4. 사용이 끝나면 연결을 해제하고 공유 메모리를 제거한다.

```text
Process A
    │
    │ 공유 메모리 생성 요청
    ▼
운영체제
    │
    │ 공유 메모리 영역 생성
    ▼
Shared Memory
    ▲
    │ 연결
Process B
```

공유 메모리 영역을 생성하고 연결하는 과정에는 시스템 콜이 필요하다. 그러나 영역이 설정된 이후에는 일반적인 메모리 접근처럼 사용할 수 있다.

```text
초기 설정:
Process → 시스템 콜 → Kernel → 공유 메모리 생성

설정 이후:
Process A ↔ Shared Memory ↔ Process B
```

즉, 데이터를 교환할 때마다 커널을 거칠 필요가 없다.

---

## 3.5.3 공유 메모리가 빠른 이유

메시지 전달 방식에서는 데이터를 전송할 때 일반적으로 커널이 중간에 개입한다.

```text
Process A
    │ 데이터 복사
    ▼
Kernel
    │ 데이터 복사
    ▼
Process B
```

반면 공유 메모리는 설정 이후 두 프로세스가 같은 메모리 영역에 직접 접근한다.

```text
Process A ── 읽기·쓰기 ── Shared Memory ── 읽기·쓰기 ── Process B
```

따라서 대량의 데이터를 반복적으로 교환할 때 공유 메모리가 메시지 전달보다 빠를 수 있다. 교재에서도 공유 메모리는 초기 영역 생성 이후 일반 메모리 접근으로 처리되어 커널 개입이 줄어든다고 설명한다.

---

## 3.5.4 공유 메모리의 책임 주체

공유 메모리에 어떤 형식으로 데이터를 저장할지, 어느 위치에 어떤 값을 둘지는 운영체제가 결정하지 않는다.

통신하는 프로세스들이 직접 약속해야 한다.

```text
공유 메모리 구조 예시

offset 0    : 데이터 개수
offset 4    : 첫 번째 데이터
offset 8    : 두 번째 데이터
offset 12   : 상태 플래그
```

또한 여러 프로세스가 동시에 같은 영역을 수정하지 않도록 프로세스들이 직접 동기화해야 한다.

---

## 3.5.5 Producer–Consumer Problem

공유 메모리의 대표적인 예시는 **생산자–소비자 문제(Producer–Consumer Problem)**다.

- 생산자: 데이터를 생성한다.
- 소비자: 생성된 데이터를 사용한다.
- 버퍼: 생산자와 소비자 사이에서 데이터를 보관한다.

```text
Producer ── 데이터 생성 ──▶ Shared Buffer ── 데이터 소비 ──▶ Consumer
```

예를 들어 웹 서버에서 요청을 받는 프로세스가 생산자이고, 요청을 실제로 처리하는 워커 프로세스가 소비자일 수 있다.

---

### Unbounded Buffer

버퍼의 크기에 제한이 없다고 가정하는 방식이다.

```text
Producer → [ item ][ item ][ item ][ item ] → Consumer
                    제한 없음
```

생산자는 버퍼가 가득 차는 상황을 고려하지 않아도 된다.

하지만 실제 컴퓨터의 메모리는 유한하므로 현실적인 구현에서는 완전히 무한한 버퍼를 만들 수 없다.

---

### Bounded Buffer

크기가 고정된 버퍼를 사용하는 방식이다.

```text
버퍼 크기 = 5

[ item ][ item ][      ][      ][      ]
```

이 경우 다음 규칙이 필요하다.

- 버퍼가 가득 차면 생산자는 기다린다.
- 버퍼가 비어 있으면 소비자는 기다린다.
- 빈 공간이 생기면 생산자가 다시 데이터를 넣는다.
- 데이터가 들어오면 소비자가 다시 꺼낸다.

```text
버퍼가 가득 참
Producer → Waiting

Consumer가 데이터 제거
→ 빈 공간 발생
→ Producer가 다시 실행 가능
```

---

## 3.5.6 Circular Buffer

고정 크기 버퍼를 효율적으로 사용하기 위해 **원형 버퍼(Circular Buffer)**를 사용할 수 있다.

교재에서는 다음 두 변수를 사용한다.

- `in`: 생산자가 다음 데이터를 넣을 위치
- `out`: 소비자가 다음 데이터를 꺼낼 위치

```text
buffer[0] buffer[1] buffer[2] buffer[3] buffer[4]
    ▲                                       ▲
   out                                      in
```

인덱스가 배열 끝에 도달하면 다시 처음으로 돌아간다.

```c
in = (in + 1) % BUFFER_SIZE;
out = (out + 1) % BUFFER_SIZE;
```

예를 들어 버퍼 크기가 5이고 `in`이 4였다면 다음 위치는 다음과 같다.

```text
(4 + 1) % 5 = 0
```

따라서 버퍼를 원형으로 재사용할 수 있다.

---

### 버퍼가 비어 있는 조건

```c
in == out
```

생산자가 넣을 위치와 소비자가 꺼낼 위치가 같으면 버퍼가 비어 있다고 판단한다.

---

### 버퍼가 가득 찬 조건

교재의 기본 구현에서는 다음 조건을 사용한다.

```c
(in + 1) % BUFFER_SIZE == out
```

이 방식에서는 빈 상태와 가득 찬 상태를 구분하기 위해 실제 버퍼 크기보다 하나 적은 개수만 저장할 수 있다.

예를 들어 배열 크기가 10이라면 최대 9개만 저장한다.

```text
실제 배열 크기: 10
사용 가능한 공간: 9
```

---

## 3.5.7 Producer 코드의 개념

생산자는 버퍼가 가득 차지 않을 때까지 기다린 후 데이터를 저장한다.

```c
while (true) {
    /* next_produced에 데이터 생성 */

    while ((in + 1) % BUFFER_SIZE == out) {
        ; // 버퍼가 가득 차면 대기
    }

    buffer[in] = next_produced;
    in = (in + 1) % BUFFER_SIZE;
}
```

`while`문 안에서 계속 조건을 확인하며 기다리는 방식은 **Busy Waiting**이다.

```text
CPU를 놓지 않고 계속 확인

버퍼 비었나?
버퍼 비었나?
버퍼 비었나?
...
```

이 방식은 CPU를 낭비할 수 있으며, 이후 동기화 장에서 세마포어와 뮤텍스를 이용해 개선한다.

---

## 3.5.8 Consumer 코드의 개념

소비자는 버퍼가 비어 있지 않을 때 데이터를 가져간다.

```c
while (true) {
    while (in == out) {
        ; // 버퍼가 비어 있으면 대기
    }

    next_consumed = buffer[out];
    out = (out + 1) % BUFFER_SIZE;

    /* next_consumed 소비 */
}
```

생산자와 소비자는 `buffer`, `in`, `out`을 공유한다.

```text
공유 데이터
├── buffer[]
├── in
└── out
```

따라서 접근 순서가 잘못되면 Race Condition이 발생할 수 있다.

---

## 3.5 핵심 요약

- 공유 메모리는 여러 프로세스가 같은 메모리 영역을 읽고 쓰는 IPC 방식이다.
- 초기 설정에는 커널이 개입하지만, 설정 이후에는 일반 메모리 접근처럼 동작한다.
- 데이터 복사가 적어 대량 데이터 통신에 유리하다.
- 공유 데이터의 형식과 접근 순서는 프로세스가 직접 관리한다.
- 동시에 같은 위치를 수정하면 Race Condition이 발생할 수 있다.
- 생산자–소비자 문제는 공유 메모리의 대표적인 예다.
- 원형 버퍼는 고정된 버퍼 공간을 반복적으로 사용할 수 있게 한다.

# 3.6 IPC in Message-Passing Systems

## 3.6.1 메시지 전달의 개념

**메시지 전달(Message Passing)**은 프로세스들이 공유 메모리를 직접 사용하지 않고 메시지를 보내고 받으며 통신하는 방식이다.

기본 연산은 다음 두 가지다.

```text
send(message)
receive(message)
```

```text
Process A
    │ send(message)
    ▼
운영체제의 통신 기능
    │ receive(message)
    ▼
Process B
```

메시지 전달 방식은 동일한 컴퓨터뿐만 아니라 네트워크로 연결된 다른 컴퓨터의 프로세스와 통신할 때도 사용할 수 있다.

---

## 3.6.2 Communication Links

프로세스 P와 Q가 통신하려면 두 프로세스 사이에 **통신 링크(Communication Link)**가 존재해야 한다.

```text
Process P ◀──────── Communication Link ────────▶ Process Q
```

통신 링크는 다음 속성에 따라 여러 방식으로 설계할 수 있다.

- 직접 통신 또는 간접 통신
- 동기식 또는 비동기식
- 자동 버퍼링 또는 명시적 버퍼링
- 단방향 또는 양방향
- 고정 크기 메시지 또는 가변 크기 메시지

---

## 3.6.1 Naming

> 교재 번호 기준으로 `3.6.1 Naming`이다.

메시지를 누구에게 보낼 것인지 지정하는 방식에 따라 **직접 통신**과 **간접 통신**으로 나뉜다.

---

### Direct Communication

송신자와 수신자가 서로의 이름을 명시적으로 지정한다.

```text
send(P, message)
receive(Q, message)
```

예를 들어 프로세스 A가 B에게 메시지를 보낸다면 다음처럼 표현할 수 있다.

```text
send(B, message)
```

B는 A가 보낸 메시지를 받는다.

```text
receive(A, message)
```

---

### 직접 통신의 특징

- 통신하려는 두 프로세스가 서로의 이름을 알아야 한다.
- 두 프로세스 사이에 자동으로 링크가 설정된다.
- 하나의 링크는 일반적으로 정확히 두 프로세스와 연결된다.
- 두 프로세스 사이에는 하나의 링크만 존재한다.

```text
Process A ───── 직접 링크 ───── Process B
```

---

### Addressing Symmetry

송신자와 수신자가 모두 상대방 이름을 명시하는 방식을 **대칭 주소 지정(Symmetric Addressing)**이라고 한다.

```text
send(P, message)
receive(Q, message)
```

반면 수신자가 누구에게서 온 메시지인지 미리 지정하지 않는 방식도 있다.

```text
send(P, message)
receive(id, message)
```

수신된 메시지의 송신자 정보가 `id`에 저장된다. 이를 비대칭 주소 지정으로 볼 수 있다.

---

### 직접 통신의 단점

프로세스 이름이 통신 코드에 직접 연결된다.

```text
Process A가 반드시 Process B를 알아야 함
```

따라서 프로세스 구성이 변경되거나 수신자가 바뀌면 코드를 수정해야 할 수 있다.

이는 모듈 간 결합도를 높인다.

---

### Indirect Communication

간접 통신에서는 메시지를 프로세스에게 직접 보내지 않고 **메일박스(Mailbox)** 또는 **포트(Port)**에 보낸다.

```text
Process A
    │
    │ send(mailbox, message)
    ▼
Mailbox
    │
    │ receive(mailbox, message)
    ▼
Process B
```

기본 연산은 다음과 같다.

```text
send(A, message)
receive(A, message)
```

여기서 `A`는 프로세스 이름이 아니라 메일박스 이름이다.

---

### 메일박스의 역할

메일박스는 메시지를 임시로 보관하는 운영체제 객체다.

```text
Mailbox A
┌──────────────┐
│ Message 1    │
│ Message 2    │
│ Message 3    │
└──────────────┘
```

프로세스는 다음 작업을 수행할 수 있다.

- 새 메일박스 생성
- 메일박스로 메시지 전송
- 메일박스에서 메시지 수신
- 메일박스 제거

---

### 간접 통신의 특징

- 프로세스들이 동일한 메일박스를 공유할 때만 통신할 수 있다.
- 하나의 메일박스에 여러 프로세스가 연결될 수 있다.
- 두 프로세스 사이에 여러 메일박스가 존재할 수 있다.
- 송신자는 실제 수신자가 누구인지 몰라도 된다.

```text
Process A ─┐
Process B ─┼── Mailbox M
Process C ─┘
```

---

### 여러 수신자가 있는 경우

프로세스 P가 메일박스 M에 메시지를 보내고, Q와 R이 모두 M에서 메시지를 받으려고 할 수 있다.

```text
          ┌── Process Q
Mailbox M ┤
          └── Process R
```

이때 어떤 프로세스가 메시지를 받을 것인지 결정해야 한다.

가능한 정책은 다음과 같다.

1. 링크를 최대 두 프로세스만 공유하도록 제한한다.
2. 한 번에 한 프로세스만 `receive()`를 수행하도록 제한한다.
3. 운영체제가 임의로 수신자를 선택한다.
4. 송신자에게 어느 프로세스가 메시지를 받았는지 알려준다.

---

## 3.6.2 Synchronization

메시지 전달은 `send()`와 `receive()`가 호출됐을 때 프로세스가 기다리는지에 따라 동기식과 비동기식으로 나뉜다.

---

### Blocking Send

송신한 메시지가 수신자 또는 메일박스에 전달될 때까지 송신 프로세스가 기다린다.

```text
Process A
    │ send()
    ▼
Waiting
    │ 메시지 전달 완료
    ▼
Ready
```

---

### Nonblocking Send

메시지를 전송한 뒤 송신 프로세스가 즉시 다음 작업을 수행한다.

```text
Process A
    │ send()
    ▼
다음 명령어 계속 실행
```

---

### Blocking Receive

받을 메시지가 없으면 수신 프로세스가 기다린다.

```text
Process B
    │ receive()
    ▼
메시지 없음
    ▼
Waiting
    │ 메시지 도착
    ▼
Ready
```

---

### Nonblocking Receive

메시지가 있으면 메시지를 반환하고, 없으면 `null` 등의 값을 반환한다.

```text
message = receive()

메시지 있음 → message 반환
메시지 없음 → null 반환
```

---

### 조합

| Send        | Receive     | 의미                                            |
| ----------- | ----------- | ----------------------------------------------- |
| Blocking    | Blocking    | 송신자와 수신자가 서로 만날 때까지 기다림       |
| Blocking    | Nonblocking | 송신자는 전달을 기다리고 수신자는 즉시 확인     |
| Nonblocking | Blocking    | 송신자는 계속 실행하고 수신자는 메시지를 기다림 |
| Nonblocking | Nonblocking | 양쪽 모두 즉시 반환                             |

---

### Rendezvous

`send()`와 `receive()`가 모두 Blocking이면 송신자와 수신자가 서로 만나는 형태가 된다.

이를 **랑데부(Rendezvous)**라고 한다.

```text
Sender                 Receiver
  │ send()                │ receive()
  │                       │
  └──────── 만나야 진행 ──┘
```

생산자–소비자 문제에서 Blocking 통신을 사용하면 별도의 Busy Waiting 없이 구현할 수 있다.

```c
// Producer
while (true) {
    /* item 생산 */
    send(item);
}
```

```c
// Consumer
while (true) {
    receive(item);
    /* item 소비 */
}
```

메시지 전달은 Blocking 또는 Nonblocking으로 설계할 수 있으며, 두 연산이 모두 Blocking이면 송신자와 수신자가 랑데부한다.

---

## 3.6.3 Buffering

전송된 메시지는 수신되기 전까지 임시 큐에 저장된다.

```text
Sender → Message Queue → Receiver
```

큐의 크기에 따라 세 가지 방식으로 나뉜다.

---

### Zero Capacity

메시지 큐의 크기가 0이다.

```text
Sender ───── 직접 전달 ─────▶ Receiver
```

메시지를 저장할 공간이 없으므로 수신자가 메시지를 받을 준비가 될 때까지 송신자가 기다려야 한다.

```text
Sender send()
    ↓
Receiver receive() 전까지 Blocking
```

이 방식을 **No Buffering**이라고도 한다.

---

### Bounded Capacity

큐의 크기가 고정되어 있다.

```text
최대 크기 = 3

[ message ][ message ][ empty ]
```

큐가 가득 차지 않았다면 송신자는 메시지를 넣고 계속 실행한다.

```text
Queue에 공간 있음
→ 메시지 저장
→ Sender 계속 실행
```

큐가 가득 차면 공간이 생길 때까지 송신자가 기다린다.

```text
Queue full
→ Sender Waiting
→ Receiver가 메시지 제거
→ Sender Ready
```

---

### Unbounded Capacity

큐의 크기가 이론적으로 무제한이다.

```text
[ message ][ message ][ message ][ ... ]
```

큐가 가득 차지 않는다고 가정하므로 송신자는 메시지 큐 공간 때문에 기다리지 않는다.

실제 시스템의 메모리는 유한하기 때문에 현실적으로 완전히 무제한은 아니지만, 개념적으로 충분히 큰 큐를 의미한다.

---

### 버퍼 방식 비교

| 방식               |         큐 크기 | 송신자 Blocking              |
| ------------------ | --------------: | ---------------------------- |
| Zero Capacity      |               0 | 수신자가 받을 때까지 기다림  |
| Bounded Capacity   |            유한 | 큐가 가득 차면 기다림        |
| Unbounded Capacity | 무제한으로 가정 | 큐 공간 때문에 기다리지 않음 |

교재는 메시지 큐를 Zero, Bounded, Unbounded Capacity로 구분한다.

---

## 3.6 핵심 요약

- 메시지 전달은 `send()`와 `receive()`로 통신한다.
- 직접 통신은 상대 프로세스 이름을 지정한다.
- 간접 통신은 메일박스 또는 포트를 통해 통신한다.
- Blocking 연산은 조건이 충족될 때까지 프로세스를 기다리게 한다.
- Nonblocking 연산은 즉시 반환한다.
- Send와 Receive가 모두 Blocking이면 Rendezvous가 발생한다.
- 메시지는 임시 큐에 저장될 수 있다.
- 메시지 큐는 Zero, Bounded, Unbounded Capacity로 나뉜다.

---

# 3.7 Examples of IPC Systems

교재는 IPC의 실제 구현 사례로 다음 네 가지를 소개한다.

1. POSIX Shared Memory
2. Mach Message Passing
3. Windows IPC
4. Pipes

---

## 3.7.1 POSIX Shared Memory

POSIX 공유 메모리는 **Memory-Mapped File**을 이용한다.

파일이나 공유 메모리 객체를 프로세스의 주소 공간에 매핑하면 프로세스는 포인터를 통해 해당 영역에 접근할 수 있다.

```text
공유 메모리 객체
       │
       ├── Process A 주소 공간에 mmap
       └── Process B 주소 공간에 mmap
```

---

### 주요 함수

| 함수           | 역할                                    |
| -------------- | --------------------------------------- |
| `shm_open()`   | 공유 메모리 객체 생성 또는 열기         |
| `ftruncate()`  | 공유 메모리 객체의 크기 설정            |
| `mmap()`       | 공유 메모리를 프로세스 주소 공간에 매핑 |
| `shm_unlink()` | 공유 메모리 객체 제거                   |

---

### `shm_open()`

공유 메모리 객체를 생성하거나 연다.

```c
fd = shm_open(name, O_CREAT | O_RDWR, 0666);
```

- `name`: 공유 메모리 객체 이름
- `O_CREAT`: 객체가 없으면 생성
- `O_RDWR`: 읽기와 쓰기 허용
- 반환값 `fd`: 공유 메모리 객체의 파일 디스크립터

---

### `ftruncate()`

공유 메모리의 크기를 지정한다.

```c
ftruncate(fd, SIZE);
```

예를 들어 `SIZE`가 4096이면 4KB 크기의 공유 메모리를 생성한다.

---

### `mmap()`

공유 메모리 객체를 프로세스의 주소 공간에 연결한다.

```c
ptr = mmap(
    0,
    SIZE,
    PROT_READ | PROT_WRITE,
    MAP_SHARED,
    fd,
    0
);
```

`MAP_SHARED`를 지정하면 한 프로세스가 변경한 내용이 같은 객체를 매핑한 다른 프로세스에도 보인다.

---

### 생산자 흐름

```text
shm_open()
    ↓
ftruncate()
    ↓
mmap()
    ↓
공유 메모리에 데이터 쓰기
```

교재의 생산자 예제는 `"OS"`라는 공유 메모리 객체를 만들고 `"Hello World!"`를 기록한다.

---

### 소비자 흐름

```text
shm_open()
    ↓
mmap()
    ↓
공유 메모리 데이터 읽기
    ↓
shm_unlink()
```

소비자는 기존 공유 메모리 객체를 열어 내용을 읽고, 사용이 끝난 후 `shm_unlink()`로 객체를 제거한다.

---

### 주의할 점

공유 메모리에 데이터가 존재한다고 해서 생산자와 소비자의 실행 순서가 자동으로 맞춰지는 것은 아니다.

```text
소비자가 먼저 실행
→ 생산자가 아직 데이터를 쓰지 않음
→ 잘못된 값 읽을 가능성
```

따라서 실제 프로그램에서는 별도의 동기화가 필요하다.

---

## 3.7.2 Mach Message Passing

Mach 운영체제는 메시지 전달을 중심으로 설계되었다.

Mach에서 시스템 콜과 프로세스 간 통신은 메시지 전달 방식으로 수행된다.

---

### Port

Mach에서 메시지를 주고받는 기본 객체는 **포트(Port)**다.

포트는 메시지를 저장하는 커널 관리 큐다.

```text
Process A
    │ message
    ▼
Mach Port
    │ message
    ▼
Process B
```

포트는 특정 프로세스의 물리적인 위치보다 독립적인 통신 종점으로 볼 수 있다.

---

### 권한

Mach에서는 포트에 대해 권한을 가진 프로세스만 메시지를 보내거나 받을 수 있다.

대표적으로 다음 권한이 있다.

- Send Right: 포트로 메시지를 보낼 수 있는 권한
- Receive Right: 포트에서 메시지를 받을 수 있는 권한

일반적으로 하나의 포트에는 하나의 수신 권한이 있지만 여러 송신 권한이 존재할 수 있다.

```text
Process A ─┐
Process B ─┼── Send Right ──▶ Port
Process C ─┘

Process D ─── Receive Right ◀── Port
```

---

### 메시지 크기

작은 메시지는 일반적으로 커널이 복사한다.

대용량 메시지는 실제 데이터를 전부 복사하지 않고 가상 메모리 기술을 활용할 수 있다.

```text
작은 메시지
Process A → Kernel 복사 → Process B

큰 메시지
메모리 매핑 또는 가상 복사 활용
```

복사 비용을 줄이기 위해 Copy-on-Write와 유사한 기법을 사용할 수 있다.

---

### Mailbox와 Port의 관계

Mach의 포트는 앞서 배운 간접 통신의 메일박스와 같은 역할을 한다.

```text
일반 IPC 개념     Mach
Mailbox       ≈   Port
```

---

## 3.7.3 Windows

Windows는 **Advanced Local Procedure Call, ALPC**를 사용해 로컬 프로세스 간 통신을 지원한다.

> 교재에서는 당시 명칭과 구조를 중심으로 설명하며, 핵심은 Windows가 포트 기반 메시지 전달과 공유 메모리를 결합한다는 점이다.

---

### 연결 포트와 통신 포트

서버는 클라이언트가 접근할 수 있는 연결 포트를 공개한다.

```text
Client
   │ 연결 요청
   ▼
Server Connection Port
```

연결이 성립하면 클라이언트와 서버가 사용할 통신 채널이 만들어진다.

```text
Client-to-Server Port
Server-to-Client Port
```

이를 통해 양방향 통신이 가능하다.

---

### 메시지 크기에 따른 처리

Windows는 메시지 크기에 따라 다른 전달 방식을 사용할 수 있다.

#### 작은 메시지

메시지 큐를 통해 데이터를 복사한다.

```text
Client → Port Message Queue → Server
```

#### 큰 메시지

공유 메모리 영역을 생성하고 메시지에는 해당 영역을 가리키는 정보를 넣는다.

```text
Client ── 데이터 기록 ──▶ Shared Memory
    │
    └── 위치·크기 정보 ──▶ Message Queue ──▶ Server
```

서버는 공유 메모리에서 실제 데이터를 직접 확인한다.

이 방식은 큰 메시지를 반복해서 복사하는 비용을 줄인다.

---

### 핵심 의미

Windows IPC는 공유 메모리와 메시지 전달을 완전히 분리하지 않고 상황에 따라 결합한다.

```text
작은 데이터 → 메시지 복사
큰 데이터 → 공유 메모리 + 메시지로 위치 전달
```

이는 IPC 구현이 반드시 한 가지 방식만 사용해야 하는 것은 아니라는 점을 보여준다.

---

## 3.7.4 Pipes

**파이프(Pipe)**는 두 프로세스가 바이트 스트림을 주고받을 수 있도록 연결하는 IPC 방식이다.

```text
Process A ── write ──▶ Pipe ── read ──▶ Process B
```

UNIX에서 오래전부터 사용된 대표적인 IPC다.

---

### 파이프를 이해할 때 확인할 사항

교재는 파이프를 비교할 때 다음 문제를 살펴봐야 한다고 설명한다.

1. 단방향인가, 양방향인가?
2. 양방향이라면 반이중인가, 전이중인가?
3. 통신하는 프로세스 사이에 부모–자식 관계가 필요한가?
4. 네트워크를 통해 통신할 수 있는가?

---

## 3.7.4.1 Ordinary Pipes

**일반 파이프(Ordinary Pipe)**는 보통 부모 프로세스와 자식 프로세스 사이에서 사용한다.

UNIX에서는 `pipe()` 시스템 콜로 생성한다.

```c
int fd[2];

pipe(fd);
```

배열 `fd`에는 두 개의 파일 디스크립터가 들어간다.

| 디스크립터 | 역할            |
| ---------- | --------------- |
| `fd[0]`    | 파이프에서 읽기 |
| `fd[1]`    | 파이프에 쓰기   |

```text
fd[1] ── write ──▶ Pipe ── read ──▶ fd[0]
```

---

### 부모와 자식의 사용

부모가 파이프를 만든 뒤 `fork()`를 호출하면 자식도 파이프의 파일 디스크립터를 상속받는다.

```text
Parent
  │
  ├── pipe()
  │
  └── fork()
       ├── Parent: fd[1]에 쓰기
       └── Child: fd[0]에서 읽기
```

---

### 단방향 통신

일반 파이프는 기본적으로 단방향이다.

```text
Parent ─────▶ Child
```

양방향 통신이 필요하다면 일반적으로 파이프 두 개가 필요하다.

```text
Pipe 1: Parent ─────▶ Child
Pipe 2: Parent ◀───── Child
```

---

### 수명

일반 파이프는 통신하는 프로세스들이 종료되면 함께 사라진다.

파일 시스템에 영구적인 이름을 가지지 않으며, 보통 생성한 프로세스와 그 자식 사이에서만 접근할 수 있다.

---

### 명령어 파이프 예시

쉘에서 다음 명령어를 실행할 수 있다.

```bash
ls | grep ".txt"
```

동작은 다음과 같다.

```text
ls의 출력
    │
    ▼
Pipe
    │
    ▼
grep의 입력
```

`ls`와 `grep`은 서로 다른 프로세스이며, 파이프를 통해 데이터를 전달한다.

---

## 3.7.4.2 Named Pipes

**Named Pipe**는 파일 시스템에 이름을 가진 파이프다.

UNIX에서는 FIFO라고도 한다.

```text
Process A
    │
    ▼
/tmp/my_pipe
    │
    ▼
Process B
```

---

### Ordinary Pipe와의 차이

Named Pipe는 부모–자식 관계가 없는 프로세스도 사용할 수 있다.

```text
서로 관련 없는 Process A와 Process B
→ 동일한 Named Pipe 이름으로 통신
```

파이프를 생성한 프로세스가 종료된 뒤에도 파일 시스템의 이름이 남아 있을 수 있다.

---

### 비교

| 구분     | Ordinary Pipe          | Named Pipe                              |
| -------- | ---------------------- | --------------------------------------- |
| 이름     | 없음                   | 파일 시스템 이름 존재                   |
| 관계     | 주로 부모–자식         | 관련 없는 프로세스도 가능               |
| 방향     | 일반적으로 단방향      | 시스템에 따라 양방향 가능               |
| 수명     | 프로세스와 함께 사라짐 | 명시적으로 제거할 때까지 이름 유지 가능 |
| 네트워크 | 보통 로컬              | 구현에 따라 원격 통신 지원 가능         |

---

## 3.7 핵심 요약

- POSIX 공유 메모리는 `shm_open()`, `ftruncate()`, `mmap()`을 사용한다.
- Mach는 Port 중심의 메시지 전달 방식을 사용한다.
- Windows는 작은 메시지는 복사하고 큰 메시지는 공유 메모리를 활용한다.
- Ordinary Pipe는 주로 부모와 자식 사이에서 사용한다.
- Named Pipe는 서로 관련 없는 프로세스 사이에서도 사용할 수 있다.
- 파이프는 바이트 스트림 형태로 데이터를 전달한다.

---

# 3.8 Communication in Client–Server Systems

서로 다른 컴퓨터에서 실행되는 클라이언트와 서버가 통신하려면 네트워크 기반 IPC가 필요하다.

교재에서는 대표적인 방식으로 다음을 설명한다.

1. Sockets
2. Remote Procedure Calls
3. Android RPC

---

## 3.8.1 Sockets

### 소켓의 개념

**소켓(Socket)**은 네트워크에서 통신하는 두 프로세스의 끝점(Endpoint)이다.

```text
Client Process                              Server Process
     │                                           │
 Client Socket ◀──────── Network ─────────▶ Server Socket
```

소켓은 일반적으로 IP 주소와 포트 번호의 조합으로 식별된다.

```text
Socket = IP Address + Port Number
```

예:

```text
192.168.0.10:6013
```

- `192.168.0.10`: 컴퓨터의 주소
- `6013`: 해당 컴퓨터에서 통신할 프로세스 또는 서비스 번호

---

### 포트가 필요한 이유

한 컴퓨터에서는 여러 네트워크 프로그램이 동시에 실행된다.

```text
하나의 서버 IP
├── 80: HTTP
├── 443: HTTPS
├── 22: SSH
└── 6013: 특정 애플리케이션
```

IP 주소는 컴퓨터를 찾고, 포트 번호는 그 컴퓨터 안에서 어떤 서비스와 통신할지 구분한다.

---

### 서버 소켓의 동작

서버는 특정 포트에서 연결을 기다린다.

```text
ServerSocket 생성
    ↓
특정 포트에 Bind
    ↓
Client 연결 대기
    ↓
연결 수락
    ↓
데이터 송수신
```

Java의 개념적인 예시는 다음과 같다.

```java
ServerSocket server = new ServerSocket(6013);
Socket client = server.accept();
```

`accept()`는 클라이언트가 연결할 때까지 Blocking될 수 있다.

---

### 클라이언트 소켓의 동작

클라이언트는 서버의 IP 주소와 포트 번호를 이용해 연결한다.

```java
Socket socket = new Socket("127.0.0.1", 6013);
```

연결 이후에는 입력 스트림과 출력 스트림으로 데이터를 주고받을 수 있다.

---

### Loopback Address

`127.0.0.1`은 현재 컴퓨터 자신을 의미하는 **Loopback Address**다.

```text
127.0.0.1 = 자기 자신의 컴퓨터
```

같은 컴퓨터에서 클라이언트와 서버를 실행하고 테스트할 때 사용할 수 있다.

교재의 Java 클라이언트 예제는 `127.0.0.1:6013`에 연결해 서버로부터 날짜 정보를 읽는다.

---

### 소켓의 특징

소켓은 기본적으로 구조 없는 바이트 스트림을 전달한다.

```text
[01010100 01100101 01110011 01110100 ...]
```

어디까지가 메시지 하나인지, 각 바이트가 무엇을 의미하는지는 애플리케이션이 직접 정해야 한다.

예를 들어 다음과 같은 프로토콜을 설계할 수 있다.

```text
앞 4바이트: 메시지 길이
다음 1바이트: 메시지 종류
나머지: 실제 데이터
```

따라서 소켓은 유연하지만 상대적으로 저수준 통신 방식이다.

---

## 3.8.2 Remote Procedure Calls

### RPC의 개념

**RPC(Remote Procedure Call)**는 다른 컴퓨터나 다른 프로세스에 있는 함수를 마치 현재 프로그램의 일반 함수처럼 호출할 수 있도록 추상화한 통신 방식이다.

일반 함수 호출은 다음과 같다.

```javascript
const result = add(10, 20);
```

RPC는 겉보기에는 비슷하지만 실제 함수는 원격 서버에서 실행된다.

```text
Client                     Server
add(10, 20) 호출
    │
    │ 네트워크 요청
    ▼
Server의 add(10, 20) 실행
    │
    │ 결과 전송
    ▼
result = 30
```

소켓이 단순한 바이트 스트림을 제공한다면 RPC는 함수 이름, 매개변수, 반환값을 구조화한다.

교재는 RPC를 네트워크를 사이에 둔 프로세스가 원격 함수를 호출할 수 있도록 하는 상위 수준 통신 방식으로 설명한다.

---

### Stub

RPC에서는 클라이언트와 서버에 **Stub**이 존재한다.

```text
Client Application
        │ 함수 호출
        ▼
Client Stub
        │ 네트워크 메시지 생성
        ▼
Network
        │
        ▼
Server Stub
        │ 실제 함수 호출
        ▼
Server Procedure
```

#### Client Stub

클라이언트가 일반 함수처럼 호출할 수 있는 인터페이스를 제공한다.

호출 인자를 네트워크 메시지로 변환해 서버에 보낸다.

#### Server Stub

클라이언트로부터 받은 메시지를 해석하고 실제 서버 함수를 호출한다.

함수 실행 결과를 다시 메시지로 만들어 클라이언트에 반환한다.

---

### Marshaling

함수의 매개변수를 네트워크 전송이 가능한 형식으로 변환하는 과정을 **Marshaling**이라고 한다.

```text
함수 호출:
add(10, 20)

Marshaling:
{
  function: "add",
  args: [10, 20]
}
```

서버에서 메시지를 다시 함수 호출 형태로 복원하는 것을 Unmarshaling이라고 한다.

---

### 데이터 표현 문제

클라이언트와 서버의 컴퓨터 구조가 다를 수 있다.

예를 들어 숫자를 메모리에 저장하는 바이트 순서가 다를 수 있다.

```text
Big Endian
12 34 56 78

Little Endian
78 56 34 12
```

따라서 RPC는 양쪽이 이해할 수 있는 표준 데이터 표현을 사용해야 한다.

교재에서는 **XDR(External Data Representation)**과 같은 형식을 예로 든다.

---

### 포인터 전달 문제

일반 함수에서는 메모리 주소인 포인터를 전달할 수 있다.

```c
update(&value);
```

하지만 RPC에서 클라이언트의 메모리 주소를 서버에 그대로 보내는 것은 의미가 없다.

```text
Client의 주소 0x1000
≠
Server에서 같은 데이터가 있는 주소
```

따라서 포인터가 가리키는 실제 데이터를 복사해 전송해야 한다.

---

### RPC 실패 문제

일반적인 로컬 함수 호출은 프로세스가 정상 실행 중이라면 비교적 확실하게 수행된다.

하지만 RPC는 네트워크를 사용하므로 다음 문제가 발생할 수 있다.

- 요청 메시지 손실
- 응답 메시지 손실
- 네트워크 지연
- 서버 장애
- 클라이언트 장애
- 동일 요청의 중복 전송

---

### At Most Once

**At Most Once**는 RPC가 최대 한 번만 실행되도록 보장하는 방식이다.

```text
실행 횟수 = 0번 또는 1번
```

요청마다 고유한 식별자 또는 타임스탬프를 붙인다.

```text
Request ID = 1234
```

서버는 이미 처리한 요청 ID를 기록한다.

```text
처리된 요청 목록
├── 1232
├── 1233
└── 1234
```

같은 요청이 다시 도착하면 실행하지 않는다.

```text
Request 1234 재도착
→ 이미 처리됨
→ 무시
```

따라서 중복 실행은 막을 수 있다. 그러나 요청이 서버에 전혀 도착하지 않으면 0번 실행될 수 있다.

---

### Exactly Once

**Exactly Once**는 요청이 정확히 한 번 실행되도록 보장하는 의미다.

```text
실행 횟수 = 반드시 1번
```

이를 위해 다음이 필요하다.

1. At Most Once 방식으로 중복 실행을 방지한다.
2. 서버가 요청 처리 후 ACK를 보낸다.
3. 클라이언트가 ACK를 받지 못하면 요청을 재전송한다.

```text
Client                        Server
  │ Request ID 1234              │
  ├─────────────────────────────▶│
  │                              │ 실행
  │             ACK              │
  │◀─────────────────────────────┤
```

ACK가 손실되면 클라이언트는 같은 요청을 다시 보낸다.

```text
Client                        Server
  │ Request 1234                 │
  ├─────────────────────────────▶│ 실행
  │           ACK 손실           │
  │             X                │
  │                              │
  │ Request 1234 재전송          │
  ├─────────────────────────────▶│
  │                              │ 이미 처리됨 → 재실행하지 않음
  │             ACK              │
  │◀─────────────────────────────┤
```

다만 서버 자체가 장애를 일으키고 처리 기록까지 잃으면 Exactly Once를 완벽히 보장하기 어렵다.

교재에서는 At Most Once에 ACK와 재전송을 추가해 Exactly Once 의미를 설명한다.

---

### RPC Binding

클라이언트는 서버의 어떤 포트에 RPC 요청을 보내야 하는지 알아야 한다.

이를 연결하는 과정을 **Binding**이라고 한다.

---

#### 고정 포트 방식

특정 RPC 서비스의 포트 번호를 미리 정한다.

```text
File Service → Port 5000
Print Service → Port 5001
```

구현은 단순하지만 서버가 포트를 바꾸기 어렵다.

---

#### 동적 바인딩

클라이언트가 Rendezvous 또는 Matchmaker 서비스에 요청해 실제 서비스 포트를 알아낸다.

```text
Client
    │ "File Service 포트가 어디인가?"
    ▼
Rendezvous Daemon
    │ "Port 5000"
    ▼
Client
    │ RPC 요청
    ▼
File Service : 5000
```

초기 조회 비용이 있지만 서비스 구성을 유연하게 변경할 수 있다.

---

### 분산 파일 시스템에서의 RPC

분산 파일 시스템은 RPC를 사용해 원격 파일 작업을 수행할 수 있다.

```text
Client
  │ read("/remote/file.txt")
  ▼
RPC Request
  │
  ▼
Remote File Server
  │ 파일 읽기
  ▼
RPC Response
  │
  ▼
Client가 데이터 수신
```

RPC 메시지에는 다음과 같은 파일 연산이 들어갈 수 있다.

- `read()`
- `write()`
- `rename()`
- `delete()`
- `status()`

---

## 3.8.3 Android RPC

Android에서는 각 애플리케이션이 일반적으로 별도의 프로세스와 주소 공간에서 실행된다.

```text
App A Process      App B Process
독립 주소 공간      독립 주소 공간
```

따라서 애플리케이션이나 시스템 서비스 간 통신에 IPC가 필요하다.

Android는 **Binder Framework**를 이용한 RPC를 제공한다.

---

### Binder의 구조

```text
Client Application
        │ RPC 요청
        ▼
Binder Driver
        │
        ▼
Server Service
```

Binder 드라이버는 커널에서 클라이언트와 서버 사이의 메시지 전달을 중개한다.

---

### AIDL

Android는 **AIDL(Android Interface Definition Language)**을 이용해 프로세스 간 호출 인터페이스를 정의할 수 있다.

개념적인 인터페이스는 다음과 같다.

```text
interface Calculator {
    int add(int a, int b);
}
```

AIDL 도구는 클라이언트와 서버가 사용할 Stub 코드를 생성한다.

```text
AIDL 정의
   │
   ├── Client Proxy 생성
   └── Server Stub 생성
```

클라이언트는 마치 일반 메서드처럼 호출하지만 실제 실행은 다른 프로세스의 서비스에서 이루어진다.

```text
Client: calculator.add(10, 20)
    ↓ Binder
Server: add(10, 20) 실행
    ↓ Binder
Client: 결과 30 수신
```

---

### Binder의 의미

Binder는 다음 기능을 함께 제공한다.

- 프로세스 간 메시지 전달
- RPC 인터페이스
- 객체 참조 관리
- 호출자 식별
- 권한 확인

교재는 Android가 Binder Framework를 통해 RPC 형태의 프로세스 간 통신을 지원한다고 정리한다.

---

## 3.8 핵심 요약

- 소켓은 네트워크 통신의 끝점이다.
- 소켓은 IP 주소와 포트 번호로 식별된다.
- 소켓은 구조 없는 바이트 스트림을 제공하므로 데이터 형식을 애플리케이션이 정의해야 한다.
- RPC는 원격 함수를 일반 함수처럼 호출하도록 추상화한다.
- Stub은 매개변수와 반환값을 메시지로 변환한다.
- Marshaling은 데이터를 전송 가능한 형식으로 직렬화하는 과정이다.
- RPC는 네트워크 장애와 중복 실행을 고려해야 한다.
- At Most Once는 최대 한 번, Exactly Once는 정확히 한 번 실행되는 의미다.
- Android는 Binder Framework와 AIDL을 이용해 RPC를 지원한다.

# 3.9 Summary

## 3.9.1 프로세스의 개념

프로세스는 실행 중인 프로그램이다.

프로세스는 다음 요소를 포함한다.

```text
Process
├── 프로그램 코드
├── 데이터
├── Heap
├── Stack
├── Program Counter
├── CPU Registers
└── 운영체제가 할당한 자원
```

운영체제는 PCB를 이용해 각 프로세스의 상태와 실행 문맥을 관리한다.

---

## 3.9.2 프로세스 상태와 스케줄링

프로세스는 다음 상태를 이동한다.

```text
New → Ready → Running → Waiting → Ready → Running → Terminated
```

CPU 스케줄러는 Ready Queue에서 실행할 프로세스를 선택한다.

실행 프로세스가 변경될 때 운영체제는 Context Switch를 수행한다.

```text
현재 프로세스 상태 저장
→ 다음 프로세스 상태 복원
→ 다음 프로세스 실행
```

---

## 3.9.3 프로세스 생성과 종료

UNIX 계열 운영체제에서는 다음 시스템 콜이 대표적이다.

| 함수     | 역할                                 |
| -------- | ------------------------------------ |
| `fork()` | 자식 프로세스 생성                   |
| `exec()` | 현재 프로세스의 프로그램 교체        |
| `wait()` | 자식 프로세스 종료 대기 및 정보 회수 |
| `exit()` | 프로세스 종료                        |

자식이 종료되었지만 부모가 종료 정보를 회수하지 않으면 Zombie가 된다.

부모가 먼저 종료된 실행 중 자식은 Orphan이 된다.

---

## 3.9.4 IPC

협력 프로세스는 데이터를 교환하거나 실행 순서를 맞추기 위해 IPC를 사용한다.

대표적인 모델은 다음 두 가지다.

```text
IPC
├── Shared Memory
└── Message Passing
```

| 구분          | Shared Memory         | Message Passing              |
| ------------- | --------------------- | ---------------------------- |
| 통신          | 같은 메모리 영역 접근 | 메시지 송수신                |
| 속도          | 일반적으로 빠름       | 커널 개입으로 비용 발생 가능 |
| 동기화        | 직접 해결해야 함      | 통신 연산이 일부 제공        |
| 대용량 데이터 | 적합                  | 상대적으로 불리할 수 있음    |
| 분산 시스템   | 구현이 어려움         | 적합                         |

---

## 3.9.5 실제 IPC 방식

| 방식                | 특징                               |
| ------------------- | ---------------------------------- |
| POSIX Shared Memory | `shm_open()`, `mmap()` 사용        |
| Mach Port           | 포트 중심 메시지 전달              |
| Windows ALPC        | 메시지 전달과 공유 메모리 결합     |
| Ordinary Pipe       | 주로 부모–자식 프로세스 통신       |
| Named Pipe          | 관련 없는 프로세스도 통신 가능     |
| Socket              | 네트워크를 통한 바이트 스트림 통신 |
| RPC                 | 원격 함수를 로컬 함수처럼 호출     |
| Android Binder      | Android 프로세스 간 RPC            |

# Chapter 3 전체 핵심 요약

1. 프로세스는 실행 중인 프로그램이며 운영체제의 기본 작업 단위다.

2. 운영체제는 PCB에 프로세스 상태, 프로그램 카운터, CPU 레지스터, 메모리 및 I/O 정보를 저장한다.

3. 프로세스는 New, Ready, Running, Waiting, Terminated 상태를 이동한다.

4. CPU 스케줄러는 Ready Queue에서 다음 프로세스를 선택한다.

5. Context Switch는 현재 프로세스의 실행 문맥을 저장하고 다음 프로세스의 문맥을 복원하는 과정이다.

6. 프로세스는 `fork()`로 생성되고 `exit()`로 종료될 수 있으며 부모는 `wait()`로 자식의 종료 정보를 회수한다.

7. 협력 프로세스는 Shared Memory 또는 Message Passing으로 통신한다.

8. Shared Memory는 빠르지만 Race Condition을 막기 위한 동기화가 필요하다.

9. Message Passing은 `send()`와 `receive()`를 사용하며 직접 또는 간접 통신으로 구현할 수 있다.

10. Blocking 통신은 조건이 충족될 때까지 기다리고, Nonblocking 통신은 즉시 반환한다.

11. 메시지 큐는 Zero, Bounded, Unbounded Capacity로 구성할 수 있다.

12. 파이프는 프로세스 사이에 바이트 스트림을 전달하는 IPC 방식이다.

13. 소켓은 IP 주소와 포트 번호로 식별되는 네트워크 통신 종점이다.

14. RPC는 원격 프로세스의 함수를 로컬 함수처럼 호출하도록 추상화한다.

15. Android는 Binder Framework를 통해 프로세스 간 RPC를 지원한다.

# 면접 포인트

## 공유 메모리가 메시지 전달보다 빠른 이유는 무엇인가요?

공유 메모리는 영역을 생성하고 매핑하는 초기 단계에만 커널이 개입합니다. 설정 이후에는 프로세스들이 같은 메모리 영역을 일반 메모리처럼 직접 읽고 쓰므로 매번 시스템 콜이나 데이터 복사가 필요하지 않습니다. 반면 메시지 전달은 일반적으로 메시지를 커널을 통해 전달하므로 모드 전환과 데이터 복사 비용이 발생할 수 있습니다.

---

## 공유 메모리의 단점은 무엇인가요?

여러 프로세스가 같은 메모리 영역에 동시에 접근하면 Race Condition이 발생할 수 있습니다. 운영체제가 공유 데이터의 접근 순서까지 자동으로 보장하지 않으므로 뮤텍스, 세마포어 등의 동기화 도구를 함께 사용해야 합니다.

---

## 직접 통신과 간접 통신의 차이는 무엇인가요?

직접 통신은 송신자와 수신자가 서로의 프로세스 이름을 명시합니다. 간접 통신은 메일박스 또는 포트를 통해 메시지를 교환합니다. 간접 통신은 실제 통신 상대를 직접 알 필요가 없어 결합도가 낮고 여러 프로세스가 같은 메일박스를 공유할 수 있습니다.

---

## Blocking과 Nonblocking 통신의 차이는 무엇인가요?

Blocking 연산은 메시지가 전달되거나 도착할 때까지 호출한 프로세스를 대기시킵니다. Nonblocking 연산은 작업 완료 여부와 관계없이 즉시 반환합니다. Blocking Send와 Blocking Receive를 함께 사용하면 송신자와 수신자가 서로 준비될 때까지 기다리는 Rendezvous가 형성됩니다.

---

## Zero Capacity와 Bounded Capacity의 차이는 무엇인가요?

Zero Capacity는 메시지를 저장할 공간이 없으므로 송신자가 수신자가 메시지를 받을 때까지 기다려야 합니다. Bounded Capacity는 유한한 크기의 메시지 큐를 사용하며, 큐에 공간이 있으면 송신자가 계속 실행할 수 있지만 큐가 가득 차면 기다려야 합니다.

---

## Ordinary Pipe와 Named Pipe의 차이는 무엇인가요?

Ordinary Pipe는 이름이 없고 일반적으로 부모–자식처럼 관련된 프로세스 사이에서 사용되며, 프로세스가 종료되면 사라집니다. Named Pipe는 파일 시스템에 이름이 존재하므로 부모–자식 관계가 없는 프로세스도 같은 이름을 통해 통신할 수 있습니다.

---

## 소켓과 RPC의 차이는 무엇인가요?

소켓은 IP 주소와 포트 번호를 이용해 프로세스 사이에서 바이트 스트림을 전달하는 저수준 통신 방식입니다. 데이터 구조와 메시지 형식은 애플리케이션이 직접 정의해야 합니다. RPC는 함수 이름, 매개변수, 반환값을 구조화하여 원격 함수를 로컬 함수처럼 호출할 수 있도록 추상화한 고수준 통신 방식입니다.

---

## At Most Once와 Exactly Once의 차이는 무엇인가요?

At Most Once는 요청이 중복 실행되지 않도록 최대 한 번만 수행되는 것을 보장하지만, 요청이 유실되면 실행되지 않을 수 있습니다. Exactly Once는 중복 방지에 더해 ACK와 재전송을 사용하여 요청이 반드시 한 번 실행되도록 시도합니다. 다만 서버 장애와 상태 유실까지 고려하면 완전한 Exactly Once 보장은 매우 어렵습니다.
