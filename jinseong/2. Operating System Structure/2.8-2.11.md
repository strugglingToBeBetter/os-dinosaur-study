# Chapter 2. 운영체제 구조 — Part 3

## 2.8 Operating-System Structure

현대 운영체제는 프로세스 관리, 메모리 관리, 파일 시스템, 장치 드라이버, 네트워크, 보안처럼 매우 많은 기능을 포함한다. 이러한 기능을 아무 기준 없이 하나의 코드 덩어리로 만들면 수정과 디버깅이 어렵다. 따라서 운영체제는 각 기능을 어떤 방식으로 나누고 연결할 것인지에 따라 여러 구조를 사용한다.

운영체제 구조를 구분할 때 핵심은 다음 두 질문이다.

1. 어떤 기능이 커널 안에서 실행되는가?
2. 각 기능은 서로 어떤 방식으로 통신하는가?

### 2.8.1 Monolithic Structure

모놀리식 구조는 운영체제의 주요 기능이 하나의 큰 커널 안에서 실행되는 구조다. 프로세스 관리, 메모리 관리, 파일 시스템, 장치 드라이버 등이 모두 커널 모드의 같은 주소 공간에 존재한다.

대표적인 예는 전통적인 UNIX와 Linux다. Linux는 내부적으로 여러 하위 시스템으로 코드가 나뉘어 있지만, 실행 관점에서는 대부분의 핵심 기능이 하나의 커널 주소 공간에서 동작하므로 모놀리식 커널로 분류된다.

예를 들어 프로그램이 파일을 읽는다고 하자. 시스템 콜이 커널에 진입하면 파일 시스템 코드가 장치 드라이버를 호출하고, 장치 드라이버가 저장 장치와 통신한다. 이 과정의 대부분이 같은 커널 주소 공간 안에서 이루어지므로 함수 호출만으로 빠르게 연결할 수 있다.

모놀리식 구조의 가장 큰 장점은 성능이다. 커널 구성 요소들이 같은 주소 공간에 있으므로 메시지를 복사하거나 별도 프로세스로 전환할 필요가 적다. 반면 한 구성 요소의 오류가 전체 커널에 영향을 줄 수 있고, 기능 간 결합도가 높아 수정과 확장이 어렵다.

```text
응용 프로그램
→ 시스템 콜
→ 파일 시스템
→ 장치 드라이버
→ 하드웨어

파일 시스템과 장치 드라이버가 모두 커널 안에서 실행된다.
```

Linux는 모놀리식 구조이지만 순수한 단일 덩어리는 아니다. 필요할 때 장치 드라이버나 파일 시스템 기능을 커널 모듈로 추가할 수 있기 때문에 흔히 **모놀리식 커널 + 모듈 구조**라고 설명한다.

### 2.8.2 Layered Approach

계층 구조는 운영체제를 여러 층으로 나누고, 각 계층이 자신보다 아래 계층의 기능을 사용하도록 설계하는 방식이다.

예를 들면 가장 아래에는 하드웨어가 있고, 그 위에 장치 제어, 메모리 관리, 프로세스 관리, 시스템 콜 인터페이스, 사용자 인터페이스가 올라갈 수 있다.

```text
사용자 프로그램
시스템 콜 인터페이스
파일 시스템·프로세스 관리
메모리 관리·장치 관리
하드웨어
```

각 계층은 아래 계층이 어떻게 구현되었는지 모두 알 필요 없이 정해진 인터페이스만 사용한다. 이 때문에 구조를 이해하고 검증하기 쉽고, 특정 계층을 수정할 때 다른 계층에 미치는 영향을 줄일 수 있다.

다만 실제 운영체제 기능은 완전히 위아래 관계로만 나누기 어렵다. 예를 들어 파일 시스템이 메모리 관리와 장치 드라이버를 모두 필요로 하고, 메모리 관리가 다시 파일 시스템을 이용하는 경우도 있다. 계층을 엄격히 지키면 요청이 여러 단계를 거쳐 성능이 떨어질 수도 있다.

#### Layered 구조는 Window 패턴인가?

아니다. 여기서 Layered는 화면의 창이나 프론트엔드 UI 패턴을 의미하지 않는다. 운영체제 내부 기능을 의존 관계에 따라 층으로 분리하는 설계 방식이다.

다만 웹 애플리케이션의 계층형 아키텍처와는 비슷한 면이 있다.

```text
Controller
→ Service
→ Repository
→ Database
```

상위 계층이 하위 계층의 기능을 사용하는 방식이라는 점은 비슷하지만, 운영체제의 Layered Approach는 커널 내부와 하드웨어 사이의 구조를 설명한다.

### 2.8.3 Microkernel

마이크로커널은 커널 안에 꼭 필요한 최소 기능만 남기고 나머지 서비스를 사용자 공간의 별도 프로세스로 분리하는 구조다.

일반적으로 커널에는 다음과 같은 최소 기능만 둔다.

- 프로세스 또는 스레드 스케줄링
- 기본 메모리 관리
- 프로세스 간 통신
- 낮은 수준의 하드웨어 제어

파일 시스템, 네트워크, 장치 드라이버 같은 기능은 사용자 공간의 서버 프로세스로 실행할 수 있다.

예를 들어 응용 프로그램이 파일을 읽으려면 커널 안의 파일 시스템 함수를 직접 호출하는 대신, 파일 서버에 메시지를 보낸다. 파일 서버는 필요한 경우 장치 드라이버 서버와 통신하고 결과를 다시 응용 프로그램에 전달한다.

```text
응용 프로그램
→ 메시지
→ 파일 서버
→ 메시지
→ 장치 드라이버 서버
→ 커널
→ 하드웨어
```

대표적인 예로 Mach와 MINIX 3가 있다.

마이크로커널의 장점은 격리와 안정성이다. 장치 드라이버가 사용자 공간에서 고장 나더라도 커널 전체가 즉시 중단되지 않고 해당 서비스만 다시 시작할 수 있다. 기능 추가와 이식도 비교적 쉽고, 커널에 포함되는 코드가 적어 보안상 검증 범위도 줄어든다.

단점은 성능 오버헤드다. 서비스 간 요청이 메시지 전달과 문맥 전환을 거치므로, 같은 커널 주소 공간에서 함수 호출로 처리하는 모놀리식 구조보다 느릴 수 있다.

### 2.8.4 Modules

모듈 구조는 커널의 핵심 부분은 유지하면서 필요한 기능을 실행 중에 동적으로 추가하거나 제거할 수 있게 하는 방식이다.

Linux의 장치 드라이버, 파일 시스템, 네트워크 기능 중 일부는 Loadable Kernel Module 형태로 동작한다. USB 장치를 연결했을 때 필요한 드라이버 모듈을 적재하고, 더 이상 필요하지 않으면 제거할 수 있다.

모듈은 별도 파일로 존재하지만 적재된 뒤에는 커널 모드와 커널 주소 공간에서 실행된다. 따라서 마이크로커널의 사용자 공간 서버와는 다르다.

```text
Microkernel 서비스
→ 사용자 공간에서 별도 프로세스로 실행

Kernel Module
→ 필요할 때 커널 안으로 적재되어 커널 모드에서 실행
```

모듈 구조는 모놀리식 커널의 성능을 유지하면서도 기능 추가와 교체를 쉽게 만든다. 하지만 모듈도 커널 권한으로 실행되므로 잘못된 모듈은 전체 시스템을 손상시킬 수 있다.

### 2.8.5 Hybrid Systems

현대 운영체제는 하나의 구조만 순수하게 따르기보다 여러 구조의 장점을 섞은 하이브리드 방식을 주로 사용한다.

#### Windows

Windows 커널은 스케줄링, 메모리 관리, 동기화 같은 핵심 기능을 커널에서 처리한다. 동시에 다양한 서브시스템과 서비스를 분리하며, 일부 기능은 사용자 공간에서 실행한다.

Windows를 단순히 마이크로커널이라고 부르기 어려운 이유는 성능상 중요한 많은 서비스가 커널 공간에 존재하기 때문이다. 따라서 마이크로커널의 개념을 일부 사용하지만 실제 구조는 하이브리드 커널에 가깝다.

#### macOS와 iOS

macOS와 iOS의 커널 환경은 Darwin이며, Mach 마이크로커널과 BSD UNIX 구성 요소를 결합한다.

Mach는 스케줄링, 메모리 관리, IPC 같은 기본 기능을 제공하고, BSD 계층은 POSIX 시스템 콜, 프로세스, 파일 시스템, 네트워크 기능을 제공한다. 여기에 I/O Kit와 커널 확장 기능이 결합된다.

순수 마이크로커널이라면 여러 서비스가 사용자 공간에 분리되어야 하지만, Darwin은 성능을 위해 Mach, BSD, I/O Kit 등을 같은 커널 주소 공간에 배치한다. 즉, 마이크로커널 개념을 사용하면서도 모놀리식 방식의 성능을 취한 하이브리드 구조다.

#### Android

Android는 Linux 커널을 기반으로 한다. Linux 커널이 프로세스, 메모리, 장치 드라이버, 보안 기능을 관리하고, 그 위에 네이티브 라이브러리, Android Runtime, 애플리케이션 프레임워크가 계층적으로 올라간다.

Android는 전체 시스템 관점에서는 계층 구조를 사용하고, 커널은 모놀리식·모듈형 Linux 커널을 사용한다. 따라서 Android 역시 여러 구조가 결합된 시스템이다.

### 운영체제 구조 비교

| 구조        | 핵심 특징                                           | 장점                   | 단점                             | 대표 예시                    |
| ----------- | --------------------------------------------------- | ---------------------- | -------------------------------- | ---------------------------- |
| Monolithic  | 주요 기능이 하나의 커널 공간에서 실행               | 빠른 성능              | 오류 전파, 높은 결합도           | UNIX, Linux                  |
| Layered     | 기능을 계층별로 분리                                | 이해와 검증이 쉬움     | 계층 정의가 어렵고 오버헤드 가능 | THE 시스템, 일부 OS 구조     |
| Microkernel | 최소 기능만 커널에 두고 서비스를 사용자 공간에 분리 | 안정성, 격리, 확장성   | 메시지 전달과 문맥 전환 비용     | Mach, MINIX 3                |
| Modules     | 필요한 기능을 실행 중 커널에 추가                   | 성능과 확장성의 균형   | 모듈 오류가 커널에 영향          | Linux                        |
| Hybrid      | 여러 구조의 장점을 결합                             | 현실적인 성능과 유연성 | 구조가 복잡해짐                  | Windows, macOS, iOS, Android |

### 2.8 핵심 정리

모놀리식 구조는 대부분의 기능을 커널 안에 두어 빠르지만 오류의 영향 범위가 크다. 마이크로커널은 서비스를 사용자 공간으로 분리하여 안정성과 확장성을 높이지만 통신 비용이 발생한다. 계층 구조는 의존 관계를 명확히 하지만 실제 운영체제를 완전히 계층화하기 어렵다. 현대 운영체제는 모듈과 여러 구조를 조합한 하이브리드 형태를 주로 사용한다.

### 2.8 면접 포인트

**Q. 모놀리식 커널과 마이크로커널의 차이는 무엇인가요?**

모놀리식 커널은 파일 시스템, 드라이버, 메모리 관리 같은 주요 기능을 같은 커널 주소 공간에서 실행해 성능이 좋다. 마이크로커널은 최소 기능만 커널에 남기고 나머지 서비스를 사용자 공간에 분리해 안정성과 확장성을 높이지만, 메시지 전달과 문맥 전환 비용이 발생한다.

**Q. Linux는 모놀리식인가요, 모듈형인가요?**

기본 구조는 주요 기능이 하나의 커널 주소 공간에서 실행되는 모놀리식 커널이다. 다만 실행 중 커널 모듈을 동적으로 적재할 수 있으므로 모놀리식 기반의 모듈형 구조라고 설명하는 것이 정확하다.

## 2.9 Building and Booting an Operating System

운영체제는 다양한 CPU, 메모리 크기, 저장 장치, 네트워크 카드, 주변 장치에서 동작해야 한다. 따라서 운영체제를 만들 때는 대상 하드웨어에 맞게 기능과 드라이버를 구성하고, 컴파일하고, 설치하는 과정이 필요하다.

### 운영체제 생성

운영체제를 처음부터 구성하는 과정은 대체로 다음 순서를 따른다.

1. 운영체제 소스 코드를 작성하거나 가져온다.
2. 대상 하드웨어와 필요한 기능을 설정한다.
3. 운영체제를 컴파일한다.
4. 컴파일된 커널과 관련 파일을 설치한다.
5. 시스템을 부팅한다.

여기서 설정은 어떤 CPU를 지원할지, 어떤 파일 시스템과 장치 드라이버를 포함할지, 네트워크 기능이나 보안 기능을 사용할지 결정하는 과정이다.

운영체제를 구성하는 방식은 크게 세 가지로 생각할 수 있다.

첫째, 특정 하드웨어에 맞게 소스 코드를 완전히 다시 컴파일할 수 있다. 불필요한 기능이 빠져 작고 최적화된 시스템을 만들 수 있지만, 하드웨어가 변경되면 다시 빌드해야 한다. 임베디드 시스템에서 자주 사용한다.

둘째, 미리 컴파일된 여러 모듈 중 필요한 것만 선택해 링크할 수 있다. 전체 소스 코드를 다시 컴파일하는 것보다 빠르지만 유연성이 제한될 수 있다.

셋째, 필요한 기능을 실행 중에 모듈로 적재할 수 있다. 현대 데스크톱과 서버 운영체제에서 많이 사용하는 방식이다.

### Linux 커널 빌드 예시

Linux 커널을 직접 빌드할 때는 일반적으로 소스 코드를 내려받고, 설정 파일을 만든 뒤, 커널과 모듈을 컴파일하고 설치한다.

```text
소스 코드 다운로드
→ 커널 설정
→ 커널 및 모듈 컴파일
→ 설치
→ 부트 로더 설정
→ 재부팅
```

이 과정에서 설정 파일에는 지원할 CPU, 파일 시스템, 드라이버, 네트워크 기능 등이 기록된다.

### 부팅이 필요한 이유

운영체제가 실행되려면 커널이 메모리에 있어야 한다. 그러나 전원을 켠 직후 메모리는 비어 있고, 운영체제 자체도 아직 실행되지 않는다.

즉, 운영체제를 메모리에 올려야 운영체제가 실행되는데, 운영체제가 실행되지 않은 상태에서는 운영체제 스스로 자신을 메모리에 올릴 수 없다. 이 문제를 해결하는 것이 부트스트랩 프로그램과 부트 로더다.

### 부팅 과정

#### 1. 펌웨어 실행

전원을 켜면 CPU는 미리 정해진 주소에서 펌웨어를 실행한다. 전통적인 PC에서는 BIOS, 현대 시스템에서는 UEFI가 주로 사용된다.

펌웨어는 CPU, 메모리, 저장 장치 등 기본 하드웨어를 검사하고 초기화한다. 이후 부팅 가능한 장치를 찾고 부트 로더를 실행한다.

#### 2. 부트 로더 실행

부트 로더는 저장 장치에서 운영체제 커널을 찾아 메모리에 적재한다. Linux의 대표적인 부트 로더가 GRUB이다.

부트 로더는 여러 운영체제가 설치된 경우 사용자가 부팅할 운영체제를 선택하게 할 수도 있고, 커널 버전과 부팅 옵션을 전달할 수도 있다.

#### 3. 커널 실행

커널이 메모리에 적재되면 CPU 제어권이 커널의 시작 지점으로 넘어간다. 커널은 메모리 관리, 스케줄러, 인터럽트, 장치 드라이버 등 핵심 기능을 초기화한다.

#### 4. 초기 RAM 파일 시스템 사용

커널이 실제 루트 파일 시스템에 접근하려면 저장 장치 드라이버나 파일 시스템 드라이버가 필요할 수 있다. 그런데 그 드라이버가 실제 루트 파일 시스템 안에 있다면 접근 순서가 모순된다.

이를 해결하기 위해 Linux는 초기 RAM 파일 시스템인 `initramfs`를 사용한다. 필요한 최소 드라이버와 도구를 임시 메모리 파일 시스템에 넣어 먼저 실행하고, 실제 저장 장치를 사용할 준비가 되면 루트 파일 시스템을 전환한다.

#### 5. 첫 사용자 공간 프로세스 실행

커널 초기화가 끝나면 Linux는 `systemd`와 같은 첫 번째 사용자 공간 프로세스를 실행한다. 이 프로세스는 네트워크, 로그, 데이터베이스, 웹 서버 등 필요한 서비스들을 시작하고 로그인 화면이나 셸을 제공한다.

```text
전원 켜짐
→ BIOS/UEFI
→ 부트 로더
→ 커널 적재
→ 커널 초기화
→ initramfs
→ 실제 루트 파일 시스템 연결
→ systemd 실행
→ 시스템 서비스 시작
→ 로그인 화면
```

### 부팅과 로더의 차이

2.5의 로더는 일반 실행 파일을 메모리에 적재하는 운영체제 기능이다. 반면 부트 로더는 운영체제가 아직 실행되기 전에 커널 자체를 메모리에 적재한다.

| 구분      | 일반 Loader             | Boot Loader            |
| --------- | ----------------------- | ---------------------- |
| 실행 시점 | 운영체제가 실행 중일 때 | 운영체제가 실행되기 전 |
| 적재 대상 | 일반 응용 프로그램      | 운영체제 커널          |
| 대표 예시 | 실행 파일 로더          | GRUB                   |

### 복구 모드

많은 운영체제의 부트 로더는 복구 모드나 단일 사용자 모드를 제공한다. 정상 부팅이 되지 않을 때 손상된 파일 시스템을 복구하거나, 비밀번호를 변경하거나, 운영체제를 다시 설치하는 데 사용한다.

### 2.9 핵심 정리

운영체제 생성은 대상 하드웨어에 맞게 기능을 설정하고 컴파일·설치하는 과정이다. 부팅 시에는 BIOS나 UEFI가 부트 로더를 실행하고, 부트 로더가 커널을 메모리에 적재한다. 커널은 하드웨어와 드라이버를 초기화하고 첫 사용자 공간 프로세스를 실행해 시스템 서비스를 시작한다.

### 2.9 면접 포인트

**Q. 컴퓨터 전원을 켠 뒤 운영체제가 실행되기까지의 과정을 설명해 보세요.**

펌웨어인 BIOS나 UEFI가 하드웨어를 초기화하고 부팅 장치를 찾는다. 이후 부트 로더가 커널을 메모리에 적재하고 실행한다. 커널은 메모리, 스케줄러, 장치 드라이버를 초기화하고 루트 파일 시스템을 연결한 뒤 `systemd` 같은 첫 사용자 공간 프로세스를 실행한다.

**Q. 부트 로더와 일반 로더의 차이는 무엇인가요?**

일반 로더는 운영체제가 실행 중일 때 응용 프로그램을 메모리에 적재한다. 부트 로더는 운영체제가 실행되기 전에 운영체제 커널 자체를 메모리에 적재한다.

## 2.10 Operating-System Debugging

디버깅은 시스템의 오류를 찾아 원인을 분석하고 수정하는 과정이다. 운영체제에서는 프로그램이 비정상 종료되는 기능 오류뿐 아니라 성능 저하와 병목 현상도 디버깅 대상으로 본다.

운영체제 디버깅이 어려운 이유는 커널이 CPU, 메모리, 파일 시스템, 장치 등 시스템 전체를 관리하기 때문이다. 일반 응용 프로그램은 오류가 나면 해당 프로세스만 종료될 수 있지만, 커널 오류는 전체 시스템 중단으로 이어질 수 있다.

### 2.10.1 Failure Analysis

사용자 프로세스가 실패하면 운영체제는 오류 정보를 로그에 기록할 수 있다. 또한 프로세스가 실패한 순간의 메모리 상태를 파일로 저장할 수 있는데, 이를 코어 덤프라고 한다.

개발자는 디버거를 사용해 코어 덤프를 분석하면서 다음 내용을 확인할 수 있다.

- 어떤 함수에서 오류가 발생했는가
- 호출 스택은 어떤 상태였는가
- 변수와 레지스터 값은 무엇이었는가
- 잘못된 메모리 주소에 접근했는가

커널이 실패하는 상황은 크래시라고 하며, 이때 저장되는 메모리 상태를 크래시 덤프라고 한다.

커널 디버깅은 일반 프로세스 디버깅보다 어렵다. 예를 들어 파일 시스템 코드에서 커널 오류가 발생했다면, 고장 난 파일 시스템을 이용해 크래시 덤프를 파일로 저장하는 것 자체가 위험할 수 있다. 따라서 별도 디스크 영역이나 원격 시스템에 덤프를 기록하는 방법을 사용할 수 있다.

### 2.10.2 Performance Monitoring and Tuning

프로그램이 정상적으로 동작하더라도 지나치게 느리거나 CPU와 메모리를 과도하게 사용한다면 성능 문제가 있다.

성능 튜닝은 먼저 병목 지점을 찾고, 그 원인을 수정하는 과정이다. 추측만으로 코드를 최적화하는 것이 아니라 측정 데이터를 기반으로 판단해야 한다.

대표적인 측정 대상은 다음과 같다.

- CPU 사용률
- 메모리 사용량
- 디스크 입출력 횟수와 지연 시간
- 네트워크 처리량
- 시스템 콜 횟수
- 문맥 전환 횟수
- 페이지 폴트 횟수

### Counters

카운터는 특정 이벤트가 얼마나 발생했는지를 숫자로 기록한다.

예를 들어 CPU 사용률, 시스템 콜 횟수, 디스크 읽기 횟수, 페이지 폴트 횟수 등을 누적할 수 있다.

카운터는 전체 상태를 빠르게 파악하는 데 유용하다. CPU 사용률이 지속적으로 100%라면 CPU 병목을 의심할 수 있고, 디스크 대기 시간이 높다면 저장 장치 병목을 의심할 수 있다.

하지만 카운터만으로는 어떤 함수나 어떤 요청이 문제를 만들었는지 정확히 알기 어렵다.

### Tracing

트레이싱은 프로그램이나 커널에서 발생하는 사건의 흐름을 시간 순서대로 기록하는 방식이다.

예를 들어 한 프로세스가 어떤 시스템 콜을 호출했는지, 디스크 요청이 언제 시작되고 끝났는지, 어떤 프로세스가 언제 CPU를 사용했는지를 추적할 수 있다.

```text
12:00:00 open()
12:00:00 read()
12:00:02 disk I/O complete
12:00:02 close()
```

이 기록을 보면 `read()` 이후 디스크 응답에 2초가 걸렸다는 것을 확인할 수 있다.

카운터와 트레이싱의 차이는 다음과 같다.

| 구분      | Counter                      | Tracing                             |
| --------- | ---------------------------- | ----------------------------------- |
| 기록 내용 | 이벤트의 횟수와 통계         | 이벤트의 시간 순서와 세부 흐름      |
| 장점      | 가볍고 전체 상태 파악이 쉬움 | 원인 분석에 유리                    |
| 단점      | 구체적인 원인을 알기 어려움  | 데이터 양과 오버헤드가 커질 수 있음 |

일반적으로 카운터로 이상 징후를 발견한 뒤, 트레이싱으로 구체적인 원인을 분석한다.

### BCC와 eBPF

eBPF는 실행 중인 Linux 커널에 검증된 작은 프로그램을 동적으로 삽입해 특정 이벤트를 관찰할 수 있게 하는 기술이다.

예를 들어 다음과 같은 정보를 수집할 수 있다.

- 특정 시스템 콜이 몇 번 호출되는가
- 어느 프로세스가 파일을 열고 있는가
- 디스크 I/O에 시간이 얼마나 걸리는가
- 네트워크 패킷이 어떻게 처리되는가
- 스케줄링 지연이 어디서 발생하는가

eBPF 프로그램은 커널에 들어가기 전에 검증기를 통과한다. 검증기는 프로그램이 무한 루프를 돌거나 잘못된 메모리에 접근해 시스템의 안정성과 보안을 해치지 않는지 확인한다.

BCC는 eBPF 도구를 더 쉽게 작성하고 사용할 수 있도록 만든 도구 모음이다. Python 인터페이스와 C 기반 eBPF 코드를 조합해 커널 이벤트를 추적한다.

BCC와 eBPF의 중요한 장점은 실행 중인 시스템을 중단하지 않고도 비교적 낮은 오버헤드로 커널 내부를 관찰할 수 있다는 점이다. 따라서 실제 운영 서버의 성능 문제를 분석하는 데 유용하다.

### 2.10 핵심 정리

운영체제 디버깅은 기능 오류뿐 아니라 성능 병목까지 포함한다. 프로세스 오류는 로그와 코어 덤프로 분석하고, 커널 오류는 크래시 덤프로 분석한다. 카운터는 전체적인 수치와 통계를 보여주고, 트레이싱은 사건의 구체적인 흐름을 보여준다. Linux에서는 eBPF와 BCC를 이용해 실행 중인 커널을 동적으로 추적할 수 있다.

### 2.10 면접 포인트

**Q. Counter와 Tracing의 차이는 무엇인가요?**

Counter는 CPU 사용률이나 페이지 폴트 횟수처럼 이벤트의 누적 수치와 통계를 제공한다. Tracing은 시스템 콜이나 스케줄링 같은 이벤트가 언제 어떤 순서로 발생했는지 기록해 구체적인 원인 분석에 사용한다.

**Q. 코어 덤프와 크래시 덤프의 차이는 무엇인가요?**

코어 덤프는 일반 사용자 프로세스가 실패했을 때 해당 프로세스의 메모리 상태를 저장한 것이다. 크래시 덤프는 커널이 실패했을 때 시스템 또는 커널 메모리 상태를 저장한 것이다.

## 2.11 Chapter 2 Summary

Chapter 2는 운영체제를 사용자, 응용 프로그램, 운영체제 개발자의 관점에서 바라본다.

사용자 입장에서는 CLI, GUI, 터치 인터페이스를 통해 운영체제를 사용한다. 시스템 프로그램은 `cp`, `rm`, `ps`처럼 운영체제 기능을 편리하게 사용할 수 있도록 제공되는 프로그램이다.

응용 프로그램 입장에서는 API를 호출하고, 라이브러리와 시스템 콜 인터페이스를 거쳐 커널 기능을 사용한다. 시스템 콜은 사용자 모드 프로그램이 파일, 프로세스, 장치, 통신, 보호 같은 커널 기능을 요청하는 공식 인터페이스다.

프로그램은 컴파일러, 링커, 로더를 거쳐 실행된다. 링커는 목적 파일과 라이브러리를 결합해 실행 파일을 만들고, 로더는 실행 파일을 메모리에 적재한다.

프로그램이 운영체제와 CPU에 종속되는 이유는 시스템 콜, 실행 파일 형식, 라이브러리, ABI, CPU 명령어가 서로 다르기 때문이다.

운영체제를 설계할 때는 사용자 목표와 시스템 목표를 정하고, 정책과 메커니즘을 분리해야 한다. 정책은 무엇을 선택할지에 대한 기준이고, 메커니즘은 그 결정을 실행하는 수단이다.

운영체제 내부 구조에는 모놀리식, 계층형, 마이크로커널, 모듈형, 하이브리드 구조가 있다. 현대 운영체제는 하나의 구조만 사용하기보다 여러 구조를 혼합한다.

컴퓨터가 부팅될 때는 펌웨어가 부트 로더를 실행하고, 부트 로더가 커널을 메모리에 적재한다. 커널은 하드웨어와 서비스를 초기화한 뒤 사용자 환경을 시작한다.

운영체제의 기능 오류와 성능 문제는 로그, 덤프, 카운터, 트레이싱, eBPF와 같은 도구를 이용해 분석한다.

# Chapter 2 최종 핵심 요약

- 운영체제 서비스는 사용자와 프로그램에 실행 환경과 자원 관리 기능을 제공한다.
- 시스템 콜은 사용자 프로그램이 커널 기능을 요청하는 인터페이스다.
- 시스템 프로그램은 여러 시스템 콜을 조합해 사용자가 직접 사용할 수 있는 기능을 제공한다.
- 링커는 실행 파일을 만들고, 로더는 실행 파일을 메모리에 적재한다.
- 운영체제 종속성은 시스템 콜, 실행 파일 형식, 라이브러리, ABI 차이에서 발생한다.
- CPU 종속성은 기계어 명령어 집합의 차이에서 발생한다.
- 정책은 무엇을 선택할지, 메커니즘은 그 선택을 어떻게 실행할지에 관한 것이다.
- 모놀리식은 빠르고, 마이크로커널은 격리와 확장성이 좋다.
- 현대 운영체제는 대부분 모듈과 하이브리드 구조를 사용한다.
- 부트 로더는 운영체제가 실행되기 전에 커널을 메모리에 적재한다.
- 카운터는 통계를, 트레이싱은 구체적인 실행 흐름을 보여준다.

# Chapter 2 종합 면접 질문

## Q1. 시스템 서비스와 시스템 콜의 차이는 무엇인가요?

시스템 서비스는 운영체제가 제공하는 기능이나 이를 편리하게 사용하는 시스템 프로그램을 의미한다. 시스템 콜은 사용자 프로그램이 커널의 개별 기능을 요청하는 저수준 인터페이스다. 예를 들어 `rm`은 시스템 프로그램이고, 내부적으로 `unlink()` 시스템 콜을 사용한다.

## Q2. API와 시스템 콜의 차이는 무엇인가요?

API는 개발자가 소스 코드에서 사용하는 함수 인터페이스다. 시스템 콜은 실제로 커널에 진입해 운영체제 기능을 요청한다. 하나의 API가 여러 시스템 콜을 사용하거나 시스템 콜 없이 사용자 공간에서 끝날 수도 있다.

## Q3. 링커와 로더의 차이는 무엇인가요?

링커는 여러 목적 파일과 라이브러리를 연결해 실행 파일을 만든다. 로더는 그 실행 파일을 메모리에 적재하고 실행 환경을 구성한다.

## Q4. 운영체제와 CPU가 다르면 프로그램이 실행되지 않는 이유는 무엇인가요?

운영체제가 다르면 시스템 콜, 실행 파일 형식, 시스템 라이브러리, ABI가 다르다. CPU가 다르면 기계어 명령어 집합 자체가 다르다.

## Q5. Policy와 Mechanism을 분리하는 이유는 무엇인가요?

정책은 요구사항에 따라 자주 바뀌지만 기본 동작을 제공하는 메커니즘은 상대적으로 안정적이다. 둘을 분리하면 정책 변경 시 핵심 구현을 재사용할 수 있어 유연성과 유지보수성이 높아진다.

## Q6. Monolithic Kernel과 Microkernel을 비교해 보세요.

모놀리식 커널은 주요 기능이 같은 커널 주소 공간에서 실행되므로 빠르지만 한 구성 요소의 오류가 전체 시스템으로 퍼질 수 있다. 마이크로커널은 최소 기능만 커널에 남기고 서비스를 사용자 공간으로 분리해 안정성과 확장성이 좋지만, 메시지 전달과 문맥 전환으로 인한 성능 비용이 발생한다.

## Q7. 부팅 과정을 설명해 보세요.

BIOS 또는 UEFI가 하드웨어를 초기화하고 부트 로더를 실행한다. 부트 로더는 커널을 메모리에 적재하고 실행한다. 커널은 메모리, 스케줄러, 장치 드라이버를 초기화하고 루트 파일 시스템을 연결한 뒤 `systemd` 같은 첫 사용자 공간 프로세스를 실행한다.

## Q8. Counter와 Tracing을 비교해 보세요.

Counter는 CPU 사용률, 페이지 폴트 횟수처럼 누적 통계를 제공한다. Tracing은 시스템 콜과 스케줄링 이벤트가 발생한 시간과 순서를 기록해 구체적인 원인 분석에 사용한다.
