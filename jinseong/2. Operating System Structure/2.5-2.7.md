# Chapter 2. 운영체제 구조 — Part 2

## 2.5 Linkers and Loaders

소스 코드는 작성한 직후 바로 실행할 수 없다. 먼저 컴파일러가 소스 코드를 목적 파일로 변환하고, 링커가 목적 파일과 라이브러리를 연결해 실행 파일을 만든다. 이후 로더가 실행 파일을 메모리에 적재해야 CPU가 실행할 수 있다.

```text
소스 코드
→ 컴파일러
→ 목적 파일
→ 링커
→ 실행 파일
→ 로더
→ 메모리에 적재된 프로세스
```

### 목적 파일과 링커

컴파일러는 각 소스 파일을 개별적으로 컴파일해 **재배치 가능한 목적 파일(Relocatable Object File)** 을 만든다. 재배치 가능하다는 것은 목적 파일이 아직 메모리나 최종 실행 파일의 어느 주소에 배치될지 확정되지 않았다는 뜻이다.

예를 들어 다음과 같이 파일이 나뉘어 있다고 하자.

```c
// main.c
int add(int, int);

int main() {
    return add(1, 2);
}
```

```c
// math.c
int add(int a, int b) {
    return a + b;
}
```

`main.c`만 컴파일할 때 컴파일러는 `add()` 함수가 최종적으로 어느 주소에 위치할지 모른다. 다만 외부에 존재하는 함수라는 정보만 목적 파일에 기록한다. 이후 링커가 `main.o`와 `math.o`를 결합하면서 `add()`의 실제 위치를 찾아 연결한다.

따라서 링커의 핵심 역할은 다음과 같다.

- 여러 목적 파일을 하나의 실행 파일로 결합한다.
- 목적 파일이 참조하는 외부 함수와 전역 변수의 실제 정의를 찾는다.
- 필요한 라이브러리를 실행 파일에 연결한다.
- 각 코드와 데이터의 최종 주소를 결정하고 참조 주소를 수정한다.

### 주소 재배치(Relocation)

주소 재배치는 단순히 “소스 코드의 순서를 다시 배치한다”는 뜻이 아니다. 목적 파일 안의 코드와 데이터가 최종적으로 배치될 주소를 결정하고, 그 주소를 기준으로 함수 호출이나 변수 참조를 수정하는 작업이다.

예를 들어 `main.o`에는 다음과 같은 상태가 있을 수 있다.

```text
add 함수 호출 위치 → 아직 모름
전역 변수 주소      → 아직 모름
```

링커가 파일들을 결합하면 최종 실행 파일 안에서 다음과 같이 주소가 정해진다.

```text
main() 주소: 0x1000
add() 주소:  0x1100
```

그러면 `main()` 내부의 `add()` 호출 부분도 `0x1100`을 참조하도록 수정된다. 이처럼 **최종 배치 위치에 맞게 코드와 데이터의 주소 참조를 조정하는 작업**이 재배치다.

다만 현대 시스템에서는 실행 파일 생성 시 모든 실제 메모리 주소가 완전히 고정되는 것은 아니다. 실행 파일 내부의 상대적 주소를 정리하는 작업은 링커가 하고, 실제 메모리에 적재될 때 필요한 추가 재배치는 로더가 처리할 수 있다.

### 로더(Loader)

로더는 링커가 만든 실행 파일을 메모리에 적재하고 실행 가능한 프로세스로 만든다. 일반적으로 다음 작업을 수행한다.

1. 실행 파일의 형식과 헤더를 확인한다.
2. 코드와 데이터를 배치할 메모리 공간을 마련한다.
3. 실행 파일의 코드 및 데이터를 메모리에 적재한다.
4. 필요한 동적 라이브러리를 연결한다.
5. 스택과 힙 등 실행 환경을 준비한다.
6. 프로그램의 시작 지점으로 실행을 넘긴다.

즉, 링커가 **실행 파일을 만드는 도구**라면 로더는 **실행 파일을 실제 실행 상태로 만드는 도구**다.

### 정적 링크와 동적 링크

정적 링크는 필요한 라이브러리 코드를 실행 파일 안에 포함하는 방식이다. 프로그램이 독립적으로 실행되기 쉽지만, 동일한 라이브러리를 사용하는 프로그램마다 라이브러리 코드가 중복된다.

동적 링크는 실행 파일에 라이브러리 전체를 넣지 않고, 어떤 라이브러리의 어떤 기능이 필요한지만 기록한다. 실행 시 로더가 시스템에 설치된 공유 라이브러리와 연결한다.

| 구분                      | 정적 링크                    | 동적 링크                         |
| ------------------------- | ---------------------------- | --------------------------------- |
| 라이브러리 포함 위치      | 실행 파일 내부               | 별도 라이브러리 파일              |
| 실행 파일 크기            | 커짐                         | 작아짐                            |
| 외부 라이브러리 필요 여부 | 보통 불필요                  | 실행 환경에 필요                  |
| 라이브러리 공유           | 어려움                       | 여러 프로그램이 공유 가능         |
| 배포 편의성               | 독립적이라 편리              | 버전과 설치 상태를 확인해야 함    |
| 업데이트                  | 실행 파일을 다시 빌드해야 함 | 호환된다면 라이브러리만 교체 가능 |

동적 링크에서도 라이브러리는 로컬 시스템이나 실행 환경에 존재해야 한다. Windows의 DLL, Linux의 `.so` 파일이 대표적이다. 다만 여러 실행 파일이 같은 라이브러리를 각각 포함하지 않고 하나의 공유 라이브러리를 사용하므로 실행 파일 크기와 메모리 사용량을 줄일 수 있다.

정적 링크가 항상 더 좋은 것은 아니다. 단일 실행 파일 배포와 환경 독립성이 중요하면 정적 링크가 유리하고, 디스크·메모리 절약과 공통 라이브러리 관리가 중요하면 동적 링크가 유리하다.

### 핵심 정리

링커는 여러 목적 파일과 라이브러리를 연결해 실행 파일을 만들고, 로더는 그 실행 파일을 메모리에 적재해 실행 가능한 프로세스로 만든다. 재배치는 코드와 데이터의 최종 배치 위치를 정하고 주소 참조를 수정하는 작업이다. 정적 링크는 라이브러리를 실행 파일에 포함하고, 동적 링크는 실행 시 외부 공유 라이브러리와 연결한다.

### 면접 포인트

**Q. 링커와 로더의 차이는 무엇인가요?**

링커는 컴파일된 목적 파일과 라이브러리를 결합해 실행 파일을 만든다. 로더는 실행 파일을 메모리에 적재하고 필요한 실행 환경을 구성한 뒤 프로그램 실행을 시작한다.

**Q. 재배치란 무엇인가요?**

목적 파일에 아직 확정되지 않은 함수와 변수의 주소를 최종 배치 위치에 맞게 결정하고, 코드와 데이터의 주소 참조를 수정하는 작업이다.

## 2.6 Why Applications Are Operating-System Specific

일반적으로 특정 운영체제와 CPU를 대상으로 컴파일된 실행 파일은 다른 환경에서 그대로 실행되지 않는다. 프로그램은 단순한 소스 코드가 아니라 운영체제와 CPU가 이해할 수 있는 형식의 바이너리로 변환되기 때문이다.

### 운영체제에 따라 달라지는 요소

첫째, 운영체제마다 제공하는 API와 시스템 콜이 다르다. 같은 기능이라도 프로세스를 생성하는 방식, 파일을 열고 닫는 방식, 결과를 반환하는 방식이 다를 수 있다.

```text
Linux/UNIX 계열: fork(), exec()
Windows: CreateProcess()
```

둘째, 실행 파일 형식이 다르다. 운영체제는 실행 파일 안에서 코드, 데이터, 라이브러리 정보, 시작 위치 등을 읽어야 하므로 자신이 지원하는 실행 파일 형식을 사용한다.

```text
Windows: PE
Linux: ELF
macOS: Mach-O
```

셋째, 시스템 라이브러리와 런타임 환경도 다르다. 실행 파일이 특정 운영체제의 DLL이나 공유 라이브러리를 전제로 만들어졌다면, 다른 운영체제에서는 해당 라이브러리를 찾거나 사용할 수 없다.

넷째, ABI가 다르다. 같은 CPU를 사용하더라도 운영체제와 컴파일 환경에 따라 함수 호출 규칙, 시스템 콜 매개변수 전달 방식, 스택 구성, 자료형 크기 등이 달라질 수 있다.

### CPU 차이와 운영체제 차이의 구분

운영체제 차이와 CPU 차이는 서로 다른 계층의 문제다.

운영체제 차이는 프로그램이 커널 기능을 요청하는 규칙과 실행 파일 환경의 차이다. 예를 들어 Windows와 Linux는 같은 x86-64 CPU에서 실행될 수 있지만 시스템 콜, 실행 파일 형식, 라이브러리가 다르다.

CPU 차이는 기계어 명령어 자체의 차이다. x86-64용으로 컴파일된 기계어는 ARM CPU가 그대로 이해할 수 없다.

```text
운영체제 차이
→ 시스템 콜, 실행 파일 형식, 시스템 라이브러리, ABI가 다름

CPU 차이
→ CPU가 이해하는 명령어 집합이 다름
```

따라서 다음 두 경우는 서로 다른 이유로 실행되지 않을 수 있다.

```text
Windows x86-64 프로그램 → Linux x86-64
CPU는 같지만 운영체제 규칙이 달라 실행 불가

Linux x86-64 프로그램 → Linux ARM64
운영체제 계열은 같지만 기계어가 달라 실행 불가
```

### API와 ABI

API는 개발자가 소스 코드에서 사용하는 함수와 사용 규칙을 정의한다. 함수 이름, 매개변수, 반환값처럼 프로그래머가 직접 보는 수준이다.

ABI는 컴파일된 바이너리들이 서로 상호작용하기 위해 지켜야 하는 저수준 규칙이다. 다음과 같은 내용이 포함된다.

- 인자를 어떤 레지스터나 스택 위치에 넣는지
- 반환값을 어디에 저장하는지
- 스택 프레임을 어떻게 구성하는지
- 자료형의 크기와 정렬을 어떻게 정하는지
- 실행 파일과 시스템 라이브러리의 바이너리 형식
- 시스템 콜 번호와 매개변수 전달 방식

예를 들어 소스 코드에서 다음 함수는 하나의 API로 보인다.

```c
int sum(int a, int b);
```

하지만 컴파일된 프로그램이 `sum()`을 호출하려면 첫 번째 인자와 두 번째 인자를 어느 레지스터에 넣을지, 결과는 어느 레지스터에서 받을지 등의 규칙이 필요하다. 이 규칙이 ABI에 해당한다.

따라서 ABI를 단순히 “기계어 프로그램 간의 인터페이스”라고 해도 큰 방향은 맞지만, 더 정확하게는 **특정 운영체제와 CPU 환경에서 컴파일된 바이너리 구성 요소들이 상호작용하는 규칙**이다.

### 이식성을 높이는 방법

응용 프로그램이 여러 운영체제에서 동작하도록 만드는 대표적인 방법은 다음과 같다.

첫째, 공통 소스 코드와 운영체제별 구현을 분리해 각 환경에서 별도로 컴파일한다. 하나의 프로젝트라도 Windows용, macOS용, Linux용 실행 파일은 각각 따로 만들어진다.

둘째, Java Virtual Machine이나 Python 인터프리터처럼 각 운영체제에 맞는 런타임 환경을 둔다. 프로그램 자체는 공통 바이트코드나 소스 형태로 배포하고, 운영체제별 런타임이 실제 시스템 기능과 연결한다.

셋째, 웹 애플리케이션처럼 브라우저를 공통 실행 환경으로 사용한다. 다만 이 경우에도 브라우저 자체는 운영체제와 CPU에 맞게 구현되어 있어야 한다.

소스 코드에 운영체제별 분기 처리를 넣는 방식도 가능하다. 그러나 일반적으로 모든 운영체제 코드를 하나의 바이너리에 넣는 것이 아니라, 빌드 시 현재 대상에 필요한 코드만 선택해 별도의 실행 파일을 만든다. 문제는 단순히 파일 크기가 커지는 것뿐 아니라 운영체제별 빌드, 테스트, 라이브러리 호환성, 권한 처리, UI 차이를 모두 관리해야 한다는 점이다.

### 핵심 정리

프로그램의 운영체제 종속성은 시스템 콜, 실행 파일 형식, 시스템 라이브러리, ABI 차이에서 발생한다. CPU 종속성은 기계어 명령어 집합의 차이에서 발생한다. API가 소스 코드 수준의 인터페이스라면 ABI는 바이너리 수준의 규칙이다.

### 면접 포인트

**Q. 같은 CPU를 쓰는 Windows 프로그램이 Linux에서 실행되지 않는 이유는 무엇인가요?**

CPU 명령어는 같을 수 있지만 실행 파일 형식, 시스템 콜, 시스템 라이브러리, ABI가 서로 다르기 때문이다.

**Q. API와 ABI의 차이는 무엇인가요?**

API는 개발자가 소스 코드에서 사용하는 함수와 규칙이고, ABI는 컴파일된 바이너리 사이에서 인자 전달, 스택 구성, 자료형 크기, 실행 파일 형식 등을 정의하는 저수준 규칙이다.

## 2.7 Operating-System Design and Implementation

운영체제는 매우 크고 복잡하기 때문에 구현 전에 어떤 시스템을 만들 것인지 목표를 명확히 해야 한다. 데스크톱, 모바일, 서버, 실시간 시스템은 서로 요구사항이 다르므로 하나의 설계가 모든 환경에 가장 적합할 수는 없다.

### 설계 목표

운영체제의 설계 목표는 사용자 관점과 시스템 개발자 관점으로 나눌 수 있다.

사용자 관점에서는 사용하기 쉽고, 배우기 편하며, 빠르고, 안전하고, 신뢰할 수 있는 시스템이 중요하다.

시스템 개발자 관점에서는 설계와 구현, 유지보수가 쉬워야 하며, 유연하고 효율적이고 오류가 적어야 한다.

| 관점        | 주요 목표                                            |
| ----------- | ---------------------------------------------------- |
| 사용자 목표 | 편의성, 학습 용이성, 빠른 응답, 안전성, 신뢰성       |
| 시스템 목표 | 구현 용이성, 유지보수성, 유연성, 효율성, 오류 최소화 |

이러한 목표는 서로 충돌할 수도 있다. 보안을 강화하면 사용 절차가 복잡해질 수 있고, 구조를 단순화하면 확장성이 떨어질 수 있다. 따라서 운영체제 설계는 대상 환경에 맞는 우선순위를 정하는 과정이다.

### Policy와 Mechanism

정책(Policy)은 **무엇을 할 것인지 결정하는 기준**이고, 메커니즘(Mechanism)은 **그 결정을 실제로 수행할 수 있게 하는 수단**이다.

책의 예시에서는 타이머가 CPU를 보호하는 메커니즘이고, 타이머를 몇 밀리초로 설정할지는 정책이다.

```text
Mechanism: 일정 시간이 지나면 인터럽트를 발생시켜 CPU 제어권을 회수한다.
Policy: 한 프로세스에 CPU를 몇 밀리초 동안 허용할 것인가?
```

CPU 스케줄링에서도 같은 구분을 적용할 수 있다.

```text
Mechanism
- 준비 큐에 프로세스를 저장한다.
- 타이머 인터럽트를 발생시킨다.
- 현재 프로세스를 중단하고 다른 프로세스로 전환한다.

Policy
- 어떤 프로세스를 다음에 선택할 것인가?
- I/O 중심 프로세스와 CPU 중심 프로세스 중 누구에게 높은 우선순위를 줄 것인가?
- 한 프로세스에 얼마 동안 CPU를 줄 것인가?
```

따라서 “정책을 정하고 이를 구현하는 방법이 메커니즘이다”라는 설명은 대체로 맞다. 다만 둘이 항상 일대일로 묶이는 것은 아니다. 좋은 메커니즘은 여러 정책을 지원할 수 있어야 한다.

### 왜 정책과 메커니즘을 분리하는가?

정책은 시스템의 목적이나 환경에 따라 자주 바뀐다. 반면 CPU를 전환하거나 권한을 검사하는 기본 메커니즘은 상대적으로 자주 바뀌지 않는다.

예를 들어 우선순위를 처리할 수 있는 일반적인 메커니즘이 있다고 하자. 이 메커니즘은 다음과 같이 서로 반대되는 정책에도 사용할 수 있다.

```text
정책 A: 사용자 입력에 빠르게 반응하기 위해 I/O 중심 프로세스를 우선한다.
정책 B: 계산 처리량을 높이기 위해 CPU 중심 프로세스를 우선한다.
```

정책과 메커니즘이 분리되어 있다면 우선순위 기준만 바꾸면 된다. 반대로 특정 정책이 메커니즘 내부에 강하게 박혀 있으면 정책이 바뀔 때 큐 구조, 스케줄러, 인터럽트 처리 코드까지 함께 수정해야 할 수 있다.

즉, 분리의 목적은 **정책 변경에 따른 코드 수정 범위를 줄이고 시스템의 유연성과 재사용성을 높이는 것**이다.

웹 개발에 비유하면 다음과 유사하다.

```text
Mechanism: 목록을 정렬할 수 있는 공통 정렬 기능
Policy: 최신순, 가격순, 평점순 중 어떤 기준을 선택할지
```

정렬 기능 자체를 새로 만들지 않고 정렬 기준만 바꾸는 것과 같다.

### 운영체제 구현 언어

초기 운영체제는 하드웨어를 직접 제어하기 위해 대부분 어셈블리어로 작성되었다. 현대 운영체제는 주로 C나 C++ 같은 고급 언어로 구현하고, 하드웨어 제어와 문맥 전환처럼 낮은 수준의 기능에만 어셈블리어를 사용한다.

고급 언어를 사용하면 코드 작성, 디버깅, 유지보수, 다른 하드웨어로의 이식이 쉬워진다. 반면 컴파일러가 생성한 코드가 직접 작성한 어셈블리어보다 비효율적일 수 있다는 우려가 있다. 그러나 현대 컴파일러의 최적화 수준이 높고, 운영체제 성능은 언어 자체보다 자료구조와 알고리즘 선택의 영향을 더 크게 받는 경우가 많다.

따라서 일반적인 구현 방식은 다음과 같다.

```text
하드웨어와 직접 맞닿는 매우 낮은 수준
→ 일부 어셈블리어

커널의 주요 기능
→ C

상위 시스템 구성 요소와 라이브러리
→ C, C++ 또는 더 높은 수준의 언어
```

### 신뢰성의 의미

운영체제에서 신뢰성은 단순히 한 번 원하는 결과가 나오는 것만을 뜻하지 않는다. 다양한 상황과 오랜 실행 시간 동안 시스템이 의도한 기능을 안정적으로 수행하고, 오류가 발생하더라도 전체 시스템의 손상이나 데이터 유실을 최소화하는 성질이다.

정확성은 특정 입력에 대해 올바른 결과를 내는지에 더 가깝고, 신뢰성은 그러한 올바른 동작이 지속적으로 유지되는지까지 포함한다.

```text
정확성: 파일 저장 요청에 대해 올바른 내용이 저장된다.
신뢰성: 수많은 저장 요청과 예외 상황에서도 시스템이 안정적으로 동작하고 데이터가 손상되지 않는다.
```

### 핵심 정리

운영체제 설계는 대상 환경에 따라 사용자 목표와 시스템 목표를 정하는 것에서 시작한다. 정책은 무엇을 할 것인지 결정하고, 메커니즘은 그 결정을 수행하는 수단을 제공한다. 둘을 분리하면 정책이 바뀌어도 기본 구현을 재사용할 수 있어 유연성과 유지보수성이 높아진다. 현대 운영체제는 대부분 C나 C++로 작성하고, 하드웨어 의존적인 일부 기능에 어셈블리어를 사용한다.

### 면접 포인트

**Q. Policy와 Mechanism을 분리해야 하는 이유는 무엇인가요?**

정책은 환경과 요구사항에 따라 자주 변경되지만 기본 메커니즘은 비교적 안정적이다. 둘을 분리하면 정책 변경 시 핵심 구현을 수정하지 않고 매개변수나 선택 기준만 바꿀 수 있어 유연성과 유지보수성이 높아진다.

**Q. 운영체제를 전부 어셈블리어로 구현하지 않는 이유는 무엇인가요?**

어셈블리어는 하드웨어 제어에는 유리하지만 개발과 유지보수가 어렵고 이식성이 낮다. 현대 운영체제는 대부분 C나 C++로 구현하고, 문맥 전환이나 특정 레지스터 제어처럼 하드웨어에 밀접한 부분만 어셈블리어를 사용한다.

# Part 2 핵심 요약

프로그램은 소스 코드에서 목적 파일로 컴파일되고, 링커가 목적 파일과 라이브러리를 결합해 실행 파일을 만든다. 로더는 실행 파일을 메모리에 적재해 실행 가능한 프로세스로 만든다. 프로그램이 특정 운영체제와 CPU에 종속되는 이유는 시스템 콜, 실행 파일 형식, 시스템 라이브러리, ABI, CPU 명령어 집합이 서로 다르기 때문이다. 운영체제 설계에서는 사용자 및 시스템 목표를 정한 뒤, 변경 가능한 정책과 재사용 가능한 메커니즘을 분리해 유연한 구조를 만드는 것이 중요하다.
