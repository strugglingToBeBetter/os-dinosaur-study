# Chapter 6. Synchronization Tools — 6.7 ~ 6.10

앞에서 **Race Condition → Critical Section → Peterson → 하드웨어 지원 → Mutex → Semaphore**까지 봤다.

6.7부터는 질문이 한 단계 바뀐다.

> **"Semaphore로 동기화는 할 수 있는데, 프로그래머가 `wait()` / `signal()`을 잘못 쓰면 어떡하지?"**

그래서 더 높은 수준의 **Monitor**가 등장하고, 이후에는 동기화 도구를 사용하면서 생길 수 있는 **Liveness 문제**와 각 동기화 도구의 **성능 선택 기준**을 다룬다. 교재 기준 범위는 6.7 Monitors, 6.8 Liveness, 6.9 Evaluation, 6.10 Summary이다.

# 6.7 Monitors

## 6.7.0 왜 Monitor가 필요한가?

Semaphore는 강력하지만 **사용법을 프로그래머가 직접 지켜야 한다.**

Critical Section을 Semaphore로 보호한다면 정상적인 코드는 다음과 같다.

```c
wait(mutex);

/* critical section */

signal(mutex);
```

그런데 프로그래머가 실수하면 문제가 생긴다.

### 실수 1. 순서를 반대로 사용

```c
signal(mutex);

/* critical section */

wait(mutex);
```

Lock을 얻기도 전에 Critical Section에 들어가므로 여러 프로세스가 동시에 들어갈 수 있다.

→ **Mutual Exclusion 위반**

---

### 실수 2. `signal()` 대신 `wait()`을 사용

```c
wait(mutex);

/* critical section */

wait(mutex);
```

첫 번째 `wait()`에서 Semaphore를 획득한 뒤 두 번째 `wait()`에서 자기 자신이 반환할 Semaphore를 기다리게 된다.

```text
P1
wait(mutex) → 획득

Critical Section

wait(mutex)
     ↓
mutex를 가진 사람 = P1 자신
     ↓
P1이 영원히 대기
```

---

### 실수 3. `wait()` 또는 `signal()` 누락

```text
wait() 누락
→ Mutual Exclusion이 깨질 수 있음

signal() 누락
→ 다른 프로세스가 영원히 기다릴 수 있음
```

즉 Semaphore 자체는 정상이어도 **사용자가 프로토콜을 잘못 작성하면 프로그램이 망가진다.**

게다가 이런 오류는 특정 실행 순서에서만 나타날 수 있기 때문에 재현하기도 어렵다.

그래서 교재는 동기화 기능 자체를 **고수준 언어 구조 안에 포함시키는 방법**으로 Monitor를 소개한다.

---

# 6.7.1 Monitor Usage

## 1. Monitor란?

Monitor는 **ADT(Abstract Data Type, 추상 자료형)** 의 한 종류다.

ADT는 기본적으로:

```text
데이터
+
그 데이터를 조작하는 함수
```

를 하나의 단위로 묶는다.

Monitor는 여기에 중요한 성질을 하나 추가한다.

> **Monitor 내부에서는 한 시점에 하나의 프로세스만 활성화될 수 있다.**

즉 Mutual Exclusion이 Monitor 자체에 포함되어 있다.

---

## 구조

교재 Figure 6.11의 개념적인 Monitor 구조는 다음과 같다.

```c
monitor monitor_name
{
    /* shared variable declarations */

    function P1(...) {
        ...
    }

    function P2(...) {
        ...
    }

    ...

    function Pn(...) {
        ...
    }

    initialization_code(...) {
        ...
    }
}
```

Monitor 안에는:

```text
Monitor
├─ 공유 데이터
├─ 데이터를 조작하는 함수들
└─ 초기화 코드
```

가 존재한다.

중요한 것은 **Monitor 내부 공유 데이터에 외부 프로세스가 직접 접근할 수 없다는 것**이다.

```text
외부 프로세스
    │
    │ 함수 호출
    ▼
┌──────── Monitor ────────┐
│ shared data             │
│                         │
│ function A()            │
│ function B()            │
└─────────────────────────┘
```

공유 데이터는 Monitor 내부 함수만 접근한다.

---

## Monitor가 Mutual Exclusion을 자동으로 보장

Semaphore에서는 우리가 직접:

```c
wait(mutex);

critical_section();

signal(mutex);
```

를 작성해야 했다.

Monitor에서는:

```text
P1 → Monitor 함수 실행 중

P2 → Monitor 진입 요청
      ↓
     대기
```

가 자동으로 처리된다.

즉 프로그래머가 각 함수마다 Mutex 코드를 명시적으로 작성할 필요가 없다.

### 핵심

```text
Semaphore
→ Mutual Exclusion 프로토콜을 개발자가 관리

Monitor
→ Monitor 구조 자체가 Mutual Exclusion을 관리
```

교재 Figure 6.12도 Monitor 앞에 **Entry Queue**가 있고, 한 프로세스만 Monitor 내부에서 실행되는 구조를 보여준다.

---

# 그런데 Mutual Exclusion만으로는 부족하다

다음 상황을 생각해보자.

Consumer가 Monitor에 들어왔다.

```text
buffer = empty
```

Consumer는 데이터가 들어올 때까지 기다려야 한다.

그런데 Consumer가 Monitor 안에서 계속 기다리면:

```text
Consumer → Monitor 점유

Producer → Monitor에 못 들어감

Producer가 데이터를 넣을 수 없음
```

이 된다.

즉 특정 조건이 만족될 때까지 **Monitor 사용권을 내려놓고 기다릴 방법**이 필요하다.

그래서 등장하는 것이 **Condition Variable**이다.

---

# Condition Variable

Monitor 내부에서 다음과 같이 선언한다.

```c
condition x, y;
```

Condition Variable에서 사용할 수 있는 핵심 연산은 두 가지다.

```text
wait()
signal()
```

---

## `x.wait()`

```c
x.wait();
```

의 의미는:

> 현재 프로세스를 조건 `x`의 대기 큐에서 기다리게 한다.

이때 중요한 점은 **Monitor를 점유한 채 기다리는 것이 아니라 Monitor를 놓고 기다린다는 것**이다.

```text
P1 Monitor 실행 중
     ↓
x.wait()
     ↓
Monitor 사용권 반환
     ↓
P1 → x condition queue에서 Waiting
```

그러므로 다른 프로세스가 Monitor에 들어갈 수 있다.

---

## `x.signal()`

```c
x.signal();
```

은:

> `x`에서 기다리는 프로세스 중 정확히 하나를 깨운다.

예:

```text
Condition x Queue

P2 → P3 → P4
```

`x.signal()`:

```text
P2 하나를 재개
```

---

## 아무도 기다리지 않는다면?

여기가 Semaphore와 매우 중요한 차이다.

Monitor Condition Variable에서:

```c
x.signal();
```

했는데 `x`에서 기다리는 프로세스가 없다면

> **아무 일도 일어나지 않는다.**

signal의 효과가 저장되지 않는다.

---

### Semaphore와 비교

Semaphore:

```text
S = 0

signal(S)
→ S = 1

나중에 P1이 wait(S)
→ 바로 통과
```

signal의 효과가 Semaphore 값에 남는다.

반면 Condition Variable:

```text
x 대기자 없음

x.signal()
→ 아무 효과 없음

나중에 P1이 x.wait()
→ 기다림
```

이 차이는 반드시 기억해야 한다.

|                           | Semaphore        | Condition Variable             |
| ------------------------- | ---------------- | ------------------------------ |
| `signal()` 시 대기자 없음 | 값 증가          | 아무 효과 없음                 |
| 상태 저장                 | O                | signal 자체를 저장하지 않음    |
| 용도                      | 자원 개수/동기화 | 특정 조건이 만족될 때까지 대기 |

---

# Signal 이후 누가 Monitor를 사용할까?

문제가 하나 있다.

프로세스 P가 Monitor 내부에서:

```c
x.signal();
```

을 실행했다고 하자.

그리고 Q가 `x.wait()`에서 기다리고 있었다.

```text
P → 현재 Monitor 안에 있음
Q → x에서 Waiting
```

`signal()`에 의해 Q가 깨어났다고 해서 P와 Q가 동시에 Monitor에서 실행되면:

```text
P + Q 동시 Monitor 실행
```

Monitor의 Mutual Exclusion이 깨진다.

따라서 둘 중 하나는 기다려야 한다.

교재는 두 방법을 설명한다.

---

## ① Signal-and-Wait

P가 Q를 깨우면 **P가 기다리고 Q가 바로 실행**한다.

```text
P
x.signal()
    ↓
P 대기

Q 재개
    ↓
Q Monitor 작업 완료
    ↓
P 다시 실행
```

---

## ② Signal-and-Continue

P가 계속 실행한다.

Q는 P가 Monitor에서 나갈 때까지 기다린다.

```text
P
x.signal()
    ↓
P 계속 실행
    ↓
P Monitor 종료
    ↓
Q 실행
```

---

## 두 방식의 차이

Signal-and-Continue는 현재 실행하고 있는 P를 그대로 실행시키므로 자연스러워 보인다.

하지만 Q 입장에서는 문제가 있을 수 있다.

Q는 어떤 조건이 참이기를 기다렸다.

```text
Q:
"x 조건이 참이 되면 깨워줘"
```

P가 `signal()`한 순간에는 조건이 참이었다.

그런데 P가 계속 실행하면서 그 조건을 다시 바꿀 수도 있다.

```text
조건 true
 ↓
signal(Q)
 ↓
P 계속 실행
 ↓
조건 false
 ↓
Q 실행
```

Q가 깨어났을 때는 자신이 기다리던 조건이 더 이상 참이 아닐 수 있다.

그래서 Signal-and-Wait 역시 논리적인 장점이 있다.

교재는 중간 형태도 설명한다.

> P가 `signal()`하면 즉시 Monitor에서 나가고 Q를 실행한다.

---

# 6.7.2 Implementing a Monitor Using Semaphores

Monitor는 고수준 개념이지만 내부적으로 Semaphore를 이용해 구현할 수도 있다.

교재에서는 **Signal-and-Wait 방식**을 구현한다.

---

## 기본 Mutual Exclusion

Monitor마다:

```c
semaphore mutex = 1;
```

을 둔다.

Monitor 함수에 들어올 때:

```c
wait(mutex);
```

나갈 때:

```c
signal(mutex);
```

을 한다.

그래서 한 프로세스만 Monitor 내부에서 실행된다.

---

## 그런데 `signal()`한 프로세스를 기다리게 해야 한다

Signal-and-Wait에서는:

```text
P → x.signal()
Q → 깨어나서 실행

P는 기다려야 함
```

이 필요하다.

그래서 추가 Semaphore:

```c
semaphore next = 0;
int next_count = 0;
```

을 둔다.

- `next`: signal을 실행하고 잠시 양보한 프로세스들이 기다림
- `next_count`: 그러한 프로세스의 수

---

## Monitor 함수 F의 기본 형태

```c
wait(mutex);

/* body of F */

if (next_count > 0)
    signal(next);
else
    signal(mutex);
```

끝날 때 무조건 `mutex`를 반환하는 것이 아니다.

만약 `signal()`을 실행하고 양보해서 기다리고 있는 프로세스가 있다면:

```c
signal(next);
```

로 그 프로세스에게 먼저 실행권을 돌려준다.

없다면:

```c
signal(mutex);
```

로 Monitor를 완전히 외부에 개방한다.

---

# Condition Variable 구현

Condition `x`마다:

```c
semaphore x_sem = 0;
int x_count = 0;
```

을 둔다.

---

## `x.wait()`

교재의 구현은 다음과 같다.

```c
x_count++;

if (next_count > 0)
    signal(next);
else
    signal(mutex);

wait(x_sem);

x_count--;
```

### 동작

현재 P가:

```c
x.wait();
```

을 호출했다.

1. `x_count++`
   - 자신이 x를 기다리는 프로세스라는 것을 기록한다.

2. Monitor 사용권을 다른 프로세스에게 넘긴다.

```text
기다리던 signal 프로세스 존재
→ signal(next)

그렇지 않음
→ signal(mutex)
```

3. `wait(x_sem)`
   - 자신은 Sleep한다.

즉:

```text
Monitor 안에서 기다리는 것이 아니라
Monitor를 반환하고 Waiting으로 이동
```

한다.

---

## `x.signal()`

```c
if (x_count > 0) {
    next_count++;

    signal(x_sem);

    wait(next);

    next_count--;
}
```

P가 `x.signal()`을 호출하면:

```text
x에서 기다리는 Q 존재
       ↓
Q를 깨움
       ↓
P 자신은 next에서 기다림
       ↓
Q가 Monitor 실행
       ↓
Q가 끝난 후 P가 다시 실행
```

따라서 **Signal-and-Wait**가 구현된다.

---

# Monitor 구현 흐름

```text
P Monitor 실행
      ↓
x.signal()
      ↓
Q를 깨움
      ↓
P → next 대기
      ↓
Q Monitor 실행
      ↓
Q 종료
      ↓
next에 P가 있음
      ↓
P 깨움
      ↓
P Monitor 실행 계속
```

여기서도 결국 밑단에는 Semaphore가 사용되지만, 사용자 입장에서는 Semaphore 조작을 직접 하지 않고 Monitor라는 더 안전한 추상화를 사용한다.

---

# 6.7.3 Resuming Processes within a Monitor

Condition Variable 하나에 여러 프로세스가 기다리고 있다고 하자.

```text
x Condition Queue

P1
P2
P3
P4
```

`x.signal()`이 호출되었을 때 **누구를 깨울 것인가?**

---

## 방법 1. FCFS

가장 단순하게:

> 가장 오래 기다린 프로세스를 먼저 실행

한다.

```text
P1 → P2 → P3 → P4
```

그러나 모든 상황에서 FCFS가 최선은 아니다.

예를 들어:

```text
P1 : Resource를 100ms 사용 예정
P2 : Resource를 10ms 사용 예정
```

10ms짜리를 먼저 처리하고 싶을 수도 있다.

그래서 **Conditional Wait**를 사용할 수 있다.

---

# Conditional Wait

형태:

```c
x.wait(c);
```

여기서 `c`는 정수 표현식이며 **Priority Number**라고 한다.

`wait()` 시점에 `c`를 평가하고 프로세스와 함께 저장한다.

`x.signal()`이 호출되면:

> **Priority Number가 가장 작은 프로세스가 먼저 깨어난다.**

---

# ResourceAllocator 예제

교재 Figure 6.14는 하나의 자원을 여러 프로세스에 할당하는 Monitor를 보여준다.

```c
monitor ResourceAllocator
{
    boolean busy;
    condition x;

    void acquire(int time) {
        if (busy)
            x.wait(time);

        busy = true;
    }

    void release() {
        busy = false;
        x.signal();
    }

    initialization_code() {
        busy = false;
    }
}
```

프로세스는:

```c
R.acquire(t);

/* resource 사용 */

R.release();
```

형태로 사용한다.

여기서 `t`는 예상 사용 시간이다.

```c
x.wait(t);
```

이므로 대기하는 프로세스 중 **가장 작은 `t`를 가진 프로세스**가 먼저 재개된다.

즉:

```text
P1 : 30ms
P2 : 5ms
P3 : 20ms

→ P2 → P3 → P1
```

와 같은 방식으로 자원을 할당할 수 있다.

---

# 그런데 Monitor도 모든 프로그래밍 오류를 막지는 못한다

이 부분이 중요하다.

Monitor를 만들었다고 해도 사용자 프로그램이 다음 프로토콜을 반드시 지킨다는 보장은 없다.

정상:

```c
R.acquire(t);

resource 사용;

R.release();
```

그런데 프로그래머가 다음처럼 만들 수도 있다.

---

### ① `acquire()` 없이 자원에 직접 접근

```text
ResourceAllocator 무시
→ 공유 자원 직접 사용
```

---

### ② 자원을 얻고 반환하지 않음

```c
R.acquire(t);

/* 사용 */

... R.release() 없음
```

다른 프로세스들이 계속 기다릴 수 있다.

---

### ③ 얻지도 않은 자원을 반환

```c
R.release();
```

---

### ④ 같은 자원을 두 번 요청

```c
R.acquire(t);

R.acquire(t);
```

첫 번째 자원을 반환하기도 전에 다시 요청한다.

---

## Monitor의 한계

Monitor는:

> **Monitor 내부의 Mutual Exclusion**

은 보장할 수 있다.

하지만:

> **프로그램 전체가 반드시 Monitor를 올바른 순서로 사용하는가?**

까지 자동으로 보장하지는 않는다.

교재는 올바른 시스템을 위해 두 가지를 확인해야 한다고 설명한다.

1. 프로세스들이 Monitor 함수를 올바른 순서로 호출하는가?
2. 프로세스가 Monitor를 무시하고 공유 자원에 직접 접근하지 않는가?

작고 정적인 프로그램이라면 코드를 검사할 수도 있지만, 큰 동적 시스템에서는 현실적이지 않다.

이 문제는 이후 **Chapter 17 Protection**의 접근 제어 메커니즘과 연결된다.

---

## 6.7 핵심 비교

| 방법               | Mutual Exclusion 관리    | 특징                         |
| ------------------ | ------------------------ | ---------------------------- |
| Mutex              | 프로그래머가 lock/unlock | 단순                         |
| Semaphore          | 프로그래머가 wait/signal | 강력하지만 실수 가능         |
| Monitor            | 구조 자체가 보장         | 더 높은 수준의 추상화        |
| Condition Variable | Monitor 내부 조건 대기   | wait/signal로 실행 순서 제어 |

# 6.8 Liveness

지금까지는 주로:

> **여러 프로세스가 동시에 Critical Section에 들어가는 것을 어떻게 막을까?**

를 고민했다.

그런데 Lock을 너무 잘 막아도 새로운 문제가 발생한다.

```text
P1
Critical Section 들어가고 싶음
       ↓
계속 기다림
       ↓
영원히 못 들어감
```

이것 역시 올바른 동기화가 아니다.

---

# Liveness란?

**Liveness**는:

> 프로세스가 실행 생명주기 동안 계속 진행할 수 있도록 시스템이 만족해야 하는 성질들의 집합

이다.

즉 단순히:

```text
"동시에 들어가지 않는다"
```

만으로는 부족하고,

```text
"언젠가는 앞으로 진행한다"
```

도 보장해야 한다.

---

## Critical Section 조건과 연결

6.2에서 세 조건을 배웠다.

```text
Mutual Exclusion
Progress
Bounded Waiting
```

프로세스가 무한히 기다린다면:

```text
Progress        위반 가능
Bounded Waiting 위반
```

이다.

이런 상황을 **Liveness Failure**라고 한다.

---

## Liveness Failure 예

아주 단순하게는:

```c
while (true) {
}
```

같은 Infinite Loop도 Liveness Failure다.

Busy Waiting도 무한히 오래 지속될 수 있다면 Liveness 문제가 될 수 있다.

교재에서는 대표적인 두 가지를 살펴본다.

```text
Liveness Failure
├─ Deadlock
└─ Priority Inversion
```

---

# 6.8.1 Deadlock

## 개념

**Deadlock(교착 상태)** 는 여러 프로세스가 서로가 일으켜야 할 이벤트를 기다리면서 **아무도 진행하지 못하는 상태**다.

---

## Semaphore 예제

Semaphore:

```text
S = 1
Q = 1
```

두 프로세스가 있다고 하자.

### P0

```c
wait(S);
wait(Q);

...

signal(S);
signal(Q);
```

### P1

```c
wait(Q);
wait(S);

...

signal(Q);
signal(S);
```

---

## 실행 순서

먼저 P0:

```text
P0 → wait(S)

S 획득
```

그다음 P1:

```text
P1 → wait(Q)

Q 획득
```

상태:

```text
P0가 S 보유
P1이 Q 보유
```

이제 P0:

```text
P0 → wait(Q)

Q는 P1이 가지고 있음
→ P0 대기
```

P1:

```text
P1 → wait(S)

S는 P0가 가지고 있음
→ P1 대기
```

결과:

```text
P0
S 가지고 있음
Q 기다림
   ↑
   │
   │
P1
Q 가지고 있음
S 기다림
```

둘 다 멈춘다.

---

## 왜 풀리지 않는가?

P0가 원하는 Q는 P1이:

```c
signal(Q);
```

해야 반환된다.

그런데 P1은 S를 기다리고 있다.

P1이 원하는 S는 P0가:

```c
signal(S);
```

해야 한다.

그런데 P0 역시 Q를 기다리고 있다.

```text
P0 → P1 기다림
↑           ↓
└───────────┘
P1 → P0 기다림
```

누구도 `signal()`까지 갈 수 없다.

---

## 교재의 Deadlock 정의

> 프로세스 집합의 모든 프로세스가, 그 집합 내부의 다른 프로세스만 발생시킬 수 있는 이벤트를 기다리고 있는 상태.

이번 장에서는 주로:

```text
Mutex Lock 획득/반환
Semaphore 획득/반환
```

같은 Resource 관련 이벤트를 생각한다.

Deadlock은 Chapter 8에서 별도 챕터로 자세하게 다룬다.

---

# 6.8.2 Priority Inversion

이번에는 Lock과 **CPU Scheduling의 Priority**가 결합해서 발생하는 문제다.

---

## 상황

세 프로세스가 있다고 하자.

```text
L = Low Priority
M = Medium Priority
H = High Priority
```

우선순위:

```text
L < M < H
```

그리고 Resource `S`가 있다.

---

## 1. L이 S를 사용 중

```text
L
wait(S)
↓
S 사용
```

---

## 2. H가 실행 가능해짐

H의 우선순위가 가장 높으므로 CPU를 얻는다.

그런데 H도 `S`가 필요하다.

```text
H
wait(S)
↓
S는 L이 사용 중
↓
Waiting
```

이것 자체는 정상이다.

H가 L을 기다려야 한다.

---

## 3. 그런데 M이 실행 가능해짐

현재:

```text
H → S 기다리는 중
L → S 가지고 있음
```

이때 M이 Ready 상태가 된다.

M의 우선순위는 L보다 높다.

```text
M > L
```

그러므로 Scheduler는:

```text
L 선점
↓
M 실행
```

한다.

---

## 이상한 결과

원래 Priority는:

```text
H > M > L
```

이다.

그런데 실제 상황은:

```text
H
↓
L이 자원을 반환해야 실행 가능

L
↓
M 때문에 실행하지 못함
```

결국 **M이 간접적으로 H보다 먼저 실행**한다.

```text
H가 M 때문에 기다리는 상황
```

이 발생한다.

이것을 **Priority Inversion**이라고 한다.

---

## 왜 "Inversion"인가?

원래:

```text
H > M
```

이므로 H가 우선되어야 한다.

하지만:

```text
H → L 기다림
L → M에게 선점됨
```

때문에 결과적으로:

```text
M 실행
H 대기
```

가 된다.

우선순위 관계가 실질적으로 역전된 것이다.

교재는 Priority Inversion이 **둘보다 많은 Priority Level이 있는 시스템에서 발생할 수 있다**고 설명한다.

---

# 해결 — Priority Inheritance

대표적인 해결 방법은 **Priority-Inheritance Protocol**이다.

> 낮은 Priority 프로세스가 높은 Priority 프로세스가 필요한 자원을 가지고 있다면, 잠시 높은 Priority를 상속받는다.

---

## 앞선 예제

원래:

```text
L = 1
M = 5
H = 10
```

H가 L의 S를 기다리게 된다.

그러면:

```text
L priority

1 → 10
```

으로 임시 상승한다.

---

### 결과

```text
L(priority 10)
```

이 되므로 M(priority 5)이 L을 선점하지 못한다.

```text
L 계속 실행
↓
S 사용 완료
↓
signal(S)
```

그다음:

```text
L → 원래 Priority 1로 복귀
H → S 획득
H → 실행
```

결과:

```text
L이 빠르게 자원을 반환
↓
H가 실행
```

된다.

---

# 교재 사례 — Mars Pathfinder

교재에서는 Priority Inversion의 실제 사례로 **1997년 NASA Mars Pathfinder / Sojourner**를 소개한다.

Priority Inversion이 단순한 성능 저하가 아니라 Real-Time 시스템에서는 **시스템 실패까지 일으킬 수 있음**을 보여주는 사례다.

Sojourner가 Mars에서 동작하기 시작한 뒤 컴퓨터가 자주 Reset되는 문제가 발생했다.

구조를 단순화하면:

```text
High Priority
bc_dist
   ↓
공유 자원 필요
   ↓
Low Priority ASI/MET가 보유
   ↓
ASI/MET가 여러 Medium Priority Task에게 선점됨
   ↓
bc_dist가 오랫동안 기다림
```

결국 `bc_sched` task가 문제가 있다고 판단하고 시스템을 Reset했다.

사용하던 Real-Time OS는 **VxWorks**였고 Priority Inheritance를 Semaphore에 활성화할 수 있었다.

Priority Inheritance를 활성화한 뒤 문제가 해결되었다.

핵심은:

```text
Low가 Resource 보유
+
High가 Resource 기다림
+
Medium이 Low를 선점
=
Priority Inversion
```

이다.

# 6.9 Evaluation

여기서는 지금까지 배운 동기화 도구 중:

> **어떤 상황에서 어떤 도구를 선택할 것인가?**

를 성능 관점에서 비교한다.

---

# 6.9.1 Hardware Solution은 기반 도구

6.4에서 본:

```text
Memory Barrier
Test-and-Set
CAS
Atomic Operation
```

등은 매우 Low-Level이다.

보통 애플리케이션 개발자가 직접 사용하는 것보다:

```text
Hardware Atomic Instruction
          ↓
      Mutex / Lock
          ↓
 Application
```

처럼 더 높은 수준의 동기화 도구를 구현하는 기반으로 사용한다.

---

# Lock-Free와 CAS

최근에는 CAS를 직접 이용해 **Lock-Free Algorithm**을 만드는 방식도 사용된다.

```text
Mutex 방식
→ Lock을 먼저 얻음
→ 수정

CAS 방식
→ 일단 수정 시도
→ 충돌 여부 확인
→ 실패하면 다시 시도
```

Lock-Free 방식은 Lock의 비용을 없앨 수 있다는 장점이 있지만, 교재는 **알고리즘을 개발하고 테스트하기 어렵다**는 점도 강조한다.

---

# Optimistic vs Pessimistic

교재에서는 두 접근을 이렇게 구분한다.

## CAS — Optimistic

**낙관적 접근**

```text
"아마 다른 Thread가 동시에 안 바꾸겠지."
```

먼저 업데이트를 시도한다.

```text
값 읽기
↓
CAS
↓
성공?
├─ YES → 완료
└─ NO  → 누군가 먼저 바꿈 → 재시도
```

즉 충돌이 발생하면 다시 시도한다.

---

## Lock — Pessimistic

**비관적 접근**

```text
"다른 Thread가 동시에 바꿀 수도 있어."
```

그래서 업데이트 전에 Lock부터 획득한다.

```text
lock()
↓
값 수정
↓
unlock()
```

---

# Contention에 따른 성능

교재가 제시하는 일반적인 기준은 중요하다.

| Contention  | CAS               | 전통적인 Mutex/Semaphore |
| ----------- | ----------------- | ------------------------ |
| Uncontended | 조금 더 빠름      | 빠름                     |
| Moderate    | 훨씬 빠를 수 있음 | 상대적으로 느림          |
| High        | 성능 악화         | 최종적으로 더 유리       |

---

## ① Uncontended

경쟁이 거의 없다.

```text
Thread A
→ CAS 한 번
→ 성공
```

Lock도 빠르지만 CAS가 조금 더 가볍다.

---

## ② Moderate Contention

적당한 경쟁이 있다.

CAS:

```text
CAS
↓ 실패
CAS
↓ 성공
```

몇 번 정도만 반복하면 된다.

반면 Mutex에서 이미 Lock이 사용 중이라면:

```text
Lock 요청
↓
Blocked
↓
Wait Queue
↓
Context Switch
↓
나중에 Wakeup
↓
다시 Scheduling
```

같은 더 복잡한 과정이 발생할 수 있다.

따라서 교재는 Moderate Contention에서 **CAS가 상당히 빠를 수 있다**고 설명한다.

---

## ③ High Contention

많은 Thread가 동시에 경쟁하면:

```text
T1 → CAS 실패
T2 → CAS 실패
T3 → CAS 실패
T4 → CAS 실패
...
```

계속 재시도가 발생한다.

CPU와 Memory System에 많은 부하가 발생한다.

이 정도로 경쟁이 심하면 차라리:

```text
Mutex
↓
한 Thread 실행
↓
나머지는 Sleep
```

하는 전통적인 방식이 최종적으로 더 빠를 수 있다.

---

# 6.9.2 상황별 동기화 도구 선택

교재가 제시하는 실용적인 선택 기준을 정리하면 다음과 같다.

## Atomic Integer

```text
단순 Counter 하나 증가
Sequence Number 증가
```

처럼 **공유 변수 하나를 단순히 업데이트**한다면:

```text
Atomic Integer
```

가 적합하다.

Mutex나 Semaphore보다 훨씬 가볍다.

---

## Spinlock

```text
Multiprocessor
+
Lock 보유 시간이 매우 짧음
```

이라면 Spinlock이 적합할 수 있다.

앞에서 본 것처럼 Sleep/Wakeup과 Context Switch 비용보다 잠깐 Spin하는 것이 저렴할 수 있기 때문이다.

---

## Mutex Lock

일반적인 Critical Section 보호라면:

> **Binary Semaphore보다 Mutex가 일반적으로 단순하고 Overhead도 적다.**

따라서 단순 Mutual Exclusion 목적이라면 Mutex가 선호된다.

```text
Critical Section 보호
→ Mutex
```

---

## Counting Semaphore

동일한 Resource가 여러 개라면:

```text
DB Connection 10개
Thread Pool 자원 N개
Buffer Slot N개
```

처럼 **유한한 여러 자원의 개수를 관리**할 때 Counting Semaphore가 적합하다.

```text
N개의 Resource
→ Counting Semaphore
```

---

## Reader-Writer Lock

교재는 여러 Reader가 동시에 접근할 수 있는 상황에서는 Reader-Writer Lock이 Mutex보다 더 높은 Concurrency를 제공할 수 있다고 언급한다.

```text
Reader A ─┐
Reader B ─┼→ 동시에 읽기 가능
Reader C ─┘

Writer
→ 단독 접근
```

Reader-Writer 문제는 Chapter 7에서 더 구체적으로 나온다.

---

## Monitor / Condition Variable

장점:

```text
추상화 수준 높음
사용하기 쉬움
동기화 로직 구조화 가능
```

하지만 구현 방법에 따라:

```text
Overhead 증가
High Contention에서 Scalability 저하
```

가 발생할 수 있다.

즉 **높은 추상화 = 항상 가장 빠른 것**은 아니다.

---

# 동기화 도구 선택 한 장 정리

| 상황                                  | 적합한 도구                         |
| ------------------------------------- | ----------------------------------- |
| Counter 하나 증가                     | Atomic Variable                     |
| 짧은 Critical Section + Multi Core    | Spinlock                            |
| 일반적인 Critical Section             | Mutex                               |
| N개의 동일 Resource                   | Counting Semaphore                  |
| 실행 순서 제어                        | Semaphore / Condition Variable      |
| Read가 많고 동시 읽기 허용            | Reader-Writer Lock                  |
| 복잡한 동기화를 안전하게 구조화       | Monitor + Condition Variable        |
| 낮거나 중간 정도 경쟁, Lock-Free 가능 | CAS                                 |
| CAS 충돌이 매우 심한 환경             | Blocking 기반 Lock이 유리할 수 있음 |

---

# 앞으로의 동기화 연구 방향

교재는 동시성 프로그램의 중요성이 커짐에 따라 다음 분야가 계속 개선되고 있다고 설명한다.

- 더 효율적인 동시성 코드를 생성하는 Compiler
- Concurrent Programming을 직접 지원하는 Programming Language
- 기존 Synchronization Library와 API의 성능 개선

즉 현대 멀티코어 시스템에서는 **정확성뿐 아니라 Synchronization 자체의 성능 비용도 매우 중요한 문제**다.

---

# 6.10 Summary

교재의 Chapter 6 전체 내용을 연결해서 정리하면 다음과 같다.

## 1. Race Condition

여러 프로세스가 공유 데이터에 동시에 접근하고 최종 결과가 실행 순서에 따라 달라지는 현상이다.

```text
Concurrent Access
+
Shared Mutable Data
+
실행 순서 의존
=
Race Condition
```

---

## 2. Critical Section

공유 데이터를 수정하여 Race Condition이 발생할 수 있는 코드 영역이다.

Critical-Section Solution은 반드시:

```text
1. Mutual Exclusion
2. Progress
3. Bounded Waiting
```

을 만족해야 한다.

---

## 3. Peterson's Solution

두 프로세스의 Critical Section 문제를 소프트웨어적으로 해결하며 세 조건을 만족한다.

하지만 현대 CPU와 Compiler는 **Instruction Reordering**을 수행할 수 있기 때문에 Peterson의 가정이 깨질 수 있다.

따라서 현대 시스템에서는 그대로 사용하기 어렵다.

---

## 4. Hardware Support

현대 CPU는 동기화를 위해:

```text
Memory Barrier
Test-and-Set
Compare-and-Swap(CAS)
Atomic Variable
```

등을 지원한다.

특히 CAS는 현재 값이 예상 값과 같을 때만 값을 Atomic하게 변경한다.

---

## 5. Mutex Lock

```text
acquire()
↓
Critical Section
↓
release()
```

구조로 Mutual Exclusion을 제공한다.

Busy Waiting을 사용하는 Mutex가 Spinlock이다.

Spinlock은 CPU를 소비하지만 Context Switch가 없기 때문에 **멀티코어 + 매우 짧은 Lock**에서 유리할 수 있다.

---

## 6. Semaphore

Integer 값을 가지며:

```text
wait()
signal()
```

을 통해 동기화한다.

### Binary Semaphore

```text
0 / 1
```

Mutual Exclusion에 사용할 수 있다.

### Counting Semaphore

```text
0 ~ N
```

여러 Resource 개수를 관리할 수 있다.

Semaphore는 실행 순서를 제어하는 데도 사용할 수 있다.

Waiting Queue를 이용하면 긴 Busy Waiting 대신 프로세스를 Sleep시킬 수 있다.

---

## 7. Monitor

Semaphore보다 더 높은 수준의 동기화 구조다.

```text
Monitor
├─ Shared Data
├─ Operations
└─ Condition Variables
```

Monitor 내부에는 한 시점에 하나의 프로세스만 활성화될 수 있으므로 Mutual Exclusion을 구조적으로 제공한다.

Condition Variable:

```text
wait()
→ 조건이 만족될 때까지 기다림

signal()
→ 기다리는 프로세스 하나를 깨움
```

을 이용해 조건 기반 동기화를 구현한다.

---

## 8. Liveness

동기화의 목적은 단순히 Race Condition만 방지하는 것이 아니다.

프로세스가 **계속 앞으로 진행할 수 있어야 한다.**

대표적인 Liveness 문제:

```text
Deadlock
Priority Inversion
```

이다.

Priority Inversion은 Priority Inheritance를 통해 완화할 수 있다.

---

## 9. 성능도 중요하다

동기화 도구 선택은 Contention에 따라 달라진다.

```text
낮은/중간 Contention
→ CAS가 유리한 경우 많음

매우 높은 Contention
→ Mutex 등 전통적 Blocking 방식이 유리할 수 있음
```

따라서 **무조건 하나의 동기화 방법이 최고의 방법인 것은 아니다.**

# Chapter 6 면접 포인트

### Q1. Mutex와 Semaphore의 차이는?

Mutex는 주로 **하나의 Critical Section에 Mutual Exclusion을 제공하는 Lock**이고, Semaphore는 Integer Counter를 이용하기 때문에 Mutual Exclusion뿐 아니라 **여러 자원 관리와 실행 순서 동기화**에도 사용할 수 있다.

---

### Q2. Semaphore가 있는데 Monitor는 왜 필요한가?

Semaphore는 `wait()`과 `signal()`의 호출 순서를 개발자가 직접 관리해야 하므로 실수하기 쉽다. Monitor는 공유 데이터와 연산을 하나의 ADT 안에 캡슐화하고, **Monitor 내부 Mutual Exclusion을 구조적으로 보장**하여 동기화 코드를 더 안전하게 작성하도록 한다.

---

### Q3. Condition Variable의 `signal()`과 Semaphore의 `signal()` 차이는?

Semaphore의 `signal()`은 Counter를 증가시키므로 **효과가 남는다.**

Condition Variable의 `signal()`은 현재 기다리는 프로세스가 없다면 **아무 효과도 없다.**

이 차이가 중요하다.

---

### Q4. Condition Variable에서 `wait()`하면 Lock을 가지고 기다리는가?

아니다.

Monitor 내부에서 `wait()`를 호출하면 프로세스는 **Monitor 사용권을 반환하고 Waiting 상태로 들어간다.**

그래야 다른 프로세스가 Monitor에 들어와 기다리던 조건을 만족시킬 수 있다.

---

### Q5. Deadlock이란?

프로세스 집합의 모든 프로세스가 **다른 대기 프로세스만 발생시킬 수 있는 이벤트를 서로 기다리면서 영원히 진행하지 못하는 상태**다.

예:

```text
P0: S 보유 → Q 기다림
P1: Q 보유 → S 기다림
```

---

### Q6. Priority Inversion이란?

높은 Priority 프로세스가 낮은 Priority 프로세스가 가진 Lock을 기다리는 사이, **중간 Priority 프로세스가 낮은 Priority 프로세스를 계속 선점하여 높은 Priority 프로세스가 간접적으로 지연되는 현상**이다.

---

### Q7. Priority Inversion의 대표 해결 방법은?

**Priority Inheritance**다.

낮은 Priority 프로세스가 높은 Priority 프로세스가 필요한 Resource를 보유하면, Resource를 반환할 때까지 높은 Priority를 임시로 상속한다.

---

### Q8. CAS와 Mutex 중 무엇이 더 빠른가?

항상 한쪽이 빠른 것은 아니다.

```text
Uncontended
→ CAS 조금 유리

Moderate Contention
→ CAS가 크게 유리할 수 있음

Very High Contention
→ 반복적인 CAS 실패 때문에
  Blocking Mutex/Semaphore가 더 유리할 수 있음
```

---

### Q9. Atomic Variable과 Mutex 중 어떤 것을 사용해야 하는가?

단순히 Counter 하나를 증가시키는 것처럼 **하나의 공유 값에 대한 단일 Atomic Update**라면 Atomic Variable이 가볍다.

여러 변수나 여러 연산을 하나의 논리적 Critical Section으로 묶어야 한다면 Mutex 같은 Lock이 필요하다.
