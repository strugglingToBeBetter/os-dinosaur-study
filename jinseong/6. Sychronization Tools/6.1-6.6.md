# 6.1 Background

## 6.1.1 왜 동기화가 필요한가

앞 장까지는 프로세스와 스레드가 **동시성(Concurrency)** 또는 **병렬성(Parallelism)** 을 가지고 실행된다는 것을 배웠다.

동시 실행에서는 CPU가 프로세스의 명령을 실행하다가 중간에 다른 프로세스로 전환할 수 있다.

```text
P1 실행
 ↓
일부 명령 실행
 ↓
Context Switch
 ↓
P2 실행
 ↓
다시 P1 실행
```

멀티코어에서는 더 직접적인 문제가 발생한다.

```text
Core 1 → Thread A
Core 2 → Thread B

Thread A와 B가
같은 데이터에 동시에 접근 가능
```

문제는 **공유 데이터를 여러 실행 흐름이 동시에 수정할 때** 발생한다.

---

## 6.1.2 Producer-Consumer 예제

교재는 Chapter 3에서 본 **Bounded Buffer** 예제를 다시 사용한다.

기존 버퍼는 최대 `BUFFER_SIZE - 1`개만 저장할 수 있었기 때문에, 이를 개선하기 위해 현재 버퍼에 들어 있는 데이터 개수를 나타내는 `count`를 추가한다.

초기값은 다음과 같다.

```c
int count = 0;
```

Producer는 데이터를 넣은 후 증가시킨다.

```c
buffer[in] = next_produced;
in = (in + 1) % BUFFER_SIZE;
count++;
```

Consumer는 데이터를 꺼낸 후 감소시킨다.

```c
next_consumed = buffer[out];
out = (out + 1) % BUFFER_SIZE;
count--;
```

각 프로그램을 **따로 실행하면 문제없다.**

문제는 둘이 동시에 실행될 때다.

---

## 6.1.3 `count++`는 하나의 명령이 아니다

프로그래머가 보기에는 다음 한 줄이다.

```c
count++;
```

하지만 실제 CPU 수준에서는 대략 다음 과정으로 이루어진다.

```text
register1 = count
register1 = register1 + 1
count = register1
```

마찬가지로

```c
count--;
```

도 실제로는 다음과 비슷하다.

```text
register2 = count
register2 = register2 - 1
count = register2
```

즉,

> **`count++`와 `count--` 자체가 원자적(Atomic) 명령이 아니다.**

---

## 6.1.4 Race Condition 발생 과정

현재

```text
count = 5
```

라고 하자.

Producer가 `count++`, Consumer가 `count--`를 동시에 수행하면 논리적으로 최종 결과는 다시 `5`여야 한다.

그런데 다음과 같이 명령이 섞일 수 있다.

```text
T0 Producer : register1 = count        → register1 = 5
T1 Producer : register1 = register1+1  → register1 = 6

T2 Consumer : register2 = count        → register2 = 5
T3 Consumer : register2 = register2-1  → register2 = 4

T4 Producer : count = register1        → count = 6
T5 Consumer : count = register2        → count = 4
```

최종 결과:

```text
count = 4   ← 잘못됨
```

마지막 두 명령의 순서가 반대면:

```text
count = 6   ← 역시 잘못됨
```

정답은 `5`인데 **실행 순서에 따라 4, 5, 6 중 하나가 될 수 있다.**

---

## 6.1.5 Race Condition

이러한 상황을 **Race Condition(경쟁 상태)** 이라고 한다.

> 여러 프로세스나 스레드가 같은 데이터를 동시에 접근·수정하고, **최종 결과가 실행 순서에 따라 달라지는 상태**다.

핵심은 단순히 "동시에 접근했다"가 아니다.

```text
공유 데이터
+
동시 접근/수정
+
실행 순서에 따라 결과가 달라짐
=
Race Condition
```

따라서 `count`를 변경하는 순간에는 다음을 보장해야 한다.

```text
Producer가 count 수정 중
        ↓
Consumer 접근 금지
```

이것이 **Process Synchronization**이 필요한 이유다.

---

# 6.2 The Critical-Section Problem

Race Condition을 막으려면 **공유 데이터를 수정하는 코드 영역**을 특별하게 관리해야 한다.

그 영역이 **Critical Section(임계 구역)** 이다.

---

## 6.2.1 Critical Section

프로세스가 공유 데이터를 읽거나 수정하는 코드 영역이다.

예를 들어:

```c
count++;
```

공유 변수 `count`를 수정하므로 이 코드를 포함한 영역이 Critical Section이 될 수 있다.

핵심 조건은 다음과 같다.

```text
P1이 Critical Section 실행 중
             ↓
P2는 같은 공유 데이터를 다루는 Critical Section 진입 불가
```

즉 **한 번에 하나만 들어갈 수 있어야 한다.**

---

## 6.2.2 프로세스의 기본 구조

교재 Figure 6.1의 구조는 다음과 같다.

```c
while (true) {

    entry section

    critical section

    exit section

    remainder section
}
```

각 영역을 이해하는 것이 중요하다.

| 영역              | 역할                                |
| ----------------- | ----------------------------------- |
| Entry Section     | Critical Section에 들어갈 권한 요청 |
| Critical Section  | 공유 데이터 접근/수정               |
| Exit Section      | 사용하던 권한/Lock 반환             |
| Remainder Section | 공유 데이터와 관계없는 나머지 작업  |

예를 들어 Mutex를 쓰면 나중에 이렇게 연결된다.

```text
Entry Section
→ lock 획득

Critical Section
→ 공유 데이터 수정

Exit Section
→ lock 해제
```

---

# 6.2.3 Critical-Section 문제의 3가지 조건

올바른 동기화 알고리즘이라면 **반드시 세 조건을 만족해야 한다.**

## ① Mutual Exclusion — 상호 배제

Pi가 Critical Section에 있다면 다른 프로세스는 Critical Section에 들어갈 수 없다.

```text
P1 : Critical Section 실행 중

P2 : X
P3 : X
```

가장 기본 조건이다.

---

## ② Progress — 진행

현재 아무도 Critical Section을 사용하지 않고 있고, 들어가고 싶어 하는 프로세스가 있다면 **누가 들어갈지 결정하는 작업을 무한히 미뤄서는 안 된다.**

예:

```text
Critical Section = 비어 있음

P1 → 들어가고 싶음
P2 → 들어가고 싶음

그런데 아무도 선택되지 않음...
영원히 기다림
```

이것은 잘못된 알고리즘이다.

또한 Critical Section에 관심 없는 프로세스가 결정에 끼어들어 다른 프로세스를 방해해서도 안 된다.

---

## ③ Bounded Waiting — 한정 대기

프로세스가 Critical Section 진입을 요청했다면 **다른 프로세스들이 무한히 먼저 들어가서는 안 된다.**

예:

```text
P1 진입 요청

P2 진입
P3 진입
P2 진입
P3 진입
P2 진입
P3 진입
...
P1은 영원히 대기
```

이런 상황은 허용되지 않는다.

따라서

```text
P1이 요청한 뒤
다른 프로세스가 먼저 들어갈 수 있는 횟수
≤ 어떤 유한한 값
```

이어야 한다.

즉 **Starvation 방지와 관련된 조건**이다.

---

## 세 조건 비교

| 조건             | 질문                                     |
| ---------------- | ---------------------------------------- |
| Mutual Exclusion | 둘이 동시에 들어갈 수 있는가?            |
| Progress         | 비어 있는데 아무도 못 들어가는가?        |
| Bounded Waiting  | 특정 프로세스가 영원히 기다릴 수 있는가? |

이 셋을 구분하는 것이 중요하다.

---

# 6.2.4 Kernel에서도 Race Condition이 발생한다

Race Condition은 사용자 프로그램만의 문제가 아니다.

Kernel도 많은 공유 자료구조를 관리한다.

예를 들어:

```text
Open File List
Memory Allocation 정보
Process List
Interrupt 관련 구조
PID 관리
```

여러 프로세스가 동시에 `fork()`를 실행한다고 생각해보자.

Kernel에 다음 변수가 있을 수 있다.

```text
next_available_pid = 2615
```

두 프로세스가 동시에 값을 읽으면:

```text
P0 → 2615 읽음
P1 → 2615 읽음

P0 child PID = 2615
P1 child PID = 2615
```

서로 다른 두 프로세스에 같은 PID가 배정될 수도 있다.

교재 Figure 6.2가 이 Race Condition을 보여준다.

---

# 6.2.5 Interrupt를 막으면 해결할 수 있지 않을까?

### Single Core

싱글 코어라면 공유 데이터를 변경하는 동안 Interrupt를 막는 방법이 가능하다.

```text
Interrupt Disable
        ↓
공유 데이터 수정
        ↓
Interrupt Enable
```

Interrupt가 없으므로 현재 프로세스가 중간에 선점되지 않는다.

따라서 다른 프로세스가 끼어들 수 없다.

---

### Multi Core

하지만 멀티코어에서는 단순하지 않다.

```text
Core 1 → P1
Core 2 → P2
Core 3 → P3
```

Core 1에서 Interrupt를 막아도 Core 2에서는 P2가 공유 데이터에 접근할 수 있다.

모든 CPU의 Interrupt를 막으려면 모든 프로세서에 이를 알려야 하며, 이 과정 자체가 비싸다.

또 Interrupt는 시스템 Clock 등을 처리하는 데도 사용되므로 장시간 막는 것은 좋지 않다.

---

# 6.2.6 Preemptive Kernel vs Nonpreemptive Kernel

Critical Section 문제를 다루는 Kernel 구조도 두 가지로 나눌 수 있다.

|                      | Preemptive Kernel | Nonpreemptive Kernel |
| -------------------- | ----------------- | -------------------- |
| Kernel Mode에서 선점 | 가능              | 불가능               |
| Race Condition 관리  | 어려움            | 상대적으로 쉬움      |
| 응답성               | 높음              | 상대적으로 낮음      |
| Real-Time 적합성     | 높음              | 상대적으로 낮음      |

### Nonpreemptive Kernel

Kernel Mode에 진입한 프로세스는 다음 상황까지 계속 실행한다.

```text
Kernel Mode 종료
또는
Block
또는
자발적으로 CPU 양보
```

따라서 싱글 프로세서에서는 한 순간에 하나의 Kernel 작업만 수행되므로 Kernel 자료구조에서 Race Condition을 피하기 쉽다.

### Preemptive Kernel

Kernel Mode에서도 선점될 수 있다.

```text
P1 Kernel 코드 실행
      ↓
중간에 선점
      ↓
P2 Kernel 코드 실행
```

따라서 공유 Kernel 데이터를 철저히 동기화해야 한다.

특히 SMP에서는 여러 코어가 동시에 Kernel 코드를 실행할 수도 있어 설계가 더 어려워진다.

그런데도 Preemptive Kernel을 사용하는 이유는 **응답성이 좋고 Real-Time 시스템에도 더 적합하기 때문**이다.

# 6.3 Peterson's Solution

Peterson's Solution은 **Critical Section 문제를 소프트웨어만으로 해결하려는 고전적 알고리즘**이다.

현재 컴퓨터에서 그대로 사용하기 위한 실용적인 Lock이라기보다는,

> Mutual Exclusion / Progress / Bounded Waiting을 어떻게 모두 만족시킬 수 있는지 이해하기 위한 알고리즘

이라고 보는 것이 좋다.

또한 **프로세스 2개만을 대상으로 한다.**

---

## 6.3.1 공유 변수

두 프로세스 `P0`, `P1`이 다음을 공유한다.

```c
int turn;
boolean flag[2];
```

### `flag`

```text
flag[i] = true
```

는

> Pi가 Critical Section에 들어가고 싶다.

는 의미다.

### `turn`

둘 다 들어가고 싶은 경우 우선권을 조정한다.

---

# 6.3.2 알고리즘

Pi 입장에서 상대 프로세스를 Pj라고 하자.

```c
while (true) {

    flag[i] = true;
    turn = j;

    while (flag[j] && turn == j)
        ;

    /* critical section */

    flag[i] = false;

    /* remainder section */
}
```

핵심은 다음 두 줄이다.

```c
flag[i] = true;
turn = j;
```

의미는:

```text
나도 들어가고 싶다.
그런데 너도 원하면 일단 너한테 우선권을 줄게.
```

라고 생각하면 이해하기 쉽다.

---

# 6.3.3 둘이 동시에 진입하려고 하면

P0:

```text
flag[0] = true
turn = 1
```

P1:

```text
flag[1] = true
turn = 0
```

`turn`은 최종적으로 하나의 값만 가진다.

예를 들어:

```text
turn = 0
```

이면 P0가 먼저 들어가고 P1은 기다린다.

즉 둘 다 동시에 Critical Section에 들어갈 수 없다.

---

# 6.3.4 세 조건을 만족하는 이유

### Mutual Exclusion

두 프로세스 모두 `flag = true`여도 `turn`은 0 또는 1 중 하나뿐이다.

따라서 둘이 동시에 `while`을 탈출할 수 없다.

### Progress

상대 프로세스가 Critical Section에 관심 없다면:

```text
flag[j] = false
```

이므로 즉시 진입할 수 있다.

둘 다 원한다면 `turn` 값으로 둘 중 한 명이 선택된다.

### Bounded Waiting

Pj가 먼저 들어가더라도 Critical Section에서 나오면서

```c
flag[j] = false;
```

를 수행한다.

Pi는 이후 진입할 수 있다.

Pj가 다시 들어오려고 하면 다시 `turn = i`를 설정해야 하기 때문에 Pi를 계속 무한정 추월할 수 없다.

교재는 **상대 프로세스가 최대 한 번 진입한 뒤 Pi가 진입할 수 있음**을 설명한다.

---

# 6.3.5 그런데 현대 CPU에서는 왜 Peterson이 안 되는가?

중요한 부분이다.

Compiler와 CPU는 성능을 높이기 위해 **서로 의존성이 없는 명령의 실행 순서를 바꿀 수 있다.**

이를 **Instruction Reordering**이라고 한다.

싱글 스레드에서는 최종 결과만 같으면 문제가 없는 경우가 많다.

하지만 공유 데이터를 사용하는 멀티스레드에서는 문제가 된다.

---

## 예제

공유 데이터:

```c
boolean flag = false;
int x = 0;
```

Thread 1:

```c
while (!flag)
    ;

print x;
```

Thread 2:

```c
x = 100;
flag = true;
```

우리가 예상하는 순서는:

```text
x = 100
flag = true

Thread1이 flag 확인
→ x 출력
→ 100
```

그런데 CPU가 Thread 2의 명령을 재배치하면:

```text
flag = true
x = 100
```

Thread 1이 그 사이 실행될 수 있다.

```text
flag == true 확인
        ↓
print x
        ↓
0 출력
```

즉 프로그램 작성자가 생각한 순서와 실제 메모리에서 관찰되는 순서가 달라질 수 있다.

Peterson's Solution에서도

```c
flag[i] = true;
turn = j;
```

가 재배치되면 **Mutual Exclusion 자체가 깨질 수 있다.**

그래서 현대 시스템에서는 하드웨어 수준의 동기화 지원이 필요하다.

# 6.4.1 Memory Barriers

## Memory Model

CPU Architecture가

> 한 CPU에서 수행한 메모리 변경이 다른 CPU에게 언제, 어떤 순서로 보이는가

를 정의하는 규칙을 **Memory Model**이라고 한다.

교재는 크게 두 종류로 설명한다.

| 모델             | 의미                                                    |
| ---------------- | ------------------------------------------------------- |
| Strongly Ordered | 한 Processor의 메모리 변경이 즉시 다른 Processor에 보임 |
| Weakly Ordered   | 변경이 다른 Processor에 즉시 보이지 않을 수 있음        |

멀티코어에서는 다음과 같은 상황이 가능하다.

```text
Core 1
x = 100

Core 2
아직 x = 0으로 관찰
```

때문에 단순히 소스 코드 순서만 보고 판단할 수 없다.

---

## Memory Barrier / Memory Fence

Memory Barrier는 **Barrier 이전의 메모리 연산이 완료된 뒤 Barrier 이후 연산이 진행되도록 강제한다.**

```text
이전 Load / Store
      ↓
Memory Barrier
      ↓
이후 Load / Store
```

예:

```c
x = 100;

memory_barrier();

flag = true;
```

이 경우 다른 Core가 `flag == true`를 봤다면 `x = 100`이 먼저 반영되도록 순서를 보장할 수 있다.

Peterson's Solution에서도:

```c
flag[i] = true;

memory_barrier();

turn = j;
```

처럼 명령 재배치를 방지할 수 있다.

Memory Barrier는 매우 Low-Level 도구여서 보통 Kernel과 같은 특수한 코드에서 사용된다.

---

# 6.4.2 Hardware Instructions

하드웨어가 **읽기 + 수정** 같은 작업을 하나의 끊을 수 없는 명령으로 제공할 수 있다.

이러한 연산을 **Atomic Operation**이라고 한다.

```text
Atomic

시작 ───────── 완료
      ↑
다른 Thread가 중간에 끼어들 수 없음
```

교재에서는 대표적으로 두 가지를 다룬다.

```text
Test-and-Set
Compare-and-Swap(CAS)
```

---

## Test-and-Set

개념적인 구현:

```c
boolean test_and_set(boolean *target) {

    boolean rv = *target;

    *target = true;

    return rv;
}
```

중요한 것은 저 세 줄이 실제로 따로 실행된다는 뜻이 아니라 **전체가 하나의 Atomic Hardware Instruction처럼 수행된다는 것**이다.

---

## Test-and-Set으로 Lock 구현

```c
boolean lock = false;
```

프로세스:

```c
do {

    while (test_and_set(&lock))
        ;

    /* critical section */

    lock = false;

    /* remainder section */

} while (true);
```

### 첫 프로세스

```text
lock = false

test_and_set(lock)
→ 이전 값 false 반환
→ lock = true

while(false)
→ Critical Section 진입
```

### 두 번째 프로세스

```text
lock = true

test_and_set(lock)
→ true 반환

while(true)
→ 계속 반복
```

따라서 Mutual Exclusion을 만들 수 있다.

---

# Compare-and-Swap — CAS

현대 동시성 프로그래밍에서 매우 중요한 개념이다.

개념적으로 다음과 같다.

```c
int compare_and_swap(
    int *value,
    int expected,
    int new_value
) {

    int temp = *value;

    if (*value == expected)
        *value = new_value;

    return temp;
}
```

핵심:

```text
현재 값 == 내가 예상한 값인가?

YES
→ 새 값으로 교체

NO
→ 변경하지 않음
```

그리고 이 전체 과정이 **Atomic**이다.

---

## CAS로 Lock 만들기

```text
lock = 0 → 사용 가능
lock = 1 → 사용 중
```

```c
while (true) {

    while (compare_and_swap(&lock, 0, 1) != 0)
        ;

    /* critical section */

    lock = 0;

    /* remainder section */
}
```

첫 프로세스:

```text
CAS(lock, 0, 1)

lock == 0
→ lock = 1
→ Critical Section 진입
```

다른 프로세스:

```text
CAS(lock, 0, 1)

lock == 1
→ 변경 실패
→ 반복
```

---

## 단순 CAS Lock의 문제

이 구현은 **Mutual Exclusion은 만족하지만 Bounded Waiting을 만족하지 않는다.**

예를 들어:

```text
P1 기다림

P2 획득
P2 반환

P3 획득

P2 다시 획득

P3 다시 획득
...

P1이 언제 획득할지 보장 없음
```

따라서 교재에서는 `waiting[n]` 배열을 사용한 개선 알고리즘도 제시한다.

---

## Bounded Waiting CAS

공유 데이터:

```c
boolean waiting[n];
int lock;
```

초기값:

```text
waiting[] = false
lock = 0
```

프로세스 Pi가 기다리면:

```text
waiting[i] = true
```

Lock을 반환하는 프로세스는 다음 순서로 기다리는 프로세스를 찾는다.

```text
i+1
i+2
...
n-1
0
1
...
i-1
```

즉 원형으로 다음 대기자를 찾는다.

찾았다면:

```text
waiting[j] = false
```

로 다음 프로세스에게 실행 기회를 넘긴다.

그 결과 어떤 프로세스도 **최대 `n - 1`번의 다른 Critical Section 실행 이후에는 기회를 얻는다.**

따라서:

```text
Mutual Exclusion  O
Progress          O
Bounded Waiting   O
```

를 모두 만족한다.

---

### 교재 참고 — x86 CAS

Intel x86에서는 CAS에 해당하는 명령으로 `cmpxchg`를 사용하며, 원자성을 보장하기 위해 `lock` prefix를 사용할 수 있다.

```asm
lock cmpxchg <destination>, <source>
```

이 내용은 CAS가 단순한 소프트웨어 함수가 아니라 **실제 CPU 명령의 지원을 받는다는 점**을 보여주는 예다.

---

# 6.4.3 Atomic Variables

CAS를 프로그래머가 매번 직접 사용하면 복잡하다.

그래서 CAS 등을 기반으로 **Atomic Variable**이라는 더 높은 수준의 기능을 제공한다.

```text
CAS
 ↓
Atomic Variable
 ↓
atomic increment
atomic decrement
atomic exchange
...
```

Atomic Variable은 `int`, `boolean`과 같은 기본 자료형의 변경을 원자적으로 수행한다.

---

## Atomic Increment

예:

```c
increment(&sequence);
```

교재의 개념적 구현:

```c
void increment(atomic_int *v)
{
    int temp;

    do {
        temp = *v;
    }
    while (temp != compare_and_swap(v, temp, temp + 1));
}
```

동작은:

```text
현재 값 읽음
   ↓
현재 값이 여전히 내가 읽은 값인지 CAS로 확인
   ↓
맞으면 +1
틀리면 누군가 중간에 바꾼 것
   ↓
다시 시도
```

이다.

---

## Atomic Variable도 모든 Race Condition을 해결하지는 못한다

아주 중요한 내용이다.

`count++` 하나만 놓고 보면 Atomic Integer로 해결할 수 있다.

하지만 Producer-Consumer에는 다음 조건도 존재한다.

```c
while (count == 0)
    ;
```

예를 들어:

```text
count = 0

Consumer A → count를 기다림
Consumer B → count를 기다림

Producer → 데이터 하나 생성
count = 1
```

그러면 Consumer A와 B가 모두 `count > 0`을 보고 반복문에서 빠져나올 수 있다.

```text
데이터는 1개

Consumer A → consume
Consumer B → consume
```

문제가 생긴다.

즉:

> Atomic Variable은 **하나의 변수에 대한 단일 업데이트**에는 매우 적합하지만, 여러 연산을 묶은 복잡한 동기화 조건 전체를 보호하지는 못한다.

따라서 Counter, Sequence Generator와 같은 용도에 특히 적합하다.

---

# 6.5 Mutex Locks

하드웨어 명령을 애플리케이션 개발자가 직접 다루기는 어렵다.

그래서 운영체제는 더 사용하기 쉬운 고수준 도구를 제공한다.

가장 단순한 것이 **Mutex Lock**이다.

`mutex`는 **Mutual Exclusion**의 줄임말이다.

---

## 6.5.1 기본 구조

```c
while (true) {

    acquire();

    /* critical section */

    release();

    /* remainder section */
}
```

즉:

```text
Lock 획득
  ↓
Critical Section
  ↓
Lock 반환
```

이다.

---

# `available`

교재의 Mutex는 Boolean 변수 `available`로 설명한다.

```text
available = true
→ Lock 사용 가능

available = false
→ 누군가 사용 중
```

---

## `acquire()`

```c
acquire() {

    while (!available)
        ;

    available = false;
}
```

---

## `release()`

```c
release() {

    available = true;
}
```

여기서 매우 중요하다.

다음 두 작업:

```text
available 확인
available = false
```

이 그냥 따로 실행되면 다시 Race Condition이 발생한다.

따라서 `acquire()`와 `release()` 자체가 **Atomic**이어야 한다.

실제로 이러한 Lock은 CAS 같은 하드웨어 명령을 기반으로 구현할 수 있다.

---

# 6.5.2 Busy Waiting

위 `acquire()`를 다시 보자.

```c
while (!available)
    ;
```

Lock이 사용 중인 동안 아무것도 하지 않고 계속 조건을 검사한다.

```text
Lock?
X

Lock?
X

Lock?
X

Lock?
X
...
```

이를 **Busy Waiting**이라고 한다.

문제는 기다리는 동안에도 CPU를 계속 사용한다는 것이다.

```text
Thread A
→ Critical Section

Thread B
→ while while while while...
→ CPU 계속 사용
```

특히 Single Core에서는 낭비가 심하다.

---

# Spinlock

Busy Waiting을 사용하는 Mutex 형태를 **Spinlock**이라고 한다.

Thread가 Lock을 기다리며 계속 "빙빙 돈다(spin)"는 의미다.

```text
while(lock)
    spin
    spin
    spin
```

---

## 그런데 Spinlock이 무조건 나쁜 것은 아니다

Spinlock의 장점은 **Context Switch가 필요 없다는 것**이다.

멀티코어라고 하자.

```text
Core 1
Thread A → Critical Section

Core 2
Thread B → Spin
```

A가 아주 짧은 시간 안에 Lock을 반환한다면 B는 바로 Lock을 얻을 수 있다.

반대로 B를 Sleep시키면:

```text
Running → Waiting
Context Switch

나중에

Waiting → Ready → Running
Context Switch
```

추가 비용이 발생한다.

따라서 Lock 보유 시간이 아주 짧으면 Spinlock이 더 유리할 수 있다.

---

## 교재의 "Short Duration" 기준

교재의 참고 박스에서는 대략 다음 기준을 제시한다.

Lock 대기로 Sleep하는 경우:

```text
Running → Waiting
1번 Context Switch

Lock 획득 가능

Waiting → Running
2번 Context Switch
```

따라서

> **Lock을 기다릴 시간이 Context Switch 두 번보다 짧을 것으로 예상된다면 Spinlock이 유리할 수 있다.**

---

# 6.5.3 Lock Contention

Lock을 얻으려는 Thread 간 경쟁 정도를 **Contention**이라고 한다.

| 상태            | 의미                       |
| --------------- | -------------------------- |
| Uncontended     | 요청 시 Lock이 비어 있음   |
| Contended       | 다른 Thread가 이미 사용 중 |
| Low Contention  | 적은 수의 Thread가 경쟁    |
| High Contention | 많은 Thread가 경쟁         |

High Contention이면 여러 Thread가 같은 Lock을 기다리므로 동시 프로그램의 전체 성능이 떨어질 수 있다.

---

# 6.6 Semaphores

Mutex는 기본적으로 하나의 Critical Section을 보호하기 좋은 단순한 도구다.

Semaphore는 Mutex처럼 Mutual Exclusion을 구현할 수도 있지만, **프로세스 실행 순서 제어 또는 여러 개의 동일 자원 관리까지 할 수 있는 더 일반적인 동기화 도구**다.

---

# 6.6 기본 개념

Semaphore `S`는 **Integer 변수**다.

단, 일반 변수처럼 마음대로 접근하지 않는다.

초기화를 제외하면 오직 두 Atomic Operation으로만 접근한다.

```text
wait()
signal()
```

Dijkstra가 만든 개념이며 원래 이름은:

```text
wait()   → P
signal() → V
```

였다.

`P`는 네덜란드어 _proberen_("시험하다"), `V`는 _verhogen_("증가시키다")에서 유래한다.

---

## `wait()`

고전적 정의:

```c
wait(S) {

    while (S <= 0)
        ;

    S--;
}
```

의미:

```text
사용 가능한 자원이 있는가?

S > 0
→ 하나 사용
→ S--

S <= 0
→ 기다림
```

---

## `signal()`

```c
signal(S) {

    S++;
}
```

의미:

```text
사용하던 자원 하나 반환
→ 사용 가능한 개수 +1
```

---

## 반드시 Atomic이어야 한다

특히 `wait()`에서

```text
S > 0인지 확인
+
S--
```

은 하나의 Atomic Operation으로 수행되어야 한다.

그렇지 않으면:

```text
S = 1

P1 → S > 0 확인
P2 → S > 0 확인

P1 → S--
P2 → S--
```

처럼 둘이 동시에 하나의 자원을 얻는 문제가 다시 발생한다.

---

# 6.6.1 Semaphore Usage

Semaphore는 크게 두 종류로 나눈다.

| 종류               |                 값 | 대표 사용           |
| ------------------ | -----------------: | ------------------- |
| Binary Semaphore   |           0 또는 1 | Mutual Exclusion    |
| Counting Semaphore | 일반적인 정수 범위 | 여러 동일 자원 관리 |

---

## Binary Semaphore

값이:

```text
0
1
```

만 존재한다.

따라서 Mutex와 비슷하게 사용할 수 있다.

```text
Semaphore = 1

P1 wait()
→ 0
→ Critical Section

P2 wait()
→ 기다림

P1 signal()
→ 1

P2 실행
```

Mutex가 없는 시스템에서는 Binary Semaphore를 Mutual Exclusion에 사용할 수도 있다.

---

## Counting Semaphore

여러 개의 동일한 Resource를 관리할 때 사용한다.

예를 들어 DB Connection이 5개 있다고 하자.

```text
S = 5
```

Thread가 하나 사용하면:

```text
wait(S)

5 → 4
```

또 사용:

```text
4 → 3
```

5개가 모두 사용되면:

```text
S = 0
```

이후 요청자는 기다려야 한다.

누군가 자원을 반환하면:

```text
signal(S)

0 → 1
```

대기하던 Thread가 사용할 수 있다.

즉 Semaphore 값은 기본적으로 **사용 가능한 Resource 개수**로 이해하면 쉽다.

---

# Semaphore를 실행 순서 제어에 사용하기

Semaphore는 단순한 Lock보다 중요한 기능이 하나 더 있다.

> **두 작업의 실행 순서를 강제할 수 있다.**

P1:

```text
S1
```

P2:

```text
S2
```

반드시:

```text
S1 → S2
```

순서로 실행해야 한다고 하자.

Semaphore:

```c
synch = 0;
```

P1:

```c
S1;

signal(synch);
```

P2:

```c
wait(synch);

S2;
```

처음에는:

```text
synch = 0
```

이므로 P2가 먼저 실행되어도:

```text
wait(synch)
→ 대기
```

한다.

P1이 `S1`을 완료하면:

```text
signal(synch)
```

가 실행되고 P2가 진행한다.

따라서:

```text
S1 완료
   ↓
signal
   ↓
P2 wake
   ↓
S2
```

가 보장된다.

---

# 6.6.2 Semaphore Implementation

지금까지 본 `wait()` 역시 문제가 있다.

```c
while (S <= 0)
    ;
```

이것도 **Busy Waiting**이다.

그래서 실제 구현에서는 계속 CPU를 사용하지 않고, 기다리는 프로세스를 **Waiting State로 보내는 방식**을 사용할 수 있다.

---

## Busy Waiting 방식

```text
S = 0

P1:
while(S <= 0)
while(S <= 0)
while(S <= 0)
...
```

CPU 사용:

```text
계속 사용
```

---

## Blocking 방식

```text
S = 0

P1 wait()
    ↓
Waiting Queue 이동
    ↓
P1 상태 = Waiting
    ↓
CPU Scheduler
    ↓
다른 Process 실행
```

누군가:

```c
signal(S);
```

하면:

```text
P1
Waiting → Ready
```

로 바뀐다.

이 동작을 교재에서는 `sleep()`과 `wakeup()`으로 설명한다.

---

# Semaphore 자료구조

```c
typedef struct {

    int value;

    struct process *list;

} semaphore;
```

두 가지 정보를 가진다.

```text
value
→ Semaphore 값

list
→ 이 Semaphore를 기다리는 프로세스 목록
```

---

# Blocking 방식 `wait()`

```c
wait(semaphore *S) {

    S->value--;

    if (S->value < 0) {

        add this process to S->list;

        sleep();
    }
}
```

예를 들어:

```text
S = 0

P1 wait()

S = -1
→ P1 Waiting Queue
```

다시 P2가 `wait()`:

```text
S = -2
→ P2 Waiting Queue
```

---

# Blocking 방식 `signal()`

```c
signal(semaphore *S) {

    S->value++;

    if (S->value <= 0) {

        remove a process P from S->list;

        wakeup(P);
    }
}
```

예를 들어:

```text
S = -2
```

이면 두 프로세스가 기다리고 있다.

`signal()`:

```text
-2 → -1

대기 Process 하나 wakeup
```

---

## 음수 Semaphore의 의미

고전적인 Busy-Waiting 정의에서는 Semaphore 값이 음수가 되지 않는다.

하지만 Blocking 구현에서는 음수가 가능하다.

그리고:

```text
|S|
=
현재 기다리는 Process 수
```

다.

예:

```text
S = -3
```

이면 세 프로세스가 대기하고 있다.

# Waiting Queue

Semaphore의 Waiting List는 PCB의 링크 필드를 이용해 구현할 수 있다.

```text
Semaphore
   ↓
P2 PCB → P5 PCB → P8 PCB
```

Bounded Waiting까지 보장하려면 대표적으로 **FIFO Queue**를 사용할 수 있다.

```text
먼저 기다린 Process
        ↓
먼저 Wakeup
```

다만 교재는 Semaphore의 기본적인 올바른 동작 자체가 특정 Queue 방식에 의존하는 것은 아니라고 설명한다.

---

# `sleep()`과 `wakeup()`

`wait()`:

```text
Running
   ↓ sleep()
Waiting
```

`signal()`:

```text
Waiting
   ↓ wakeup()
Ready
```

이다.

`wakeup()`됐다고 바로 Running이 되는 것은 아니다.

```text
Waiting
 ↓
Ready Queue
 ↓
CPU Scheduler의 선택
 ↓
Running
```

순서다.

---

# 그런데 `wait()`와 `signal()` 자체의 Race Condition은?

Semaphore를 구현하기 위해 Semaphore를 동시에 수정한다면 또 Race Condition이 생길 수 있다.

따라서:

> `wait()`와 `signal()` 자체가 Atomic이어야 한다.

### Single Core

잠깐 Interrupt를 Disable하는 방법을 사용할 수 있다.

```text
interrupt disable
      ↓
wait()/signal() 내부 수정
      ↓
interrupt enable
```

### Multi Core

한 Core의 Interrupt를 끄는 것만으로는 부족하다.

```text
Core 1 → wait()
Core 2 → signal()
```

이 동시에 일어날 수 있기 때문이다.

모든 Core의 Interrupt를 끄는 것은 비효율적이므로 SMP에서는:

```text
CAS
또는
Spinlock
```

같은 하드웨어 기반 기법을 이용하여 `wait()` / `signal()` 내부를 보호한다.

# 결국 Busy Waiting은 완전히 사라진 것인가?

**아니다.**

교재가 강조하는 부분이다.

Busy Waiting을 없앤 것이 아니라 **아주 짧은 구간으로 옮겼다.**

기존 방식:

```text
Application의 Critical Section 전체 동안
다른 Process가 Busy Waiting
```

개선 방식:

```text
Semaphore 내부 wait()/signal()의
아주 짧은 Critical Section에서만 Busy Waiting
```

교재는 잘 구현된 `wait()` / `signal()` 내부 Critical Section이 대략 **10개 정도의 명령을 넘지 않을 정도로 짧아야 한다**고 설명한다.

따라서 Spin하는 시간이 매우 짧아서 실질적인 낭비가 크게 줄어든다.

반면 애플리케이션 Critical Section은 수초, 수분, 심지어 더 길 수도 있으므로 그 전체를 Busy Waiting하는 것은 매우 비효율적이다.

```text
공유 데이터가 있음
      ↓
두 Thread가 동시에 수정
      ↓

      ↓

 ┌─────────────────────┐

      ↓

      ↓

      ↓

      ↓

 ├─ Memory Barrier
 ├─ Test-and-Set
```

# 6.1 ~ 6.6 핵심 비교

| 도구               | 핵심 역할                    | 특징                                 |

| Peterson           | SW만으로 Mutual Exclusion    | 2개 프로세스, 현대 HW 재정렬 문제    |

| Spinlock           | Mutex를 Busy Waiting         | 매우 짧은 Lock에서 유리              |

# 면접 포인트

### Q1. Race Condition이 무엇인가?

여러 실행 흐름이 공유 데이터를 동시에 접근·수정하여 **실행 순서에 따라 결과가 달라지는 현상**이다. `count++` 같은 코드도 내부적으로 read-modify-write의 여러 명령으로 나뉘므로 Race Condition이 발생할 수 있다.

### Q2. Critical Section 해결책의 세 조건은?

**Mutual Exclusion, Progress, Bounded Waiting**이다. Mutual Exclusion은 동시 진입을 막고, Progress는 비어 있는데 무한정 진입 결정이 미뤄지는 것을 막으며, Bounded Waiting은 특정 프로세스가 무한히 기다리는 것을 방지한다.

### Q3. Peterson's Solution을 실제 현대 시스템에서 그대로 사용하기 어려운 이유는?

CPU와 Compiler가 성능 최적화를 위해 독립적인 Load/Store 명령의 순서를 재배치할 수 있기 때문이다. 이로 인해 Peterson 알고리즘이 가정하는 메모리 접근 순서가 깨질 수 있다.

### Q4. CAS란?

현재 메모리 값이 `expected`와 같을 때만 `newValue`로 바꾸고, 이 비교와 변경을 **Atomic하게 수행하는 하드웨어 연산**이다.

### Q5. Atomic Variable이면 모든 Race Condition을 해결할 수 있는가?

아니다. 하나의 변수 업데이트는 Atomic하게 만들 수 있지만, **여러 연산이나 조건 검사를 하나의 논리적 단위로 묶어야 하는 문제까지 해결하지는 못한다.**

### Q6. Spinlock과 Sleep 방식 Mutex의 차이는?

Spinlock은 기다리는 동안 CPU를 계속 사용하지만 Context Switch가 없다. 따라서 **멀티코어에서 Lock 보유 시간이 매우 짧다면 Spinlock이 유리**할 수 있다. 오래 기다릴 경우에는 Thread를 Sleep시키는 방식이 낫다.

### Q7. Mutex와 Semaphore의 가장 큰 차이는?

이번 범위에서 핵심적으로는 **Mutex는 하나의 Critical Section을 상호 배제하는 단순 도구이고, Semaphore는 정수 값을 이용해 여러 자원을 관리하거나 작업의 실행 순서를 동기화할 수도 있는 더 일반적인 도구**다.

### Q8. Binary Semaphore와 Counting Semaphore의 차이는?

Binary Semaphore는 값이 `0/1`이라 Mutual Exclusion에 사용할 수 있고, Counting Semaphore는 여러 개의 동일 Resource 수를 관리하는 데 사용한다.

### Q9. Semaphore에서 값이 `-3`이면 무슨 뜻인가?

교재의 **Blocking 기반 구현에서는 3개의 프로세스가 해당 Semaphore를 기다리고 있다는 의미**다. 고전적 Busy-Waiting 정의에서는 Semaphore 값이 음수가 되지 않는다는 점도 같이 기억하면 된다.
