# 4.5 Implicit Threading

## 4.5.0 명시적 스레딩의 한계

앞의 4.4에서는 프로그래머가 직접 스레드를 생성하는 방법을 살펴봤다.

예를 들어 다음과 같은 방식이다.

```text
Pthreads
→ pthread_create()

Windows
→ CreateThread()

Java
→ new Thread(...).start()
```

이러한 방식에서는 프로그래머가 직접 다음을 관리해야 한다.

- 몇 개의 스레드를 만들 것인지
- 각 스레드에 어떤 작업을 맡길 것인지
- 스레드를 언제 생성하고 종료할 것인지
- 스레드 실행 결과를 어떻게 합칠 것인지
- 동기화를 어떻게 처리할 것인지

코어 수와 병렬 작업 수가 많아질수록 이런 관리가 복잡해진다.

예를 들어 100개의 작업이 있다고 해서 스레드를 100개 직접 만드는 것은 바람직하지 않을 수 있다.

```text
작업 100개
→ 스레드 100개 생성
→ 생성 비용 증가
→ 스케줄링 부담 증가
→ 메모리 사용 증가
```

따라서 현대의 동시성 라이브러리는 프로그래머가 스레드를 직접 다루기보다 **수행할 작업만 지정**하도록 발전했다.

이를 **Implicit Threading**, 즉 암시적 스레딩이라고 한다.

---

## 암시적 스레딩의 개념

암시적 스레딩에서는 스레드의 생성과 관리를 컴파일러 또는 런타임 라이브러리에 맡긴다.

```text
명시적 스레딩

프로그래머
├─ 스레드 생성
├─ 작업 배정
├─ 스레드 종료
└─ 결과 병합
```

```text
암시적 스레딩

프로그래머
└─ 실행할 작업만 정의

런타임 라이브러리
├─ 스레드 생성
├─ 작업 배정
├─ 스레드 재사용
├─ 스케줄링
└─ 종료 관리
```

핵심은 **Thread와 Task를 분리하는 것**이다.

- Thread: 실제로 CPU에서 코드를 실행하는 실행 주체
- Task: 실행해야 하는 작업 단위

```text
Task 1 ─┐
Task 2 ─┼→ Runtime → 사용 가능한 Thread에 배정
Task 3 ─┘
```

교재는 다음과 같은 암시적 스레딩 기법을 다룬다.

1. Thread Pools
2. Fork Join
3. OpenMP
4. Grand Central Dispatch
5. Intel Threading Building Blocks

# 4.5.1 Thread Pools

## 개념

스레드 풀은 여러 스레드를 미리 생성해 풀에 보관하고, 작업이 들어오면 사용 가능한 스레드에 작업을 할당하는 방식이다.

```text
Thread Pool

┌───────────────────────────┐
│ Worker Thread 1           │
│ Worker Thread 2           │
│ Worker Thread 3           │
│ Worker Thread 4           │
└───────────────────────────┘
          ↑
       Task Queue
```

---

## 왜 필요한가

요청이 올 때마다 새 스레드를 생성하면 다음 비용이 반복된다.

```text
요청 도착
→ 스레드 생성
→ 스택 및 자료구조 할당
→ 작업 수행
→ 스레드 종료
→ 자원 회수
```

요청이 매우 많으면 스레드 생성과 종료 자체가 큰 오버헤드가 된다.

또한 요청 하나당 스레드 하나를 무제한으로 생성하면 시스템 자원이 고갈될 수 있다.

```text
요청 100,000개
→ 스레드 100,000개
→ 메모리 부족
→ 문맥 교환 증가
→ 시스템 성능 저하
```

스레드 풀은 스레드를 미리 만들고 재사용해 이 문제를 줄인다.

---

## 동작

```text
1. 프로그램 시작 시 Worker Thread를 미리 생성한다.
2. 생성된 스레드는 작업을 기다린다.
3. 요청이 들어오면 Task Queue에 저장한다.
4. 대기 중인 Worker Thread가 작업을 가져간다.
5. 작업 완료 후 스레드는 종료되지 않고 다시 대기한다.
```

```text
Task A → Worker 1
Task B → Worker 2
Task C → Worker 3

작업 완료 후

Worker 1 → 다시 Pool에서 대기
Worker 2 → 다시 Pool에서 대기
Worker 3 → 다시 Pool에서 대기
```

---

## 장점

### 1. 작업 처리 속도 향상

이미 존재하는 스레드가 작업을 실행하므로 새 스레드 생성 시간이 필요하지 않다.

### 2. 자원 사용량 제한

스레드 풀 크기를 제한하면 동시에 실행되는 스레드 수도 제한할 수 있다.

```text
요청 1,000개
Thread Pool 크기 = 10

동시에 실행되는 스레드 = 최대 10개
나머지 요청 = Queue에서 대기
```

### 3. 작업과 실행 메커니즘 분리

프로그래머는 작업을 정의하고 풀에 제출하면 된다.

```text
프로그래머
→ “이 작업을 실행해줘”

Thread Pool
→ 사용 가능한 스레드 선택
→ 작업 실행
```

---

## 스레드 풀 크기 결정

스레드 수는 다음 요소에 따라 달라질 수 있다.

- CPU 코어 수
- 사용 가능한 메모리
- 작업이 CPU 중심인지 I/O 중심인지
- 예상되는 동시 요청 수
- Blocking되는 작업의 비율

### CPU 중심 작업

CPU 계산이 대부분이라면 코어 수와 비슷한 수준의 스레드가 효율적일 수 있다.

```text
4코어 CPU
→ 실행 가능한 CPU 중심 스레드를 지나치게 많이 만들면
→ 문맥 교환만 증가할 수 있음
```

### I/O 중심 작업

I/O 대기가 많다면 스레드 일부가 Block되는 동안 다른 스레드가 실행할 수 있으므로 코어 수보다 많은 스레드를 둘 수 있다.

---

## Windows Thread Pool

Windows는 스레드 풀 API를 제공한다.

교재에서는 `QueueUserWorkItem()`을 예로 든다.

```c
QueueUserWorkItem(
    &PoolFunction,
    NULL,
    0
);
```

주요 인자는 다음과 같다.

| 인자       | 의미                            |
| ---------- | ------------------------------- |
| `Function` | 풀의 스레드가 실행할 함수       |
| `Param`    | 함수에 전달할 매개변수          |
| `Flags`    | 스레드 풀 실행 방식에 관한 옵션 |

위 코드는 스레드 풀의 스레드 하나가 `PoolFunction()`을 실행하도록 요청한다.

프로그래머가 직접 `CreateThread()`를 호출하지 않아도 된다.

Windows Thread Pool API는 다음과 같은 작업도 지원한다.

- 주기적으로 함수 실행
- 비동기 I/O 완료 후 함수 실행
- 작업 Queue 관리

---

## 4.5.1.1 Java Thread Pools

Java는 `java.util.concurrent` 패키지에서 스레드 풀과 Executor 프레임워크를 제공한다.

교재는 세 가지 대표적인 Executor를 설명한다.

### Single Thread Executor

```java
Executors.newSingleThreadExecutor();
```

스레드가 하나인 풀을 만든다.

```text
Task A
Task B
Task C

↓ 하나의 스레드에서 순차 실행

A → B → C
```

작업은 순차 실행되지만 작업 제출과 실행을 분리할 수 있다.

---

### Fixed Thread Pool

```java
Executors.newFixedThreadPool(size);
```

지정한 개수만큼 스레드를 만든다.

```java
ExecutorService pool =
    Executors.newFixedThreadPool(4);
```

```text
Worker 1
Worker 2
Worker 3
Worker 4
```

동시에 실행되는 스레드 수를 예측하고 제한하기 쉽다.

---

### Cached Thread Pool

```java
Executors.newCachedThreadPool();
```

필요에 따라 스레드를 만들고, 이전에 생성된 스레드를 재사용한다.

```text
작업 증가
→ 필요하면 스레드 추가 생성

작업 감소
→ 기존 스레드 재사용
→ 오랫동안 사용하지 않는 스레드 정리
```

교재에서는 이를 크기가 고정되지 않은 풀로 설명한다.

---

## ExecutorService 사용

```java
ExecutorService pool =
    Executors.newCachedThreadPool();

for (int i = 0; i < numTasks; i++) {
    pool.execute(new Task());
}

pool.shutdown();
```

### `execute()`

```java
pool.execute(new Task());
```

Task를 풀에 제출한다.

사용 가능한 Worker Thread가 Task의 `run()`을 실행한다.

### `shutdown()`

```java
pool.shutdown();
```

이후 새로운 Task는 받지 않는다.

이미 제출된 Task가 모두 끝나면 스레드 풀을 종료한다.

```text
shutdown() 호출
→ 새로운 작업 거부
→ 기존 작업은 완료
→ 풀 종료
```

# 4.5.2 Fork Join

## 기본 Fork-Join 모델

Fork-Join은 하나의 큰 작업을 여러 개의 작은 작업으로 나누고, 각 작업을 병렬 실행한 뒤 결과를 합치는 구조다.

```text
Parent Task
     │
     ├─ fork → Child Task 1
     ├─ fork → Child Task 2
     └─ fork → Child Task 3

Child 작업 실행

     └─ join → 결과 결합
```

앞서 배운 명시적 스레딩도 Fork-Join 구조로 볼 수 있다.

```text
Parent Thread
├─ Child Thread 생성
├─ Child Thread 생성
└─ Child Thread 종료 대기
```

---

## 명시적 Fork-Join의 문제

작업이 재귀적으로 계속 분할되면 프로그래머가 모든 스레드를 직접 만들기 어렵다.

예를 들어 병합 정렬은 배열을 계속 절반으로 나눈다.

```text
전체 배열
├─ 왼쪽 절반
│  ├─ 왼쪽
│  └─ 오른쪽
└─ 오른쪽 절반
   ├─ 왼쪽
   └─ 오른쪽
```

각 작업마다 직접 스레드를 만들면 스레드 수가 급격히 증가할 수 있다.

Fork-Join 라이브러리는 작업 분할과 스레드 배정을 런타임이 처리하도록 한다.

---

## Java Fork-Join Framework

Java의 Fork-Join Framework는 다음 개념을 사용한다.

- `ForkJoinPool`
- `ForkJoinTask`
- `RecursiveTask`
- `RecursiveAction`

### RecursiveTask

결과값을 반환하는 작업이다.

```java
class SumTask extends RecursiveTask<Integer> {
    @Override
    protected Integer compute() {
        // 작업 수행
    }
}
```

### RecursiveAction

결과값을 반환하지 않는 작업이다.

```java
class SortTask extends RecursiveAction {
    @Override
    protected void compute() {
        // 작업 수행
    }
}
```

---

## 작업 분할 기준

Fork-Join에서는 작업이 충분히 작아질 때까지 분할한다.

```text
현재 작업 크기 > 임계값
→ 두 개 이상의 하위 작업으로 분할

현재 작업 크기 ≤ 임계값
→ 직접 계산
```

```java
protected Integer compute() {
    if (end - begin <= THRESHOLD) {
        return sequentialSum();
    }

    int mid = (begin + end) / 2;

    SumTask left = new SumTask(begin, mid);
    SumTask right = new SumTask(mid, end);

    left.fork();

    int rightResult = right.compute();
    int leftResult = left.join();

    return leftResult + rightResult;
}
```

---

## Work Stealing

Java Fork-Join Framework의 중요한 특징은 **Work Stealing**이다.

각 Worker Thread는 자신만의 작업 Queue를 가질 수 있다.

```text
Worker 1 Queue: Task A, Task B, Task C
Worker 2 Queue: 없음
```

Worker 2가 자신의 작업을 모두 끝내면 Worker 1의 Queue에서 작업을 가져온다.

```text
Worker 2
→ Worker 1의 Queue에서 Task C를 훔쳐 실행
```

이를 통해 특정 스레드에 작업이 몰리는 현상을 줄이고 작업 균형을 높인다.

---

## 일반 Thread Pool과 Fork-Join 비교

| 구분      | 일반 Thread Pool       | Fork-Join                       |
| --------- | ---------------------- | ------------------------------- |
| 작업 형태 | 독립적인 Task          | 재귀적으로 분할 가능한 Task     |
| 작업 분할 | 프로그래머가 미리 정의 | 실행 중 동적으로 분할 가능      |
| 부하 분산 | 공용 Queue 중심        | Work Stealing 활용 가능         |
| 대표 예시 | 서버 요청 처리         | 병합 정렬, 배열 합계, 트리 탐색 |

# 4.5.3 OpenMP

## 개념

OpenMP는 C, C++, Fortran에서 병렬 프로그래밍을 지원하는 컴파일러 지시어와 API의 집합이다.

주로 공유 메모리 멀티코어 시스템을 대상으로 한다.

프로그래머는 병렬화할 영역을 지시어로 표시하고, 컴파일러와 런타임이 스레드를 생성하고 관리한다.

---

## Parallel Region

```c
#pragma omp parallel
{
    printf("parallel region\n");
}
```

`#pragma omp parallel` 뒤의 블록은 여러 스레드가 실행한다.

```text
프로그램 실행
    ↓
Master Thread
    ↓ Parallel Region 진입
여러 Worker Thread 생성
    ↓
각 스레드가 블록 실행
    ↓
Region 종료 시 Join
```

이를 **Fork-Join Parallelism**이라고 볼 수 있다.

---

## Parallel For

반복문을 여러 스레드에 나누어 실행할 수 있다.

```c
#pragma omp parallel for
for (int i = 0; i < N; i++) {
    result[i] = input[i] * 2;
}
```

런타임은 반복 범위를 스레드에 분배한다.

```text
Thread 1 → i = 0 ~ 249
Thread 2 → i = 250 ~ 499
Thread 3 → i = 500 ~ 749
Thread 4 → i = 750 ~ 999
```

프로그래머가 직접 스레드를 만들거나 반복 범위를 나눌 필요가 없다.

---

## 장점

- 기존 순차 코드에 병렬 지시어를 추가하기 쉽다.
- 스레드 생성과 관리를 런타임이 담당한다.
- 반복문 기반 데이터 병렬화에 적합하다.
- 코어 수에 따라 런타임이 실행을 조절할 수 있다.

---

## 주의점

OpenMP가 자동으로 모든 동기화 문제를 해결해 주는 것은 아니다.

여러 스레드가 같은 변수를 수정하면 Race Condition이 발생할 수 있다.

```c
int sum = 0;

#pragma omp parallel for
for (int i = 0; i < N; i++) {
    sum += arr[i];
}
```

위 코드는 여러 스레드가 `sum`을 동시에 수정하므로 잘못된 결과가 나올 수 있다.

이때 Reduction 같은 기능을 사용할 수 있다.

```c
#pragma omp parallel for reduction(+:sum)
for (int i = 0; i < N; i++) {
    sum += arr[i];
}
```

> **추가 설명:** Reduction은 각 스레드가 지역 부분합을 계산한 뒤 마지막에 합치는 방식이다.

# 4.5.4 Grand Central Dispatch

## 개념

Grand Central Dispatch, 줄여서 GCD는 Apple이 macOS와 iOS에서 제공하는 동시성 기술이다.

개발자는 실행할 작업을 **Block** 형태로 정의하고 Dispatch Queue에 제출한다.

```text
Application
→ Task를 Block으로 정의
→ Dispatch Queue에 제출
→ GCD가 적절한 Thread에서 실행
```

스레드 생성과 관리는 GCD가 담당한다.

---

## Block

Block은 실행할 코드의 단위다.

C 언어 계열에서는 `^` 기호로 표현한다.

```c
^{
    printf("task executed\n");
}
```

Swift에서는 Closure를 사용한다.

```swift
DispatchQueue.global().async {
    print("task executed")
}
```

---

## Dispatch Queue

GCD는 작업을 Queue에 넣고 스레드 풀을 통해 실행한다.

Dispatch Queue는 크게 두 종류로 구분된다.

### Serial Queue

한 번에 하나의 작업만 실행한다.

```text
Task A → Task B → Task C
```

작업 순서를 보장하며 공유 데이터 보호에 활용할 수 있다.

### Concurrent Queue

여러 작업을 동시에 실행할 수 있다.

```text
Task A ─────────→
Task B ─────────→
Task C ─────────→
```

실제 병렬 실행 여부는 코어 수와 시스템 상황에 따라 결정된다.

---

## Main Queue와 Global Queue

### Main Queue

메인 스레드에서 실행되는 Serial Queue다.

UI 갱신 같은 작업에 사용한다.

```swift
DispatchQueue.main.async {
    // UI 업데이트
}
```

### Global Queue

시스템이 제공하는 Concurrent Queue다.

```swift
DispatchQueue.global().async {
    // 백그라운드 작업
}
```

---

## 동기와 비동기 제출

### `async`

작업을 Queue에 넣은 뒤 호출한 스레드는 기다리지 않는다.

```text
Caller
→ Task 제출
→ 즉시 다음 코드 실행
```

### `sync`

제출한 작업이 끝날 때까지 호출한 스레드가 기다린다.

```text
Caller
→ Task 제출
→ Task 종료까지 대기
→ 다음 코드 실행
```

Serial Queue에 잘못된 `sync` 호출을 사용하면 Deadlock이 발생할 수 있다.

---

## GCD의 장점

- 개발자가 스레드 수를 직접 정하지 않아도 된다.
- 시스템 전체 부하와 코어 수를 고려해 실행한다.
- Thread Pool을 사용해 스레드 생성 비용을 줄인다.
- Queue로 작업 순서를 쉽게 제어할 수 있다.
- Apple 플랫폼의 UI 및 비동기 작업 구조와 잘 결합된다.

---

# 4.5.5 Intel Threading Building Blocks

## 개념

Intel Threading Building Blocks, 즉 TBB는 C++에서 병렬 프로그래밍을 지원하는 템플릿 라이브러리다.

프로그래머가 직접 스레드를 만들기보다 병렬적으로 실행할 **작업**을 표현하도록 한다.

TBB 런타임이 작업을 사용 가능한 스레드에 배정한다.

---

## 대표 기능

TBB는 다음과 같은 고수준 병렬 알고리즘을 제공한다.

- `parallel_for`
- `parallel_reduce`
- 병렬 정렬
- Task Scheduler
- Concurrent Container

---

## `parallel_for`

반복 구간을 자동으로 나누어 병렬 실행한다.

개념적으로 다음과 같다.

```cpp
parallel_for(0, N, [](int i) {
    result[i] = input[i] * 2;
});
```

런타임이 데이터 구간을 분할하고 Worker Thread에 배정한다.

---

## `parallel_reduce`

배열 합계처럼 각 부분 결과를 마지막에 합치는 연산에 사용한다.

```text
전체 배열
├─ 부분합 A
├─ 부분합 B
├─ 부분합 C
└─ 부분합 D

최종 결과
= A + B + C + D
```

---

## Task Scheduler

TBB는 작업을 Task 단위로 관리하며 Work Stealing을 이용해 부하를 분산할 수 있다.

따라서 프로그래머는 운영체제 스레드보다 작업 구조에 집중한다.

---

## OpenMP, GCD, TBB 비교

| 구분        | OpenMP             | GCD            | TBB           |
| ----------- | ------------------ | -------------- | ------------- |
| 주요 환경   | C/C++/Fortran      | Apple 플랫폼   | C++           |
| 작업 표현   | Compiler Directive | Block/Closure  | Template·Task |
| 주된 방식   | 반복문 병렬화      | Dispatch Queue | 병렬 알고리즘 |
| 스레드 관리 | OpenMP Runtime     | GCD Runtime    | TBB Scheduler |
| 대표 용도   | 수치 계산          | 앱 비동기 작업 | C++ 병렬 처리 |

---

교재는 다음 다섯 가지를 다룬다.

1. `fork()`와 `exec()`의 의미
2. Signal Handling
3. Thread Cancellation
4. Thread-Local Storage
5. Scheduler Activations

# 4.6.1 The `fork()` and `exec()` System Calls

## 문제

단일 스레드 프로세스에서 `fork()`를 호출하면 부모 프로세스의 복사본이 생성된다.

그런데 멀티스레드 프로세스에서 한 스레드가 `fork()`를 호출하면 다음 질문이 생긴다.

> 자식 프로세스는 호출한 스레드 하나만 복사해야 하는가, 아니면 부모의 모든 스레드를 복사해야 하는가?

---

## 두 가지 방식

### 호출한 스레드만 복제

```text
부모 프로세스
├─ Thread A
├─ Thread B → fork() 호출
└─ Thread C

자식 프로세스
└─ Thread B만 존재
```

### 모든 스레드 복제

```text
부모 프로세스
├─ Thread A
├─ Thread B → fork()
└─ Thread C

자식 프로세스
├─ Thread A
├─ Thread B
└─ Thread C
```

일부 UNIX 시스템은 두 가지 버전의 `fork()`를 제공하기도 한다.

---

## 어떤 방식이 필요한가

### `fork()` 직후 `exec()`를 호출하는 경우

```c
fork();
exec(...);
```

`exec()`는 현재 프로세스의 주소 공간을 새로운 프로그램으로 교체한다.

따라서 기존의 다른 스레드를 모두 복제해도 곧 사라진다.

이 경우 호출한 스레드 하나만 복제하는 방식이 적절하다.

```text
fork()
→ 호출 스레드만 자식에 생성
→ exec()
→ 새로운 프로그램으로 교체
```

### 자식이 기존 코드를 계속 실행하는 경우

자식 프로세스가 `exec()` 없이 기존 멀티스레드 프로그램의 작업을 계속하려면 모든 스레드를 복제해야 할 수도 있다.

---

## 실제 주의점

멀티스레드 프로세스에서 `fork()`한 자식은 일반적으로 호출한 스레드만 갖는다.

이때 다른 스레드가 소유하던 Lock은 그대로 잠긴 상태로 복사될 수 있다.

```text
부모의 Thread A
→ Mutex 획득 중

Thread B
→ fork()

자식에는 Thread B만 존재
→ Mutex는 잠겨 있음
→ Mutex를 풀 Thread A는 존재하지 않음
```

이 때문에 멀티스레드 환경에서 `fork()` 후에는 보통 빠르게 `exec()`를 호출하거나 제한된 async-signal-safe 함수만 사용해야 한다.

> **추가 설명:** 이 세부 제한은 POSIX 실무에서 중요하다.

---

# 4.6.2 Signal Handling

## Signal의 개념

Signal은 UNIX 계열 시스템에서 프로세스에 특정 이벤트가 발생했음을 알리는 방법이다.

예를 들면 다음과 같다.

- 0으로 나누기
- 잘못된 메모리 접근
- 프로그램 강제 종료 요청
- Timer 만료
- 사용자의 `Ctrl + C`

Signal은 동기식 또는 비동기식으로 발생할 수 있다.

---

## Signal 처리 흐름

모든 Signal은 일반적으로 다음 흐름을 따른다.

```text
1. 특정 사건으로 Signal이 발생한다.
2. Signal이 프로세스에 전달된다.
3. Signal Handler가 Signal을 처리한다.
```

Signal 처리 방식은 다음 중 하나다.

- 기본 Signal Handler 실행
- 사용자 정의 Signal Handler 실행
- Signal 무시

---

## 동기 Signal

현재 실행 중인 스레드의 동작 때문에 발생한다.

```text
Thread A
→ 0으로 나누기
→ SIGFPE 발생
```

동기 Signal은 문제를 발생시킨 해당 스레드에 전달된다.

---

## 비동기 Signal

현재 스레드의 명령 실행과 직접 관계없이 외부 사건으로 발생한다.

```text
사용자가 Ctrl + C 입력
→ SIGINT 발생
```

비동기 Signal은 멀티스레드 프로세스에서 전달 대상 결정이 복잡하다.

---

## 멀티스레드 프로세스에서 Signal 전달 방식

Signal 종류와 상황에 따라 다음 방식이 가능하다.

1. Signal이 적용되는 특정 스레드에 전달
2. 프로세스의 모든 스레드에 전달
3. 일부 스레드에 전달
4. Signal 전용 스레드에 전달

---

## Signal Mask

각 스레드는 어떤 Signal을 차단할지 나타내는 Signal Mask를 가질 수 있다.

```text
Thread A
→ SIGINT 허용

Thread B
→ SIGINT 차단

Thread C
→ SIGINT 차단
```

프로세스 대상 Signal은 해당 Signal을 차단하지 않은 스레드 중 하나가 받을 수 있다.

---

## Windows의 APC

Windows는 UNIX Signal과 완전히 동일한 구조는 아니지만 비슷한 개념으로 **Asynchronous Procedure Call**, APC를 제공한다.

APC는 특정 스레드가 지정된 함수를 비동기적으로 실행하게 할 수 있다.

단, 대상 스레드가 APC를 처리할 수 있는 상태에 있어야 한다.

---

# 4.6.3 Thread Cancellation

## 개념

Thread Cancellation은 스레드가 작업을 끝내기 전에 강제로 종료하도록 요청하는 것이다.

종료 대상 스레드를 **Target Thread**라고 한다.

```text
Thread A
→ Thread B의 작업 취소 요청

Thread B
→ Target Thread
```

예를 들어 사용자가 검색 작업을 취소하면 검색 스레드를 중단해야 할 수 있다.

---

## 두 가지 취소 방식

### Asynchronous Cancellation

Target Thread를 즉시 종료한다.

```text
취소 요청
→ 즉시 종료
```

### Deferred Cancellation

Target Thread가 안전한 지점에서 취소 요청을 확인하고 스스로 종료한다.

```text
취소 요청
→ 요청 Pending
→ Target Thread가 Cancellation Point 도달
→ 정리 작업 수행
→ 종료
```

---

## 비동기 취소의 문제

스레드가 어떤 자원을 사용하는 중인지 알 수 없는 상태에서 종료될 수 있다.

```text
Thread
├─ Mutex 보유 중
├─ 파일 쓰기 중
├─ Heap 메모리 수정 중
└─ 공유 자료구조 갱신 중

이 시점에 즉시 종료
→ Lock이 해제되지 않음
→ 데이터가 일관되지 않음
→ 자원 누수
```

따라서 일반적으로 Deferred Cancellation이 더 안전하다.

---

## Pthreads Cancellation

Pthreads에서는 다음과 같이 취소를 요청한다.

```c
pthread_cancel(tid);
pthread_join(tid, NULL);
```

`pthread_cancel()`은 즉시 종료시키는 명령이 아니라 **취소 요청**이다.

실제 취소 여부는 Target Thread의 설정에 따라 달라진다.

---

## Pthreads의 취소 모드

| Mode         | State    | Type         |
| ------------ | -------- | ------------ |
| Off          | Disabled | 없음         |
| Deferred     | Enabled  | Deferred     |
| Asynchronous | Enabled  | Asynchronous |

### Disabled

취소 요청을 처리하지 않는다.

요청 자체는 Pending 상태로 남을 수 있다.

### Deferred

기본 방식이다.

Cancellation Point에서 취소 요청을 확인하고 종료한다.

### Asynchronous

취소 요청을 받으면 즉시 종료할 수 있다.

안전성 문제 때문에 권장되지 않는다.

---

## Cancellation Point

Deferred Cancellation에서는 스레드가 안전하게 취소될 수 있는 위치가 필요하다.

대부분의 POSIX Blocking 함수는 Cancellation Point다.

예:

- `read()`
- 일부 대기 함수
- `pthread_testcancel()`

```c
while (1) {
    /* 작업 수행 */

    pthread_testcancel();
}
```

취소 요청이 Pending 상태라면 `pthread_testcancel()`에서 스레드가 종료된다.

취소 요청이 없으면 함수가 반환되고 실행을 계속한다.

---

## Cleanup Handler

취소되기 전에 자원을 정리하기 위한 함수를 등록할 수 있다.

```text
취소 요청
→ Cleanup Handler 실행
├─ Mutex 해제
├─ 메모리 해제
└─ 파일 닫기
→ 스레드 종료
```

---

## Java Thread Cancellation

Java에서는 스레드를 직접 강제 종료하기보다 `interrupt()`로 중단 요청을 전달한다.

```java
worker.interrupt();
```

스레드는 자신의 interrupt 상태를 확인한다.

```java
while (!Thread.currentThread().isInterrupted()) {
    // 작업 수행
}
```

즉, Java도 Deferred Cancellation과 비슷한 협력적 취소 방식을 사용한다.

`interrupt()`는 일반적으로 다음 의미다.

> “즉시 죽어라”가 아니라 “중단 요청이 왔으니 적절하게 대응하라.”

---

# 4.6.4 Thread-Local Storage

## 개념

같은 프로세스의 스레드들은 Data와 Heap을 공유한다.

그러나 어떤 데이터는 스레드마다 독립적으로 보관할 필요가 있다.

이를 **Thread-Local Storage**, TLS라고 한다.

```text
Thread A → 자신의 TLS
Thread B → 자신의 TLS
Thread C → 자신의 TLS
```

변수 이름은 같더라도 각 스레드가 서로 다른 값을 가진다.

---

## Stack 지역 변수와 차이

스택의 지역 변수도 스레드마다 별도로 존재한다.

하지만 TLS는 함수 호출 동안만 존재하는 일반 지역 변수와 다르다.

### 일반 지역 변수

```text
함수 호출 시작
→ 변수 생성

함수 종료
→ 변수 제거
```

### TLS

```text
스레드 시작
→ Thread별 데이터 생성

여러 함수에서 접근 가능

스레드 종료
→ 데이터 제거
```

즉, TLS는 스레드 전체 실행 기간 동안 유지되는 고유 데이터다.

---

## 필요한 이유

### 예시 1: 고유 식별 정보

웹 서버의 각 스레드가 자신이 처리 중인 요청 ID를 보관할 수 있다.

```text
Thread 1 TLS → Request ID 101
Thread 2 TLS → Request ID 102
Thread 3 TLS → Request ID 103
```

### 예시 2: 난수 생성기 상태

난수 생성기의 내부 상태를 공유하면 동기화가 필요하다.

스레드별 난수 상태를 두면 Lock 없이 사용할 수 있다.

### 예시 3: 라이브러리 상태

런타임 라이브러리나 DLL이 스레드별 상태를 저장할 수 있다.

---

## TLS와 정적 데이터 비교

| 구분          | Static/Global Data     | TLS                                  |
| ------------- | ---------------------- | ------------------------------------ |
| 데이터 개수   | 프로세스 전체에 하나   | 스레드마다 하나                      |
| 공유 여부     | 모든 스레드가 공유     | 스레드별 독립                        |
| 동기화 필요성 | 수정 시 필요할 수 있음 | 다른 스레드와 공유하지 않으면 불필요 |
| 수명          | 프로세스 실행 기간     | 해당 스레드 실행 기간                |

---

# 4.6.5 Scheduler Activations

## 등장 배경

Many-to-Many 또는 Two-Level 모델에서는 사용자 스레드와 커널 스레드 사이를 조정해야 한다.

```text
User Threads
   ↓
Thread Library
   ↓
Kernel Threads
```

사용자 영역의 스레드 라이브러리와 커널이 서로 독립적으로 스케줄링하면 문제가 생길 수 있다.

예를 들어 사용자 스레드가 Blocking되었지만 사용자 스레드 라이브러리가 이를 알지 못하면 다른 사용자 스레드를 적절히 실행하지 못할 수 있다.

Scheduler Activation은 커널과 스레드 라이브러리가 협력하도록 하는 방식이다.

---

## LWP

Many-to-Many 모델에서는 사용자 스레드와 커널 스레드 사이에 **Lightweight Process**, LWP라는 중간 구조를 둘 수 있다.

```text
User Thread
     ↓
LWP
     ↓
Kernel Thread
```

교재의 Figure 4.20은 이 구조를 보여준다.

사용자 스레드 라이브러리 관점에서 LWP는 스레드를 실행할 수 있는 **Virtual Processor**처럼 보인다.

```text
LWP 1 → User Thread A 실행
LWP 2 → User Thread B 실행
LWP 3 → User Thread C 실행
```

각 LWP는 하나의 커널 스레드에 연결된다.

---

## Upcall

커널이 사용자 영역의 스레드 라이브러리에 특정 사건을 알려주는 것을 **Upcall**이라고 한다.

일반적으로 시스템 콜은 사용자 영역에서 커널로 내려간다.

```text
User Space
    ↓ System Call
Kernel Space
```

Upcall은 반대 방향이다.

```text
Kernel Space
    ↑ Upcall
Thread Library
```

스레드 라이브러리는 Upcall Handler를 통해 이를 처리한다.

---

## 스레드가 Block될 때의 동작

```text
1. User Thread A가 Blocking되려 한다.
2. 커널이 스레드 라이브러리에 Upcall을 보낸다.
3. 어떤 스레드가 Blocking되는지 알린다.
4. 커널이 새로운 Virtual Processor/LWP를 제공할 수 있다.
5. Upcall Handler가 A의 상태를 저장한다.
6. 실행 가능한 다른 User Thread를 새 LWP에 배정한다.
```

```text
Thread A → Block
             ↓ Upcall

Thread Library
→ Thread A 상태 저장
→ Thread B 선택
→ 새로운 LWP에서 Thread B 실행
```

---

## Block된 스레드가 다시 실행 가능해질 때

```text
1. Thread A가 기다리던 사건이 완료된다.
2. 커널이 Thread Library에 다시 Upcall을 보낸다.
3. Thread A가 실행 가능 상태임을 알린다.
4. Thread Library가 적절한 LWP에 A를 스케줄링한다.
```

---

## 장점과 단점

### 장점

- 사용자 스레드 라이브러리가 커널 상태를 알 수 있다.
- Blocking 시 다른 사용자 스레드를 빠르게 실행할 수 있다.
- 사용자 수준 스케줄링과 커널 수준 스케줄링을 조정할 수 있다.

### 단점

- 커널과 Thread Library 모두 복잡해진다.
- Upcall Handler와 LWP 관리가 필요하다.
- 현대 운영체제에서 One-to-One 모델이 일반화되면서 중요성이 줄었다.

---

# 4.7 Operating-System Examples

교재는 실제 운영체제에서 스레드가 어떻게 구현되는지 Windows와 Linux를 통해 설명한다.

---

# 4.7.1 Windows Threads

## 기본 모델

Windows의 각 응용 프로그램은 하나의 프로세스로 실행되며, 프로세스는 하나 이상의 스레드를 가질 수 있다.

Windows는 **One-to-One Model**을 사용한다.

```text
User Thread 1 → Kernel Thread 1
User Thread 2 → Kernel Thread 2
User Thread 3 → Kernel Thread 3
```

---

## Windows 스레드의 일반 구성요소

Windows 스레드는 다음 정보를 가진다.

- Thread ID
- Register Set
- Program Counter
- User Stack
- Kernel Stack
- Runtime Library와 DLL이 사용하는 Private Storage

Register Set, Stack, Private Storage를 합쳐 스레드의 **Context**라고 한다.

---

## User Stack과 Kernel Stack

Windows 스레드는 스택을 하나만 갖는 것이 아니라 사용자 모드와 커널 모드용 스택을 각각 가진다.

```text
User Mode 실행
→ User Stack 사용

System Call 또는 Interrupt
→ Kernel Mode 진입
→ Kernel Stack 사용
```

사용자 프로그램이 커널 스택을 직접 접근할 수 없도록 분리해 보호한다.

---

## 주요 자료구조

Windows 스레드는 다음 세 자료구조로 표현된다.

1. ETHREAD
2. KTHREAD
3. TEB

교재의 Figure 4.21은 세 구조가 커널 영역과 사용자 영역에 나뉘어 연결되는 모습을 보여준다.

---

## ETHREAD

**Executive Thread Block**이다.

커널 영역에 존재한다.

주요 정보는 다음과 같다.

- 스레드가 속한 프로세스 포인터
- 스레드 시작 함수 주소
- 대응되는 KTHREAD 포인터

```text
ETHREAD
├─ Parent Process Pointer
├─ Thread Start Address
└─ KTHREAD Pointer
```

---

## KTHREAD

**Kernel Thread Block**이다.

커널 영역에 존재한다.

주요 정보는 다음과 같다.

- 스케줄링 정보
- 동기화 정보
- Kernel Stack
- TEB를 가리키는 포인터

```text
KTHREAD
├─ Scheduling Information
├─ Synchronization Information
├─ Kernel Stack
└─ TEB Pointer
```

운영체제 스케줄러가 스레드를 관리할 때 핵심적으로 사용하는 구조다.

---

## TEB

**Thread Environment Block**이다.

사용자 영역에 존재한다.

주요 정보는 다음과 같다.

- Thread ID
- User Stack
- Thread-Local Storage 배열

```text
TEB
├─ Thread Identifier
├─ User Stack
└─ TLS Array
```

ETHREAD와 KTHREAD는 커널만 접근할 수 있지만, TEB는 사용자 모드에서 접근되는 구조다.

---

## Windows 스레드 구조

```text
Kernel Space

ETHREAD
├─ Parent Process
├─ Start Address
└─ KTHREAD ─────────────┐

KTHREAD                  │
├─ Scheduling            │
├─ Synchronization       │
├─ Kernel Stack          │
└─ TEB Pointer ──────────┼───┐

User Space               │   │

TEB ◀────────────────────┘   │
├─ Thread ID                 │
├─ User Stack                │
└─ Thread-Local Storage      │
```

---

# 4.7.2 Linux Threads

## Linux의 기본 관점

Linux는 내부적으로 프로세스와 스레드를 엄격하게 구분하지 않는다.

Linux에서는 실행 흐름을 **Task**라고 부른다.

```text
일반적인 개념

Process
Thread
```

```text
Linux Kernel 관점

Task
```

프로세스와 스레드의 차이는 **어떤 자원을 공유하느냐**로 결정된다.

---

## `fork()`와 `clone()`

Linux의 `fork()`는 전통적으로 부모 프로세스를 복제한다.

스레드를 만들 때는 `clone()` 시스템 콜을 사용할 수 있다.

```text
fork()
→ 자원을 독립적으로 가지는 새 Task

clone()
→ 지정한 자원을 공유하는 새 Task
```

---

## `clone()`의 Flags

`clone()`은 여러 Flag를 받아 부모와 자식 Task가 무엇을 공유할지 결정한다.

대표적인 Flag는 다음과 같다.

| Flag            | 공유 대상        |
| --------------- | ---------------- |
| `CLONE_FS`      | 파일 시스템 정보 |
| `CLONE_VM`      | 같은 메모리 공간 |
| `CLONE_SIGHAND` | Signal Handler   |
| `CLONE_FILES`   | 열린 파일 집합   |

예를 들어 다음 Flag를 모두 지정한다고 하자.

```text
CLONE_FS
CLONE_VM
CLONE_SIGHAND
CLONE_FILES
```

부모와 자식 Task는 다음을 공유한다.

- 현재 작업 디렉터리 등 파일 시스템 정보
- 같은 주소 공간
- Signal Handler
- 열린 파일 테이블

이 경우 두 Task는 일반적으로 같은 프로세스의 스레드처럼 동작한다.

---

## Flag를 지정하지 않으면

공유 Flag가 적다면 자식 Task는 부모와 독립적인 자원을 갖는다.

```text
공유가 적음
→ 독립적인 프로세스에 가까움

공유가 많음
→ 같은 프로세스의 스레드에 가까움
```

즉, Linux에서는 프로세스와 스레드가 완전히 다른 종류의 객체라기보다 **공유 정도가 다른 Task**다.

---

## `task_struct`

Linux에서 각 Task는 `task_struct`라는 커널 자료구조로 표현된다.

`task_struct`는 다음과 같은 실행 정보를 가진다.

- Task 상태
- 스케줄링 정보
- 식별자
- 열린 파일 관련 포인터
- 메모리 관련 포인터
- Signal 관련 포인터
- 부모와 자식 관계

Task끼리 자원을 공유하면 각각의 `task_struct`가 같은 자료구조를 가리킬 수 있다.

```text
Task A task_struct ─┐
                    ├→ 같은 Memory Descriptor
Task B task_struct ─┘
```

```text
Task A task_struct ─┐
                    ├→ 같은 Open File Table
Task B task_struct ─┘
```

이 방식으로 Linux는 스레드의 자원 공유를 구현한다.

---

## Linux 스레드는 사용자 스레드인가, 커널 스레드인가

Linux의 스레드는 커널이 각각의 Task를 인식하고 독립적으로 스케줄링한다.

따라서 Linux 스레드는 **Kernel-Level Thread**이며 One-to-One 모델에 해당한다.

```text
Pthread User Thread
→ Linux Kernel Task
→ CPU Scheduler가 직접 스케줄링
```

---

```text
→ CPU Core
```

```text

→ 동시성

멀티코어 + One-to-One

→ 병렬성 가능
```

# 면접 포인트

## Q1. 명시적 스레딩과 암시적 스레딩의 차이는 무엇인가?

명시적 스레딩은 개발자가 스레드 생성, 작업 할당, 종료와 동기화를 직접 관리하는 방식이다. 암시적 스레딩은 개발자가 Task를 정의하면 런타임이나 라이브러리가 스레드 생성과 스케줄링을 담당하는 방식이다.

---

## Q2. 스레드 풀을 사용하는 이유는 무엇인가?

작업마다 새 스레드를 만들 때 발생하는 생성과 종료 비용을 줄이고, 동시에 실행되는 스레드 수를 제한해 시스템 자원 고갈을 막기 위해 사용한다. 스레드를 미리 생성해 두고 작업마다 재사용한다.

---

## Q3. Fork-Join과 일반 Thread Pool의 차이는 무엇인가?

일반 Thread Pool은 주로 독립적인 Task를 처리한다. Fork-Join은 큰 작업을 재귀적으로 작은 작업으로 나눈 뒤 병렬로 처리하고 결과를 합치는 구조이며, Work Stealing으로 작업량을 분산할 수 있다.

---

## Q4. Java에서 `interrupt()`를 호출하면 스레드가 즉시 종료되는가?

아니다. `interrupt()`는 중단 요청을 나타내는 상태를 설정하거나 Blocking 메서드에 예외를 발생시킨다. 대상 스레드가 interrupt 상태를 확인하고 스스로 종료 처리를 해야 한다.

---

## Q5. TLS와 일반 지역 변수의 차이는 무엇인가?

일반 지역 변수는 특정 함수 호출 동안 스택에 존재한다. TLS는 스레드마다 독립적인 복사본을 가지며 해당 스레드의 실행 기간 동안 여러 함수에서 사용할 수 있다.

---

## Q6. Linux에서 프로세스와 스레드를 어떻게 구분하는가?

Linux는 둘을 모두 Task로 표현한다. `clone()`에 전달한 Flag에 따라 메모리, 파일, Signal Handler 등의 자원을 얼마나 공유하는지가 달라진다. 자원을 많이 공유하면 스레드처럼 동작하고, 공유하지 않으면 독립 프로세스처럼 동작한다.

---

## Q7. Windows의 ETHREAD, KTHREAD, TEB의 역할은 무엇인가?

ETHREAD는 스레드가 속한 프로세스와 시작 주소 등 Executive 계층 정보를 저장한다. KTHREAD는 스케줄링, 동기화 정보와 Kernel Stack을 가진다. TEB는 사용자 영역에 존재하며 Thread ID, User Stack, TLS 정보를 가진다.

## Q8. `fork()`를 멀티스레드 프로세스에서 호출할 때 문제가 되는 이유는 무엇인가?

호출한 스레드만 자식에 복제될 경우 다른 스레드가 보유했던 Lock이 잠긴 상태로 남을 수 있지만, 그 Lock을 해제할 스레드는 자식에 존재하지 않을 수 있다. 그래서 일반적으로 `fork()` 직후 `exec()`를 호출하는 방식이 안전하다.

---

## Q9. Thread Cancellation에서 Deferred 방식이 권장되는 이유는 무엇인가?

Asynchronous 방식은 스레드가 Lock을 보유하거나 공유 데이터를 수정하는 중에도 즉시 종료될 수 있어 데이터 불일치와 자원 누수를 일으킬 수 있다. Deferred 방식은 안전한 Cancellation Point에서 정리한 뒤 종료할 수 있다.

---

## Q10. 스레드는 프로세스보다 항상 빠른가?

일반적으로 생성과 문맥 교환 비용은 더 작지만 항상 성능이 좋아지는 것은 아니다. Lock 경쟁, 데이터 의존성, 캐시 일관성 비용, 문맥 교환, 과도한 스레드 생성 때문에 오히려 성능이 저하될 수 있다.
