# Chapter 5. CPU Scheduling

> 범위: **5.1 Basic Concepts → 5.4 Thread Scheduling**
> Chapter 5는 여러 프로세스 또는 커널 스레드가 실행 가능한 상태일 때, **CPU 코어를 누구에게 언제까지 할당할 것인가**를 다룬다. 교재에서는 전통적으로 “프로세스 스케줄링”이라고 표현하지만, 현대 운영체제가 실제로 스케줄링하는 대상은 대부분 **커널 스레드**다.

---

# 5.1 Basic Concepts

## CPU 스케줄링이 필요한 이유

단일 CPU 코어에서는 한 순간에 하나의 프로세스만 실행할 수 있다.

```text
Ready Process A ─┐
Ready Process B ─┼─→ CPU Core에서는 하나만 실행
Ready Process C ─┘
```

실행 중인 프로세스가 I/O를 요청하면 결과가 돌아올 때까지 CPU를 사용할 수 없다.

```text
Process A 실행
    ↓
디스크 읽기 요청
    ↓
I/O 완료까지 대기
```

이때 A가 끝날 때까지 CPU를 놀리면 CPU 이용률이 떨어진다. 따라서 운영체제는 A가 기다리는 동안 다른 프로세스 B에게 CPU를 넘긴다.

```text
A: CPU 실행 → I/O 대기 ─────────→ Ready
B:            CPU 실행 → I/O 대기
C:                        CPU 실행
```

이것이 **다중 프로그래밍과 CPU 스케줄링의 핵심**이다.

멀티코어 시스템에서는 이 원리를 모든 코어에 적용하여 가능한 한 모든 코어가 실행할 작업을 가지도록 한다.

---

# 5.1.1 CPU–I/O Burst Cycle

## 개념

프로세스 실행은 다음 두 구간이 반복되는 형태로 구성된다.

- **CPU burst**: CPU에서 명령어를 실행하는 구간
- **I/O burst**: I/O 작업이 끝나기를 기다리는 구간

```text
CPU Burst
   ↓
I/O Burst
   ↓
CPU Burst
   ↓
I/O Burst
   ↓
CPU Burst
   ↓
종료
```

프로세스는 일반적으로 CPU burst로 시작하고, 마지막 CPU burst가 끝나면 종료 요청을 한다.

---

## CPU-bound와 I/O-bound

### I/O-bound process

CPU를 짧게 사용하고 자주 I/O를 요청하는 프로세스다.

```text
짧은 CPU → I/O → 짧은 CPU → I/O → 짧은 CPU
```

예:

- 웹 브라우저의 사용자 입력 처리
- 파일을 자주 읽는 프로그램
- 네트워크 요청이 많은 프로그램
- GUI 애플리케이션

특징은 **짧은 CPU burst가 많이 존재한다**는 것이다.

---

### CPU-bound process

I/O보다 계산을 오래 수행하는 프로세스다.

```text
긴 CPU Burst → I/O → 긴 CPU Burst
```

예:

- 영상 인코딩
- 대규모 수치 계산
- 머신러닝 학습
- 압축 및 암호화

특징은 **긴 CPU burst가 적은 횟수로 존재한다**는 것이다.

---

## CPU burst 분포

실제 시스템에서 CPU burst 길이를 조사하면 대체로 다음과 같은 형태가 나타난다.

```text
빈도
▲
│■■■■■■■■
│■■■■■
│■■■
│■
│                         ■
└────────────────────────────▶ CPU burst 길이
   짧음                       김
```

대부분의 CPU burst는 짧고, 긴 CPU burst는 적다.

이 특성은 스케줄링 알고리즘을 설계할 때 중요하다. 예를 들어 짧은 CPU burst를 먼저 처리하면 평균 대기 시간이나 사용자 응답 시간을 줄일 수 있다.

---

# 5.1.2 CPU Scheduler

## 개념

CPU가 비게 되면 운영체제는 **Ready Queue에서 다음 실행 대상을 선택**해야 한다.

이 선택을 담당하는 구성요소가 **CPU Scheduler**, 즉 단기 스케줄러다.

```text
Ready Queue
┌────┬────┬────┬────┐
│ P1 │ P2 │ P3 │ P4 │
└────┴────┴────┴────┘
          ↓
    CPU Scheduler
          ↓
       CPU Core
```

CPU Scheduler의 작업은 다음과 같다.

```text
메모리에 존재하면서
실행 준비가 된 프로세스 중
하나를 선택하여 CPU를 할당
```

---

## Ready Queue는 반드시 FIFO가 아니다

이름은 Queue지만, 실제 구현이 반드시 선입선출 큐인 것은 아니다.

스케줄링 정책에 따라 다음 자료구조를 사용할 수 있다.

| 스케줄링 기준 | 가능한 자료구조        |
| ------------- | ---------------------- |
| 도착 순서     | FIFO Queue             |
| 우선순위      | Priority Queue         |
| 실행 시간     | 정렬된 Queue 또는 Heap |
| Linux CFS     | Red-Black Tree         |
| 단순 구현     | 연결 리스트            |

Ready Queue에는 일반적으로 실행 가능한 프로세스의 **PCB** 또는 커널 스레드의 관리 정보가 연결된다.

---

# 5.1.3 Preemptive and Nonpreemptive Scheduling

CPU 스케줄링 결정이 발생할 수 있는 상황은 네 가지다.

## 1. Running → Waiting

실행 중인 프로세스가 I/O나 특정 이벤트를 기다린다.

```text
Running
   │ I/O 요청
   ▼
Waiting
```

프로세스가 CPU를 스스로 사용할 수 없게 되었으므로 다른 프로세스를 선택해야 한다.

---

## 2. Running → Ready

실행 중인 프로세스가 강제로 CPU를 빼앗긴다.

```text
Running
   │ 타이머 인터럽트
   ▼
Ready
```

예:

- Time quantum 만료
- 더 높은 우선순위 프로세스 도착
- 인터럽트 발생 후 스케줄러 실행

---

## 3. Waiting → Ready

대기 중인 프로세스의 I/O가 완료된다.

```text
Waiting
   │ I/O 완료
   ▼
Ready
```

이때 새로 Ready가 된 프로세스가 현재 실행 중인 프로세스보다 높은 우선순위를 가진다면 CPU를 빼앗을 수 있다.

---

## 4. Running → Terminated

프로세스가 실행을 완료한다.

```text
Running
   │ 종료
   ▼
Terminated
```

CPU가 비었으므로 다음 실행 대상을 선택해야 한다.

---

## 비선점 스케줄링

**Nonpreemptive Scheduling**은 프로세스가 CPU를 할당받으면 다음 상황까지 CPU를 계속 사용하는 방식이다.

- 프로세스가 종료
- 프로세스가 I/O 등을 기다리며 Waiting 상태로 이동

즉, 다른 프로세스가 Ready 상태가 되어도 현재 프로세스의 CPU를 강제로 빼앗지 않는다.

```text
P1 실행 ─────────────────→ 종료 또는 대기
                     P2는 계속 Ready에서 대기
```

앞의 네 가지 상황에서 1번과 4번은 현재 프로세스가 더 이상 실행할 수 없으므로 반드시 스케줄링이 필요하다.

비선점 방식에서는 주로 이 두 상황에서만 CPU가 교체된다.

### 장점

- 구현이 단순하다.
- 문맥 교환 횟수가 적다.
- 공유 자료구조가 실행 중간에 끊길 가능성이 작다.

### 단점

- 긴 작업이 CPU를 오래 독점할 수 있다.
- 대화형 시스템의 응답성이 나빠질 수 있다.
- 긴급한 프로세스가 즉시 실행되지 못한다.

---

## 선점 스케줄링

**Preemptive Scheduling**은 운영체제가 실행 중인 프로세스로부터 CPU를 강제로 회수할 수 있는 방식이다.

```text
P1 실행
   │ 더 높은 우선순위의 P2 도착
   ▼
P1 Ready 이동
P2 실행
```

네 가지 상황 중 2번과 3번에서도 새로운 프로세스를 선택할 수 있다.

현대의 Windows, Linux, macOS를 포함한 대부분의 범용 운영체제는 선점 스케줄링을 사용한다.

### 장점

- 빠른 응답 시간을 제공할 수 있다.
- 높은 우선순위 작업을 빠르게 처리할 수 있다.
- 여러 프로세스가 공정하게 CPU를 나누어 쓸 수 있다.

### 단점

- 문맥 교환 비용이 발생한다.
- 공유 데이터에 Race Condition이 발생할 수 있다.
- 커널 내부 자료구조를 안전하게 보호해야 한다.

---

## 선점과 Race Condition

두 프로세스가 같은 데이터를 수정한다고 가정한다.

```text
P1: count 값을 읽음 → 10
P1: count + 1 계산
        ↓ 선점 발생
P2: count 값을 읽음 → 10
P2: count + 1 → 11 저장
        ↓
P1: 계산해 둔 11 저장
```

두 프로세스가 각각 1씩 증가시켰지만 최종 결과는 12가 아니라 11이다.

따라서 선점형 커널에서는 공유 커널 자료구조를 다음과 같은 동기화 도구로 보호해야 한다.

- Mutex
- Spinlock
- Semaphore
- 원자적 명령어

일부 짧고 중요한 코드 구간에서는 인터럽트를 잠시 비활성화할 수도 있다. 다만 인터럽트 비활성화 구간은 시스템 응답성을 떨어뜨리므로 **짧게 유지해야 한다.**

# 5.1.4 Dispatcher

## CPU Scheduler와 Dispatcher의 차이

CPU Scheduler는 **누구를 실행할지 선택**한다.

Dispatcher는 선택된 프로세스가 **실제로 CPU에서 실행되도록 전환**한다.

```text
CPU Scheduler
→ 다음 실행 대상 P2 선택

Dispatcher
→ 현재 P1 상태 저장
→ P2 상태 복원
→ P2 실행 위치로 이동
```

---

## Dispatcher가 수행하는 작업

1. 한 프로세스에서 다른 프로세스로 문맥을 전환한다.
2. 커널 모드에서 사용자 모드로 전환한다.
3. 사용자 프로그램에서 실행을 재개할 올바른 위치로 이동한다.

```text
P1 실행
   ↓
P1 Context 저장
   ↓
P2 Context 복원
   ↓
User Mode 전환
   ↓
P2의 Program Counter 위치부터 재실행
```

---

## Dispatch Latency

Dispatcher가 한 프로세스를 중단시키고 다른 프로세스를 실행하기까지 걸리는 시간을 **Dispatch Latency**라고 한다.

```text
P1 실행 종료
│
├─ P1 상태 저장
├─ 스케줄링 및 전환
├─ P2 상태 복원
│
P2 실행 시작

<---- Dispatch Latency ---->
```

Dispatcher는 문맥 교환마다 실행되므로 가능한 한 빨라야 한다.

---

## 자발적·비자발적 문맥 교환

### Voluntary Context Switch

프로세스가 현재 사용할 수 없는 자원을 기다리면서 스스로 CPU를 반납한다.

```text
프로세스
→ 파일 읽기 요청
→ I/O 대기
→ 자발적으로 CPU 반납
```

I/O-bound 프로세스에서 자주 발생한다.

---

### Nonvoluntary Context Switch

운영체제가 실행 중인 프로세스로부터 CPU를 강제로 회수한다.

```text
프로세스 실행
→ Time quantum 만료
→ 타이머 인터럽트
→ 강제 선점
```

CPU-bound 프로세스에서 상대적으로 자주 발생할 수 있다.

Linux에서는 시스템 전체 문맥 교환을 `vmstat`으로 확인할 수 있고, 특정 프로세스의 문맥 교환 횟수는 `/proc/[pid]/status`에서 확인할 수 있다.

# 5.2 Scheduling Criteria

스케줄링 알고리즘마다 장단점이 다르다. 따라서 무엇이 좋은 알고리즘인지는 시스템의 목적에 따라 달라진다.

---

## 5.2.1 CPU Utilization

CPU가 전체 시간 중 실제 작업을 수행한 비율이다.

```text
CPU Utilization
= CPU가 작업한 시간 / 전체 시간
```

목표는 CPU가 가능한 한 놀지 않게 만드는 것이다.

- 최대화 대상
- 가벼운 부하에서는 약 40%
- 매우 높은 부하에서는 약 90%까지 나타날 수 있음

CPU 이용률이 100%라고 무조건 좋은 것은 아니다. CPU 대기열이 지나치게 길어 응답 시간이 악화된 상태일 수도 있다.

---

## 5.2.2 Throughput

단위 시간당 완료된 프로세스 수다.

```text
Throughput
= 완료된 프로세스 수 / 시간
```

예:

```text
10초 동안 50개 요청 완료
→ Throughput = 5 requests/sec
```

CPU 이용률과 처리량은 관련이 있지만 완전히 같은 값은 아니다.

긴 작업 하나가 CPU를 계속 사용하면 CPU 이용률은 높지만 완료되는 작업 수는 적어 처리량은 낮을 수 있다.

---

## 5.2.3 Turnaround Time

프로세스가 제출된 시점부터 완전히 종료될 때까지 걸린 전체 시간이다.

```text
Turnaround Time
= Completion Time - Arrival Time
```

구성 요소로 보면 다음과 같다.

```text
Turnaround Time
= Ready Queue 대기 시간
+ CPU 실행 시간
+ I/O 시간
+ 기타 대기 시간
```

예:

```text
도착: 2초
완료: 15초

Turnaround Time = 15 - 2 = 13초
```

일괄 처리 시스템에서는 중요한 기준이다.

---

## 5.2.4 Waiting Time

프로세스가 **Ready Queue에서 CPU를 기다린 총시간**이다.

```text
Waiting Time
= Ready Queue에서 기다린 시간의 합
```

CPU 스케줄링 알고리즘은 프로세스의 실제 CPU burst 길이나 I/O 시간은 바꾸지 못한다.

스케줄러가 직접 영향을 주는 값은 주로 Ready Queue의 대기 시간이다.

프로세스가 여러 번 선점되면 대기 시간이 여러 구간으로 나뉠 수 있다.

```text
Ready 3ms
→ Running
→ Ready 5ms
→ Running
→ 종료

Waiting Time = 3 + 5 = 8ms
```

---

## 5.2.5 Response Time

요청이 제출된 시점부터 **첫 번째 응답이 시작될 때까지** 걸린 시간이다.

```text
Response Time
= First Run 또는 First Response Time - Arrival Time
```

완전히 종료되는 시간과 다르다.

예를 들어 검색 요청이 10초 만에 모두 완료되더라도 0.2초 만에 첫 결과가 보였다면:

```text
Response Time = 0.2초
Turnaround Time = 10초
```

대화형 시스템에서는 전체 종료 시간보다 첫 응답이 얼마나 빠른지가 중요하다.

---

## 평가 기준 정리

| 기준            | 의미                     | 목표   |
| --------------- | ------------------------ | ------ |
| CPU utilization | CPU가 일한 비율          | 최대화 |
| Throughput      | 단위 시간당 완료 작업 수 | 최대화 |
| Turnaround time | 도착부터 종료까지        | 최소화 |
| Waiting time    | Ready Queue 대기 총합    | 최소화 |
| Response time   | 첫 응답까지의 시간       | 최소화 |

일반적으로 평균값을 최적화하지만, 시스템에 따라 최대값이나 편차가 더 중요할 수 있다.

예를 들어 평균 응답 시간이 짧더라도 일부 사용자가 매우 오래 기다린다면 좋은 대화형 시스템이라고 보기 어렵다. 따라서 대화형 시스템에서는 평균 응답 시간뿐 아니라 **응답 시간의 변동성**을 낮추는 것도 중요하다.

# 5.3.1 First-Come, First-Served Scheduling

## 개념

먼저 Ready Queue에 도착한 프로세스가 먼저 CPU를 사용한다.

```text
Ready Queue

P1 → P2 → P3
```

FIFO Queue로 구현할 수 있다.

CPU가 비면 Queue의 앞에서 프로세스를 꺼내고, 새로 도착한 프로세스는 Queue 뒤에 삽입한다.

---

## 비선점 방식

FCFS는 기본적으로 비선점 알고리즘이다.

P1이 CPU를 할당받으면 종료하거나 I/O를 요청하기 전까지 CPU를 계속 사용한다.

---

## 예시

모든 프로세스가 동시에 도착했다고 가정한다.

| 프로세스 | CPU burst |
| -------- | --------: |
| P1       |        24 |
| P2       |         3 |
| P3       |         3 |

도착 순서가 P1, P2, P3이면:

```text
0           24   27   30
|---- P1 ----| P2 | P3 |
```

대기 시간:

```text
P1 = 0
P2 = 24
P3 = 27

평균 = (0 + 24 + 27) / 3
     = 17
```

도착 순서가 P2, P3, P1이면:

```text
0   3   6           30
| P2 | P3 |---- P1 ----|
```

```text
P2 = 0
P3 = 3
P1 = 6

평균 = (0 + 3 + 6) / 3
     = 3
```

같은 프로세스라도 도착 순서에 따라 평균 대기 시간이 크게 달라진다.

---

## Convoy Effect

긴 CPU-bound 프로세스 뒤에서 여러 개의 짧은 I/O-bound 프로세스가 기다리는 현상이다.

```text
긴 CPU-bound P1
        ↓
짧은 P2, P3, P4가 모두 대기
```

P1이 CPU를 사용하는 동안 I/O 장치는 놀 수 있다.

P1이 I/O를 시작하면 짧은 프로세스들이 CPU를 빠르게 사용한 뒤 다시 I/O로 이동한다. 이번에는 CPU가 놀게 될 수 있다.

따라서 CPU와 I/O 장치의 이용률이 함께 떨어질 수 있다.

### 평가

- 구현이 단순하다.
- 문맥 교환이 적다.
- 공정하게 도착 순서를 지킨다.
- 평균 대기 시간이 좋지 않을 수 있다.
- 대화형 시스템에 적합하지 않다.

---

# 5.3.2 Shortest-Job-First Scheduling

## 개념

Ready Queue에 존재하는 프로세스 중 **다음 CPU burst가 가장 짧은 프로세스**를 먼저 실행한다.

```text
P1: 6ms
P2: 8ms
P3: 7ms
P4: 3ms

실행 순서
P4 → P1 → P3 → P2
```

정확히는 전체 프로세스 실행 시간이 아니라 **다음 CPU burst 길이**를 기준으로 한다.

---

## 장점: 최소 평균 대기 시간

모든 프로세스의 CPU burst 길이를 알고 있다면 SJF는 평균 대기 시간을 최소화한다.

짧은 작업을 먼저 끝내면 긴 작업 하나를 조금 늦추는 대신 여러 짧은 작업의 대기 시간을 크게 줄일 수 있기 때문이다.

예:

| 프로세스 | CPU burst |
| -------- | --------: |
| P1       |         6 |
| P2       |         8 |
| P3       |         7 |
| P4       |         3 |

```text
0    3      9       16        24
| P4 |  P1  |   P3   |    P2    |
```

대기 시간:

```text
P4 = 0
P1 = 3
P3 = 9
P2 = 16

평균 = (0 + 3 + 9 + 16) / 4
     = 7
```

---

## 문제: 다음 CPU burst를 정확히 알 수 없음

운영체제는 미래의 CPU burst 길이를 정확히 알 수 없다.

따라서 과거 CPU burst를 이용하여 다음 값을 예측한다.

### 지수 평균법

```text
τ(n+1) = α × t(n) + (1 - α) × τ(n)
```

- `t(n)`: 실제로 관측한 최근 CPU burst
- `τ(n)`: 기존 예측값
- `τ(n+1)`: 다음 CPU burst 예측값
- `α`: 최근 값과 과거 값의 반영 비율, `0 ≤ α ≤ 1`

---

### α의 의미

#### α = 0

```text
τ(n+1) = τ(n)
```

최근 실제 실행 시간을 전혀 반영하지 않는다.

초기 예측값이 계속 유지된다.

#### α = 1

```text
τ(n+1) = t(n)
```

가장 최근 CPU burst만 사용한다.

과거 기록은 전혀 반영하지 않는다.

#### 0 < α < 1

최근 값과 과거 예측을 함께 반영한다.

식을 전개하면 오래된 측정값일수록 가중치가 지수적으로 작아진다.

```text
τ(n+1)
= αt(n)
+ α(1-α)t(n-1)
+ α(1-α)²t(n-2)
+ ...
```

---

## 비선점 SJF와 선점 SJF

### Nonpreemptive SJF

한 프로세스가 실행을 시작하면 CPU burst가 끝날 때까지 계속 실행한다.

```text
P1 실행 중
P2가 더 짧아도 P1이 끝날 때까지 대기
```

---

### Preemptive SJF: SRTF

선점형 SJF는 **Shortest Remaining Time First**라고 한다.

새 프로세스가 도착했을 때 현재 프로세스의 남은 시간보다 새 프로세스의 CPU burst가 짧으면 선점한다.

```text
P1 남은 시간: 7ms
새로 도착한 P2: 4ms

P1 선점
→ P2 실행
```

SRTF는 현재까지의 남은 실행 시간을 계속 비교해야 하므로 비선점 SJF보다 관리 비용이 크다.

---

## 한계

- 다음 CPU burst를 정확히 알 수 없다.
- 긴 CPU burst를 가진 프로세스가 계속 밀릴 수 있다.
- 예측 및 Queue 정렬 비용이 발생한다.

---

# 5.3.3 Round-Robin Scheduling

## 개념

Round-Robin은 시간 공유 시스템을 위해 설계된 선점형 알고리즘이다.

각 프로세스에게 일정한 CPU 시간인 **Time Quantum** 또는 **Time Slice**를 부여한다.

```text
P1 → P2 → P3 → P1 → P2 → P3 → ...
```

Ready Queue를 원형 FIFO Queue처럼 사용한다.

---

## 동작

Time quantum을 `q`라고 하자.

CPU Scheduler는 Ready Queue 앞의 프로세스를 꺼내 최대 `q`만큼 실행한다.

### CPU burst가 q보다 작거나 같은 경우

프로세스가 스스로 CPU를 반납한다.

```text
CPU burst = 3ms
q = 4ms

3ms 실행 후 종료 또는 I/O 대기
```

### CPU burst가 q보다 큰 경우

타이머 인터럽트가 발생하여 프로세스를 선점한다.

```text
CPU burst = 10ms
q = 4ms

4ms 실행
→ 선점
→ 남은 6ms 상태로 Queue 뒤에 삽입
```

---

## 예시

| 프로세스 | CPU burst |
| -------- | --------: |
| P1       |        24 |
| P2       |         3 |
| P3       |         3 |

Time quantum이 4라면:

```text
0    4   7   10                    30
| P1 | P2 | P3 |------ P1 반복 ------|
```

P2와 P3는 긴 P1이 끝날 때까지 기다리지 않고 빠르게 실행된다.

---

## 프로세스 수와 대기 시간

Ready Queue에 `n`개의 프로세스가 있고 quantum이 `q`라면, 각 프로세스는 한 번에 최대 `q`만큼 CPU를 받는다.

한 프로세스는 대략 최대 `(n-1)q` 동안 기다린 뒤 다시 CPU를 받을 수 있다. 여기에 문맥 교환 시간이 추가된다.

---

## Time Quantum이 너무 큰 경우

```text
q → 매우 큼
```

대부분의 프로세스가 한 번 할당받은 CPU로 실행을 마친다.

결국 Round-Robin은 FCFS와 비슷해진다.

```text
RR with very large q ≈ FCFS
```

---

## Time Quantum이 너무 작은 경우

프로세스가 자주 선점되어 문맥 교환이 증가한다.

CPU burst가 10이고:

| Quantum | 문맥 교환 횟수 |
| ------: | -------------: |
|      12 |              0 |
|       6 |              1 |
|       1 |              9 |

Quantum이 1이면 거의 매 실행 단위마다 문맥 교환이 발생한다.

따라서 CPU 시간이 실제 작업보다 문맥 교환에 많이 사용될 수 있다.

---

## Quantum 설정 기준

Quantum은 문맥 교환 시간보다 충분히 커야 한다.

교재에서 제시하는 일반적 기준은 다음과 같다.

> 약 80%의 CPU burst가 하나의 time quantum 안에 끝날 수 있도록 설정한다.

현대 시스템의 quantum은 일반적으로 수십 밀리초 범위이며, 문맥 교환 시간은 이보다 훨씬 짧다.

---

## 평가

### 장점

- 모든 프로세스가 주기적으로 CPU를 받는다.
- 대화형 시스템의 응답성이 좋다.
- 특정 프로세스의 장기 독점을 방지한다.

### 단점

- Quantum이 작으면 문맥 교환 오버헤드가 커진다.
- Quantum이 크면 FCFS와 비슷해진다.
- 평균 turnaround time이 항상 최소인 것은 아니다.

---

# 5.3.4 Priority Scheduling

## 개념

각 프로세스에 우선순위를 부여하고, 가장 높은 우선순위의 프로세스에 CPU를 할당한다.

```text
P1: priority 3
P2: priority 1
P3: priority 4

숫자가 작을수록 높은 우선순위라면
P2 → P1 → P3
```

주의할 점은 운영체제마다 숫자의 방향이 다르다는 것이다.

```text
어떤 시스템: 0이 최고 우선순위
다른 시스템: 큰 숫자가 최고 우선순위
```

따라서 숫자 자체보다 **higher priority / lower priority**로 이해해야 한다.

---

## SJF와의 관계

SJF는 Priority Scheduling의 특수한 형태다.

다음 CPU burst가 짧을수록 높은 우선순위를 부여하면 SJF가 된다.

```text
Priority ∝ 1 / 예상 CPU burst
```

---

## 내부 우선순위

운영체제가 측정 가능한 시스템 정보를 이용해 결정한다.

예:

- CPU 사용 시간
- 메모리 요구량
- 열린 파일 수
- I/O 비율
- 평균 CPU burst

---

## 외부 우선순위

운영체제 외부의 정책이나 사용자에 의해 결정된다.

예:

- 프로세스의 중요도
- 유료 사용자 여부
- 부서 정책
- 작업 마감 시간
- 사용자가 지정한 중요도

---

## 선점형과 비선점형

### 비선점 Priority Scheduling

높은 우선순위 프로세스가 도착해도 현재 프로세스가 종료하거나 대기할 때까지 기다린다.

### 선점형 Priority Scheduling

더 높은 우선순위 프로세스가 도착하면 현재 실행 프로세스를 즉시 선점한다.

```text
낮은 우선순위 P1 실행
      ↓
높은 우선순위 P2 도착
      ↓
P1 Ready 이동
P2 실행
```

---

## Starvation

낮은 우선순위 프로세스가 무기한 실행되지 못하는 현상이다.

```text
낮은 우선순위 P1 대기
→ 높은 우선순위 작업 계속 도착
→ P1이 계속 밀림
```

논리적으로는 Ready 상태지만 CPU를 사실상 영원히 받지 못할 수 있다.

---

## Aging

Starvation을 방지하기 위해 오래 기다린 프로세스의 우선순위를 점차 높이는 방식이다.

```text
처음 priority = 10
오래 대기 → 9
더 오래 대기 → 8
...
결국 실행 가능
```

---

## Priority Scheduling + Round-Robin

우선순위가 서로 다르면 높은 우선순위부터 실행하고, 같은 우선순위끼리는 Round-Robin을 사용할 수 있다.

```text
Priority 1: P2, P3 → RR
Priority 2: P1, P5 → RR
Priority 3: P4
```

현대 운영체제에서 자주 사용하는 조합이다.

---

# 5.3.5 Multilevel Queue Scheduling

## 개념

모든 프로세스를 하나의 Ready Queue에 넣지 않고, 우선순위나 프로세스 성격에 따라 여러 Queue로 분리한다.

```text
높은 우선순위
┌─────────────────┐
│ Real-time Queue │
├─────────────────┤
│ System Queue    │
├─────────────────┤
│ Interactive     │
├─────────────────┤
│ Batch Queue     │
└─────────────────┘
낮은 우선순위
```

프로세스는 일반적으로 처음 배정받은 Queue에 계속 머문다.

---

## Queue별 알고리즘

각 Queue에 서로 다른 스케줄링 알고리즘을 적용할 수 있다.

```text
Foreground / Interactive Queue
→ Round-Robin

Background / Batch Queue
→ FCFS
```

대화형 프로세스는 응답 시간이 중요하고, 배치 프로세스는 처리량이 중요할 수 있기 때문이다.

---

## Queue 사이의 스케줄링

### 고정 우선순위 선점 방식

상위 Queue가 비어 있을 때만 하위 Queue가 실행된다.

```text
1. Real-time
2. System
3. Interactive
4. Batch
```

Batch 프로세스가 실행 중일 때 Interactive 프로세스가 도착하면 Batch 프로세스를 선점한다.

문제는 상위 Queue에 작업이 계속 존재하면 하위 Queue가 Starvation에 빠질 수 있다는 것이다.

---

### Queue별 CPU 시간 배분

CPU 시간을 Queue마다 일정 비율로 나눌 수도 있다.

예:

```text
Foreground Queue: CPU 80%
→ 내부에서는 RR

Background Queue: CPU 20%
→ 내부에서는 FCFS
```

이 방식은 낮은 우선순위 Queue도 최소한의 CPU 시간을 보장받을 수 있다.

---

## 특징

### 장점

- 프로세스 유형별로 다른 정책을 적용할 수 있다.
- 우선순위 Queue를 빠르게 선택할 수 있다.
- 구조가 명확하다.

### 단점

- 프로세스가 Queue 사이를 이동하지 못하면 유연성이 낮다.
- 잘못 분류된 프로세스가 계속 부적절한 정책을 적용받는다.
- 낮은 우선순위 Queue에 Starvation이 발생할 수 있다.

---

# 5.3.6 Multilevel Feedback Queue Scheduling

## Multilevel Queue와의 차이

Multilevel Queue에서는 프로세스가 Queue에 고정된다.

```text
Interactive Queue에 배치
→ 실행이 끝날 때까지 Interactive Queue
```

Multilevel Feedback Queue에서는 프로세스가 실행 특성에 따라 Queue 사이를 이동할 수 있다.

```text
짧게 CPU 사용
→ 높은 우선순위 유지

CPU를 오래 사용
→ 낮은 우선순위로 이동

너무 오래 대기
→ 높은 우선순위로 승격
```

---

## 필요한 이유

운영체제는 프로세스가 CPU-bound인지 I/O-bound인지 처음부터 정확히 알기 어렵다.

따라서 프로세스의 실제 행동을 관찰하여 우선순위를 조정한다.

- 짧은 CPU burst를 반복하면 대화형 또는 I/O-bound일 가능성이 높다.
- Quantum을 모두 사용하면 CPU-bound일 가능성이 높다.

---

## 교재의 3단계 Queue 예시

```text
Queue 0: RR, quantum = 8ms
Queue 1: RR, quantum = 16ms
Queue 2: FCFS
```

우선순위는 다음과 같다.

```text
Queue 0 > Queue 1 > Queue 2
```

---

## 동작

### 새로운 프로세스

모든 새 프로세스는 Queue 0에 들어간다.

```text
New Process → Queue 0
```

### Queue 0

8ms 안에 CPU burst가 끝나면 빠르게 처리된다.

8ms를 모두 사용하고도 끝나지 않으면 Queue 1로 강등된다.

```text
Queue 0에서 8ms 모두 사용
→ Queue 1로 이동
```

### Queue 1

16ms를 추가로 사용한다.

끝나지 않으면 Queue 2로 강등된다.

```text
Queue 1에서 16ms 모두 사용
→ Queue 2로 이동
```

### Queue 2

FCFS 방식으로 실행된다.

Queue 0과 Queue 1이 모두 비어 있을 때만 실행할 수 있다.

---

## 실행 시간에 따른 결과

### 8ms 이하

```text
Queue 0에서 종료
```

가장 빠르게 처리된다.

### 8ms 초과, 24ms 이하

```text
Queue 0에서 8ms
+ Queue 1에서 최대 16ms
```

비교적 빠르게 처리된다.

### 24ms 초과

```text
Queue 0 → Queue 1 → Queue 2
```

긴 CPU-bound 프로세스로 판단되어 낮은 Queue로 내려간다.

---

## Aging 적용

Queue 2에 있는 프로세스가 너무 오래 기다리면 Queue 1이나 Queue 0으로 승격할 수 있다.

이 방식으로 Starvation을 방지한다.

---

## 정의에 필요한 매개변수

Multilevel Feedback Queue는 다음 요소로 정의된다.

1. Queue의 개수
2. 각 Queue에서 사용하는 스케줄링 알고리즘
3. 프로세스를 높은 Queue로 승격하는 조건
4. 프로세스를 낮은 Queue로 강등하는 조건
5. 새로운 프로세스가 처음 들어갈 Queue를 정하는 방법

매우 유연하고 일반적인 스케줄링 방식이지만, 적절한 Queue 수와 quantum, 승격·강등 조건을 정하기 어렵다는 단점이 있다.

---

# 5.4 Thread Scheduling

## 실제 스케줄링 대상

전통적인 설명에서는 운영체제가 프로세스를 스케줄링한다고 말한다.

하지만 현대 운영체제에서 실제 커널 스케줄러가 선택하는 대상은 일반적으로 **커널 스레드**다.

```text
Process
├─ Kernel Thread 1
├─ Kernel Thread 2
└─ Kernel Thread 3

Kernel Scheduler
→ Kernel Thread 중 하나 선택
→ CPU Core에 배치
```

사용자 스레드는 스레드 라이브러리가 관리하며, CPU에서 실행되려면 결국 커널 스레드 또는 LWP에 연결되어야 한다.

```text
User Thread
    ↓
LWP 또는 Kernel Thread
    ↓
CPU Core
```

---

# 5.4.1 Contention Scope

**Contention Scope**는 스레드가 CPU를 얻기 위해 누구와 경쟁하는지를 나타낸다.

두 종류가 있다.

```text
PCS: 같은 프로세스 내부의 사용자 스레드끼리 경쟁
SCS: 시스템 전체의 커널 스레드끼리 경쟁
```

---

## Process-Contention Scope: PCS

### 개념

같은 프로세스에 속한 사용자 스레드들이 사용 가능한 LWP를 놓고 경쟁한다.

```text
Process A

UT1 ─┐
UT2 ─┼─→ 사용 가능한 LWP
UT3 ─┘
```

경쟁 범위가 하나의 프로세스 내부이므로 **Process-Contention Scope**라고 한다.

---

### 적용 모델

PCS는 다음 모델에서 나타날 수 있다.

- Many-to-One
- Many-to-Many

스레드 라이브러리가 어떤 사용자 스레드를 LWP에 연결할지 선택한다.

중요한 점은 LWP에 연결되었다고 곧바로 CPU에서 실행되는 것은 아니라는 것이다.

```text
1단계: Thread Library
User Thread → LWP 선택

2단계: Kernel Scheduler
LWP의 Kernel Thread → CPU Core 선택
```

즉, 두 단계의 스케줄링이 존재할 수 있다.

---

### PCS의 우선순위

PCS는 일반적으로 사용자 스레드의 우선순위를 기준으로 한다.

- 프로그래머가 사용자 스레드의 우선순위를 설정한다.
- Thread Library가 가장 높은 우선순위의 Runnable Thread를 선택한다.
- 라이브러리가 우선순위를 자동 조정하지 않는 경우가 많다.

높은 우선순위 스레드가 준비되면 현재 사용자 스레드를 선점할 수 있다.

다만 **같은 우선순위 스레드 사이의 time slicing이 반드시 보장되는 것은 아니다.**

---

## System-Contention Scope: SCS

### 개념

시스템 전체의 커널 스레드들이 CPU 코어를 얻기 위해 경쟁한다.

```text
Process A: KT1, KT2
Process B: KT3
Process C: KT4, KT5

          ↓ 모두 경쟁

        CPU Cores
```

운영체제의 커널 스케줄러가 담당한다.

---

### 적용 모델

One-to-One 모델을 사용하는 Windows와 Linux는 기본적으로 SCS만 사용한다.

```text
User Thread 1 ↔ Kernel Thread 1
User Thread 2 ↔ Kernel Thread 2
User Thread 3 ↔ Kernel Thread 3

모든 Kernel Thread가 시스템 전체에서 경쟁
```

---

## PCS와 SCS 비교

| 구분          | PCS                       | SCS                     |
| ------------- | ------------------------- | ----------------------- |
| 경쟁 범위     | 같은 프로세스 내부        | 시스템 전체             |
| 스케줄링 주체 | Thread Library            | 운영체제 커널           |
| 선택 대상     | User Thread               | Kernel Thread           |
| 경쟁 자원     | 사용 가능한 LWP           | 실제 CPU Core           |
| 주요 모델     | Many-to-One, Many-to-Many | One-to-One 및 커널 단계 |
| Windows/Linux | 일반적으로 사용하지 않음  | 사용                    |

교재에서 강조하는 핵심은 다음과 같다.

```text
PCS가 User Thread를 LWP에 연결
≠ CPU에서 바로 실행

SCS가 해당 Kernel Thread를 CPU Core에 배치해야
실제 실행 가능
```

---

# 5.4.2 Pthread Scheduling

POSIX Pthreads는 스레드를 생성할 때 Contention Scope를 지정할 수 있는 API를 정의한다.

---

## Scope 값

### `PTHREAD_SCOPE_PROCESS`

PCS 방식으로 스케줄링한다.

```c
PTHREAD_SCOPE_PROCESS
```

Many-to-Many 시스템에서는 사용자 스레드를 사용 가능한 LWP에 스케줄링한다.

---

### `PTHREAD_SCOPE_SYSTEM`

SCS 방식으로 스케줄링한다.

```c
PTHREAD_SCOPE_SYSTEM
```

시스템 전체의 커널 스레드와 CPU를 두고 경쟁한다.

Many-to-Many 시스템에서 이를 선택하면 사용자 스레드마다 LWP를 연결하여 사실상 One-to-One과 유사하게 동작할 수 있다.

---

## Scope 설정 함수

```c
int pthread_attr_setscope(
    pthread_attr_t *attr,
    int scope
);
```

예:

```c
pthread_attr_t attr;

pthread_attr_init(&attr);

pthread_attr_setscope(
    &attr,
    PTHREAD_SCOPE_SYSTEM
);
```

설정된 `attr`을 `pthread_create()`에 전달하면 해당 Scope가 적용된다.

```c
pthread_create(
    &tid,
    &attr,
    runner,
    NULL
);
```

---

## Scope 조회 함수

```c
int pthread_attr_getscope(
    pthread_attr_t *attr,
    int *scope
);
```

예:

```c
int scope;

pthread_attr_getscope(&attr, &scope);

if (scope == PTHREAD_SCOPE_SYSTEM) {
    printf("PTHREAD_SCOPE_SYSTEM\n");
} else if (scope == PTHREAD_SCOPE_PROCESS) {
    printf("PTHREAD_SCOPE_PROCESS\n");
}
```

두 함수 모두 오류가 발생하면 0이 아닌 값을 반환한다.

---

## 운영체제 지원 차이

POSIX 표준이 두 Scope를 정의하더라도 운영체제가 둘 다 지원한다는 의미는 아니다.

교재 기준으로 Linux와 macOS는 다음 방식만 허용한다.

```text
PTHREAD_SCOPE_SYSTEM
```

이는 두 운영체제가 실질적으로 One-to-One 스레드 모델을 사용하고, 커널 스케줄러가 커널 스레드를 시스템 전체 범위에서 스케줄링하기 때문이다.

---

# 5.1~5.4 핵심 요약

## CPU 스케줄링 흐름

```text
프로세스 또는 커널 스레드 Ready
        ↓
CPU Scheduler가 실행 대상 선택
        ↓
Dispatcher가 Context Switch 수행
        ↓
CPU Core에서 실행
```

---

## 선점 여부

```text
Nonpreemptive
→ 종료하거나 대기할 때까지 CPU 유지

Preemptive
→ 타이머, 우선순위 등에 따라 CPU 강제 회수 가능
```

---

## 알고리즘 비교

| 알고리즘                  | 선택 기준                   | 선점 여부        | 핵심 문제            |
| ------------------------- | --------------------------- | ---------------- | -------------------- |
| FCFS                      | 먼저 도착                   | 비선점           | Convoy Effect        |
| SJF                       | 가장 짧은 CPU burst         | 비선점           | 미래 burst 예측 필요 |
| SRTF                      | 가장 짧은 남은 시간         | 선점             | 긴 작업 Starvation   |
| RR                        | 일정 Time Quantum           | 선점             | Quantum 설정         |
| Priority                  | 가장 높은 우선순위          | 둘 다 가능       | Starvation           |
| Multilevel Queue          | 고정 Queue와 우선순위       | 정책에 따라 다름 | Queue 이동 불가      |
| Multilevel Feedback Queue | 실행 특성에 따라 Queue 이동 | 선점             | 설정이 복잡함        |

---

# 면접 포인트

## 1. CPU Scheduler와 Dispatcher의 차이는?

CPU Scheduler는 Ready Queue에서 **다음 실행 대상을 선택**한다. Dispatcher는 선택된 대상에게 실제로 CPU를 넘기기 위해 **문맥 교환, 사용자 모드 전환, 실행 위치 복원**을 수행한다.

---

## 2. Turnaround Time과 Response Time의 차이는?

Turnaround Time은 요청이 들어온 시점부터 작업이 완전히 종료될 때까지의 시간이다. Response Time은 요청 이후 첫 번째 응답이 나타날 때까지의 시간이다. 대화형 서비스에서는 Response Time이 특히 중요하다.

---

## 3. SJF가 평균 대기 시간을 최소화하는데 왜 일반적으로 그대로 사용하기 어려운가?

다음 CPU burst의 길이를 미리 정확히 알 수 없기 때문이다. 실제 시스템에서는 과거 CPU burst를 지수 평균하여 다음 burst를 예측한다.

---

## 4. Round-Robin의 Quantum이 너무 작거나 크면?

Quantum이 너무 작으면 문맥 교환이 지나치게 증가한다. 너무 크면 선점이 거의 발생하지 않아 FCFS와 비슷해진다.

---

## 5. Priority Scheduling의 Starvation 해결 방법은?

오래 기다린 프로세스의 우선순위를 점진적으로 높이는 **Aging**을 적용한다.

---

## 6. Multilevel Queue와 Multilevel Feedback Queue의 차이는?

Multilevel Queue에서는 프로세스가 처음 배정된 Queue에 고정된다. Multilevel Feedback Queue에서는 CPU 사용 패턴과 대기 시간에 따라 프로세스가 Queue 사이를 이동한다.

---

## 7. 현대 운영체제가 실제로 스케줄링하는 대상은?

현대 운영체제에서는 일반적으로 프로세스 자체가 아니라 **커널 스레드**를 CPU에 스케줄링한다. One-to-One 모델을 사용하는 Linux와 Windows에서는 각 사용자 스레드에 대응하는 커널 스레드가 시스템 전체 범위에서 경쟁한다.
