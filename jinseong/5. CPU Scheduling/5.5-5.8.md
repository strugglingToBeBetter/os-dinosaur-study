# 5.5 Multi-Processor Scheduling

지금까지는 CPU 코어 하나를 전제로 스케줄링을 살펴봤다.

멀티프로세서 시스템에서는 여러 스레드를 실제로 동시에 실행할 수 있다.

```text
Single Core

T1 → T2 → T3 → T1 ...
     동시성


Multi Core

Core 0 → T1
Core 1 → T2
Core 2 → T3
     병렬성
```

문제는 CPU가 여러 개가 되면서 단순히 Ready Queue에서 하나를 고르는 것만으로 끝나지 않는다는 것이다.

이제 운영체제는 다음 문제까지 고려해야 한다.

- 어느 CPU에서 실행할 것인가?
- CPU별 부하가 균등한가?
- 실행하던 CPU를 바꿔도 되는가?
- 캐시를 어떻게 활용할 것인가?
- NUMA에서는 어느 CPU의 메모리에 둘 것인가?
- CPU 코어들의 성능이 서로 다르면 어디에 배치할 것인가?

교재에서 현대의 multiprocessor는 다음 구조까지 포함한다.

```text
Multicore CPU
Multithreaded Core
NUMA System
Heterogeneous Multiprocessing
```

---

# 5.5.1 Approaches to Multiple-Processor Scheduling

멀티프로세서 스케줄링에는 크게 두 접근 방식이 있다.

## Asymmetric Multiprocessing

하나의 프로세서가 스케줄링을 전담한다.

```text
CPU 0
└─ Scheduling
└─ I/O 처리
└─ 시스템 작업

CPU 1
└─ User Code

CPU 2
└─ User Code
```

즉, **Master Server 역할의 CPU 하나**가 전체 시스템을 관리하고 다른 CPU들은 사용자 코드를 주로 실행한다.

### 이유

모든 CPU가 동시에 운영체제의 공유 자료구조를 수정하면 동기화 문제가 발생한다.

한 CPU만 관리하게 하면:

```text
Ready Queue
Process Table
Scheduling Data

       ↑
Master CPU 하나만 접근
```

구현이 훨씬 단순해진다.

### 단점

Master CPU에 작업이 몰린다.

```text
CPU 1 ─┐
CPU 2 ─┼→ Master CPU에 요청 집중
CPU 3 ─┘
```

따라서 Master CPU가 **병목(Bottleneck)** 이 될 수 있다.

---

# Symmetric Multiprocessing, SMP

현대 운영체제가 일반적으로 사용하는 방식이다.

각 프로세서가 스스로 스케줄링한다.

```text
CPU 0 → Scheduler
CPU 1 → Scheduler
CPU 2 → Scheduler
CPU 3 → Scheduler
```

이때 Ready Queue를 구성하는 두 가지 방법이 있다.

---

## 방법 1. Common Ready Queue

모든 CPU가 하나의 Ready Queue를 공유한다.

```text
                Ready Queue
        T1 T2 T3 T4 T5 T6
               ↓ ↓ ↓

CPU 0        CPU 1        CPU 2
```

장점은 단순하다.

CPU 하나가 비면 Queue에서 작업 하나를 가져오면 된다.

하지만 동시에 두 CPU가 Queue에 접근하면 문제가 발생한다.

```text
CPU 0 → T1 선택
CPU 1 → T1 선택

→ 같은 스레드를 두 CPU가 선택하는 Race Condition
```

이를 막으려면 Lock이 필요하다.

```text
lock(readyQueue)

스레드 선택

unlock(readyQueue)
```

그런데 CPU가 많아질수록 Ready Queue Lock 경쟁이 심해진다.

```text
CPU0 ─┐
CPU1 ─┤
CPU2 ─┼→ Ready Queue Lock
CPU3 ─┘
```

결국 Queue 자체가 병목이 될 수 있다.

---

## 방법 2. Per-Processor Ready Queue

CPU마다 자신의 Ready Queue를 가진다.

```text
CPU 0
└─ Queue: T1 T4 T7

CPU 1
└─ Queue: T2 T5

CPU 2
└─ Queue: T3 T6
```

공유 Queue에 접근할 필요가 줄어들어 확장성이 좋아진다.

그래서 SMP 시스템에서는 이 방식이 일반적이다.

또 하나의 큰 장점은 **Processor Affinity**를 자연스럽게 얻을 수 있다는 것이다.

다만 새로운 문제가 생긴다.

```text
CPU 0 Queue: T1 T2 T3 T4 T5
CPU 1 Queue:
CPU 2 Queue: T6
```

CPU 1은 놀고 있는데 CPU 0은 과부하다.

그래서 **Load Balancing**이 필요하다.

---

# 5.5.2 Multicore Processors

## Multicore

여러 개의 CPU 코어를 하나의 물리적 칩에 넣는다.

```text
Physical Processor

┌───────────────┐
│ Core 0        │
│ Core 1        │
│ Core 2        │
│ Core 3        │
└───────────────┘
```

각 코어는 자신의 레지스터 등의 architectural state를 가지므로 운영체제 입장에서는 별도의 CPU처럼 보인다.

멀티코어는 여러 개의 독립된 CPU 칩을 사용하는 것보다 일반적으로:

- 통신이 빠르고
- 전력 소비가 낮으며
- 병렬 처리가 가능하다.

그런데 여기서 새로운 문제가 등장한다.

---

## Memory Stall

CPU는 매우 빠른데 메모리는 상대적으로 느리다.

CPU가 메모리에 있는 데이터를 요청하면 데이터를 기다리는 시간이 발생할 수 있다.

```text
CPU

계산 → 메모리 기다림 → 계산 → 메모리 기다림
 C          M          C          M
```

이를 **Memory Stall**이라고 한다.

캐시 미스가 발생해도 memory stall이 발생할 수 있다.

즉:

```text
CPU는 계산할 능력이 있는데
↓
메모리 데이터가 아직 안 옴
↓
CPU 자원이 놀게 됨
```

교재의 예에서는 CPU가 상당한 시간을 메모리를 기다리며 소비할 수 있음을 보여준다.

---

# Hardware Thread

이 낭비를 줄이기 위해 하나의 코어에 여러 **Hardware Thread**를 둔다.

```text
Core 0

Hardware Thread 0
Hardware Thread 1
```

Thread 0이 메모리를 기다리는 동안:

```text
Thread 0
CPU → Memory Stall

           ↓

Thread 1 실행
```

즉 코어 자체가 쉬는 시간을 줄인다.

운영체제에서는 각각의 Hardware Thread가:

- Instruction Pointer
- Register Set

등 자신의 architectural state를 가지므로 **각각의 Logical CPU처럼 보인다.**

---

# Chip Multithreading, CMT

예를 들어:

```text
Physical CPU

Core 0 → HW Thread 0, 1
Core 1 → HW Thread 2, 3
Core 2 → HW Thread 4, 5
Core 3 → HW Thread 6, 7
```

운영체제가 보는 모습:

```text
CPU0 CPU1 CPU2 CPU3 CPU4 CPU5 CPU6 CPU7
```

따라서:

> 물리 코어가 4개라고 해서 운영체제가 반드시 CPU 4개만 보는 것은 아니다.

Hardware Thread가 코어당 2개라면 **Logical CPU 8개**로 보일 수 있다.

Intel에서는 이 방식을 **Hyper-Threading**, 또는 **SMT(Simultaneous Multithreading)** 라고 부른다.

---

## Coarse-Grained Multithreading

스레드 하나를 계속 실행하다가 **큰 지연이 발생하면** 다른 Hardware Thread로 바꾼다.

```text
Thread A 실행
↓
Memory Stall 발생
↓
Thread B로 전환
```

문제는 전환할 때 instruction pipeline을 비워야 할 수 있다는 것이다.

```text
Pipeline Flush
→ 새로운 Thread 명령어 채우기
```

따라서 전환 비용이 크다.

---

## Fine-Grained Multithreading

보다 짧은 단위로 Hardware Thread를 바꾼다.

보통 instruction boundary 수준으로 교체할 수 있다.

```text
T1 instruction
T2 instruction
T1 instruction
T2 instruction
...
```

Hardware 자체가 빠른 Thread Switching을 지원하므로 전환 비용이 작다.

---

# 두 단계의 Scheduling

Multithreaded Core에서는 스케줄링이 한 번이 아니라 **두 단계**로 존재한다.

### Level 1 — OS Scheduler

운영체제가 Software Thread를 Logical CPU에 배치한다.

```text
Software Thread
      ↓
OS Scheduler
      ↓
Hardware Thread(Logical CPU)
```

### Level 2 — Core의 Hardware Scheduler

하나의 Core에 여러 Hardware Thread가 있으므로 코어 자체가 어떤 Hardware Thread를 실행할지 선택한다.

```text
HW Thread 0 ─┐
             ├→ Core
HW Thread 1 ─┘
```

교재는 Core의 Hardware Thread를 선택하는 예로:

- Round-Robin
- Hardware Thread의 urgency 값을 비교

등을 제시한다.

---

## OS도 Hardware 구조를 알아야 한다

예를 들어:

```text
Core 0
├─ Logical CPU 0
└─ Logical CPU 1

Core 1
├─ Logical CPU 2
└─ Logical CPU 3
```

실행할 Software Thread가 두 개 있다고 하자.

### 좋지 않은 배치

```text
Core 0
├─ Thread A
└─ Thread B

Core 1
└─ 비어 있음
```

A와 B가 같은 Core의 자원을 공유한다.

### 더 좋은 배치

```text
Core 0 → Thread A
Core 1 → Thread B
```

따라서 현대 스케줄러는 단순히 "Logical CPU가 비었는가?"만 보는 것이 아니라 **Logical CPU끼리 어떤 물리 자원을 공유하는지도 고려**할 수 있다.

---

# 5.5.3 Load Balancing

SMP에서는 CPU별 작업량이 달라지는 문제가 생긴다.

```text
CPU0: T1 T2 T3 T4 T5
CPU1:
CPU2: T6
CPU3: T7 T8
```

CPU1이 놀고 있으므로 자원이 낭비된다.

이를 해결하는 것이 **Load Balancing**이다.

```text
Before

CPU0: 5개
CPU1: 0개
CPU2: 1개

↓ Load Balancing

CPU0: 2개
CPU1: 2개
CPU2: 2개
```

---

## Load Balancing이 필요한 경우

CPU별 **Private Ready Queue**가 있을 때 특히 필요하다.

반대로 Common Ready Queue라면:

```text
CPU가 놀게 됨
↓
공용 Queue에서 하나 가져옴
```

이므로 별도의 Load Balancing 필요성이 작다.

---

## Push Migration

특정 작업이 주기적으로 CPU들의 부하를 확인한다.

```text
Load Balancer
   ↓
CPU0: 90%
CPU1: 10%

   ↓

CPU0의 Thread를 CPU1으로 Push
```

즉:

> 바쁜 CPU의 작업을 다른 CPU로 **밀어낸다.**

---

## Pull Migration

Idle CPU가 스스로 다른 CPU의 작업을 가져온다.

```text
CPU1 Idle
   ↓
CPU0 Queue 확인
   ↓
Thread 하나 Pull
```

즉:

> 한가한 CPU가 바쁜 CPU의 작업을 **당겨온다.**

Push와 Pull은 동시에 사용할 수도 있다.

교재에서는 Linux CFS와 FreeBSD ULE가 둘을 함께 사용할 수 있다고 설명한다.

---

## 그런데 "Load가 같다"는 게 뭘까?

단순히 Thread 개수만 같으면 될까?

```text
CPU0:
고우선순위 Thread 3개

CPU1:
저우선순위 Thread 3개
```

Thread 수는 같지만 실제 부하는 다를 수 있다.

또는:

```text
CPU0:
CPU-bound 2개

CPU1:
I/O-bound 2개
```

역시 개수는 같아도 CPU 사용량은 다르다.

따라서 부하를 무엇으로 정의할지 자체가 스케줄링 문제다.

---

# 5.5.4 Processor Affinity

어떤 Thread가 CPU0에서 오래 실행되었다고 하자.

Thread가 자주 사용하는 데이터가 CPU0의 Cache에 저장된다.

```text
CPU0 Cache

A
B
C
D

↑ Thread T가 자주 사용
```

이 상태를 **Warm Cache**라고 볼 수 있다.

그런데 Load Balancing 때문에 T가 CPU1으로 옮겨가면:

```text
CPU0 → CPU1

CPU1 Cache에는 T의 데이터가 없음
↓
Cache 다시 채워야 함
```

성능 손실이 발생한다.

그래서 운영체제는 가능하면 Thread를 **전에 실행되던 CPU에 계속 배치하려고 한다.**

이를 **Processor Affinity**라고 한다.

---

## Soft Affinity

운영체제가 가능하면 같은 CPU에 유지하지만 **보장하지는 않는다.**

```text
가능하면 CPU0 유지

하지만 Load Balancing이 필요하면
CPU0 → CPU1 이동 가능
```

---

## Hard Affinity

프로세스/스레드가 실행될 수 있는 CPU를 직접 제한한다.

예:

```text
Thread T
→ CPU {0, 2}에서만 실행 가능
```

Linux는 `sched_setaffinity()`를 통해 이런 기능을 제공한다고 교재가 설명한다.

---

# NUMA와 Processor Affinity

NUMA에서는 CPU마다 가까운 메모리가 존재한다.

```text
CPU0 ─── Local Memory 0
 │
 │ 느림
 ↓
Memory 1 ─── CPU1
```

CPU0이 자신의 Local Memory에 접근하면 빠르다.

반면 다른 CPU의 Memory에 접근하려면 interconnect를 지나야 해서 느리다.

따라서 이상적인 배치는:

```text
Thread T → CPU0에서 실행
           ↓
T 데이터 → CPU0에 가까운 Memory
```

이다.

이를 위해:

```text
CPU Scheduler
+
Memory Placement
```

가 함께 NUMA 구조를 고려해야 한다.

---

# Load Balancing vs Processor Affinity

여기서 서로 충돌하는 두 목표가 등장한다.

### Load Balancing

```text
CPU가 몰리면
→ Thread를 다른 CPU로 이동시키고 싶음
```

### Processor Affinity

```text
Cache와 NUMA 때문에
→ Thread를 같은 CPU에 유지하고 싶음
```

즉:

> **Load Balancing은 Thread를 움직이고 싶어 하고, Processor Affinity는 Thread를 움직이지 않고 싶어 한다.**

현대 CPU Scheduling이 복잡한 가장 중요한 이유 중 하나다.

---

# 5.5.5 Heterogeneous Multiprocessing

지금까지는 모든 Core가 동일한 성능을 가진다고 가정했다.

하지만 모바일 시스템에서는 서로 다른 성능의 Core를 하나의 CPU에 넣기도 한다.

이를 **Heterogeneous Multiprocessing(HMP)** 이라고 한다.

중요한 점:

> 앞에서 배운 Asymmetric Multiprocessing과 다른 개념이다.

Asymmetric Multiprocessing은 역할이 다르다.

```text
Master CPU
Slave CPU
```

HMP는 모든 Core에서 시스템/사용자 작업을 실행할 수 있지만 **Core의 성능과 전력 특성이 다르다.**

---

## ARM big.LITTLE

대표적인 예다.

```text
big Core
→ 빠름
→ 전력 소비 큼

LITTLE Core
→ 느림
→ 전력 소비 작음
```

따라서 Scheduler가 작업 특성에 따라 Core를 선택한다.

### Background 작업

```text
오래 실행
+ 높은 성능 필요 없음

→ LITTLE Core
```

### Interactive 작업

```text
짧은 시간
+ 높은 성능 필요

→ big Core
```

### Power Saving Mode

```text
big Core OFF
↓
LITTLE Core 위주 실행
```

이렇게 성능과 배터리 사용량 사이의 균형을 맞춘다.

---

# 5.6 Real-Time CPU Scheduling

일반 스케줄러의 목표는:

```text
CPU 이용률
평균 대기 시간
응답 시간
처리량
```

등을 좋게 만드는 것이다.

하지만 Real-Time 시스템에서는 완전히 다른 기준이 중요하다.

> **정해진 시간 안에 작업을 끝냈는가?**

---

## Soft Real-Time

중요한 Real-Time Process에 우선권을 준다.

하지만 Deadline을 반드시 보장하지 않는다.

```text
Real-Time Task
→ 일반 Task보다 우선

하지만
"반드시 5ms 안에 실행" 보장은 없음
```

---

## Hard Real-Time

Deadline을 반드시 만족해야 한다.

```text
Deadline = 10ms

9ms 완료 → 성공
10ms 완료 → 성공
11ms 완료 → 실패
```

Hard Real-Time에서는:

> Deadline 이후 완료한 것은 **완료하지 못한 것과 동일하게 취급**한다.

예:

- 자동차 제어
- 산업용 제어 장치
- 안전 관련 시스템

---

# 5.6.1 Minimizing Latency

Real-Time 시스템은 Event Driven인 경우가 많다.

```text
Event 발생
↓
OS가 인식
↓
Real-Time Task 실행
↓
Event 처리
```

Event 발생부터 실제 서비스를 시작하기까지 걸리는 시간이 중요하다.

이를 **Event Latency**라고 한다.

```text
Event 발생 ─────────────→ 처리 시작
          Event Latency
```

Event마다 허용 가능한 Latency가 다르다.

교재는 예를 들어 ABS와 같은 시스템은 수 ms 수준의 매우 빠른 반응을 요구하는 반면, 다른 임베디드 장치는 더 긴 지연을 허용할 수 있다고 설명한다.

Real-Time 성능에는 특히 두 Latency가 중요하다.

```text
1. Interrupt Latency
2. Dispatch Latency
```

---

# Interrupt Latency

Interrupt가 CPU에 도착한 순간부터 **Interrupt Service Routine이 시작될 때까지** 걸리는 시간이다.

```text
Interrupt 발생
      ↓
현재 Instruction 완료
      ↓
Interrupt 종류 판단
      ↓
현재 Process 상태 저장
      ↓
ISR 실행

<---- Interrupt Latency ---->
```

Hard Real-Time에서는 단순히 평균적으로 빨라서는 부족하다.

```text
평균 2ms
최악 100ms
```

이런 시스템은 Hard Real-Time에 부적합할 수 있다.

따라서 Interrupt Latency에 **상한(Bound)** 이 있어야 한다.

---

## Interrupt Disable 문제

Kernel이 중요한 자료구조를 수정하는 동안 Interrupt를 비활성화할 수 있다.

```text
Interrupt Disable
↓
Critical Kernel Operation
↓
Interrupt Enable
```

이 구간이 길면 들어온 Interrupt를 처리하지 못한다.

따라서 Real-Time OS에서는 Interrupt Disable 구간을 매우 짧게 유지해야 한다.

---

# Dispatch Latency

Dispatcher가 현재 Process를 중단하고 **다른 Process 실행을 시작하기까지의 시간**이다.

```text
현재 Process
      ↓
Preemption
      ↓
Context Switch
      ↓
Real-Time Process 실행

<---- Dispatch Latency ---->
```

Hard Real-Time 시스템에서는 이 시간도 매우 작고 예측 가능해야 한다.

교재는 Dispatch Latency를 크게 두 단계로 설명한다.

```text
Conflict Phase
     ↓
Dispatch Phase
```

Conflict Phase에는:

1. Kernel에서 실행 중인 프로세스를 선점하는 것
2. 낮은 우선순위 프로세스가 높은 우선순위 프로세스가 필요로 하는 자원을 해제하는 것

이 포함된다.

이후 Dispatcher가 높은 우선순위 Process를 CPU에 올린다.

그래서 Real-Time OS에서는 **Preemptive Kernel**이 중요하다.

---

# 5.6.2 Priority-Based Scheduling

Real-Time Task가 Ready가 되는 순간 빠르게 실행시키려면 기본적으로:

> **Preemptive Priority Scheduling**

이 필요하다.

```text
Normal Task 실행 중
        ↓
Real-Time Task Ready
        ↓
Normal Task 즉시 선점
        ↓
Real-Time Task 실행
```

Linux, Windows, Solaris 역시 Real-Time Task를 높은 Priority 영역에 둔다.

하지만 이것만으로 **Hard Real-Time을 보장할 수는 없다.**

Priority가 높다는 것은:

```text
"다른 작업보다 먼저 실행한다"
```

는 의미이지:

```text
"반드시 10ms 안에 완료한다"
```

는 것을 수학적으로 보장하지 않기 때문이다.

---

# Periodic Task

Hard Real-Time Scheduling을 설명하기 위해 교재는 주기적인 작업을 정의한다.

```text
|---- Period ----|---- Period ----|

Task             Task
실행             실행
```

Periodic Process에는 세 값이 있다.

- `t`: Processing Time
- `d`: Deadline
- `p`: Period

관계는:

[
0 \le t \le d \le p
]

이고 Task의 Rate는:

[
rate = \frac{1}{p}
]

이다.

---

## 예시

```text
Processing Time t = 20ms
Deadline d = 50ms
Period p = 50ms
```

뜻은:

> 50ms마다 작업이 생기고, CPU 작업 20ms가 필요하며 다음 주기가 시작하기 전에 끝나야 한다.

---

# Admission Control

Real-Time Process가 자신의 요구사항을 Scheduler에게 알려줄 수 있다.

```text
Task:
"50ms마다 20ms CPU가 필요합니다."
```

Scheduler가 계산한다.

```text
현재 작업들과 함께 실행 가능?
        ↓
YES → Admit
NO  → Reject
```

이를 **Admission-Control Algorithm**이라고 한다.

Hard Real-Time에서는 받아놓고 Deadline을 놓치는 것보다, 애초에 보장할 수 없는 작업을 거절하는 것이 중요하다.

---

# 5.6.3 Rate-Monotonic Scheduling

**정적 우선순위 + 선점형** Real-Time Scheduling이다.

가장 중요한 규칙:

> **Period가 짧을수록 Priority가 높다.**

왜냐하면 Period가 짧다는 것은 CPU를 더 자주 필요로 한다는 의미이기 때문이다.

```text
P1 period = 50
P2 period = 100

P1 Priority > P2 Priority
```

Rate는:

[
rate=\frac{1}{period}
]

이므로 **Rate가 높은 Task가 Priority도 높다.**

---

## 특징

Priority가 처음 결정되면 바뀌지 않는다.

```text
P1: Priority High
P2: Priority Low

→ 계속 유지
```

그래서 **Static Priority** 방식이다.

또한 같은 Periodic Process의 CPU burst는 매번 동일하다고 가정한다.

---

## 교재 예제 1

```text
P1
p1 = 50
t1 = 20

P2
p2 = 100
t2 = 35
```

CPU Utilization은:

[
U_1 = \frac{20}{50}=0.4
]

[
U_2 = \frac{35}{100}=0.35
]

따라서:

[
U=0.4+0.35=0.75
]

즉 CPU 사용률은 75%이다.

---

## 잘못된 우선순위

P2를 더 높은 우선순위로 주면:

```text
P2 먼저 35ms 실행

↓
P1 실행

P1 종료 = 55ms
```

그런데 P1의 Deadline은 50ms다.

```text
Deadline 50
Completion 55

→ Deadline Miss
```

---

## Rate-Monotonic 적용

P1의 Period가 50으로 더 짧으므로:

```text
P1 Priority > P2
```

가 된다.

```text
0 ──20       P1
20────50     P2 일부
50──70       P1
70─75        P2 남은 부분
```

둘 모두 Deadline을 만족한다.

---

# Rate-Monotonic의 Optimal 의미

Rate-Monotonic은 **Static Priority 방식 중에서 Optimal**하다.

즉:

> Rate-Monotonic으로 스케줄할 수 없는 Task Set이라면 다른 Static Priority 알고리즘으로도 스케줄할 수 없다.

그러나 모든 CPU Utilization을 사용할 수 있다는 뜻은 아니다.

---

# CPU Utilization Bound

N개의 Process에 대한 최악의 보장 가능 CPU 이용률은:

[
U \le N(2^{1/N}-1)
]

이다.

N이 커질수록 약:

[
69%
]

로 수렴한다.

예:

```text
N = 1 → 100%
N = 2 → 약 83%
N → ∞ → 약 69%
```

중요한 의미는:

> CPU 사용률이 100%보다 낮아도 Rate-Monotonic Scheduling에서 Deadline을 놓칠 수 있다.

---

## 교재의 두 번째 예

```text
P1
p1 = 50
t1 = 25

P2
p2 = 80
t2 = 35
```

CPU 이용률:

[
\frac{25}{50}+\frac{35}{80}
]

[
= 0.5 + 0.4375
= 0.9375
]

약 94%다.

CPU 자체로 보면 6% 여유가 있다.

하지만 Rate-Monotonic에서는 P2가 Deadline 80을 넘겨 85에서 끝난다.

즉:

> **CPU 여유가 존재하는 것과 Real-Time Schedule이 가능하다는 것은 같은 말이 아니다.**

---

# 5.6.4 Earliest-Deadline-First Scheduling, EDF

Rate-Monotonic과 달리 **동적 Priority**를 사용한다.

규칙은 매우 단순하다.

> Deadline이 빠른 Process가 높은 Priority를 가진다.

```text
P1 Deadline = 100
P2 Deadline = 80

→ P2 우선
```

새 Process가 Ready가 되면 Deadline을 Scheduler에게 알려준다.

Scheduler는 그때마다 Priority를 재조정한다.

---

## Rate-Monotonic과 차이

Rate-Monotonic:

```text
Period 기준
Priority 고정
```

EDF:

```text
Deadline 기준
Priority 계속 변경 가능
```

---

## 앞에서 실패했던 작업

```text
P1
p1 = 50
t1 = 25

P2
p2 = 80
t2 = 35
```

Rate-Monotonic에서는 Deadline Miss가 발생했다.

하지만 EDF는 각 시점의 다음 Deadline을 비교한다.

예를 들어:

```text
P1 next deadline = 100
P2 next deadline = 80

→ P2 계속 실행
```

따라서 동일한 Task Set을 Deadline 내에 처리할 수 있다.

---

## EDF 특징

Rate-Monotonic과 달리:

- Periodic Process일 필요가 없다.
- CPU burst 길이가 항상 동일할 필요가 없다.
- Ready가 될 때 Deadline만 Scheduler에게 알려주면 된다.

이론적으로 EDF는 최적이며 **CPU 이용률 100%까지 스케줄 가능**하다.

하지만 실제 시스템에서는:

- Context Switch
- Interrupt 처리
- Scheduler 실행

등의 오버헤드가 있으므로 실제로 100%를 사용할 수는 없다.

---

# Rate-Monotonic vs EDF

|                     | Rate-Monotonic  | EDF                     |
| ------------------- | --------------- | ----------------------- |
| Priority            | Static          | Dynamic                 |
| 기준                | Period          | Deadline                |
| 높은 Priority       | 짧은 Period     | 가까운 Deadline         |
| Periodic Task 필요  | 예              | 아니어도 됨             |
| CPU Burst 일정 가정 | 예              | 필요 없음               |
| 이론적 CPU 활용     | 제한 존재       | 최대 100% 가능          |
| 구현                | 상대적으로 단순 | Priority 관리가 더 복잡 |

---

# 5.6.5 Proportional Share Scheduling

CPU 시간을 **Share 단위로 나누는 방식**이다.

전체 Share가 `T`이고 Process가 `N` Share를 받으면:

[
CPU\ Time=\frac{N}{T}
]

만큼 보장한다.

---

## 예시

전체:

```text
T = 100 shares
```

각 Process:

```text
A = 50
B = 15
C = 20
```

CPU 시간:

```text
A → 50%
B → 15%
C → 20%
```

현재 총 할당량은:

```text
50 + 15 + 20 = 85
```

15가 남아 있다.

새 Process D가:

```text
30 Share 주세요.
```

라고 요청하면:

```text
남은 Share = 15
요구 Share = 30

→ Admission Control 거부
```

Proportional Share가 보장을 제공하려면 Admission Control과 함께 사용해야 한다.

---

# 5.6.6 POSIX Real-Time Scheduling

POSIX.1b는 Real-Time Scheduling을 위한 정책을 정의한다.

교재에서는 두 정책을 중심으로 설명한다.

```text
SCHED_FIFO
SCHED_RR
```

---

## SCHED_FIFO

Priority가 높은 Real-Time Thread를 먼저 실행한다.

같은 Priority 안에서는 FIFO 방식이다.

중요한 특징:

> 같은 Priority Thread 사이에 Time Slicing이 없다.

```text
Priority 10

T1 → T2 → T3

T1 실행
↓
종료 또는 Block할 때까지 계속 실행
```

---

## SCHED_RR

기본 구조는 SCHED_FIFO와 비슷하지만 같은 Priority Thread에 **Time Quantum**을 적용한다.

```text
T1 → T2 → T3 → T1 ...
```

즉 Round-Robin이다.

---

## SCHED_OTHER

POSIX에는 `SCHED_OTHER`도 있지만 구체적인 구현 방식은 시스템마다 다르다.

---

## POSIX API

현재 Scheduling Policy 확인:

```c
pthread_attr_getschedpolicy(&attr, &policy);
```

Policy 변경:

```c
pthread_attr_setschedpolicy(&attr, SCHED_FIFO);
```

설정 가능한 값:

```text
SCHED_FIFO
SCHED_RR
SCHED_OTHER
```

교재 Figure 5.25에서는 기본 Scheduling Policy를 가져온 뒤 `SCHED_FIFO`로 설정하고 Pthread들을 생성하는 예제를 보여준다.

# 5.7 Operating-System Examples

이제 교재는 실제 운영체제의 스케줄러를 살펴본다.

중요한 점은 여기서 "Process Scheduling"이라고 부르지만 실제 스케줄링 대상은 시스템에 따라 다르다는 것이다.

```text
Linux   → Task
Windows → Kernel Thread
Solaris → Kernel Thread
```

---

# 5.7.1 Example: Linux Scheduling

Linux Scheduler는 역사적으로 여러 번 변경되었다.

```text
초기 Linux
→ 전통적인 UNIX Scheduler

Linux 2.5
→ O(1) Scheduler

Linux 2.6.23~
→ Completely Fair Scheduler(CFS)
```

---

## O(1) Scheduler

Runnable Task 개수와 관계없이 일정한 시간에 Scheduling 결정을 할 수 있도록 설계됐다.

```text
Task 10개
Task 10,000개

→ Scheduling 선택 비용 O(1)
```

또한:

- Processor Affinity
- Load Balancing
- SMP

등을 잘 지원했다.

하지만 Desktop 환경에서 Interactive Process의 Response Time이 좋지 않은 문제가 있었다.

그래서 CFS가 도입되었다.

---

# Completely Fair Scheduler, CFS

CFS의 기본 철학은:

> 모든 Task가 CPU를 **공정한 비율로 나누어 쓰게 하자.**

기존 RR처럼 고정 Time Quantum을 직접 배정하지 않는다.

대신 각 Task가 받아야 하는 **CPU 시간의 비율**을 계산한다.

---

## nice 값

Linux CFS에서 Task의 상대적 우선순위를 표현한다.

```text
-20 ───────── 0 ───────── +19
높은 Priority               낮은 Priority
```

기본 nice는:

```text
0
```

이다.

nice 값이 낮을수록 CPU를 더 많이 배정받는다.

이름 그대로:

```text
nice 증가
→ 자신의 Priority를 낮춤
→ 다른 프로세스에게 "친절"
```

이다.

---

# Targeted Latency

CFS에서는 전통적인 고정 Quantum 대신 **Targeted Latency**를 사용한다.

의미는:

> 모든 Runnable Task가 적어도 한 번씩 CPU를 사용할 수 있게 하려는 시간 구간

예를 들어 Runnable Task가 많아지면 이 Targeted Latency도 조정될 수 있다.

---

# vruntime

CFS의 핵심이다.

각 Task마다:

```text
vruntime
```

즉 **Virtual Runtime**을 기록한다.

대략적인 의미는:

> 이 Task가 공정성 관점에서 CPU를 얼마나 사용했는가.

---

## 같은 Priority

nice = 0이라면:

```text
실제 200ms 실행
→ vruntime ≈ 200ms
```

---

## 낮은 Priority

낮은 Priority Task는 같은 실제 시간을 실행해도 vruntime이 더 빠르게 증가하도록 처리된다.

```text
Low Priority
실제 200ms

→ vruntime > 200
```

따라서 Scheduler가 다시 선택할 가능성이 낮아진다.

---

## 높은 Priority

```text
High Priority
실제 200ms

→ vruntime < 200
```

다시 실행될 기회를 상대적으로 빨리 얻는다.

---

# 다음 Task 선택

CFS는:

> **vruntime이 가장 작은 Task를 선택한다.**

```text
T1 vruntime = 100
T2 vruntime = 80
T3 vruntime = 150

→ T2 실행
```

---

# Red-Black Tree

Runnable Task들을 **Red-Black Tree**에 저장한다.

Key:

```text
vruntime
```

구조:

```text
          T4
       /      \
     T2        T6
    /  \      / \
  T1   T3    T5 T7

작은 vruntime ← → 큰 vruntime
```

가장 왼쪽 Node가 가장 작은 vruntime을 가진다.

Balanced BST이므로 일반적인 탐색은:

[
O(\log N)
]

이다.

다만 Linux Scheduler는 가장 왼쪽 Node를 캐싱하여 다음 Task 선택을 빠르게 할 수 있다고 교재가 설명한다.

---

# I/O-bound Task가 자연스럽게 유리해지는 이유

CPU-bound:

```text
CPU를 계속 사용
→ vruntime 계속 증가
```

I/O-bound:

```text
짧게 CPU 사용
→ I/O Waiting
→ vruntime 증가량 작음
```

I/O 완료 후 돌아오면:

```text
I/O-bound vruntime < CPU-bound vruntime
```

가 되기 쉬우므로 빠르게 CPU를 받을 수 있다.

따라서 Interactive/I/O-bound 작업의 Response Time이 좋아진다.

---

# Linux Real-Time Scheduling

Linux는 POSIX의:

```text
SCHED_FIFO
SCHED_RR
```

도 지원한다.

교재 기준 Linux 내부 우선순위는:

```text
Real-Time
0 ~ 99

Normal
100 ~ 139
```

여기서는 **숫자가 작을수록 높은 Priority**다.

Normal Priority는 nice에 연결된다.

```text
nice -20 → priority 100
...
nice +19 → priority 139
```

따라서 모든 Real-Time Task는 Normal Task보다 높은 Priority에 위치한다.

---

# CFS Load Balancing

CFS는 단순히 Queue의 Thread 수만 비교하지 않는다.

각 Thread의 Load를:

```text
Priority
+
평균 CPU 사용량
```

등을 고려하여 계산한다.

Queue Load는 해당 Queue에 속한 Thread Load의 합으로 생각한다.

---

# NUMA-aware Scheduling Domain

문제는 Load Balancing 때문에 Thread를 다른 CPU로 옮기면:

```text
Cache 손실
NUMA Remote Memory Access
```

가 발생할 수 있다는 것이다.

그래서 Linux는 **Scheduling Domain**이라는 계층 구조를 사용한다.

예:

```text
NUMA Node
│
├─ Domain 0
│  ├─ Core 0
│  └─ Core 1
│       ↑ L2 공유
│
└─ Domain 1
   ├─ Core 2
   └─ Core 3
        ↑ L2 공유

전체가 L3 공유
```

기본 전략:

```text
가까운 Core끼리 먼저 Load Balancing
        ↓
필요하면 더 큰 Domain
        ↓
NUMA Node 사이 이동은 최대한 피함
```

심각한 Load Imbalance가 아니면 NUMA Node를 넘어 Thread를 이동시키지 않으려 한다.

즉 다시 핵심은:

> **Load Balance와 Memory Locality 사이의 균형**이다.

---

# 5.7.2 Example: Windows Scheduling

Windows는:

> **Priority-Based Preemptive Scheduling**

을 사용한다.

항상 가장 높은 Priority의 Ready Thread를 실행한다.

Thread는 다음 경우까지 실행한다.

```text
1. 더 높은 Priority Thread에게 선점
2. Thread 종료
3. Time Quantum 만료
4. Blocking System Call 수행
```

---

# 32 Priority Levels

```text
31 ─┐
    │ Real-Time Class
16 ─┘

15 ─┐
    │ Variable Class
 1 ─┘

 0 → 특별한 Memory Management Thread
```

즉:

```text
16~31 → Real-Time
1~15  → Variable
```

이다.

Priority별 Ready Queue가 존재하고 가장 높은 Queue부터 확인한다.

실행 가능한 Thread가 하나도 없다면 **Idle Thread**를 실행한다.

---

# Windows Process Priority Classes

Windows API에서 Process는 여섯 Priority Class 중 하나를 가진다.

| Class        | 기본 Priority |
| ------------ | ------------: |
| REALTIME     |            24 |
| HIGH         |            13 |
| ABOVE NORMAL |            10 |
| NORMAL       |             8 |
| BELOW NORMAL |             6 |
| IDLE         |             4 |

일반적인 Process의 기본값은 `NORMAL_PRIORITY_CLASS`다.

---

# Thread Relative Priority

같은 Process Class 안에서도 Thread별 상대 Priority가 존재한다.

```text
TIME_CRITICAL
HIGHEST
ABOVE_NORMAL
NORMAL
BELOW_NORMAL
LOWEST
IDLE
```

최종 Thread Priority는:

```text
Process Priority Class
+
Thread Relative Priority
```

를 조합해 결정된다.

---

# Dynamic Priority Adjustment

Variable Priority Thread가 Time Quantum을 전부 사용하면 Priority를 낮춘다.

```text
CPU-bound Thread
↓
Quantum 전부 소비
↓
Priority 감소
```

단, Base Priority보다 아래로는 떨어지지 않는다.

반대로 Wait 상태에서 돌아온 Thread는 Priority를 올려준다.

```text
I/O 대기
↓
I/O 완료
↓
Ready
↓
Priority Boost
```

특히 Keyboard와 같은 Interactive I/O는 큰 Boost를 받을 수 있고, Disk I/O는 그보다 작은 Boost를 받을 수 있다.

목적은:

```text
Interactive Thread → 빠른 Response
CPU-bound Thread → Background에서 CPU 사용
```

이다.

---

# Foreground Process

현재 사용자가 보고 있는 Foreground Process는 더 좋은 Response가 필요하다.

Windows는 `NORMAL_PRIORITY_CLASS`의 Foreground Process에 대해 Quantum을 늘릴 수 있다.

교재에서는 일반적으로 약 **3배**의 Quantum을 제공하는 예를 설명한다.

---

# User-Mode Scheduling, UMS

Windows 7에서 UMS가 도입되었다.

```text
Application
↓
User Mode Scheduler
↓
여러 Thread 관리
```

Kernel Scheduler를 매번 호출하지 않고 User Mode에서 Thread를 관리할 수 있으므로, 매우 많은 Thread를 다루는 프로그램에서 효율적일 수 있다.

---

## Fiber와 차이

기존 Windows에는 Fiber가 있었다.

```text
여러 Fiber
     ↓
하나의 Kernel Thread
```

하지만 Fiber들이 동일한 Thread Environment Block(TEB)을 공유하면서 Windows API 호출 등에 제약이 있었다.

UMS는 각 User-Mode Thread에 별도 Thread Context를 제공하여 이를 개선했다.

그리고 UMS를 일반 개발자가 직접 구현하기보다 Library가 이용하는 것을 염두에 둔다.

교재는 Microsoft의 **Concurrency Runtime(ConcRT)** 을 예로 든다.

---

# Windows Multiprocessor Scheduling

Windows도 Processor Affinity와 Load Balancing을 고려한다.

Hyper-Threading 환경에서는 같은 물리 Core의 Logical CPU들을 **SMT Set**으로 묶는다.

예:

```text
4 Core × 2 Hardware Thread

SMT Set 0 = {0,1}
SMT Set 1 = {2,3}
SMT Set 2 = {4,5}
SMT Set 3 = {6,7}
```

Thread가 기존 Cache를 활용할 수 있도록 같은 SMT Set 등을 고려한다.

---

## Ideal Processor

각 Thread에는 선호 CPU인 **Ideal Processor**가 존재한다.

Thread 생성 시 특정 CPU에만 계속 몰리지 않도록 Seed 값을 이용해 분산한다.

예:

```text
Thread 1 → CPU 0
Thread 2 → CPU 2
Thread 3 → CPU 4
Thread 4 → CPU 6
Thread 5 → CPU 0
...
```

같은 Physical Core의 Hardware Thread에 처음부터 몰아넣기보다 서로 다른 Core로 분산시키려는 것이다.

---

# 5.7.3 Example: Solaris Scheduling

Solaris는 Thread를 여섯 Scheduling Class로 구분한다.

| Class | 의미           |
| ----- | -------------- |
| TS    | Time Sharing   |
| IA    | Interactive    |
| RT    | Real Time      |
| SYS   | System         |
| FSS   | Fair Share     |
| FP    | Fixed Priority |

각 Class마다:

- Priority
- Scheduling Algorithm

이 다르다.

---

# Time Sharing, TS

기본 Scheduling Class다.

**Multilevel Feedback Queue**와 비슷하게 Priority를 동적으로 변경한다.

핵심 관계:

```text
높은 Priority
→ 짧은 Time Quantum

낮은 Priority
→ 긴 Time Quantum
```

이유는:

### Interactive

```text
짧게 CPU 사용
→ 빠르게 다시 반응 필요

높은 Priority + 짧은 Quantum
```

### CPU-bound

```text
CPU 오래 사용
→ 상대적으로 낮은 Priority
→ 대신 긴 Quantum
```

이다.

---

# Interactive, IA

TS와 거의 같은 정책을 사용하지만 GUI/Window Application에 더 높은 Priority를 제공한다.

목적은 사용자 Response 향상이다.

---

# Solaris Dispatch Table

교재에서는 TS/IA용 Dispatch Table을 보여준다.

각 Entry에 다음 정보가 있다.

### Priority

현재 Thread Priority.

숫자가 클수록 높은 Priority다.

### Time Quantum

해당 Priority가 받을 실행 시간.

```text
낮은 Priority → 큰 Quantum
높은 Priority → 작은 Quantum
```

### Time Quantum Expired

Quantum을 모두 사용한 CPU-intensive Thread의 다음 Priority.

일반적으로 Priority를 낮춘다.

```text
CPU 계속 사용
→ Priority ↓
```

### Return From Sleep

I/O 등을 기다리다 돌아온 Thread에 적용할 Priority다.

```text
I/O 완료
→ Priority 크게 ↑
```

그래서 Interactive/I/O-bound Thread의 Response Time을 좋게 한다.

---

# Real-Time, RT

가장 높은 Scheduling Priority를 가진다.

다른 Class보다 먼저 실행된다.

---

# System, SYS

Kernel Thread를 위해 사용한다.

예:

```text
Scheduler
Paging Daemon
```

SYS Thread의 Priority는 설정되면 동적으로 바뀌지 않는다.

일반 User Process가 Kernel Mode에 들어갔다고 해서 SYS Class가 되는 것은 아니다.

---

# Fixed Priority, FP

Priority를 동적으로 조정하지 않는다.

TS와 비슷한 Priority 범위를 가질 수 있지만 고정되어 있다.

---

# Fair Share, FSS

Priority보다는 **CPU Share**를 기준으로 Scheduling한다.

CPU Resource에 대한 몫을 Process 묶음(Project)에 할당한다.

---

# Global Priority

Scheduling Class별 Priority 체계가 서로 다르므로 Solaris는 최종적으로 이를 **Global Priority**로 변환한다.

```text
RT Priority
TS Priority
IA Priority
SYS Priority
...

      ↓

Global Priority
```

가장 높은 Global Priority Thread를 실행한다.

같은 Priority의 Thread가 여러 개라면 **Round-Robin**을 사용한다.

Thread는 다음까지 실행한다.

```text
1. Block
2. Time Slice 소진
3. 더 높은 Priority Thread에게 선점
```

또한 Interrupt 처리를 위한 Thread들은 Scheduling Class에 속하지 않고 가장 높은 Global Priority 영역에서 실행된다.

교재에서는 Solaris가 과거 Many-to-Many 모델을 사용했지만 Solaris 9부터 One-to-One 모델로 전환했다고 설명한다.

---

# 5.8 Algorithm Evaluation

지금까지 여러 알고리즘을 봤지만 결국 문제가 하나 남는다.

> **어떤 Scheduling Algorithm이 제일 좋은가?**

정답은 없다.

시스템이 중요하게 생각하는 목표가 다르기 때문이다.

예:

```text
Desktop
→ Response Time 중요

Server
→ Throughput 중요

Real-Time
→ Deadline 중요
```

따라서 먼저 **평가 기준**을 정해야 한다.

교재는 예를 들어 다음과 같은 조건을 제시한다.

```text
CPU Utilization 최대화
단, 최대 Response Time ≤ 300ms
```

또는:

```text
Throughput 최대화
단, 평균 Turnaround Time이
실행시간에 비례하도록 유지
```

평가 방법은 네 가지를 설명한다.

```text
5.8.1 Deterministic Modeling
5.8.2 Queueing Models
5.8.3 Simulations
5.8.4 Implementation
```

---

# 5.8.1 Deterministic Modeling

**Analytic Evaluation**의 한 종류다.

미리 정해진 Workload를 넣어 각 알고리즘을 직접 계산한다.

---

## 교재 예제

모든 Process가 시간 0에 도착한다.

| Process | Burst |
| ------- | ----: |
| P1      |    10 |
| P2      |    29 |
| P3      |     3 |
| P4      |     7 |
| P5      |    12 |

FCFS, SJF, RR(q=10)을 비교한다.

### FCFS

평균 Waiting Time:

[
28ms
]

### SJF

평균 Waiting Time:

[
13ms
]

### RR

평균 Waiting Time:

[
23ms
]

따라서 이 Workload에서는:

```text
SJF < RR < FCFS
```

순으로 평균 대기 시간이 좋다.

---

## 장점

- 계산이 쉽다.
- 빠르다.
- 정확한 수치를 얻는다.
- 알고리즘을 설명하기 좋다.

## 한계

결과가 **그 Workload에서만 유효**하다.

```text
Process 구성 변경
Burst Time 변경
Arrival Time 변경

→ 결과도 변경될 수 있음
```

그래서 실제 복잡한 시스템 평가에는 제한적이다.

---

# 5.8.2 Queueing Models

실제 시스템은 매일 같은 Process가 들어오는 것이 아니다.

따라서 CPU Burst, Arrival Time 등을 **확률 분포**로 표현한다.

예:

```text
CPU Burst Distribution
Arrival Distribution
```

이를 이용해:

- 평균 Throughput
- CPU Utilization
- 평균 Waiting Time
- 평균 Queue Length

등을 계산한다.

---

# Queueing Network

컴퓨터 시스템을 여러 Server와 Queue로 모델링한다.

```text
Ready Queue
    ↓
   CPU

Device Queue
    ↓
  Disk
```

각각:

```text
Server + Waiting Queue
```

로 생각한다.

---

# Little's Formula

매우 중요한 식이다.

[
n=\lambda W
]

- `n`: Queue에서 기다리는 평균 Process 수
- `λ`: 평균 Arrival Rate
- `W`: 평균 Waiting Time

---

## 예시

평균 초당:

```text
λ = 7 processes/sec
```

Queue에는 평균:

```text
n = 14 processes
```

있다면:

[
14 = 7W
]

따라서:

[
W=2초
]

이다.

Little's Formula의 중요한 장점:

> 특정 Scheduling Algorithm이나 Arrival Distribution에 종속되지 않는다.

---

## Queueing Model의 한계

현실적인 복잡한 Scheduling Algorithm은 수학적으로 표현하기 어려울 수 있다.

그래서 계산이 쉬운 분포를 가정하다 보면 실제 시스템과 달라질 수 있다.

즉:

```text
수학적 모델 단순화
↓
계산 가능
↓
하지만 실제 시스템 정확도 감소
```

---

# 5.8.3 Simulations

Queueing Model보다 현실적으로 평가하려면 **Simulation**을 사용할 수 있다.

가상의 컴퓨터 시스템을 프로그램으로 만든다.

```text
Simulator

CPU
Ready Queue
I/O Device
Scheduler
Clock
```

Simulation Clock을 진행시키면서:

```text
Process 도착
CPU Burst
I/O 요청
Process 종료
```

등을 재현한다.

---

## Simulation 입력 생성

### 확률 분포

Random Number Generator로:

```text
Arrival
CPU Burst
Departure
```

등을 만든다.

분포 예:

- Uniform
- Exponential
- Poisson
- 실제 측정한 경험적 분포

---

## 문제

분포만 보면 **사건의 발생 순서 관계**를 잃어버릴 수 있다.

실제:

```text
A → B → C → A → D
```

였는데 단순 Distribution은:

```text
A 2회
B 1회
C 1회
D 1회
```

정도만 표현할 수 있다.

---

# Trace Files

그래서 실제 시스템의 이벤트 순서를 그대로 기록할 수 있다.

```text
CPU 10
I/O 213
CPU 12
I/O 112
CPU 2
...
```

이 Trace를 동일하게 넣어:

```text
FCFS Simulation
SJF Simulation
RR Simulation
```

을 돌린다.

모두 같은 실제 입력으로 비교하므로 상당히 좋은 비교 방법이 된다.

---

## Simulation 단점

정확도를 높일수록:

- 많은 CPU 시간 필요
- Trace 저장 공간 필요
- Simulator 구현 비용 증가
- Debugging 필요

라는 비용이 발생한다.

---

# 5.8.4 Implementation

가장 정확한 평가 방법은 결국:

> **실제 운영체제에 알고리즘을 구현해서 실행해 보는 것**

이다.

```text
Scheduling Algorithm 작성
↓
Operating System에 구현
↓
실제 Workload 실행
↓
성능 측정
```

Simulation도 실제 시스템의 완벽한 복제는 아니기 때문이다.

---

## 문제 1. 구현 비용

Scheduler는 Kernel 핵심 부분이기 때문에 변경이 어렵다.

필요한 작업:

```text
Algorithm 구현
자료구조 변경
OS 수정
테스트
```

가 있다.

교재는 이런 테스트를 VM에서 수행할 수도 있다고 설명한다.

---

## Regression Testing

Scheduler 변경 때문에 기존 동작이 깨지지 않았는지 확인해야 한다.

```text
Scheduler 변경
↓
기존 Bug 다시 발생?
새 Bug 발생?
성능 나빠짐?
```

따라서 Regression Test가 필요하다.

---

## 문제 2. 사용자가 Scheduler에 적응한다

Scheduler 정책이 알려지면 프로그램이나 사용자 행동 자체가 변할 수 있다.

예:

```text
Short Process에 Priority 부여

↓

큰 작업을 여러 작은 Process로 쪼갬
```

또는:

```text
Interactive Process에 높은 Priority

↓

Program이 Interactive로 보이도록 행동
```

교재에서는 한 시스템이 Terminal I/O를 기준으로 Interactive Process를 판단하자, 프로그램이 1초보다 짧은 간격으로 의미 없는 문자를 Terminal에 출력하여 높은 Priority를 얻은 사례를 설명한다.

즉:

> Scheduler 정책이 Workload 자체를 바꿀 수 있다.

---

# Scheduling Parameter Tuning

그래서 현실적인 Scheduler는 시스템 목적에 맞게 조정 가능한 것이 유용하다.

예:

```text
고성능 Graphic Workstation
Web Server
File Server
```

모두 최적 정책이 다를 수 있다.

Solaris에서는 `dispadmin`을 이용해 Scheduling Class의 Parameter를 변경할 수 있다고 교재가 설명한다.

Java, POSIX, Windows 역시 Process/Thread Priority를 조절할 수 있는 API를 제공한다.

다만 특정 환경에 맞게 성능을 극단적으로 튜닝했다고 해서 다른 Workload에서도 좋은 성능을 보장하는 것은 아니다.

# 헷갈리기 쉬운 핵심 4가지

## 1. Load Balancing과 Processor Affinity는 서로 충돌한다

```text
Load Balancing
→ CPU 사이에서 Thread를 옮기고 싶다.

Processor Affinity
→ Cache 때문에 Thread를 안 옮기고 싶다.
```

따라서 현대 Scheduler는 단순히 CPU 사용률만 보고 Thread를 옮기지 않는다.

---

## 2. Core와 Logical CPU를 구분해야 한다

예:

```text
4 Physical Core
×
2 Hardware Thread

= OS에서는 8 Logical CPU
```

Chapter 4에서 배운 **Kernel Thread**와 여기서 말하는 **Hardware Thread**도 다르다.

```text
Software/Kernel Thread
→ OS가 관리하는 실행 흐름

Hardware Thread
→ CPU Core 내부가 제공하는 실행 Context
```

이 구분은 중요하다.

---

## 3. CPU 이용률이 100% 미만이라고 Deadline이 보장되는 것은 아니다

Rate-Monotonic 예제에서 CPU 사용량이 약 94%라도 Deadline을 놓칠 수 있다.

```text
CPU Capacity가 충분하다
≠
Deadline을 만족하는 Schedule이 존재한다
```

Real-Time 시스템에서는 **실행 순서**가 매우 중요하다.

---

## 4. CFS의 핵심은 "Time Quantum"보다 vruntime이다

RR:

```text
각 Process에게 q ms
```

CFS:

```text
각 Task의 vruntime 비교
↓
가장 적게 CPU를 받은 Task 선택
```

Priority도 vruntime 증가 속도에 영향을 주어 결과적으로 CPU 사용 비율을 조절한다.

# 면접 포인트

### Q. SMP에서 Ready Queue를 하나만 사용하면 어떤 문제가 있나요?

공유 Ready Queue에 여러 CPU가 동시에 접근하면서 Race Condition이 발생하므로 Lock이 필요하다. CPU 수가 많아지면 Lock Contention 때문에 Ready Queue가 병목이 될 수 있다. 그래서 현대 SMP 시스템에서는 CPU별 Run Queue를 사용하는 방식이 일반적이다.

### Q. Load Balancing과 Processor Affinity의 관계는?

Load Balancing은 CPU 사용률을 균등하게 하기 위해 Thread를 다른 CPU로 이동시키려 하지만, Processor Affinity는 Cache Locality를 유지하기 위해 같은 CPU에서 계속 실행하려 한다. 따라서 둘은 상충하며 현대 Scheduler는 두 목표 사이에서 균형을 잡아야 한다.

### Q. Hyper-Threading은 Core가 두 배가 되는 것인가요?

아니다. 하나의 Physical Core가 여러 Hardware Thread의 Architectural State를 제공하여 운영체제에는 여러 Logical CPU처럼 보이게 하는 것이다. Core의 Cache나 Execution Resource 일부는 공유된다.

### Q. Soft Real-Time과 Hard Real-Time의 차이는?

Soft Real-Time은 Real-Time Task를 일반 Task보다 우선하지만 Deadline을 보장하지 않는다. Hard Real-Time은 Task가 Deadline 이내에 완료됨을 보장해야 하며 Deadline을 넘긴 결과는 실패로 간주한다.

### Q. Rate-Monotonic과 EDF의 차이는?

Rate-Monotonic은 Period가 짧을수록 높은 **고정 Priority**를 주고, EDF는 현재 Deadline이 가까울수록 높은 **동적 Priority**를 준다. EDF는 이론적으로 더 높은 CPU 이용률까지 스케줄할 수 있다.

### Q. Linux CFS에서 다음 Task를 어떻게 고르나요?

각 Task가 사용한 CPU 시간을 Priority를 고려한 `vruntime`으로 관리하고, Runnable Task 중 `vruntime`이 가장 작은 Task를 선택한다. Runnable Task는 Red-Black Tree로 관리된다.
