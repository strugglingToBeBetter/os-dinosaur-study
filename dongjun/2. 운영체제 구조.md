# 2. 운영체제 구조
- 운영체제는 프로그램이 실행될 수 있는 환경을 제공한다.
- 운영체제는 다양한 종류가 있고, 시스템을 디자인하기 전에 그것의 목표가 제대로 정의된 것은 중요하다.
- 운영체제는 시스템이 제공하는 서비스, 사용자/프로그래머에게 제공하는 인터페이스, 운영체제의 구성 요소와 상호작용의 관점에서 볼 수 있다.
- 이 챕터에서는 위 관점들을 모두 고려해서 운영체제가 어떤 서비스를 제공하고, 어떻게 제공되며, 어떻게 디버깅되며, 시스템 디자인에 대한 다양한 방법론들이 있는지 설명할 예정이다.

## 2.1. 운영체제 서비스
- 운영체제 서비스는 특정 서비스를 프로그램과 그것을 사용하는 사용자에게 허용하는 실행 환경을 제공한다.
- 특정한 서비스가 운영체제에서 다른 객체(프로그램 등)에 제공되지만, 우리는 공통 클래스(common class)를 식별할 수 있다.
- 운영 체제 서비스 세트 중 하나는 사용자에게 유용한 기능을 제공한다.

```
서비스(service)
사용자가 직접 실행하는 프로그램과 별도로 백그라운드에서 계속 실행되며 특정 기능을 제공하는 프로그램 또는 프로세스
```
### 2.1.1. 운영 체제 세트 종류

1. 사용자 인터페이스(UI)
- 거의 대부분의 운영체제는 사용자 인터페이스가 있다.
- 인터페이스는 여러 형태들이 있지만, 일반적으로 그래픽 형태(GUI)를 사용한다.
- 윈도우 시스템의 마우스는 포인터 형태로 인터페이스가 제공되며, 입출력 서비스와 직접 연결된다.
- 모바일 시스템은 터치스크린 인터페이스 형태로 구현된다.
- 그 외에 명령줄 기반(CLI) 인터페이스도 있다.
- 일부 시스템은 여러 인터페이스들을 동시에 제공하기도 한다.(\*예: 윈도우에서 GUI와 CLI를 모두 사용 가능)

2. 프로그램 실행
- 시스템은 프로그램을 실행시키기 위해, 프로그램을 메모리에 적재할 수 있어야 한다.
- 프로그램은 (정상적이든 비정상적이든) 그것의 실행을 끝낼 수 있어야 한다.
\* 비정상적으로 종료된 경우 에러를 표시한다.

3. 입출력 동작
- 실행 중인 프로그램은 파일이나 입출력 장치와 연관된 입출력을 요구한다.
- 특정 디바이스는 특별한 동작이 고려될 수 있다.(\*네트워크 인터페이스에서 데이터를 읽거나, 파일시스템에 write하는 동작 등)
- 효율성과 보호(protection)를 위해서 사용자는 입출력 장치를 직접 제어할 수 없게 되어 있다.
- 그러므로, 운영체제는 입출력이 가능한 수단을 제공해야 한다.

4. 파일시스템 제어
- 파일시스템은 특히 흥미로운 특징이 있다.
- 분명히 프로그램은 파일과 디렉토리를 읽고 쓸 필요가 있다.
- 또한 프로그램은 파일의 이름을 지정해서 생성/삭제하고, 파일 정보를 정렬한다.
- 일부 운영체제는 파일 관리 권한 시스템을 포함해서, 파일 소유권에 따라 접근을 허용/거부할 수 있다.
- 많은 운영체제들은 다양한 파일시스템을 제공하며, 때때로 개인 설정을 허용하거나 특정 기능, 성능 지향을 변경하는 기능도 제공한다.(\*예: 고성능 모드)

5. 의사소통(Communications) (\*통신)
- 한 프로세스가 다른 프로세스와 정보를 교환할 때 많은 상황들이 있다.
- 프로세스 간 소통하는 과정은 네트워크 상 서로 다른 컴퓨터와 소통하는 과정과 동일하다.
\*프로세스 간 통신은 IPC(Inter-Process Communication) 매커니즘을 통해 구현된다.
- 의사소통은 두 개 이상의 프로세스들이 공유 메모리(Shared memory)의 공유된 영역을 읽고 쓰는 과정을 통해 이루어진다.
- 이 때 정보 패킷은 운영체제에 의해 미리 정의된 형식으로 이동한다.

6. 오류 감지
- 운영체제는 오류를 지속적으로 감지하고 수정할 필요가 있다.
- 오류는 CPU와 메모리 하드웨어, 입출력 장치, 사용자 프로그램 등에서 발생할 수 있다.
- 이러한 종류의 오류에서 운영체제는 오류를 교정하고 지속적으로 컴퓨터 서비스를 제공할 수 있도록 적절한 동작을 취해야 한다.
- 때로는 시스템을 멈춰야 하는 경우도 있다.
- 그 외의 경우라면 오류를 유발하는 프로세스를 종료하고 에러 코드를 해당 프로세스에 반환하여 오류 교정 가능성을 제공할 수 있다.

7. 자원 할당
- 동시에 여러 프로세스들을 구동할 때, 자원은 각 프로세스에 할당되어 있어야 한다.
- 운영체제는 수많은 종류의 자원을 관리한다.
- 일부 자원(CPU 사이클, 메인 메모리, 파일 저장소 등)은 특별한 할당 코드가 있는 반면, 다른 자원(입출력 장치 등)은 일반적인 요청과 릴리즈 코드를 가지고 있다.
- 예를 들어 CPU를 사용하는 최적 방법을 결정하는 과정에서, 운영체제는 CPU 스케쥴링 루틴을 가지고 CPU의 속도를 관리한다. 반드시 실행되어야 하는 프로세스와 CPU의 프로세싱 코어 수, 다른 요소들도 동일하게 관리된다.
- 프린터 할당, USB 저장소 드라이브, 다른 삼차 장치들도 동일한 방식으로 관리된다.

8. 로깅(Logging)
- 우리는 어떤 프로그램이 얼마나 그리고 어떤 종류의 컴퓨터 자원을 사용하는지 추적하고 싶다.
- 기록 저장은 과금에 사용될 수도 있고, 단순히 사용 기록을 축적하는 용도로 사용할 수도 있다.
- 통계 관리는 컴퓨팅 서비스를 개선하기 위해 시스템을 재구성하고 싶어하는 시스템 관리자에게 유용한 도구가 될 수 있다.

9. 보호/보안
- 다중 사용자 체계에서 저장된 정보의 소유자는 해당 정보에 대한 사용 권한을 갖고 싶어한다.
- 일부 분리된 프로세스가 경쟁적으로 실행될 때(*race condition을 생각하면 될 듯?), 한 프로세스는 다른 프로세스(운영체제 포함)에 의해 방해받으면 안 된다.
- 보호는 제어 중인 시스템 리소스에 대한 모든 접근과 연관되어 있다.
- 외부로부터 시스템 보안을 유지하는 것도 중요하다.
- 보안은 각 사용자가 자신을 시스템에 인증하는 것에서 시작한다.
- 인증은 주로 비밀번호를 통해 이루어지며, 이를 통해 시스템 자원에 대한 접근 권한을 얻는다.
- 보안은 외부 입출력 장치로부터 유효하지 않은 접근에서 보호하는 것으로 확장된다.
- 시스템이 적절히 보호되고 보안 상태를 유지하려면, 예방 조치가 적절히 설정되어 있어야 한다.
- 보안 체계는 (그 체계의) 가장 약한 부분만큼의 수준을 가진다.

## 2.2. 사용자와 운영체제 인터페이스

- 사용자가 운영체제와 상호작용하기 위한 몇 가지 방법이 있다.
- 여기에서는 세 가지 주요 접근법을 소개한다.

1. 명령어 인터프리터(Command Interpreters)
\* 흔히 명령어 기반 인터페이스(Command Line Interface)라 부르는 그것이다.
- 명령어 인터프리터는 사용자에게 직접 커맨드를 입력해서 운영체제에 명령을 내릴 수 있도록 한다.
- 대부분의 운영체제(Linux, UNIX, Windows 등)는 커맨드 인터프리터를 '프로세스가 초기화될 때'나 '사용자가 최초로 로그인할 때'에나 구동되는 특별한 프로그램으로 간주한다.
- 서드 파티 쉘과 무료 사용자용 쉘 또한 가능하다.
- 대부분 쉘들은 유사한 기능을 제공하고, 어떤 쉘을 사용할지는 사용자의 선호에 따라 갈린다.
- 명령어 인터프리터의 주요 기능은 사용자의 특정 커맨드를 입력받아서 실행하는 것이다.
- 이 수준에서 많은 커맨드들은 파일 제어(생성, 삭제, 정렬, 출력, 복사, 실행 등)에 할당되어 있다.
- UNIX 시스템에서는 다양한 종류의 쉘들이 사용 가능하고, 이 커맨드들은 두 가지 일반적인 방식으로 실행될 수 있다.
```
1) 커맨드 인터프리터 자신이 커맨드를 실행할 수 있는 코드를 포함할 수 있다. 예를 들면 파일을 삭제하는 커맨드는 커맨드 인터프리터로 하여금 코드의 특정 영역으로 점프(jump)하게 해서 파라미터를 설정하고 적절한 시스템 콜을 할 수 있도록 한다. 이 경우 커맨드는 자신만의 실행 코드를 요구하므로, 주어지는 커맨드 수는 명령어 인터프리터의 크기를 결정한다.
2) (UNIX에서 사용하는 방식) 다른 운영체제들이 시스템 프로그램을 통해 대부분의 커맨드를 실행할 때, UNIX에서는 커맨드 인터프리터가 커맨드를 이해하지 않는다. 명령어 인터프리터는 그저 커맨드를 메모리에 적재되고 실행될 파일을 식별하는 용도로 사용한다. 예를 들어 'rm filename' 커맨드를 호출하면 먼저 'rm' 파일을 찾은 다음, 해당 파일을 실행할 때 파라미터로 'filename'을 입력하는 방식이다.
```

2. 그래픽 사용자 인터페이스(GUI)
- 운영체제와 상호작용하는 두 번째 방법은 사용자 친화적인 그래픽 사용자 인터페이스(GUI)를 사용하는 것이다.
- 커맨드를 CLI를 통해 직접 입력하기보다는 사용자가 '바탕 화면'에 의해 특정된 마우스 기반의 창과 메뉴 시스템을 사용한다.
- 사용자는 포인터나 이미지의 위치를 조정하기 위해 마우스를 움직이고, 마우스를 클릭하여 프로그램을 호출하며, 파일이나 디렉토리(폴더)를 선택한다. 커맨드를 포함한 메뉴를 당길 수도 있다.
- 최초의 GUI는 1973년에 등장했다.
- GUI는 애플의 매킨토시 컴퓨터에 의해 대중화되었다.
- 전통적으로 UNIX 시스템은 CLI가 주류였으나, GUI의 극적인 개발을 통해 다양한 GUI 오픈소스 프로젝트들이 등장했다.

### 2.2.3. 터치스크린 인터페이스

- CLI와 GUI 모두 모바일 시스템에 부족합하다 보니, 스마트폰과 태블릿 컴퓨터는 주로 터치스크린 인터페이스를 사용한다.
- 사용자는 '제스처'를 통해 터치스크린과 상호작용한다.
- 예를 들어 손가락으로 화면을 누르거나 스와이핑하는 방식이 있다.
- 초기 스마트폰은 물리 키보드를 포함하는 경우가 있었지만, 대부분의 스마트폰과 태블릿은 키보드를 터치스크린으로 구현한다.

### 2.2.4. 인터페이스의 선택
- CLI와 GUI 중 어떤 것을 사용할 것인지는 사용자의 취향에 따라 갈린다.
- 시스템 관리자와 (시스템에 대해 잘 알고 있는) 고급 사용자는 주로 CLI를 사용할 것이다.
- CLI는 더 효율적이고 실행하고 싶어하는 활동들에 대한 보다 빠른 접근을 제공한다.
- 다만 일부 시스템은 시스템 기능의 하위 집합만 GUI를 통해 제공하는 경우도 있다.(*쉘 스크립트)
- 반대로 Windows의 경우 GUI가 잘 되어 있어서, 쉘을 사용할 일이 거의 없다.
- 안드로이드와 iOS에 CLI를 제공하는 응용 프로그램이 있긴 하지만, 그것들이 사용되는 빈도는 굉장히 적다.
- UI는 시스템 간뿐만 아니라 유저 간에도 다양한 종류가 있다.
- 실용적이고 직관적인 UI 디자인은 운영체제의 기능에 직접 연결되지는 않는다.

\* macOS의 경우 CLI와 GUI가 적절히 혼합된 형태(하이브리드)로 제공한다. CLI로 단축키를 설정하면 GUI 환경에서 이를 활용할 수 있다.

## 2.3. 시스템 콜
- 시스템 콜은 인터페이스가 운영체제에 의해 실행되는 서비스를 제공할 수 있도록 해 준다.
- 시스템 콜은 일반적으로 C/C++로 구현된 함수에 의해 제공된다.
- 특정 저수준 작업의 경우에는 어셈블리어로 작성된 경우도 있다.

### 2.3.1. 시스템 콜 예시
- 파일에서 데이터를 읽고 다른 파일에 쓰는 시스템 콜을 예시로 들면, 대상 프로그램은 두 개의 파일 이름이 필요하다(\*어느 파일에서 어느 파일로 데이터를 옮길지에 대한 설명이 필요하므로).
- 두 이름들은 운영 체제의 설계에 따라 다양한 방식으로 구체화될 수 있다.(예 cp A B)
- GUI(마우스, 아이콘 기반의 시스템)의 경우 파일 이름들이 메뉴에 표시되어, 사용자가 어느 파일에서 어느 파일로 옮길지 선택/입력할 수 있게 한다. 이 경우에는 I/O 시스템 콜을 요구한다.
- 두 파일들의 이름이 확보되면, 프로그램은 입력 파일을 열고 출력 파일을 생성해야 한다.
- 각 동작들은 다른 시스템 콜을 요구한다.
- 각 시스템 콜에 대한 발생 가능 에러 조건들은 적절히 취급되어야 한다.
- 예를 들어 프로그램이 입력 파일을 열려 하면, 그에 해당하는 파일이 없거나 접근이 거부된 경우가 있을 수 있다.
- 많은 경우에서 프로그램은 오류 메시지를 표시하고, 비정상적으로 종료한다.
- 출력 파일이 이미 동일한 이름으로 존재하는 경우에는 프로그램이 시스템 콜을 거부하거나, 기존 파일을 삭제하고 새 파일을 생성할 수 있다.
- 상호작용하는 시스템에서는 사용자에게 기존 파일을 대체할 것인지, 혹은 명령을 무시할 것인지 결정할 수 있도록 물어볼 수 있다.
- 두 파일들이 구성되면, (시스템 콜을 통해) 읽고 (다른 시스템  콜을 통해) 출력 파일에 쓰는 루프에 진입한다.
- 각 읽기와 쓰기 작업은 다양한 발생 가능한 오류 조건등르 고려하여 상태 정보를 반환해야 한다.
- 입력 시 프로그램은 파일의 끝(EOF)이나 읽기 과정에서 하드웨어 실패(패리티 오류 등)를 발견할 수 있다.
- 쓰기 동작은 다양한 오류에 직면할 수 있는데, 오류는 출력 장치에 따라 다를 수 있다(예: 디스크 용량 부족).
- 모든 파일이 복사되면, 프로그램은 두 개 파일들을 닫고(시스템 콜 두 개 호출), 콘솔이나 창에 메시지를 쓰고(추가 시스템 콜), 정상적으로 종료한다(최종 시스템 콜).

### 2.3.2. 응용 프로그램 인터페이스
- 단순한 프로그램도 운영체제에 상당한 부하를 줄 수 있다.
- 일반적으로 시스템은 초당 수천 개의 시스템 콜을 실행한다.
- 다만 대부분의 프로그래머들은 이러한 수준의 세부 사항(디테일)을 간과하는 경향이 있다.
- 전통적으로 응용 프로그램 개발자들은 프로그램을 응용 프로그램 프로그래밍 인터페이스(Application Programming Interface:API)를 통해 설계한다.
- API는 애플리케이션 프로그래머에게 함수 도구들을 제공하며, API는 각 함수에 전달될 파라미터와 예상 반환값을 포함하고 있다.
- 응용 프로그램 프로그래머들이 자주 사용하는 세 가지 API는 Windows API, POSIX API, Java API(JVM)가 있다.
- 프로그래머가 운영체제가 제공한 라이브러리 코드를 통해 API에 접근한다.
- UNIX와 Linux에서는 C언어로 라이브러리가 구현된 경우가 있는데, 이를 libc라고 한다.
- 각 운영체제는 각 시스템 콜마다 고유한 이름을 갖고 있다.
- API를 구성하는 기능은 일반적으로 (애플리케이션 프로그래머 대신) 실제 시스템 콜을 호출한다.

\* 예: Windows의 CreateProcess()의 경우 실제로는 Windows 커널의 'NTCreateProcess()' 시스템 콜을 호출한다.

#### 2.3.2.1. 프로그래머가 API를 선호하는 이유?
- 직접 시스템 콜을 호출하는 대신 API를 호출하면, 프로그램 이식성이 좋아진다.
```
프로그램 이식성(portability)
API를 사용해 설계된 프로그램은 동일한 API를 제공하는 모든 시스템에서 컴파일 및 실행될 수 있을 것이라 예상할 수 있다.
```
- 실제 시스템 콜은 단순 API 호출보다 더 세심해서 제대로 사용하기 어려운 점이 있다.
- 그럼에도 API와 (API와 연관된) 커널의 시스템 콜 간의 강한 연관관계가 있는 경우가 종종 있다.
- 많은 Windows API와 POSIX API는 운영체제에서 제공하는 기본 시스템 콜과 유사하다.

#### 2.3.2.2. 런타임 환경(run-time environment:RTE)
- 소프트웨어 전체 모음은 (컴파일러, 인터프리터, 라이브러리 등을 포함해서) 주어진 프로그래밍 언어로 작성된 응용 프로그램을 실행할 수 있어야 한다.
- 런타임 환경은 '시스템 콜 인터페이스'를 제공해서, 운영 체제에서 제공하는 시스템 콜에 대한 링크 역할을 한다.
- 시스템 콜 인터페이스는 API의 기능 호출을 감지하고, 운영 체제에서 연관된 시스템을 호출한다.
- 시스템 콜 인터페이스는 운영체제 커널에서 의도된(*연관된) 시스템 콜을 호출하고, 시스템 콜의 상태를 반환한다.
- 호출자(caller)는 시스템 콜이 어떻게 실행되고 실행 중에 어떤 동작을 하는지에 대한 정보만 갖고 있다.
- 호출자는 API의 명령에만 따르고 운영체제가 시스템 콜 호출 결과로서 어떤 동작을 할 것인지에 대해 이해하고 있어야 한다.
- 그러므로 운영체제 인터페이스의 대부분은 API에 의해 (프로그래머로부터) 숨겨져 있고, RTE를 통해 관리된다.
- 시스템 콜은 사용하는 컴퓨터에 따라 다양한 방식으로 발생한다.
- 종종 정해진 시스템 콜을 식별하는 것보다 많은 정보가 필요한 경우가 있다.
- 정보의 정확한 유형과 용량(amount)은 특정 운영 체제 시스템과 시스템 콜에 따라 다양하게 나뉜다.

\* 예: 명령 입력의 경우 원본 파일이나 소스를 특정하고, (어느 영역부터 읽을지에 대해) 메모리 버퍼의 시작 위치와 길이를 지정해 주어야 한다.

- 시스템 콜 호출 시 운영체제 시스템에 파라미터를 전달하는 방식은 다음과 같다.

1) 가장 간단한 방식으로 파라미터 레지스터를 전달하는 방식이 있다. 다만 이 방식은 레지스터보다 더 많은 파라미터가 있는 경우 사용하기 어렵다.
2) (레지스터보다 파라미터가 많은 경우) 파라미터는 메모리의 블록이나 테이블에 저장되어, 블록의 메모리 주소가 레지스터의 파라미터로서 전달된다.

- 파라미터 개수가 5개보다 많다면, 블록 메서드가 사용된다.
- 파라미터는 프로그램에 의해 스택에 점유(place)되거나 푸시(push)될 수 있고, 운영체제에 의해 밖으로 꺼내어(pop)진다.
- 블록/스택 방식은 전달되는 파라미터의 길이 제한이 없기 때문에, 일부 운영체제에서 선호되는 방식이다.

### 2.3.3. 시스템 콜 종류
- 시스템 콜은 대체로 6개의 주요 카테고리로 나눌 수 있다.
```
시스템 콜 종류(크게)
1) 프로세스 컨트롤
2) 파일 관리
3) 장치 관리
4) 정보 관리
5) 소통(communication) 관리
6) 보호(protection)
```

#### 2.3.3.1. 프로세스 컨트롤
- 실행 중인 프로그램은 정상적인 방식이든(end) 비정상적인 방식이든(abort) 종료될 수 있어야 한다.
- 시스템 콜이 현재 프로그램을 비정상적으로 종료하기 위해 생성되었거나 프로그램이 실행 중 문제가 생겨서 오류에 갇힌 경우, 때때로 메모리 덤프가 발생하고 에러 메시지가 출력된다.
- 덤프는 디스크의 특별한 로그 파일에 기록(write)되어 원인 분석 과정에서 디버거에 의해 분석될 수 있다.
- 정상적/비정상적인 순환에서 운영체제는 제어를 커맨드 인터프리터 호출로 전환해야 한다.
- 커맨드 인터프리터는 그 이후 다음 커맨드를 읽는다.
- 상호작용 시스템의 경우 커맨드 인터프리터는 단순히 다음 커맨드를 계속한다.

\* (상호작용 시스템에서) 사용자는 문제가 발생했을 때 적절한 커맨드로 대응하는 것을 가정한다.

- 팝업 창이 사용자에게 에러가 발생했음을 알리고 어떻게 행동해야 하는지 알려줄 수 있다.
- 일부 시스템은 오류 발생 시 특별한 복구 작업을 수행할 수 있다.
- 프로그램이 입력에서 오류를 발견하고 비정상적으로 종료하고 싶을 때, '오류 수준'을 정의하고 싶을 수 있다.
- '오류 수준'에서는 더 심각한 오류일수록 더 높은 수준의 오류가 된다.
- 오류 수준 정의 시 에러 레벨 0은 정상 종료가 된다.
- 커맨드 인터프리터나 후속 프로그램은 에러 레벨을 보고 다음 동작을 자동으로 실행할지 결정할 수 있다.
- 한 개의 프로그램을 실행하는 프로세스는 다른 프로그램을 불러오거나(load) 실행하기를 원할 수 있다.
- 이 기능은 커맨드 인터프리터로 하여금 의도된 프로그램을 실행하는 것을 허용한다.

\* 예) 불러온 프로그램을 종료할 때 저장/저장 안 함/취소 동작 중 어떤 것을 원하는지 물어볼 수 있다.

- 새 프로그램이 종료되고 실행 중인 프로그램의 제어가 돌아올 때, 우리는 현재 실행 중인 프로그램을 위해 메모리 이미지를 저장해야 한다.
- 두 프로그램이 경쟁적으로 동작할 때, 여러 프로그램들을 안정적으로 실행할 수 있도록 새로운 프로세스를 만들 수 있다(createprocess).
- 새 프로세스(또는 프로세스 세트)를 만들 때, 생성한 프로세스를 실행 중 제어할 수 있어야 한다.
- 제어 권한은 프로세스의 우선 순위와 최대 가동 시간을 포함해서 프로세스의 동작을 결정하거나 초기화할 수 있어야 한다.
- 더 이상 필요가 없거나 오류가 발생한 경우, 프로세스를 종료(terminateprocess)할 수 잇다.
- 프로세스를 생성한 이후에는 그것이 동작을 마칠 때까지 기다려야 한다. 이 때 얼마나 오래 대기할 것인지(wait_time), 어떤 것을 대기할 것인지(wait_event)를 설정할 수 있다.

\* 이벤트 대기의 경우 프로세스는 이벤트가 발생했을 때 적절한 신호를 보내야 한다(signal_event).

- 여러 프로세스들이 데이터를 공유할 수 있다. 데이터가 올바르게 ㅔ공유될 수 있도록, 운영체제는 프로세스에 공유된 데이터를 잠글(lock) 수 있는 기능을 제공한다.
- 잠긴 데이터는 잠금이 해제될 때까지 다른 프로세스가 접근할 수 없는 상태가 된다.
- 잠금 관련 시스템 콜은 (acquire_lock), (release_lock)이 있다.

#### 2.3.3.2. 파일 관리
- 파일시스템 관련 시스템 콜로 (create), (delete)가 있다.
- 파일시스템 시스템 콜 호출 시 파일 이름이 필요하고, 일부 시스템 콜은 파일의 특성을 요구할 수 있다.
- 생성된 파일에 접근하는 시스템 콜은 (open), (read), (write), (reposition), (close)가 있다.
- 파일시스템에 파일을 조직을 직접 구성하려 하는 경우, 디렉토리에 이러한 기능을 하는 동일한 세트의 동작이 있어야 한다.
- 파일이나 디렉토리에 우리는 다양한 권한을 제정하고 필요한 경우 설정(고정)할 수 있어야 한다.
- (move)나 (copy)의 경우 다른 많은 시스템 콜이 동반되기도 한다. 그 외의 경우에는 코드나 다른 시스템 콜을 통해 API 방식으로 제공되기도 하며, 시스템 프로그램이 수행하기도 한다.
- 시스템 프로그램이 다른 프로그램에 의해 호출될 수 있다면, 각 프로그램들은 다른 시스템 프로그램의 API로 간주될 수 있다.

\* 시스템 콜을 호출하는 프로그램은 그 자체로서 간접적인 API처럼 동작한다는 뜻 같다.
