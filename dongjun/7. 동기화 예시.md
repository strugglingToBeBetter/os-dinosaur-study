# Chapter 7. 동기화 예시

- 이 장의 핵심은 Chapter 6에서 배운 동기화 도구를 **“어떻게 실제 문제에 적용하는가?”**입니다.
- Chapter 6이 Race Condition이 왜 발생하는가 → 이를 막기 위한 도구는 무엇인가를 다루었다면, Chapter 7은 그 도구들을 실제 동기화 문제와 운영체제·프로그래밍 API에서 어떻게 사용하는가를 다룬다.

## 7.1. 동기화의 고전적인 문제점들

- 동기화 알고리즘이 제대로 작동하는지 설명하고 검증할 때 자주 사용하는 세 가지 고전 문제가 등장합니다.
```
Classic Synchronization Problems
│
├─ Bounded-Buffer Problem
│    → 생산자와 소비자의 동기화
│
├─ Readers-Writers Problem
│    → 읽기와 쓰기의 동시 접근 제어
│
└─ Dining-Philosophers Problem
     → 여러 자원의 획득 + Deadlock/Starvation
```

- 교재에서는 전통적인 설명 방식에 따라 주로 Semaphore로 해결책을 보여 줍니다. 실제 구현에서는 binary semaphore 대신 mutex lock을 사용할 수도 있습니다.

### 7.1.1. 유한 버퍼(Bounded buffer) 문제

- **Bounded Buffer(유한 버퍼)**는 Producer–Consumer Problem의 대표적인 형태입니다.
- Producer는 데이터를 만들어 버퍼에 넣고, Consumer는 버퍼에서 데이터를 꺼냅니다. 그런데 버퍼의 크기가 n으로 제한되어 있습니다.
- 따라서 세 가지 조건을 지켜야 합니다.

```
Producer는 빈 공간이 있어야 데이터를 넣을 수 있다.
Consumer는 데이터가 있어야 데이터를 꺼낼 수 있다.
Producer와 Consumer가 동시에 버퍼 자체를 수정해서는 안 된다.
```

- 이를 위해 세 semaphore를 사용합니다.

```
semaphore mutex = 1;    //버퍼 자체에 대한 상호 배제
semaphore empty = n;    //비어 있는 buffer 수
semaphore full = 0;     //데이터가 들어 있는 buffer 수
```

- Producer의 구조는 아래와 같다고 가정한다.

```
데이터 생산
   ↓
wait(empty)
   ↓
wait(mutex)
   ↓
버퍼에 데이터 삽입
   ↓
signal(mutex)
   ↓
signal(full)
```

- 버퍼가 꽉 차면 empty = 0이므로, Producer는 빈 공간이 생길 때까지 기다립니다.

- 한편 Consumer의 경우에는 Producer와 반대의 구조로 동작한다.

```
wait(full)
   ↓
wait(mutex)
   ↓
버퍼에서 데이터 제거
   ↓
signal(mutex)
   ↓
signal(empty)
   ↓
데이터 소비
```

- 버퍼가 비어 있다면 full = 0이므로 Consumer가 기다립니다.
- 따라서 이 문제에서는 semaphore마다 역할이 다릅니다.
- mutex는 Mutual Exclusion, empty와 full은 실행 순서와 자원 개수를 동기화합니다

### 7.1.2 The Readers–Writers Problem

- 이번에는 여러 프로세스가 하나의 database 같은 공유 데이터를 사용한다고 가정합니다.
- 읽기 전용 프로세서(reader), 쓰기 전용 프로세서(writer)가 있는 상황을 가정한다.
- Reader끼리는 동시에 접근해도 문제가 없지만, writer의 경우에는 동시에 접근하면 문제가 될 수 있다(Reader와 Writer의 동시 접근 포함).
- 따라서 Writer는 **exclusive access(배타적 접근)**가 필요합니다.

#### First Readers–Writers Problem
- Writer가 기다리고 있다는 이유만으로 새로운 Reader를 막지 않습니다.
- 즉 Reader에 유리합니다. 그 결과 Reader가 계속 들어오면 Writer가 계속 기다리는 Writer Starvation이 발생할 수 있습니다.

##### Second Readers–Writers Problem
- Writer가 기다리기 시작하면 가능한 한 빨리 Writer가 실행되도록 새로운 Reader의 진입을 제한합니다.
- 이번에는 반대로 Reader Starvation이 발생할 수 있습니다.
- 여기서 **Starvation(기아)**은 시스템 전체는 계속 실행되지만 특정 프로세스가 자원을 계속 얻지 못하는 현상입니다.

#### 첫 번째 문제의 구현

- 다음과 같은 예시를 가정하면...

```
semaphore rw_mutex = 1;
semaphore mutex = 1;
int read_count = 0;

첫 번째 Reader
     ↓
rw_mutex 획득
     ↓
다른 Reader들도 함께 읽음
     ↓
마지막 Reader
     ↓
rw_mutex 반환
```

- 이 경우 Reader는 한 번에 여러 객체가 접근해서 읽기 동작을 수행할 수 있지만, 그 동안 writer는 모든 Reader의 동작이 종료될 때까지 기다려야 한다.
- 이 개념을 실제로 구현한 알고리즘이 Reader-Writer Lock인데, 이 lock 형태는 Reader가 Writer보다 훨씬 많은 시스템에서 유리하다.

### 7.1.3 식사하는 철학자 문제(The Dining-Philosophers Problem)

- 이 문제에서는 다섯 철학자가 원형 테이블에 앉아 있고 철학자 사이마다 젓가락 하나가 있는 상황을 가정한다.
```
생각 → 배고픔 → 젓가락 두 개 획득 → 식사 → 젓가락 반환 → 생각
```

- 이 모델은 여러 프로세스들이 동시에 제한된 자원들을 동시에 필요한 상황을 가정한다.

### 7.1.3.1 Semaphore Solution

- 젓가락 하나를 semaphore 하나로 표현합니다.

```
semaphore chopstick[5];     //각각의 세마포어는 1로 초기화됨
``` 

- 철학자 i는 다음과 같은 동작을 수행한다.

```
wait(왼쪽 젓가락)
wait(오른쪽 젓가락)

task(식사)

signal(왼쪽 젓가락)
signal(오른쪽 젓가락)
```

- 그런데 다섯 명이 동시에 왼쪽 젓가락을 집으면 Deadlock(교착 상태) 문제가 발생한다.

```
철학자 0 : 왼쪽 보유 → 오른쪽 기다림
철학자 1 : 왼쪽 보유 → 오른쪽 기다림
철학자 2 : 왼쪽 보유 → 오른쪽 기다림
철학자 3 : 왼쪽 보유 → 오른쪽 기다림
철학자 4 : 왼쪽 보유 → 오른쪽 기다림
```

- 교재는 해결 방법으로 세 가지를 제시합니다.
1. 동시에 테이블에 앉을 수 있는 철학자를 최대 4명으로 제한
2. 두 젓가락이 모두 사용 가능할 때만 한꺼번에 획득
3. 홀수 철학자와 짝수 철학자의 젓가락 획득 순서를 반대로 설정

- 다만 Deadlock을 제거했다고 Starvation까지 자동으로 제거되는 것은 아닙니다.
```
Deadlock: 관련된 프로세스들이 서로 기다려 모두 진행 불가능한 상황
Starvation: 다른 프로세스들은 진행하지만 특정 프로세스만 계속 진행하지 못하는 상황
```

### 7.1.3.2 Monitor Solution

- 철학자의 상태를 세 가지로 구분하고, 각 철학자마다 조건 변수(condition variable)를 든다.

```
THINKING
HUNGRY
EATING

condition self[5];
```

- 철학자 i가 EATING 상태가 되려면 양쪽 이웃이 모두 EATING이 아니어야 합니다.

```
pickup(i)
→ HUNGRY로 변경
→ 먹을 수 있는지 test()
→ 못 먹으면 wait()

putdown(i)
→ THINKING으로 변경
→ 양쪽 이웃이 먹을 수 있는지 test()

test(i)
→ i가 HUNGRY이고
   양쪽 이웃이 EATING이 아니면
   i를 EATING으로 변경하고 signal()
```

- 이 방법은 인접한 철학자가 동시에 먹지 못하게 하면서 Deadlock을 방지합니다.
- 하지만 교재는 이 해결책 역시 Starvation 가능성까지 제거하지는 않는다고 강조합니다.

## 7.2 커널 내의 동기화

- 이제 이론적 문제에서 실제 운영체제로 넘어갑니다.
- 교재에서는 Windows와 Linux kernel이 동기화를 어떻게 처리하는지 비교합니다.

### 7.2.1 Windows의 경우

- Windows는 multithreaded kernel이며 다중 프로세서와 실시간 애플리케이션을 지원합니다.
- 단일 프로세서에서는 특정 global resource에 접근할 때 관련 interrupt를 일시적으로 mask할 수 있습니다.
- 다중 프로세서에서는 global resource 보호에 spinlock을 사용합니다.
- 다만 spinlock은 CPU를 계속 소비하므로 Windows kernel은 짧은 코드 구간에만 사용합니다.

#### Dispatcher Objects

- Kernel 밖의 thread synchronization에는 Dispatcher Object를 제공합니다.
- 대표적으로 Mutex, Semaphore, Event, Timer가 있다.
- Dispatcher object에는 두 가지 상태가 있습니다.(signaled, nonsignaled)

\* signaled: thread가 요청해도 block되지 않음
\* nonsignaled: thread가 요청하면 waiting

- 교재의 mutex를 예로 들면 다음과 같다.

```
signaled
   ↓ thread가 mutex 획득
nonsignaled
   ↓ owner가 mutex 반환
signaled
```

- Mutex를 기다리던 thread는 waiting queue로 들어가고, mutex가 signaled가 되면 한 thread가 다시 ready 상태로 이동합니다.
- Windows의 Critical-section object는 user-mode mutex입니다. 먼저 짧게 spin하다가 너무 오래 기다려야 한다면 kernel mutex를 사용하고 CPU를 양보하는 방식으로 불필요한 kernel 개입을 줄입니다.

### 7.2.2 Synchronization in Linux

- Linux kernel은 여러 동기화 도구를 제공합니다.

#### Atomic Integer

- 가장 단순한 방법이다.

```
atomic_t counter;

//Atomic Integer는 아래와 같은 연산들을 사용    
atomic_set()
atomic_add()
atomic_sub()
atomic_inc()
atomic_read()
```

- Atomic Operation은 연산 중간에 다른 실행 흐름이 끼어들 수 없는 연산이므로, 단순한 counter 증감 같은 작업은 lock 없이 매우 효율적으로 처리할 수 있습니다.
- 하지만 여러 변수를 함께 보호해야 한다면 atomic integer만으로 부족합니다.

#### Mutex Lock
- 리눅스에서도 mutex_lock(), mutex_unlock() 시스템 콜을 사용한다.
- Lock이 이미 사용 중이면 요청한 task는 sleep하고, lock이 반환되면 깨어납니다.

#### Spinlock

- Spinlock은 lock을 얻을 수 있을 때까지 thread가 잠들지 않고 반복적으로 lock 상태를 확인하며 기다리는 동기화 도구입니다.
- SMP(Symmetric Multiprocessing) 환경에서 기본적인 kernel locking 방식 중 하나입니다.
- 다만 spinlock은 기다리는 동안 계속 CPU를 사용하기 때문에 lock을 아주 짧게 보유할 때 적합합니다.

```
Multiprocessor → Spinlock
Single Processor → Kernel Preemption Disable    //싱글코어의 경우 spin을 해봐야 lock을 가진 task가 실행될 CPU 자체가 없으므로 lock의 의미가 없다. 그래서 대신 다른 커널 작업이 끼어들지 못하게 하는 선에서 구현한 것
```

- Linux의 spinlock과 mutex는 nonrecursive입니다. 이미 lock을 가진 thread가 같은 lock을 다시 얻으려 하면 block될 수 있습니다.

## 7.3 POSIX Synchronization

- POSIX API는 일반 애플리케이션 개발자가 user level에서 사용하는 동기화 기능입니다.
- UNIX, Linux, macOS의 Pthreads 프로그램에서 많이 사용합니다.

### 7.3.1 POSIX Mutex Locks 

```
pthread_mutex_t                     //기본 자료형
pthread_mutex_init(&mutex, NULL);   //초기화

//사용
pthread_mutex_lock(&mutex);

/* critical section */

pthread_mutex_unlock(&mutex);
```

- Lock을 다른 thread가 가지고 있다면 pthread_mutex_lock()을 호출한 thread는 기다립니다.

### 7.3.2 POSIX Semaphores

- POSIX semaphore에는 두 종류가 있습니다.

#### 7.3.2.1 POSIX Named Semaphores

- 이름을 가지고 있으므로 서로 관련 없는 여러 process가 같은 semaphore를 쉽게 공유할 수 있습니다.

```
sem = sem_open("SEM", O_CREAT, 0666, 1);

//시스템 콜은 semaphore의 것에 대응함
wait()   → sem_wait()
signal() → sem_post()
```

#### 7.3.2.2 POSIX Unnamed Semaphores

- sem_init()으로 생성합니다.

```
sem_init(&sem, 0, 1);
```

- 두 번째 인자가 0이면 해당 semaphore를 생성한 process 내부 thread들 사이에서 공유합니다.
- 0이 아닌 값을 사용하면 shared memory 등을 이용하여 process 사이에서도 공유할 수 있습니다.

### 7.3.3 POSIX Condition Variables

- Pthreads의 condition variable은 Chapter 6에서 배운 monitor의 condition variable과 유사합니다.
- 하지만 C에는 monitor가 없으므로 mutex와 condition variable을 함께 사용합니다.

```
pthread_mutex_t mutex;
pthread_cond_t cond_var;

pthread_mutex_lock(&mutex);

while (a != b)
    pthread_cond_wait(&cond_var, &mutex);

pthread_mutex_unlock(&mutex);
```

- 여기서 pthread_cond_wait()의 동작이 매우 중요합니다.

```
pthread_cond_wait()
      ↓
mutex를 놓음
      ↓
condition variable에서 대기
      ↓
signal을 받음
      ↓
mutex를 다시 획득
      ↓
실행 재개
```

- 다른 스레드는 pthread_cond_signal(&cond_var); 콜로 기다리던 스레드 중 하나를 깨울 수 있다.
- 그리고 조건 검사를 if가 아니라 while로 다시 검사하는 것이 중요합니다.

## 7.4 Synchronization in Java

- Java는 언어 자체와 API 양쪽에서 풍부한 동기화 기능을 제공합니다.

```
//Java의 동기화 기능은 크게 아래의 네 가지가 있다.
Java Synchronization
├─ Monitor (synchronized)
├─ ReentrantLock
├─ Semaphore
└─ Condition Variable
```

### 7.4.1 Java Monitors

- Java의 모든 object에는 하나의 lock이 연결되어 있습니다.
- 메서드에 public synchronized void insert(...) 처럼 synchronized를 붙이면 해당 method를 실행하려면 object의 lock을 가져야 합니다.
- 다른 thread가 lock을 가지고 있다면 요청 thread는 entry set에서 기다립니다.

```
Thread들
   ↓
Entry Set
   ↓
Object Lock 획득
   ↓
synchronized method 실행
```

#### wait()
- Thread가 synchronized method 안에 들어왔지만 조건이 충족되지 않았다면 wait() 시스템 콜을 호출할 수 있다.

- 그러면
1. Object lock을 반환하고
2. Thread가 blocked 상태가 되고
3. Object의 wait set으로 이동합니다.
- 따라서 wait()은 단순히 기다리는 게 아니라 lock까지 놓는다는 점이 중요합니다.

#### notify()

- 다른 스레드가 notify();를 호출하면 wait set의 thread 하나가 선택되어 entry set으로 이동합니다.(즉시 실행되는 것은 아님)

```
wait set
   ↓ notify()
entry set
   ↓ lock 획득 경쟁
lock 획득
   ↓
wait() 이후부터 실행 재개
```

- 교재 Figure 7.11에서는 이를 이용하여 Java의 bounded buffer를 구현합니다.

### 7.4.2 Reentrant Locks

- Java API는 좀 더 유연한 **ReentrantLock**도 제공합니다.

```
Lock key = new ReentrantLock();

key.lock();

try {
    /* critical section */
}
finally {
    key.unlock();
}
```

- **Reentrant(재진입 가능)**이라는 이름은 이미 lock을 가진 thread가 같은 lock을 다시 획득할 수 있다는 의미입니다.
- 또한 fairness 설정처럼 synchronized보다 추가적인 기능을 제공합니다.
- 특히 unlock()을 finally에 넣는 이유는 critical section에서 exception이 발생하더라도 반드시 lock을 반환하기 위해서입니다.
- Java에는 Reader–Writer 문제에 대응하는 ReentrantReadWriteLock도 있습니다.

### 7.4.3 Semaphores

- Java에서도 counting semaphore를 제공합니다.

```
Semaphore sem = new Semaphore(1);
sem.acquire();  //세마포어 획득
sem.release();  //세마포어 반환
```

- Critical section 보호에 사용할 경우 release()를 finally에 두어 semaphore가 확실히 반환되도록 합니다.

### 7.4.4 Condition Variables

- ReentrantLock에는 condition variable도 연결할 수 있습니다.    

```
Lock key = new ReentrantLock();
Condition condVar = key.newCondition();

await()     //조건 대기
signal()    //대기 중인 스레드를 깨움
```

- Java의 기본 wait()/notify()는 object마다 하나의 unnamed condition만 있다는 제약이 있습니다.
- 반면 Condition을 이용하면 서로 다른 조건을 여러 개 만들어 특정 조건을 기다리는 thread만 깨울 수 있습니다.
- 예를 들어 교재 Figure 7.13은 다섯 thread 각각에 condition variable을 하나씩 만들어서, 자기 차례의 thread를 정확하게 signal하는 방식으로 구현하고 있다.

```
Thread 0 → Condition 0
Thread 1 → Condition 1
Thread 2 → Condition 2
Thread 3 → Condition 3
Thread 4 → Condition 4
```

## 7.5 Alternative Approaches

- 멀티코어가 증가하면서 lock을 직접 다루는 방식은 점점 복잡해집니다.
- 따라서 교재에서는 기존 Mutex/Semaphore/Monitor와 다른 접근도 소개합니다.

### 7.5.1 Transactional Memory

- Database의 Transaction 개념을 memory operation에 적용합니다.
- Memory Transaction은 여러 memory read/write 연산을 하나의 atomic operation처럼 취급합니다.

```
Transaction 시작
   ↓
여러 read/write 수행
   ↓
성공 ─→ Commit
   │
   └ 실패 → Abort → Rollback
```

```
//기존
acquire();
/* shared data 수정 */
release();

//transactional memory
atomic {
    /* shared data 수정 */
}
```

- 개발자가 직접 lock을 관리하지 않아도 되며 lock 자체를 사용하지 않으므로 lock으로 인한 deadlock도 발생하지 않는다는 장점이 있습니다.
- Transactional memory는 STM과 HTM 방식이 있다.
- STM은 compiler가 transaction 관리 코드를 삽입합니다.
- HTM은 CPU cache와 cache coherence 기능을 이용하므로 별도의 instrumentation overhead를 줄일 수 있지만 hardware 지원이 필요합니다.

### 7.5.2 OpenMP

- OpenMP는 compiler directive와 API를 통해 parallel programming을 쉽게 구현하게 해줍니다.
- OpenMP는 pragma 이후의 영역을 여러 스레드가 병렬적으로 실행하게 한다.

```
#pragma omp parallel

//race condition 방지를 위해 아래와 같은 방식으로도 구현 가능
#pragma omp critical
{
    counter += value;
}
```

- critical 영역에는 동시에 하나의 thread만 진입합니다.
- 따라서 개념적으로 mutex와 비슷합니다.
- 장점은 개발자가 직접 mutex를 생성하고 lock/unlock하는 것보다 간단하다는 것입니다.
- 그러나 개발자가 어디에서 Race Condition이 발생하는지는 직접 찾아야 하며, 여러 critical section을 잘못 사용하면 여전히 Deadlock이 발생할 수 있습니다.

### 7.5.3 Functional Programming Languages

- C, C++, Java 같은 **Imperative Language(명령형 언어)**는 상태가 계속 변합니다.
- 반면 **Functional Programming Language(함수형 언어)**에서는 한 번 정의된 값이 immutable, 즉 변경되지 않는 것을 기본으로 합니다.
- 대표적인 예로 Erlang과 Scala가 있다.
