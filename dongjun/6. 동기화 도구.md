# Chapter 6. 동기화 도구(Synchronization Tools)

## 6.1 배경

프로세스와 스레드는 동시에 실행되거나 여러 CPU 코어에서 병렬로 실행될 수 있다. 한 프로세스의 명령어 실행 중간에 다른 프로세스가 실행될 수 있고, 여러 프로세스가 공유 데이터를 동시에 읽고 수정할 수도 있다.

### 경쟁 조건(race condition)

- 유한 버퍼의 생산자-소비자 문제에서 `count++`와 `count--`가 동시에 실행되는 경우를 생각할 수 있다. 각각의 연산은 기계어 수준에서 다음처럼 여러 단계로 나뉜다.

```text
register = count
register = register + 1   // 또는 - 1
count = register
```

- 두 연산의 명령어가 임의로 교차 실행되면 최종 `count`가 실제 상태와 다른 값이 될 수 있다. 이처럼 여러 프로세스가 같은 데이터를 동시에 조작하고, 결과가 실행 순서에 따라 달라지는 상황을 경쟁 조건이라고 한다.
- 따라서 공유 데이터를 다루는 코드에는 실행 순서를 제어하는 동기화가 필요하다. 멀티코어 시스템과 다중 스레드 애플리케이션이 일반화되면서 이 문제의 중요성이 더 커졌다.

## 6.2 임계구역 문제

- 임계구역(critical section)은 공유 데이터를 읽거나 수정하는 코드 영역이다. 한 프로세스가 임계구역을 실행하는 동안 다른 프로세스가 자신의 임계구역을 실행하지 못하게 하는 프로토콜을 설계하는 것이 임계구역 문제다.

\* 일반적인 프로세스 구조는 다음과 같다.

```text
while (true) {
    entry section       // 임계구역 진입 요청
    critical section    // 공유 데이터 접근
    exit section        // 임계구역에서 나옴
    remainder section   // 나머지 작업
}
```

- 올바른 해결 방법은 다음 세 조건을 만족해야 한다.

1. **상호 배제(mutual exclusion)**: 한 프로세스가 임계구역에 있으면 다른 프로세스는 임계구역에 들어갈 수 없다.
2. **진행(progress)**: 임계구역이 비어 있고 진입하려는 프로세스가 있으면, 선택이 무기한 미뤄지지 않아야 한다.
3. **한정 대기(bounded waiting)**: 어떤 프로세스가 진입을 요청한 뒤 허가받기 전까지 다른 프로세스가 임계구역에 들어갈 수 있는 횟수에 상한이 있어야 한다.

\* 한정 대기는 특정한 프로세스만 계속 임계 구역에 접근해서, 사실상 독점하는 현상을 방지하기 위한 개념이다.

- 운영체제 커널에서도 열린 파일 목록, 프로세스 목록, 메모리 할당 정보, 다음 PID 등의 자료구조가 동시에 갱신되면 경쟁 조건이 발생할 수 있다.
- 단일 코어에서는 공유 변수 수정 중 인터럽트를 막는 방법을 생각할 수 있지만, 멀티프로세서에서는 모든 코어의 인터럽트를 제어해야 하므로 비효율적이다. 비선점형 커널은 커널 모드에서 실행 중인 프로세스를 선점하지 않아 경쟁 조건이 상대적으로 적지만, 선점형 커널은 응답성이 좋고 실시간 시스템에 적합한 대신 커널 자료구조를 세심하게 동기화해야 한다.

## 6.3 Peterson의 해결 방법

- Peterson의 해결 방법은 두 프로세스가 임계구역 문제를 해결하도록 만든 고전적인 소프트웨어 알고리즘이다. 두 프로세스 `P0`, `P1`이 다음 공유 변수를 사용한다.

```text
int turn;
boolean flag[2];
```

- `flag[i] == true`: 프로세스 `Pi`가 임계구역에 들어가기를 원한다.
- `turn`: 두 프로세스가 동시에 원할 때 먼저 양보할 프로세스를 나타낸다.

\* 핵심 구조는 다음과 같다.

```text
flag[i] = true;
turn = j;
while (flag[j] && turn == j)
    ;

// critical section

flag[i] = false;
```

- 어떤 프로세스가 접근을 원하는 상황에서 해당 프로세스가 (다른 경합하는 프로세스보다) 우선 순위가 있는 경우 critical section 접근 권한을 얻는 방식 같다.

- 두 프로세스가 동시에 진입을 시도해도 `turn`은 한 값만 가질 수 있으므로 상호 배제가 성립한다. 상대 프로세스가 진입을 원하지 않으면 즉시 진행할 수 있고, 상대가 먼저 들어가더라도 한 번 나간 뒤에는 진입할 수 있으므로 진행과 한정 대기도 만족한다.
- 다만 현대 프로세서와 컴파일러는 성능을 위해 서로 의존하지 않는 메모리 읽기·쓰기의 순서를 바꿀 수 있다. 이 명령어 재배치 때문에 Peterson 알고리즘이 현대 하드웨어에서 항상 올바르게 동작한다고 보장할 수 없다. 공유 메모리 동기화에는 하드웨어가 제공하는 메모리 순서 보장과 원자 명령어가 필요하다.

## 6.4 동기화를 위한 하드웨어 지원

- 현대 시스템은 소프트웨어 알고리즘의 한계를 보완하기 위해 원자적으로 실행되는 하드웨어 기능을 제공한다. 이러한 기능은 직접 동기화 도구로 사용하거나, 뮤텍스·세마포어 같은 고수준 도구의 기반으로 사용할 수 있다.

### 6.4.1 메모리 장벽

- 메모리 모델은 한 프로세서의 메모리 변경이 다른 프로세서에 보이는 방식이다.

- **강한 순서(strongly ordered)**: 메모리 변경이 다른 프로세서에 즉시 보인다.
- **약한 순서(weakly ordered)**: 변경 사항이 다른 프로세서에 즉시 보인다는 보장이 없다.

- 메모리 장벽(memory barrier 또는 memory fence)은 장벽 이전의 모든 메모리 읽기·쓰기가 완료되고 다른 프로세서에 보인 뒤에 다음 메모리 연산이 수행되도록 한다. 이를 통해 명령어 재배치로 인해 플래그는 먼저 보이지만 실제 데이터는 아직 갱신되지 않은 문제를 방지할 수 있다.
- 메모리 장벽은 매우 낮은 수준의 기능이므로 일반 애플리케이션보다는 커널 개발이나 특수한 동기화 코드에서 주로 사용된다.

### 6.4.2 하드웨어 명령어

#### Test-and-set

`test_and_set()`은 대상 값을 읽고 `true`로 설정하는 작업을 하나의 원자적 연산으로 수행한다.

```text
while (test_and_set(&lock))
    ;                   // 바쁜 대기

// critical section

lock = false;
```

\* 원자적 연산: 각자의 객체 시점에서 연산하는 작업(프로세스에서 연산을 한 경우, 메모리에서 원본 값을 가져오고 결과를 다시 쓰는 일련의 과정에 다른 객체가 접근하지 못하게 막는 기능이다.)
- 여러 코어가 동시에 실행해도 원자적 연산은 순차적으로 처리되므로 한 프로세스만 락을 획득한다. 그러나 이 방식만으로는 한 프로세스가 무한정 기다리지 않는다는 한정 대기를 보장하지 않는다.

#### Compare-and-swap(CAS)

- CAS는 현재 값이 예상 값과 같을 때만 새 값으로 바꾸고, 교체 전의 원래 값을 반환하는 원자적 명령어다.

```text
while (compare_and_swap(&lock, 0, 1) != 0)
    ;                   // 바쁜 대기

// critical section

lock = 0;
```

- 락이 `0`일 때 첫 프로세스가 `1`로 바꾸어 진입하고, 다른 프로세스는 락이 다시 `0`이 될 때까지 기다린다. 기본 형태는 상호 배제를 만족하지만 한정 대기는 보장하지 않는다. 대기 배열을 두고 락 해제 시 다음 대기 프로세스를 순환적으로 선택하면 상호 배제·진행·한정 대기를 모두 만족시킬 수 있다.

- Intel x86에서는 `cmpxchg` 명령과 `lock` 접두사를 사용해 CAS의 원자성을 구현할 수 있다.

### 6.4.3 원자 변수

- 원자 변수는 정수나 boolean 같은 기본 자료형에 대해 읽기·수정 작업을 끊김 없이 수행하도록 제공되는 자료형이다. 일반적으로 CAS를 이용해 카운터 증가나 순번 생성기 같은 단일 갱신을 안전하게 처리한다.
- 그러나 원자 변수 하나만으로 복합적인 경쟁 조건이 모두 해결되지는 않는다. 예를 들어 버퍼의 `count` 갱신은 원자적이어도, 여러 소비자(사용자)가 같은 `count` 값을 보고 동시에 버퍼에서 데이터를 꺼내는 문제는 남을 수 있다. 따라서 원자 변수는 단일 공유 값의 갱신에 적합하고, 더 복잡한 조건에는 별도의 동기화 도구가 필요하다.

## 6.5 뮤텍스 락

- 뮤텍스(mutex, mutual exclusion)는 임계구역을 보호하는 가장 단순한 고수준 동기화 도구다. 프로세스는 임계구역에 들어가기 전에 `acquire()`를 호출하고, 나올 때 `release()`를 호출한다.

```text
while (true) {
    acquire(lock)
    // critical section
    release(lock)
    // remainder section
}
```

- 락이 사용 가능하면 획득하고, 이미 다른 프로세스가 보유 중이면 대기한다. `acquire()`와 `release()` 자체는 원자적이어야 하며, CAS 같은 하드웨어 명령어로 구현할 수 있다.
- 락을 기다리는 방식에 따라 다음과 같은 특성이 있다.

- **스핀락**: 락을 얻을 때까지 반복해서 확인하는 바쁜 대기 방식이다. 컨텍스트 전환이 필요 없으므로 멀티코어에서 락 보유 시간이 매우 짧을 때 유리하다.
- **블로킹 방식**: 기다리는 프로세스를 잠들게 하여 CPU를 다른 작업에 사용한다. 긴 대기에는 적합하지만 컨텍스트 전환 비용이 발생한다.

- 락 경쟁이 심할수록 전체 병행 프로그램의 성능이 떨어진다. 특히 단일 코어에서 긴 시간 스핀락을 사용하면 CPU 시간을 낭비할 수 있다.

## 6.6 세마포어

세마포어 `S`는 초기화 이후 원자적 `wait()`와 `signal()` 연산으로만 접근하는 정수 변수다.

```text
wait(S) {
    while (S <= 0)
        ;
    S--;
}

signal(S) {
    S++;
}
```

- `wait()`는 자원을 요청하고 세마포어 값을 감소시키며, `signal()`은 자원을 반납하고 값을 증가시킨다. `wait()`에서 값 검사와 감소는 중간에 끊기지 않는 하나의 원자적 작업이어야 한다.

### 6.6.1 세마포어 사용

- **이진 세마포어**: 값이 0 또는 1이며 뮤텍스와 비슷하게 상호 배제에 사용된다.
- **카운팅 세마포어**: 값에 더 넓은 범위를 허용하며, 여러 개의 동일한 자원을 관리하는 데 사용된다. 초기값은 사용 가능한 자원 개수다.

\* 카운팅 세마포어는 critical section에 동시에 접근 가능한 프로세스 수를 n개까지 제한할 때 사용한다.
\* 세마포어의 경우 다른 프로세스가 signal() 콜을 호출해서 배타적 권한을 해제할 수 있다. 권한을 보유한 프로세스만이 스스로 해제할 수 있는 mutex lock과의 차이점이다.

- 세마포어는 실행 순서 제어에도 사용할 수 있다. `P1`의 문장 `S1`이 끝난 뒤에만 `P2`의 문장 `S2`가 실행되어야 한다면, `synch`를 0으로 초기화하고 다음처럼 작성한다.

```text
P1: S1; signal(synch);
P2: wait(synch); S2;
```

`P2`는 `P1`이 `signal()`을 호출하기 전까지 진행할 수 없다.

### 6.6.2 세마포어 구현

- 바쁜 대기를 줄이기 위해 세마포어가 0 이하일 때 기다리는 프로세스를 대기 큐에 넣고 잠들게 할 수 있다.

```text
semaphore {
    int value;
    process_list list;
}
```

- `wait()`: 값을 감소시키고, 값이 음수가 되면 현재 프로세스를 큐에 넣어 `sleep()`한다.
- `signal()`: 값을 증가시키고, 대기 프로세스가 있으면 하나를 꺼내 `wakeup()`한다.

- 이 구현에서는 세마포어 값이 음수가 될 수 있으며, 그 절댓값은 대기 중인 프로세스 수를 나타낸다. 대기 큐를 FIFO로 구성하면 한정 대기 성질을 구현하기 쉽지만, 올바른 세마포어 사용 자체가 특정 큐 방식에 의존하는 것은 아니다.

- 세마포어 연산도 임계구역 문제이므로 원자적으로 구현해야 한다. 단일 프로세서에서는 인터럽트 비활성화가 가능하지만, 멀티코어에서는 모든 코어의 인터럽트를 막아야 하므로 CAS나 스핀락 같은 방법이 필요하다. 즉, 바쁜 대기를 완전히 없앤 것이 아니라 짧은 세마포어 내부 임계구역으로 제한한 것이다.

## 중간 핵심 정리

1. 공유 데이터에 대한 동시 접근은 실행 순서에 따라 결과가 달라지는 경쟁 조건을 만든다.
2. 임계구역 해결 방법은 상호 배제, 진행, 한정 대기를 만족해야 한다.
3. Peterson 알고리즘은 개념적으로 중요하지만 현대 하드웨어의 명령어 재배치 때문에 단독 사용이 안전하지 않다.
4. 메모리 장벽과 원자적 하드웨어 명령어는 저수준 동기화의 기반이다.
5. 원자 변수는 단일 값의 갱신에는 유용하지만 복합적인 동기화 문제 전체를 해결하지는 못한다.
6. 뮤텍스는 상호 배제에 적합하고, 세마포어는 상호 배제와 자원 개수·실행 순서 제어까지 지원한다.
7. 동기화 도구는 강력하지만 사용 순서를 잘못 설계하면 교착이나 타이밍 오류가 발생할 수 있다.

## 6.7. 모니터

- Mutex Lock이나 Semaphore만으로도 임계구역(Critical Section)의 상호 배제는 구현할 수 있지만, 잘못 사용할 경우 발견하기 굉장히 까다로운 형태의 문제가 발생할 수 있다.
- 예를 들어 binary semaphore mutex를 사용할 때 정상적인 형태는
```
wait(mutex)
    ↓
critical section
    ↓
signal(mutex)
```
이어야 합니다.
- 그런데 실수로 signal()과 wait()의 순서를 바꾸거나, signal() 대신 wait()을 두 번 호출하거나, wait() 또는 signal()을 빠뜨릴 수 있습니다. 
- 이 경우 상호 배제가 깨지거나 프로세스가 영원히 block될 수 있습니다. 더 큰 문제는 이런 오류가 특정 실행 순서에서만 나타나므로 재현과 디버깅이 어렵다는 것입니다.  

- 그래서 책에서는 '동기화 자체를 좀 더 고수준의(추상화된) 언어 구조로 만들자'는 접근으로 Monitor를 소개합니다.

### 6.7.1. 모니터 사용법

#### Monitor란?

- Monitor란 **ADT(Abstract Data Type, 추상 자료형)**의 일종입니다.
- 핵심 특징은 공유 데이터 + 그 데이터를 다루는 함수 + 동기화를 하나로 묶는다는 것입니다.
- Monitor 내부에서는 한 번에 하나의 프로세스만 활성화될 수 있다. Monitor 자체가 상호 배제(Mutual Exclusion)을 보장하므로, 각각의 함수에 Mutex 관련 시스템 콜(lock, unlock, wait, signal 등)을 구현할 필요가 없다.

#### 조건 변수(Condition Variable)

- 그런데 단순히 "한 번에 하나만 들어온다"만으로 모든 동기화 문제를 해결할 수는 없습니다.
- 예를 들어 monitor 내부에 들어왔는데 특정 조건이 만족될 때까지 기다려야 하는 경우가 있습니다.
- 그래서 Monitor는 **Condition Variable(조건 변수)**을 사용합니다.
- 조건 변수에는 기본적으로 wait, signal 두 연산이 있습니다.
- wait: 현재 프로세스를 중지시킨다. 다른 프로세스가 'signal'을 실행할 때까지 기다린다.
- signal: 조건 변수 x에서 대기 중인 프로세스 중 하나를 깨운다. 기다리는 프로세스가 없으면 아무 동작도 하지 않는다.
- 대기 중인 프로세스가 없는 상황에서 semaphore의 signal은 semaphore 값이 변하는데, monitor의 signal은 아무런 변화가 없다는 점에서 차이가 있다.

#### signal을 하면 누가 monitor를 사용하는가?

- Monitor는 한 번에 하나만 있어야 하는데, 동시에 여러 프로세스가 실행될 수 있는 상황에서 우선 순위 처리가 문제가 된다.(\*하나를 제외한 다른 프로세스들은 대기 상태가 되어야 하므로...)

프로세스 P와 Q가 있을 때...
- Signal-and-wait: P가 signal을 호출하고, P는 대기 상태가 된다. Q가 실행된다.
- Signal-and-continue: P가 signal을 호출하고, P가 실행된다. Q는 P가 monitor를 벗어날 때까지 대기한다.

- 각각 장단점이 있습니다. 특히 signal-and-continue에서는 Q가 실제로 다시 실행될 때쯤에는 Q가 기다렸던 조건이 더 이상 참이 아닐 가능성이 있습니다. 책은 P가 signal 직후 monitor를 떠나 Q를 즉시 실행시키는 절충안도 설명합니다.

### 6.7.2. 세마포어를 사용해 모니터 구현하기

- 고수준 개념인 Monitor 자체를 Semaphore로 구현할 수 있습니다.
- 기본적으로 monitor마다 binary semaphore 'mutex=1'을 둔다.
- 프로세스가 monitor에 들어갈 때 'wait(mutex)'를 호출하고, monitor에서 나갈 때 'signal(mutex)'를 수행하면 한 번에 하나의 프로세스만 monitor에 들어갈 수 있다.
- signal-and-wait 방식을 구현하기 위해 추가적으로 'next','next_count'도 사용한다.
- next는 signal을 수행한 프로세스를 잠시 대기시키기 위한 semaphore이고, next_count는 그곳에서 기다리는 프로세스 수를 나타냅니다.
- Condition variable x도 내부적으로 x_sem, x_count를 사용하여 구현할 수 있다.
- 즉 전체적으로 보면 계층 관계가
```
Hardware atomic operation
        ↓
Semaphore / Mutex
        ↓
Monitor
        ↓
Condition Variable을 이용한 고수준 동기화
```
처럼 이해될 수 있습니다.

### 6.7.3. 모니터를 사용해 프로세스 속행(resume)하기

- Condition variable에서 여러 프로세스가 기다리고 있다면 새로운 문제가 생깁니다.
- 여러 프로세스들이 같이 대기 중인 상태에서 모니터에 signal 콜이 들어오면, 어떤 프로세스를 깨울지가 문제가 된다.
- 가장 간단한 방법은 **FCFS(First-Come, First-Served)**이지만, 먼저 기다린 프로세스를 깨우는 것이 최선은 아닐 수 있습니다.
- 그래서 책은 conditional-wait를 소개합니다.
- 'wait' 시스템 콜을 호출할 때 파라미터로 우선 순위 값(priority number)를 입력하면, 프로세스가 기다릴 때 우선 순위 정보도 같이 저장된다.
- 이후 모니터에서 signal 콜을 받아서 대기 중인 프로세스를 깨울 때, 우선 순위 값이 **가장 낮은** 프로세스가 먼저 실행된다.
\* wait에 입력하는 argument는 X초 동안 기다리라는 의미이므로, 값이 더 작은 경우 더 적게 기다리게 되는 원리 같다.

- ResourceAllocator 예제에서는 각 프로세스가 자원을 사용할 예상 시간을 지정하여 더 짧은 사용시간을 요청한 프로세스를 먼저 선택하는 방식으로 이를 설명합니다.
- 하지만 Monitor도 모든 문제를 자동으로 해결하지는 않습니다. 프로세스가
```
- 자원을 요청하지 않고 사용하거나
- 자원을 받은 뒤 반환하지 않거나
- 받지도 않은 자원을 반환하거나
- 반환하지 않은 상태에서 같은 자원을 다시 요청
```
할 수 있습니다.

- Monitor는 동기화 도구의 잘못된 사용 가능성을 줄여 주지만, 프로그램의 논리적 정확성 자체를 완전히 보장하지는 않는다.

## 6.8. 활성성(Liveness)

- 동기화에서는 Mutual Exclusion만 만족한다고 끝이 아닙니다.
- 프로세스가 임계구역에 들어가기 위해 기다리는데 영원히 들어가지 못할 수도 있기 때문입니다.
- 이를 이해하기 위한 개념이 Liveness입니다.
- 책에서 Liveness는 프로세스가 실행 생명주기 동안 계속 진행(progress)할 수 있도록 시스템이 만족해야 하는 속성들을 의미합니다.
- 무한 대기는 critical-section 문제의 요구조건 가운데 
```
- Progress
- Bounded Waiting
```
을 위반합니다.

### 6.8.1. 교착(Deadlock)

- 대표적인 Liveness failure가 **Deadlock(교착 상태)**입니다.
- 예를 들어 두 세마포어 S, P가 있고 두 프로세스 P0, P1이 있을 때...

```
P0                 P1

wait(S)            wait(Q)
wait(Q)            wait(S)
   ↓                  ↓
  대기                대기
```

실행 순서가 아래처럼 되면...

```
P0 : wait(S) 성공
P1 : wait(Q) 성공

P0 : wait(Q) → P1이 가지고 있으므로 대기
P1 : wait(S) → P0가 가지고 있으므로 대기
```

```
P0 ── Q를 기다림 ──→ P1
 ↑                    │
 └──── S를 기다림 ────┘
```
이렇게 무한루프에 빠지는 문제가 생긴다.

- 책에서는 deadlock을 '집합에 속한 모든 프로세스가 그 집합 안의 다른 프로세스만 발생시킬 수 있는 사건(event)을 기다리는 상태'로 설명한다.

### 6.8.2 우선 순위 반전(Priority Inversion)

- 두 번째 Liveness 문제는 **Priority Inversion(우선순위 역전)**입니다.
- 세 프로세스 L, M, H가 있을 때(\*우선 순위는 H-M-L 순임), L이 세마포어 S를 가지고 있는데, H가 S를 필요로 하는 경우...

```
L : S 보유
H : S 필요 → L을 기다림
```

- 그런데 이 떄 M이 실행 가능 상태가 되면, M이 L을 선점할 수 있다. 그렇게 되면...

```
H
↓ S 기다림
L ← S 보유
↑
M이 L을 선점
```

- 이 경우, 가장 우선 순위가 높은 H가 M 때문에 실행되지 못하는 문제가 생긴다. (L이 세마포어를 가지고 있어서 기다려야 하는데, L은 우선순위가 M보다 밀리므로...

#### 우선 순위 반전 현상 해결 방안

- 우선 순위 상속(Priority Inheritance) 프로토콜을 사용하는 방법이 있다.
- 위 예시에서 H가 L이 가진 자원을 기다릴 때, L이 일시적으로 H의 우선 순위를 상속(Inherit)받게 만들 수 있다.
- 이렇게 되면 (일시적으로) M이 L보다 우선순위에서 밀리므로, L이 우선 실행된 후 세마포어를 반환하고, H가 실행되고, M이 실행되도록 조정할 수 있다.
- 탐사선 패스파인더의 경우, 화성 탐사선에서 낮은 우선순위 작업이 공유 자원을 보유하고 있는 동안 중간 우선순위 작업들이 이를 선점하면서 높은 우선순위 작업이 지연되었고, 결국 시스템 reset을 계속 시도하는 문제가 있었다. 이 문제는 VxWorks의 priority inheritance 기능을 활성화하여 해결했다.

## 6.9. 동기화 도구의 평가

- 여기서는 지금까지 배운 여러 동기화 방법 중 어떤 상황에서 어떤 도구가 적합한가를 비교합니다.
- 먼저 hardware synchronization은 매우 저수준이므로 보통 Mutex 같은 고수준 동기화 도구를 만드는 기반으로 사용됩니다.
- 특히 책에서는 CAS(Compare-and-Swap) 기반 lock-free 방식과 전통적인 locking을 비교합니다.

#### CAS

- CAS = Optimistic(낙관적으로 가정): CAS 방식은 기본적으로 "아마 다른 thread와 충돌하지 않을 것이다."라고 가정합니다.
- 먼저 값을 업데이트하려 시도하고, 충돌하면 다시 시도합니다.

#### Locking

- Lock = Pessimistic(보수적으로 가정): 반대로 Mutex Lock은 "다른 thread가 사용하고 있을 수도 있다."라고 가정하고 먼저 lock을 얻은 다음 값을 변경합니다

#### Contention(경합)에 따른 성능

- 여기서 Contention은 여러 thread/process가 같은 자원을 동시에 얻으려고 경쟁하는 정도라고 이해하면 됩니다.
- Contention이 낮을수록 CAS가 속도가 빠르지만, Contention이 높아질수록 전통적인 동기화 방식(Locking)이 더 유리하다.
- 특히 중간 contention에서는 CAS가 실패하더라도 몇 번 retry하면 성공하는 경우가 많습니다.
- 반면 Mutex가 이미 잠겨 있다면 thread를 suspend하고 wait queue에 넣고 다른 thread로 context switch하는 등의 더 무거운 작업이 필요합니다.(\*스레드를 대기 큐에 넣고, 그 동안 다른 스레드를 실행시키는 방식으로 운영해야 한다는 뜻임)

#### 어떤 도구를 언제 사용하는가?

```
상황	적합한 도구
단순 shared counter 변경	Atomic integer
멀티프로세서 + 매우 짧은 lock	Spinlock
일반적인 Critical Section	Mutex Lock
제한된 N개의 자원 관리	Counting Semaphore
Reader가 동시에 접근해도 됨	Reader–Writer Lock
코드의 단순성/추상화가 중요	Monitor + Condition Variable
낮음~중간 contention에서 lock overhead를 줄이고 싶음	CAS / Lock-free
```

- 책에서는 일반적인 critical section 보호라면 Mutex가 Semaphore보다 단순하고 overhead도 적기 때문에 binary semaphore보다 선호될 수 있다고 설명합니다. 
- 반면 여러 개의 동일 자원을 관리할 때는 counting semaphore가 더 적절합니다.
- Monitor와 condition variable은 사용하기 쉽고 추상화 수준이 높다는 장점이 있지만, 구현에 따라 overhead가 크거나 contention이 높은 상황에서 확장성이 떨어질 수 있습니다.

## 6.10. 요약

```
Race Condition
      ↓
Critical Section
      ↓
Mutual Exclusion 필요
      ↓
Mutex / Semaphore
      ↓
프로그래머가 잘못 사용할 위험
      ↓
Monitor
 ├─ 자동 Mutual Exclusion
 └─ Condition Variable
       ├─ wait()
       └─ signal()
      ↓
하지만 동기화를 잘못 설계하면
      ↓
Liveness Failure
 ├─ Deadlock
 └─ Priority Inversion
       ↓
 Priority Inheritance로 완화
      ↓
실제 시스템에서는 성능도 고려
      ↓
CAS / Atomic / Spinlock / Mutex /
Semaphore / Reader-Writer Lock / Monitor
중 상황에 맞게 선택
```

- Chapter 6 전체의 핵심은 결국 Race Condition을 막기 위해 Critical Section을 동기화하는 방법입니다. 
- 이를 위해 hardware instruction, atomic variable, mutex, semaphore, monitor 등을 사용할 수 있으며, 올바른 해법은 Mutual Exclusion, Progress, Bounded Waiting을 고려해야 합니다. 
- 동시에 Deadlock 같은 Liveness 문제와 contention에 따른 성능 문제까지 고려해야 합니다.
