# 4. 스레드(Thread)

## 4.1. 스레드(Thread)의 개요 및 필요성
- 정의: 스레드는 CPU 이용의 기본 단위로, 스레드 ID, 프로그램 카운터(PC), 레지스터 세트, 스택으로 구성됩니다.  
- 자원 공유: 같은 프로세스에 속한 스레드들은 코드 영역, 데이터 영역, 그리고 열린 파일이나 신호와 같은 운영체제 자원을 서로 공유합니다. 
- 멀티스레딩의 동기: 기존의 단일 스레드 프로세스와 달리, 멀티스레드 프로세스는 한 번에 여러 작업을 수행할 수 있습니다. 예를 들어, 웹 브라우저에서 한 스레드가 이미지를 표시하는 동안 다른 스레드가 네트워크에서 데이터를 가져오거나, 웹 서버가 클라이언트의 요청이 들어올 때마다 새로운 프로세스를 만드는 대신 새 스레드를 생성하여 효율적으로 요청을 처리할 수 있습니다. 프로세스 생성은 시간과 자원이 많이 소모되므로 스레드를 사용하는 것이 훨씬 효율적입니다.
- 하나의 프로세스 내에 여러 스레드들이 존재해서, 거대한 작업을 단일 프로세스 내에서 처리하는 것이 효율적이다.

### 4.1.1. 멀티스레드 프로그래밍의 이점
- 응답성(Responsiveness): 애플리케이션의 일부분이 차단(block)되거나 긴 작업을 수행하더라도 프로그램이 계속 실행되므로 사용자에 대한 응답성이 높아집니다. 

\* 싱글 스레드의 경우 긴 시간이 소요되는 작업을 수행할 때 사용자에게 적절한 응답을 주지 못할 가능성이 있다.

- 자원 공유(Resource sharing): 프로세스는 공유 메모리나 메시지 전달을 통해서만 자원을 공유할 수 있지만, 스레드는 기본적으로 자신이 속한 프로세스의 메모리와 자원을 공유하므로 같은 주소 공간 내에서 여러 활동을 할 수 있습니다.

\* IPC를 구현하지 않아도 되므로 훨씬 편하다.

- 경제성(Economy): 프로세스 생성을 위한 메모리와 자원 할당은 비용이 많이 듭니다. 스레드는 자원을 공유하기 때문에 스레드 생성 및 문맥 교환(Context-switch)이 프로세스보다 훨씬 경제적이고 빠릅니다.
- 확장성(Scalability):멀티프로세서(Multiprocessor) 아키텍처에서는 각 스레드가 서로 다른 프로세스 코어에서 병렬적으로 실행될 수 있으므로 이점이 더욱 커집니다.  

## 4.2. 멀티코어 프로그래밍

- 최근의 CPU 디자인은 하나의 프로세스 칩에 여러 컴퓨팅 코어를 포함하는 설계가 많이 사용되고 있다.
- 코어 숫자가 적은 경우 단순히 실시간으로 분할하여 작업하는 것에 지나지 않지만, 코어 수가 충분한 경우 시스템은 각 코어에 작업을 적절히 배분해서 스레드가 병렬적으로 동작할 수 있게 한다.    

### 4.2.1. 프로그래밍 도전 과제(challenges)
- 동시성: 단일 코어 시스템에서 여러 작업이 시간에 따라 번갈아 가며 실행되어 모든 작업이 진행되는 것처럼 보이게 하는 것입니다.  
- 병렬성: 멀티코어 시스템에서 실제로 여러 작업이 동시에(simultaneously) 수행되는 것을 의미합니다.  
- 프로그래밍 도전 과제: 멀티코어 시스템을 활용하기 위해 개발자는 태스크 식별, 균형, 데이터 분할, 데이터 의존성(동기화), 테스팅 및 디버깅이라는 5가지 영역의 과제를 해결해야 합니다.  
- 암달의 법칙(Amdahl's Law): 애플리케이션에 순차적(비병렬) 부분과 병렬 부분이 모두 존재할 때, 코어를 추가함으로써 얻을 수 있는 이론적인 최대 성능 향상 비율을 나타내는 공식입니다. 이 법칙은 애플리케이션의 순차적인 부분이 성능 향상에 지대한 영향을 미친다는 것을 보여줍니다.  
- 데이터 분배(Data Splitting): 응용 프로그램이 여러 task들로 나뉘면서, task에 의해 제어/접근되는 데이터는 각 코어에 분배되어야 한다.
- 데이터 의존성: task 간 데이터 의존 관계가 있는 경우, 데이터 의존성을 충족할 수 있도록 task 간 동기화되어야 한다.

#### 4.2.2. 병렬성의 종류
- 데이터 병렬성: 동일한 데이터의 하위 세트를 여러 코어에 분배하고 각 코어에서 동일한 연산을 수행하는 방식입니다. 
- 태스크 병렬성: 데이터가 아니라 태스크(스레드)를 여러 코어에 분배하여, 각 스레드가 고유한 연산을 수행하도록 하는 방식입니다.  

## 4.3. 멀티스레드 모델
- 스레드는 사용자 공간의 사용자 스레드와 커널 수준의 커널 스레드로 나뉘며, 이 둘의 관계를 설정하는 세 가지 모델이 있습니다.  

### 4.3.1. 다대일(Many-to-One) 모델
- 많은 사용자 스레드를 하나의 커널 스레드로 매핑합니다. 스레드 관리가 사용자 공간에서 이루어져 효율적이지만, 하나의 스레드가 차단 시스템 호출을 하면 프로세스 전체가 차단되며 멀티코어에서 병렬 실행이 불가능합니다.  

### 4.3.2. 일대일(One-to-One) 모델
- 각 사용자 스레드를 커널 스레드에 매핑합니다. 다대일 모델보다 더 많은 동시성을 제공하고 병렬 실행이 가능하지만, 사용자 스레드를 만들 때마다 커널 스레드를 생성해야 하므로 시스템 성능에 부담을 줄 수 있습니다. Windows와 Linux가 이 모델을 사용합니다.  

### 4.3.3. 다대다(Many-to-Many) 모델
- 여러 사용자 스레드를 그보다 작거나 같은 수의 커널 스레드로 다중화합니다. 개발자가 원하는 만큼 스레드를 만들 수 있고 병렬 실행도 가능하지만, 구현이 어렵습니다. (변형으로 특정 사용자 스레드를 커널 스레드에 고정하는 '두 수준 모델'이 있습니다.)  

## 4.4. 스레드 라이브러리
- 프로그래밍 언어나 운영체제는 개발자에게 스레드를 생성하고 관리할 수 있는 API를 제공하며, 크게 세 가지 라이브러리가 주로 사용됩니다.  
- POSIX Pthreads: POSIX 표준(IEEE 1003.1c)에 정의된 스레드 생성 및 동기화 API로, 구현이 아닌 '규격'입니다. 주로 Linux, macOS 등 UNIX 계열 시스템에서 사용됩니다.  
- Windows Threads: Windows 시스템에서 제공하는 커널 수준의 스레드 라이브러리입니다.  
- Java Threads: Java 프로그램에서 직접 스레드를 생성하고 관리할 수 있게 해줍니다. JVM이 구동되는 호스트 운영체제의 스레드 라이브러리(Windows API 또는 Pthreads)를 사용하여 구현됩니다.  

\* Java 1.5부터는 스레드 생성과 실행을 분리하고 스레드로부터 결과를 반환받을 수 있는 Callable과 Future 인터페이스 기반의 Executor 프레임워크(java.util.concurrent)를 제공하여 보다 견고한 멀티스레드 관리를 지원합니다.  

- 스레드를 생성할 때 부모 스레드가 자식 스레드를 만들고 각자 독립적으로 실행되는 방식을 비동기 스레딩(Asynchronous threading)이라 하고, 부모 스레드가 생성한 모든 자식 스레드가 종료(join)될 때까지 기다렸다가 실행을 재개하는 방식을 동기 스레딩(Synchronous threading)이라고 합니다.  

## 4.5 Implicit Threading (암묵적 스레딩)
- 수백~수천 개의 코어를 갖춘 멀티코어 환경이 일반화됨에 따라, 개발자가 직접 명시적(Explicit)으로 스레드를 생성·관리하고 동기화하는 작업이 매우 복잡해졌습니다.
- 암묵적 스레딩은 스레드의 생성과 관리 책임을 개발자에서 컴파일러 및 런타임 라이브러리로 넘기는 기법입니다. 
- 개발자는 동시 실행이 가능한 '작업(Task)' 단위만 정의하고, 실제 스레드 생성 및 스케줄링은 시스템이 자동으로 처리합니다.

### 4.5.1. Thread Pools (스레드 풀)

- 프로세스 시작 시 또는 초기에 일정한 수의 스레드를 미리 생성해 풀(Pool)에 보관해 두고, 작업 요청이 들어올 때마다 풀에서 놀고 있는 스레드를 할당해 처리하는 방식입니다.

#### 4.5.1.1. 스레드 풀의 장점:
- 매번 스레드를 새롭게 생성/해제하는 비용이 줄어들어 처리 속도가 향상됩니다.
- 스레드의 최대 개수를 제한할 수 있어 시스템 자원 고갈을 방지합니다.
- 작업 생성 메커니즘과 작업 실행 메커니즘을 분리할 수 있습니다.

### 4.5.2. Fork-Join parallelism (포크-조인 병렬성)
- 메인 스레드가 작업을 여러 개의 작은 작업으로 분할하여 자식 스레드를 생성(fork)한 후, 병렬로 실행된 결과를 모아 하나의 최종 결과로 합치는(join) 방식입니다.
- 암묵적 스레딩에서의 Fork-Join은 개발자가 직접 스레드를 생성하는 대신 병렬 영역만 지정하고, 라이브러리가 스레드 수와 작업 배정을 관리합니다.
- Java의 ForkJoinPool 및 여러 병렬 프레임워크의 기본 구조로 사용됩니다.

### 4.5.3. OpenMP
- C, C++, Fortran 등에서 컴파일러 지시어(Directive)를 통해 병렬 처리를 지원하는 API 및 런타임 라이브러리입니다.

#### 4.5.3.1. OpenMP의 주요 특징
- #pragma omp parallel 지시어를 코드 블록 앞에 선언하면, 컴파일러가 해당 블록을 '병렬 영역(Parallel region)'으로 지정합니다.
- 코어 개수만큼 자동으로 스레드를 생성하여 병렬 영역 내의 코드를 동시에 수행합니다.
- #pragma omp parallel for를 통해 반복문(for loop)의 반복 작업을 여러 코어에 자동으로 나누어 처리할 수 있습니다.

### 4.5.4. Grand Central Dispatch (GCD)
- macOS 및 iOS 환경에서 쓰이는 Apple의 C/C++/Swift 언어용 병렬 처리 프레임워크입니다.

\* 작동 방식 (디스패치 큐, Dispatch Queue):

- 개발자는 블록(Block, ^{ ... }) 단위로 작업을 정의하여 디스패치 큐에 제출하기만 하면, GCD가 시스템 상황에 맞게 스레드 풀을 관리하며 실행합니다.
- 직렬 큐 (Serial Queue): FIFO 순서로 작업을 한 번에 하나씩 순차 실행합니다. (Main Queue가 대표적)
- 동시 큐 (Concurrent Queue): FIFO 순서로 작업을 꺼내되, 여러 작업을 동시에 병렬로 실행합니다.
- QoS(Quality of Service) 등급에 따라 우선순위(USER_INTERACTIVE, USER_INITIATED, UTILITY, BACKGROUND)를 다르게 부여할 수 있습니다.

### 4.5.5. Intel Threading Building Blocks (TBB)
- Intel에서 개발한 C++ 전용 템플릿 기반 라이브러리입니다.
- 개발자가 로우 레벨 스레드를 다루지 않고, parallel_for나 parallel_reduce 같은 고수준 반복문 알고리즘을 사용해 병렬 처리를 구현할 수 있게 돕습니다.
- 런타임 엔진이 가용한 코어에 맞춰 동적으로 부하 분산(Load balancing)과 작업 훔치기(Work stealing) 기법을 적용합니다.

## 4.6. Threading Issues(스레딩 이슈)

### 4.6.1. The fork() and exec() System Calls
- 다중 스레드 프로그램에서 fork() 시스템 콜을 호출할 때의 동작 방식 변화 문제입니다.
- fork() 호출 시 선택지:
```
호출한 스레드 하나만 새로 복사할 것인가?
프로세스의 모든 스레드를 통째로 복사할 것인가?
```
- 해결책:
```
UNIX 계열 OS는 두 가지 버전의 fork()를 모두 제공합니다.
만약 fork() 실행 직후 바로 exec()를 호출하여 새로운 프로그램을 로드할 예정이라면, 어차피 새로 복사된 스레드가 전부 덮어씌워지므로 호출한 스레드 하나만 복사하는 것이 효율적입니다.
```

### 4.6.2. Signal Handling (신호 처리)
- 신호(Signal)는 UNIX/Linux 환경에서 프로세스에 특정 이벤트(예: 0으로 나누기 오류, Ctrl+C 입력 등)가 발생했음을 알리기 위해 전달하는 메커니즘입니다.
- 문제점: 단일 스레드와 달리, 스레드가 여러 개인 프로세스에서는 신호를 어떤 스레드에게 전달해야 하는가?

신호 전달 방식 (4가지 옵션):
```
신호가 발생한 해당 스레드에게 전달 (예: Synchronous signal - 0으로 나누기)
프로세스 내의 모든 스레드에게 전달 (예: Asynchronous signal - Ctrl+C 종료)
프로세스 내의 특정 선택된 스레드들에게만 전달
프로세스 내에서 모든 신호를 전담하여 처리할 지정 스레드(Signal handling thread) 하나에 전달
```

### 4.6.3. Thread Cancellation (스레드 취소)
- 스레드가 작업을 완료하기 전에 외부(타 스레드)에서 해당 스레드를 중단시키는 작업입니다 (예: 웹 페이지 로딩 중 '취소' 버튼 클릭).
- 대상 스레드(Target Thread)를 취소하는 방식은 2가지가 있습니다.

#### 4.6.3.1. 비동기 취소 (Asynchronous Cancellation):
- 타 스레드가 대상 스레드를 즉시 강제 종료시킵니다.
- 문제점: 대상 스레드가 공유 자원을 수정 중이거나 할당받은 자원을 해제하지 못한 상태에서 중단되면 시스템 자원 누수 및 데이터 불일치가 발생할 수 있습니다.

#### 4.6.3.2. 지연 취소 (Deferred Cancellation):
- 대상 스레드가 주기적으로 취소 여부 플래그를 확인하여, 스스로 안전하게 종료할 수 있는 지점(Cancellation Point)에서 종료합니다.
- 자원 해제 및 상태 정리가 안전하게 이루어져 권장되는 방식입니다.

### 4.6.4. Thread-Local Storage (TLS, 스레드 로컬 저장소)
- 같은 프로세스에 속한 스레드들은 기본적으로 메모리와 데이터(전역 변수)를 공유하지만, 때로는 각 스레드만이 독점적으로 사용할 전역 데이터 공간이 필요할 수 있습니다.
- 함수 내부의 지역 변수(Local variable)와는 다릅니다. 지역 변수는 함수 실행 동안만 유효하지만, TLS는 전체 함수 호출 과정에 걸쳐 스레드가 살아있는 동안 계속 유지됩니다.
- static 변수와 유사하나, 스레드별로 독립된 값을 보장받는다는 점이 차이점입니다.

### 4.6.5. Scheduler Activations (스케줄러 활성화)
- 다대다(Many-to-Many) 또는 두 수준(Two-Level) 스레딩 모델에서 사용자 스레드 라이브러리와 커널 간의 통신 기술입니다.

#### 4.6.5.1. LWP (Lightweight Process):
- 사용자 스레드와 커널 스레드 사이를 연결해 주는 중간 가상 Processor 구조체입니다.
- Upcall 메커니즘: 커널 스레드가 블록(Block)되거나 특정 이벤트가 발생하면, 커널이 사용자 스레드 라이브러리에 알림(Upcall)을 보냅니다.
- 라이브러리는 Upcall 핸들러를 통해 가용한 다른 사용자 스레드를 LWP에 재배정하여 스케줄링을 지속할 수 있도록 돕습니다.

## 4.7. Operating-System Examples

### 4.7.1. Windows Threads
- Windows는 일대일(One-to-One) 스레딩 모델을 사용하여, 사용자 수준 스레드 하나당 하나의 커널 스레드를 맵핑합니다.
- 기본 특징: Windows 애플리케이션은 프로세스 단위로 실행되며, 프로세스는 하나 이상의 스레드를 포함합니다.
- 커널 전체가 다중 스레드로 동작합니다.

스레드의 주요 구성 요소:
```
Thread ID: 스레드를 고유하게 식별하는 ID.
Register set: 프로세서의 상태를 나타내는 레지스터 집합.
User / Kernel Stacks: 사용자 모드와 커널 모드 실행 시 각각 사용되는 별도의 스택.
TLS (Thread-Local Storage): 런타임 라이브러리 및 DLL이 사용하는 스레드 전용 데이터 영역.
```

내부 데이터 구조 (커널 레벨):
```
ETHREAD (Executive Thread Block): 스레드가 속한 프로세스 포인터, 실행 시작 주소, KTHREAD 포인터 등을 포함합니다.
KTHREAD (Kernel Thread Block): 커널 스케줄링 정보, 동기화 채널, 커널 스택 포인터 등을 포함하며 커널 공간에 상주합니다.
TEB (Thread Environment Block): 스레드 ID, 사용자 스택 포인터, TLS 배열 등을 포함하며 사용자 공간에 상주합니다.
```

### 4.7.2. Linux Threads
- Linux는 전통적인 프로세스와 스레드를 엄격히 구분하지 않으며, 제어 흐름 단위 전체를 작업(Task)이라는 용어로 다룹니다.

기본 특징:
```
Linux는 스레드를 특별한 형태의 프로세스, 즉 '자원을 공유하는 lightweight process(LWP)'로 취급합니다.
프로세스 생성 시 fork()를, 스레드 생성 시 clone() 시스템 콜을 사용합니다.
```

clone() 시스템 콜과 플래그:
```
clone()이 호출되면 task_struct 구조체가 생성되어 제어 흐름을 관리합니다.
전달되는 플래그(Flag) 값에 따라 부모 작업의 자원을 얼마만큼 공유(Share)할지 결정합니다.
```

동작 방식 차이:
```
플래그를 아무것도 전달하지 않고 clone()을 호출하면 fork()와 동일하게 자원을 전부 복사합니다.
CLONE_FS, CLONE_VM, CLONE_SIGHAND, CLONE_FILES 플래그를 모두 켜고 호출하면 부모와 데이터/자원을 공유하는 스레드(Thread)가 생성됩니다.
```
