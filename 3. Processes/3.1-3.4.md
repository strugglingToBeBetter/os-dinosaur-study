## Chapter 3 개요

현대 운영체제는 여러 프로그램을 동시에 실행한다. 사용자는 웹 브라우저, 음악 재생 프로그램, 코드 편집기 등을 동시에 사용하고, 운영체제 내부에서도 다양한 시스템 서비스가 실행된다.

운영체제는 이렇게 실행되는 작업을 **프로세스(Process)** 라는 단위로 관리한다. 각 프로세스의 실행 상태를 저장하고, CPU를 어떤 프로세스에 할당할지 결정하며, 프로세스를 생성하거나 종료하고, 필요한 경우 프로세스 간 통신을 지원한다.

이 장의 핵심 주제는 다음과 같다.

- 프로세스의 개념과 메모리 구조
- 프로세스 상태와 PCB
- 프로세스 스케줄링과 문맥 교환
- 프로세스 생성과 종료
- 프로세스 간 통신

# 3.1 Process Concept

## 3.1.1 The Process

### 프로세스의 개념

**프로세스는 실행 중인 프로그램이다.**

프로그램은 저장장치에 보관된 정적인 실행 파일이다. 반면 프로세스는 프로그램이 메모리에 적재되어 CPU 명령어를 실행하고 있는 동적인 존재다.

예를 들어 Chrome 실행 파일 자체는 프로그램이다. 사용자가 Chrome을 실행하면 운영체제는 해당 프로그램을 메모리에 적재하고 실행에 필요한 정보를 구성하여 프로세스로 만든다.

| 구분      | 프로그램             | 프로세스                       |
| --------- | -------------------- | ------------------------------ |
| 성격      | 수동적이고 정적      | 능동적이고 동적                |
| 위치      | 저장장치             | 주로 메인 메모리               |
| 실행 상태 | 없음                 | 존재                           |
| 구성      | 명령어와 정적 데이터 | 명령어, 데이터, CPU 상태, 자원 |
| 예시      | Chrome 실행 파일     | 현재 실행 중인 Chrome          |

하나의 프로그램에서 여러 프로세스가 만들어질 수도 있다.

```text
Chrome 프로그램
├── Chrome 프로세스 A
├── Chrome 프로세스 B
└── Chrome 프로세스 C
```

각 프로세스는 같은 프로그램 코드를 실행할 수 있지만, 서로 다른 프로그램 카운터, 레지스터, 스택과 실행 상태를 가진다.

---

### 프로세스의 구성 요소

프로세스는 단순히 프로그램 코드만 의미하지 않는다. 실행에 필요한 다음 요소를 포함한다.

- 프로그램 코드
- 현재 실행 위치
- CPU 레지스터 값
- 전역 변수와 정적 변수
- 동적 할당 메모리
- 함수 호출 정보
- 열린 파일과 I/O 자원

---

### 프로세스의 메모리 구조

프로세스의 주소 공간은 일반적으로 다음과 같이 구성된다.

```text
높은 주소
┌─────────────────────────┐
│ Stack                   │
│ 함수 호출 정보          │
│ 매개변수, 지역 변수     │
│ 반환 주소               │
│            ↓            │
├─────────────────────────┤
│                         │
│ 사용 가능한 영역        │
│                         │
├─────────────────────────┤
│            ↑            │
│ Heap                    │
│ 동적 할당 메모리        │
├─────────────────────────┤
│ Data Section            │
│ 전역 변수, 정적 변수    │
├─────────────────────────┤
│ Text Section            │
│ 실행 가능한 프로그램 코드│
└─────────────────────────┘
낮은 주소
```

#### Text Section

CPU가 실행할 기계어 명령어가 저장되는 영역이다.

```c
int add(int a, int b) {
    return a + b;
}
```

위 함수가 컴파일된 기계어 코드가 Text 영역에 저장된다.

#### Data Section

전역 변수와 정적 변수가 저장되는 영역이다.

```c
int global_value = 10;
static int count = 0;
```

초기값이 있는 데이터와 초기값이 없는 데이터는 내부적으로 더 세부적인 영역으로 구분될 수 있다.

#### Heap

프로그램 실행 중 동적으로 할당한 메모리가 저장되는 영역이다.

```c
int *array = malloc(sizeof(int) * 100);
```

일반적으로 낮은 주소에서 높은 주소 방향으로 확장된다.

#### Stack

함수 호출과 관련된 정보가 저장되는 영역이다.

- 함수 매개변수
- 지역 변수
- 반환 주소
- 저장된 레지스터 값

```c
void calculate(int value) {
    int result = value * 2;
}
```

`value`, `result`, 호출이 끝난 뒤 돌아갈 주소 등이 스택에 저장된다. 스택은 일반적으로 높은 주소에서 낮은 주소 방향으로 확장된다.

---

### 프로그램과 프로세스의 관계

프로그램 자체는 수동적이다. 프로그램이 실행되면서 CPU와 메모리 등의 자원을 할당받아야 프로세스가 된다.

```text
저장장치의 실행 파일
        │
        │ 메모리에 적재
        ▼
프로세스 생성
├── 프로그램 코드
├── 실행 상태
├── 메모리
└── 운영체제가 할당한 자원
```

---

## 3.1.2 Process State

프로세스는 생성된 후 종료될 때까지 여러 상태를 이동한다.

### New

프로세스가 생성되고 있는 상태다.

운영체제가 프로세스를 관리하기 위한 자료구조를 만들고, 필요한 자원을 준비한다.

### Ready

CPU만 할당되면 즉시 실행할 수 있는 상태다.

프로세스는 메모리에 적재되어 실행 준비를 마쳤지만, 다른 프로세스가 CPU를 사용하고 있어 대기한다.

### Running

프로세스가 CPU를 할당받아 명령어를 실제로 실행하는 상태다.

하나의 CPU 코어에서는 특정 순간에 하나의 프로세스만 Running 상태가 될 수 있다. 여러 코어가 있다면 코어 수만큼 프로세스 또는 스레드가 병렬로 실행될 수 있다.

### Waiting

프로세스가 특정 이벤트를 기다리는 상태다. 운영체제에 따라 Blocked 상태라고도 부른다.

대표적으로 다음 상황에서 Waiting 상태가 된다.

- 디스크 읽기 완료 대기
- 네트워크 응답 대기
- 사용자 입력 대기
- 자식 프로세스 종료 대기
- 특정 동기화 이벤트 대기

Waiting 상태의 프로세스는 CPU를 할당받아도 실행을 계속할 수 없다. 기다리는 이벤트가 먼저 완료되어야 한다.

### Terminated

프로세스가 실행을 완료한 상태다.

운영체제는 프로세스가 사용하던 메모리, 열린 파일, I/O 자원 등을 회수한다.

---

### 프로세스 상태 전이

```text
                       CPU 할당
              ┌──────────────────────┐
              │                      ▼
New ───────▶ Ready ───────────────▶ Running ───────▶ Terminated
             ▲    ▲                   │                  종료
             │    │                   │
             │    │ 선점 또는         │ I/O 요청
             │    │ 시간 할당량 만료   │ 이벤트 대기
             │    └───────────────────┘
             │                        ▼
             └──────────────────── Waiting
                   I/O 또는 이벤트 완료
```

주요 상태 전이는 다음과 같다.

| 전이                 | 원인                         |
| -------------------- | ---------------------------- |
| New → Ready          | 프로세스 생성과 초기화 완료  |
| Ready → Running      | CPU 스케줄러가 프로세스 선택 |
| Running → Ready      | 시간 할당량 만료 또는 선점   |
| Running → Waiting    | I/O 요청 또는 이벤트 대기    |
| Waiting → Ready      | 기다리던 이벤트 완료         |
| Running → Terminated | 정상 종료 또는 강제 종료     |

여러 프로세스가 Ready나 Waiting 상태에 있을 수 있지만, 하나의 CPU 코어에서는 한 순간에 하나의 프로세스만 실행된다.

## 3.1.3 Process Control Block

### PCB의 개념

운영체제는 각 프로세스를 **Process Control Block, PCB**라는 커널 자료구조로 표현한다.

PCB는 프로세스를 중단했다가 나중에 다시 실행하는 데 필요한 정보를 저장한다. 따라서 PCB는 운영체제 관점에서 프로세스를 나타내는 관리 정보라고 볼 수 있다.

```text
실행 중인 프로세스
        │
        ▼
운영체제 내부 PCB
├── 현재 상태
├── 다음 명령어 주소
├── CPU 레지스터
├── 메모리 정보
└── 열린 파일 정보
```

PCB는 Task Control Block이라고도 한다.

---

### PCB가 필요한 이유

CPU는 여러 프로세스를 번갈아 실행한다.

프로세스 A를 실행하다가 프로세스 B로 전환한 후, 다시 A를 실행하려면 A가 중단되기 직전의 상태를 알아야 한다.

예를 들어 다음 정보가 필요하다.

- 다음에 실행할 명령어 주소
- CPU 레지스터 값
- 스택 포인터
- 현재 프로세스 상태
- 사용 중인 메모리
- 열린 파일과 I/O 장치

운영체제는 이러한 정보를 PCB에 저장한다.

---

### PCB의 주요 구성 정보

| 항목                          | 설명                                         |
| ----------------------------- | -------------------------------------------- |
| Process State                 | New, Ready, Running, Waiting 등의 현재 상태  |
| Program Counter               | 다음에 실행할 명령어의 주소                  |
| CPU Registers                 | 범용 레지스터, 스택 포인터, 상태 레지스터 등 |
| CPU-Scheduling Information    | 우선순위, 스케줄링 큐 포인터 등              |
| Memory-Management Information | 페이지 테이블, 기준·한계 레지스터 등         |
| Accounting Information        | CPU 사용 시간, 프로세스 번호, 시간 제한 등   |
| I/O Status Information        | 할당된 I/O 장치와 열린 파일 목록             |

PCB는 프로세스의 전체 코드나 데이터를 복사해 보관하는 구조가 아니다. 프로세스를 관리하고 다시 시작하는 데 필요한 실행 문맥과 메타데이터를 보관한다.

```text
Process
├── Text
├── Data
├── Heap
├── Stack
└── 운영체제가 관리하는 PCB
    ├── Process State
    ├── Program Counter
    ├── CPU Registers
    ├── Scheduling Information
    ├── Memory Information
    └── I/O Information
```

교재는 PCB를 프로세스를 시작하거나 재시작하는 데 필요한 모든 데이터의 저장소라고 설명한다.

---

### Linux의 프로세스 관리

Linux에서는 PCB에 해당하는 구조체로 `task_struct`를 사용한다.

개념적으로 다음과 같은 정보를 포함한다.

```c
struct task_struct {
    long state;
    struct task_struct *parent;
    struct list_head children;
    struct files_struct *files;
    struct mm_struct *mm;
};
```

| 필드       | 역할                    |
| ---------- | ----------------------- |
| `state`    | 프로세스 상태           |
| `parent`   | 부모 프로세스           |
| `children` | 자식 프로세스 목록      |
| `files`    | 열린 파일 정보          |
| `mm`       | 프로세스 주소 공간 정보 |

실제 Linux의 `task_struct`는 훨씬 많은 정보를 포함하며, 커널은 이를 사용해 프로세스와 스레드를 관리한다.

## 3.1.4 Threads

앞에서 설명한 기본 프로세스 모델은 하나의 프로세스가 하나의 실행 흐름만 가진다고 가정한다.

```text
Process
└── 하나의 실행 흐름
```

하나의 실행 흐름을 **스레드(Thread)**라고 한다.

단일 스레드 프로세스는 한 번에 하나의 작업 흐름만 수행한다. 예를 들어 워드 프로세서가 단일 스레드로만 동작한다면 사용자의 입력을 처리하면서 동시에 맞춤법 검사를 수행하기 어렵다.

멀티스레드 프로세스에서는 하나의 프로세스가 여러 실행 흐름을 가질 수 있다.

```text
Word Processor Process
├── Thread 1: 사용자 입력 처리
├── Thread 2: 맞춤법 검사
└── Thread 3: 자동 저장
```

멀티코어 시스템에서는 여러 스레드가 서로 다른 코어에서 실제로 병렬 실행될 수 있다.

스레드를 지원하는 시스템에서는 PCB 또는 관련 커널 자료구조가 각 스레드의 실행 상태도 관리해야 한다.

- 각 스레드의 프로그램 카운터
- 각 스레드의 CPU 레지스터
- 각 스레드의 스택
- 각 스레드의 실행 상태

프로세스 내부의 스레드 구조와 멀티스레딩 모델은 Chapter 4에서 자세히 다룬다.

# 3.2 Process Scheduling

운영체제에는 Ready 상태인 프로세스가 여러 개 존재할 수 있다. 그러나 CPU 코어 수는 제한되어 있으므로 운영체제는 어떤 프로세스를 실행할지 선택해야 한다.

이 과정을 **프로세스 스케줄링(Process Scheduling)**이라고 한다.

프로세스 스케줄링의 목적은 다음과 같다.

- CPU 사용률을 높인다.
- 여러 프로세스에 CPU 사용 기회를 제공한다.
- 사용자에게 빠른 응답을 제공한다.
- CPU와 I/O 장치가 가능한 한 쉬지 않도록 한다.

---

## 3.2.1 Scheduling Queues

운영체제는 프로세스의 상태와 대기 목적에 따라 프로세스를 여러 큐에 보관한다.

### Ready Queue

메모리에 적재되어 있고, CPU만 할당되면 실행할 수 있는 프로세스들이 대기하는 큐다.

```text
Ready Queue
┌──────┐   ┌──────┐   ┌──────┐
│ PCB1 │ → │ PCB4 │ → │ PCB7 │
└──────┘   └──────┘   └──────┘
```

큐에 프로세스의 전체 메모리 내용이 저장되는 것은 아니다. 일반적으로 프로세스를 나타내는 PCB가 연결된다.

---

### Wait Queue

특정 이벤트가 완료되기를 기다리는 프로세스가 들어가는 큐다.

이벤트 종류마다 별도의 Wait Queue가 존재할 수 있다.

```text
Disk Wait Queue
[Process A] → [Process C]

Network Wait Queue
[Process B]

Child-Termination Wait Queue
[Process D]
```

예를 들어 디스크 읽기를 요청한 프로세스는 디스크 작업이 완료될 때까지 해당 I/O Wait Queue에서 대기한다. I/O가 완료되면 다시 Ready Queue로 이동한다.

---

### 프로세스의 큐 이동

```text
                    시간 할당량 만료
                  ┌─────────────────┐
                  │                 ▼
Ready Queue ──▶ CPU 실행 ───────▶ Ready Queue
                  │
                  │ I/O 요청
                  ▼
             I/O Wait Queue
                  │
                  │ I/O 완료
                  └──────────────▶ Ready Queue
```

프로세스는 실행 과정에서 Ready Queue와 여러 Wait Queue 사이를 반복적으로 이동한다.

1. 새로운 프로세스가 Ready Queue에 들어간다.
2. 스케줄러가 프로세스를 선택한다.
3. 선택된 프로세스가 CPU에서 실행된다.
4. I/O를 요청하면 Wait Queue로 이동한다.
5. I/O가 끝나면 Ready Queue로 돌아온다.
6. 실행이 끝나면 종료된다.

---

## 3.2.2 CPU Scheduling

### CPU 스케줄러의 역할

**CPU 스케줄러**는 Ready Queue에 있는 프로세스 중 하나를 선택해 CPU 코어를 할당한다.

```text
Ready Queue
[P1] → [P2] → [P3]
          │
          ▼
     CPU Scheduler
          │
          ▼
       CPU Core
```

프로세스는 다음과 같은 이유로 CPU 사용을 중단할 수 있다.

- I/O를 요청함
- 실행을 완료함
- 시간 할당량을 모두 사용함
- 더 높은 우선순위 프로세스에 의해 선점됨
- 특정 이벤트를 기다림

따라서 CPU 스케줄러는 매우 자주 실행된다.

---

### 다중 프로그래밍의 목적

다중 프로그래밍은 여러 프로세스를 메모리에 적재해 CPU가 가능한 한 쉬지 않도록 하는 방식이다.

```text
Process A: CPU 사용 → I/O 대기
Process B:             CPU 사용 → I/O 대기
Process C:                         CPU 사용
```

프로세스 A가 I/O를 기다리는 동안 운영체제가 B 또는 C를 실행하면 CPU가 놀지 않는다.

---

### 시분할의 목적

시분할 시스템에서는 CPU를 여러 프로세스에 짧은 시간씩 번갈아 할당한다.

```text
시간 ───────────────────────────▶

P1 실행 │ P2 실행 │ P3 실행 │ P1 실행 │ ...
```

CPU 전환이 빠르게 반복되므로 사용자는 여러 프로그램이 동시에 실행되는 것처럼 느낀다.

---

### I/O-bound 프로세스와 CPU-bound 프로세스

프로세스는 CPU를 사용하는 특성에 따라 크게 두 종류로 나눌 수 있다.

| 구분          | I/O-bound Process        | CPU-bound Process      |
| ------------- | ------------------------ | ---------------------- |
| 주된 작업     | I/O 요청                 | 계산                   |
| CPU 사용 구간 | 짧음                     | 김                     |
| 대기 빈도     | 높음                     | 상대적으로 낮음        |
| 예시          | 네트워크 요청, 파일 읽기 | 영상 인코딩, 수치 계산 |

#### I/O-bound 프로세스

짧게 CPU를 사용한 뒤 자주 I/O를 요청한다.

```text
CPU 사용 → 네트워크 대기 → CPU 사용 → 디스크 대기
```

#### CPU-bound 프로세스

긴 시간 동안 계산을 수행한다.

```text
CPU 계산 → CPU 계산 → CPU 계산 → 소량의 I/O
```

운영체제가 서로 다른 특성의 프로세스를 적절히 스케줄링하면 CPU와 I/O 장치를 효율적으로 사용할 수 있다.

---

## 3.2.3 Context Switch

### 문맥의 의미

프로세스의 **문맥(Context)**은 프로세스가 현재 어디까지 실행되었으며, 다시 실행하기 위해 어떤 상태가 필요한지를 의미한다.

주요 문맥 정보는 다음과 같다.

- 프로그램 카운터
- CPU 레지스터
- 스택 포인터
- 프로세스 상태
- 메모리 관리 정보

이러한 정보는 PCB에 저장된다.

---

### Context Switch의 개념

**문맥 교환(Context Switch)**은 CPU가 현재 실행 중인 프로세스의 상태를 저장하고, 다른 프로세스의 상태를 복원하여 실행 대상을 바꾸는 과정이다.

```text
Process P0 실행
       │
       ▼
P0의 CPU 상태를 PCB0에 저장
       │
       ▼
PCB1에서 P1의 CPU 상태 복원
       │
       ▼
Process P1 실행
```

---

### 동작 과정

P0에서 P1으로 CPU 사용자가 변경된다고 가정하면 다음 순서로 진행된다.

1. 인터럽트, 시스템 콜 또는 스케줄링 이벤트가 발생한다.
2. 운영체제가 P0의 실행 상태를 PCB0에 저장한다.
3. CPU 스케줄러가 다음 프로세스 P1을 선택한다.
4. PCB1에 저장된 실행 상태를 CPU에 복원한다.
5. P1이 이전에 중단된 위치부터 실행을 재개한다.

```text
P0 Running
    │
    ├── P0 상태 저장 → PCB0
    │
    ├── 다음 프로세스 P1 선택
    │
    └── P1 상태 복원 ← PCB1
                         │
                         ▼
                     P1 Running
```

---

### Context Switch의 비용

문맥 교환 중에는 사용자 프로세스의 실제 작업이 수행되지 않는다. 따라서 문맥 교환에 사용되는 시간은 운영체제의 관리 오버헤드다.

문맥 교환 비용에 영향을 주는 요소는 다음과 같다.

- 저장하고 복원할 레지스터 수
- CPU 아키텍처
- 메모리 관리 구조
- 운영체제 구현 방식
- 캐시와 TLB 상태

문맥 교환이 지나치게 자주 발생하면 CPU가 실제 작업보다 프로세스 상태를 저장하고 복원하는 데 많은 시간을 사용할 수 있다.

---

### 인터럽트와 Context Switch의 차이

인터럽트가 발생한다고 해서 항상 프로세스 간 Context Switch가 발생하는 것은 아니다.

```text
P1 실행
→ 인터럽트 발생
→ 커널이 인터럽트 처리
→ 다시 P1 실행
```

위 경우에는 사용자 모드와 커널 모드 사이의 실행 전환은 있지만, 실행 프로세스는 계속 P1이므로 프로세스 간 문맥 교환은 발생하지 않을 수 있다.

반면 인터럽트 처리 후 스케줄러가 다른 프로세스를 선택하면 Context Switch가 발생한다.

```text
P1 실행
→ 타이머 인터럽트
→ 스케줄러 실행
→ P2 선택
→ P2 실행
```

---

# 3.3 Operations on Processes

운영체제는 프로세스를 생성하고 종료할 수 있는 기능을 제공한다.

대부분의 시스템에서 프로세스는 다른 프로세스를 생성할 수 있다. 이때 생성하는 프로세스를 **부모 프로세스**, 생성된 프로세스를 **자식 프로세스**라고 한다.

---

## 3.3.1 Process Creation

### 프로세스 계층

프로세스가 다른 프로세스를 생성하면 부모와 자식 관계가 만들어진다. 이 관계가 반복되면 트리 형태의 프로세스 계층이 형성된다.

```text
Parent Process
├── Child Process 1
│   └── Grandchild Process
└── Child Process 2
```

운영체제는 각 프로세스에 고유한 **Process Identifier, PID**를 부여한다.

PID는 운영체제가 프로세스를 구분하고 관리하는 데 사용된다.

---

### 부모와 자식의 자원 공유

부모와 자식 프로세스의 자원 관계는 운영체제 정책에 따라 다음과 같이 구성될 수 있다.

1. 부모와 자식이 모든 자원을 공유한다.
2. 부모 자원의 일부만 자식과 공유한다.
3. 부모와 자식이 자원을 공유하지 않는다.

일반적으로 부모와 자식은 별도의 주소 공간을 가진 독립된 프로세스다. 따라서 자식이 자신의 일반 변수를 변경해도 부모의 변수에는 직접 반영되지 않는다.

```c
int value = 10;

pid_t pid = fork();

if (pid == 0) {
    value = 20;
}
```

자식 프로세스가 `value`를 20으로 변경하더라도 부모 프로세스의 `value`는 10으로 유지된다.

부모와 자식이 데이터를 공유하려면 공유 메모리나 메시지 전달 등의 IPC가 필요하다.

---

### 부모와 자식의 실행 방식

부모와 자식은 다음 두 방식 중 하나로 실행될 수 있다.

#### 동시에 실행

부모와 자식이 독립적으로 계속 실행된다.

```text
Parent ─────────────────────────▶
Child  ─────────────────────────▶
```

#### 부모가 자식의 종료를 기다림

부모가 `wait()`를 호출해 자식이 종료될 때까지 기다린다.

```text
Parent: 실행 → wait() ───────────────▶ 실행 재개
                       Child 실행 → 종료
```

---

### 부모와 자식의 주소 공간

새 프로세스가 생성될 때 주소 공간은 다음 방식으로 구성될 수 있다.

1. 자식이 부모의 주소 공간을 복제한다.
2. 자식의 주소 공간에 새로운 프로그램을 적재한다.

UNIX 계열 시스템은 일반적으로 `fork()`와 `exec()`를 조합한다.

```text
부모 프로세스
     │
     └── fork()
          │
          └── 자식 프로세스
               부모의 주소 공간을 복제
                    │
                    └── exec()
                         새로운 프로그램으로 교체
```

---

### UNIX의 `fork()`

`fork()`는 현재 프로세스를 복제하여 자식 프로세스를 생성한다.

```c
pid_t pid = fork();
```

`fork()`의 반환값을 이용하여 부모와 자식을 구분한다.

| 반환값 | 의미                                    |
| ------ | --------------------------------------- |
| 음수   | 프로세스 생성 실패                      |
| 0      | 현재 실행 흐름이 자식 프로세스          |
| 양수   | 현재 실행 흐름이 부모이며 값은 자식 PID |

```c
pid_t pid = fork();

if (pid < 0) {
    // 프로세스 생성 실패
} else if (pid == 0) {
    // 자식 프로세스가 실행
} else {
    // 부모 프로세스가 실행
}
```

`fork()` 이후 부모와 자식은 `fork()` 다음 명령어부터 각각 실행한다.

다만 둘 중 어떤 프로세스가 먼저 실행될지는 CPU 스케줄링 결과에 따라 달라진다.

---

### UNIX의 `exec()`

`exec()` 계열 시스템 콜은 현재 프로세스의 주소 공간을 새로운 프로그램으로 교체한다.

```c
execlp("/bin/ls", "ls", NULL);
```

성공하면 현재 프로세스의 다음 요소들이 새 프로그램으로 대체된다.

- Text 영역
- Data 영역
- Heap
- Stack

```text
자식 프로세스
기존 프로그램 실행
       │
       └── exec("/bin/ls")
                  │
                  ▼
             ls 프로그램 실행
```

`exec()`는 새로운 프로세스를 생성하지 않는다.

- `fork()`: 새로운 프로세스를 생성
- `exec()`: 현재 프로세스가 실행하는 프로그램을 교체

`exec()`가 성공하면 기존 프로그램으로 돌아오지 않는다. 기존 주소 공간이 새로운 프로그램으로 교체되었기 때문이다.

---

### UNIX의 `wait()`

부모 프로세스는 `wait()`를 호출해 자식 프로세스가 종료될 때까지 기다릴 수 있다.

```c
wait(NULL);
```

```text
Parent
  │
  ├── fork()
  │      └── Child 실행
  │
  ├── wait()
  │      └── Parent는 Waiting 상태
  │
  └── Child 종료 후 실행 재개
```

`wait()`는 단순히 기다리는 역할만 하는 것이 아니다.

- 자식 프로세스의 종료를 기다린다.
- 자식의 종료 상태를 전달받는다.
- 종료된 자식의 남은 프로세스 정보를 정리한다.

---

### `fork()`-`exec()`-`wait()` 실행 흐름

```c
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();

    if (pid < 0) {
        return 1;
    }

    if (pid == 0) {
        execlp("/bin/ls", "ls", NULL);
        return 1;
    }

    wait(NULL);
    return 0;
}
```

실행 과정은 다음과 같다.

1. 부모 프로세스가 `fork()`를 호출한다.
2. 자식 프로세스가 생성된다.
3. 자식이 `exec()`를 호출한다.
4. 자식의 주소 공간이 `ls` 프로그램으로 교체된다.
5. 부모는 `wait()`를 호출하고 대기한다.
6. 자식이 종료된다.
7. 부모가 다시 실행된다.

---

### Windows의 `CreateProcess()`

Windows는 UNIX의 `fork()`와 다른 프로세스 생성 방식을 사용한다.

Windows에서는 `CreateProcess()`를 호출할 때 새 프로세스와 실행할 프로그램을 함께 지정한다.

```c
CreateProcess(
    applicationName,
    commandLine,
    NULL,
    NULL,
    FALSE,
    0,
    NULL,
    NULL,
    &startupInfo,
    &processInfo
);
```

| UNIX                          | Windows                             |
| ----------------------------- | ----------------------------------- |
| `fork()`로 자식 프로세스 생성 | `CreateProcess()`로 프로세스 생성   |
| `exec()`로 새 프로그램 적재   | 생성할 때 프로그램을 함께 지정      |
| `wait()`로 종료 대기          | `WaitForSingleObject()`로 종료 대기 |

---

## 3.3.2 Process Termination

### 정상 종료

프로세스는 마지막 명령어를 실행하거나 `exit()` 시스템 콜을 호출해 종료할 수 있다.

```c
exit(0);
```

프로세스가 종료되면 운영체제는 프로세스가 사용하던 자원을 회수한다.

- 메모리
- 열린 파일
- I/O 버퍼
- 할당된 장치
- 커널 내부 관리 자원

프로세스는 종료하면서 부모에게 종료 상태 값을 전달할 수 있다.

```c
exit(1);
```

부모는 `wait()` 또는 관련 시스템 콜로 이 종료 상태를 확인할 수 있다.

---

### 부모에 의한 자식 종료

부모 프로세스는 특정 상황에서 자식 프로세스를 종료할 수 있다.

대표적인 이유는 다음과 같다.

- 자식이 할당된 자원을 초과 사용함
- 자식이 수행하는 작업이 더 이상 필요하지 않음
- 부모가 종료되어 자식을 유지할 필요가 없음
- 자식이 비정상적으로 동작함

운영체제는 임의의 프로세스가 다른 프로세스를 종료하지 못하도록 권한을 검사한다.

---

### Cascading Termination

일부 운영체제에서는 부모 프로세스가 종료될 때 자식과 후손 프로세스도 함께 종료된다.

이를 **연쇄 종료(Cascading Termination)**라고 한다.

```text
Parent 종료
├── Child 1 종료
│   └── Grandchild 종료
└── Child 2 종료
```

운영체제가 프로세스 계층을 따라 내려가면서 모든 후손 프로세스를 종료한다.

---

### Zombie Process

자식 프로세스가 종료되었지만 부모가 아직 `wait()`를 호출하지 않은 상태를 **Zombie Process**라고 한다.

자식의 실행은 이미 끝났으며 대부분의 자원도 회수되었다. 하지만 부모에게 종료 정보를 전달하기 위해 다음과 같은 최소 정보가 남아 있다.

- PID
- 종료 상태
- CPU 사용 통계
- 프로세스 테이블 엔트리

```text
Child 종료
    │
    ├── 메모리와 대부분의 자원 회수
    └── 종료 정보 유지
             │
             ▼
          Zombie
```

부모가 `wait()`를 호출하면 남은 정보가 완전히 제거된다.

```text
Parent가 wait() 호출
        │
        ▼
Zombie 정보 수거 및 제거
```

Zombie 프로세스는 실행되지 않으므로 CPU를 사용하지 않지만, 프로세스 테이블의 엔트리와 PID를 차지한다. 부모가 계속 `wait()`를 호출하지 않으면 Zombie가 누적되어 새로운 프로세스 생성에 문제가 생길 수 있다.

---

### Orphan Process

자식 프로세스가 실행 중인데 부모 프로세스가 먼저 종료된 경우, 해당 자식을 **Orphan Process**라고 한다.

```text
Parent 종료
    │
    └── Child는 계속 실행
             │
             ▼
           Orphan
```

전통적인 UNIX에서는 `init` 프로세스가 고아 프로세스의 새로운 부모가 된다.

현대 Linux에서는 `systemd` 또는 고아 프로세스를 관리하도록 지정된 다른 프로세스가 부모 역할을 넘겨받을 수 있다. 새 부모는 해당 프로세스가 종료되면 `wait()`를 통해 종료 정보를 수거한다.

---

### Zombie와 Orphan 비교

| 구분         | Zombie Process                        | Orphan Process                        |
| ------------ | ------------------------------------- | ------------------------------------- |
| 자식의 상태  | 이미 종료됨                           | 아직 실행 중                          |
| 부모의 상태  | 살아 있지만 종료 정보를 수거하지 않음 | 부모가 먼저 종료됨                    |
| 남아 있는 것 | 종료 상태와 프로세스 테이블 정보      | 정상적인 실행 자원                    |
| 처리 방법    | 부모가 `wait()` 호출                  | 다른 시스템 프로세스가 부모 역할 상속 |
| 주요 문제    | 누적 시 프로세스 테이블 고갈          | 일반적으로 운영체제가 자동 관리       |

---

### 3.3.2.1 Android Process Hierarchy

모바일 장치는 데스크톱이나 서버보다 메모리와 배터리 자원이 제한적이다. 따라서 Android는 메모리가 부족할 때 실행 중인 프로세스를 종료하여 자원을 확보할 수 있다.

Android는 프로세스를 임의로 종료하지 않고 중요도에 따라 분류한다.

중요도가 높은 순서는 다음과 같다.

| 순위 | 프로세스 종류      | 설명                                           |
| ---: | ------------------ | ---------------------------------------------- |
|    1 | Foreground Process | 사용자가 현재 직접 상호작용하는 프로세스       |
|    2 | Visible Process    | 전면에는 없지만 화면에 영향을 주는 프로세스    |
|    3 | Service Process    | 음악 재생 등 사용자에게 인식되는 서비스를 수행 |
|    4 | Background Process | 화면에는 보이지 않지만 백그라운드 작업을 수행  |
|    5 | Empty Process      | 활성 컴포넌트 없이 캐시 목적으로 존재          |

자원을 회수해야 할 때는 중요도가 낮은 프로세스부터 종료한다.

```text
Empty
  ↓
Background
  ↓
Service
  ↓
Visible
  ↓
Foreground
```

하나의 프로세스가 여러 조건에 해당하면 Android는 더 높은 중요도를 적용한다.

예를 들어 어떤 프로세스가 서비스를 수행하면서 화면에도 영향을 준다면 Service가 아니라 Visible Process로 분류한다.

Android 애플리케이션이 권장 생명주기 규칙을 따르면, 프로세스가 종료되기 전에 필요한 상태를 저장하고 사용자가 다시 애플리케이션으로 돌아왔을 때 해당 상태를 복원할 수 있다.

---

# 3.4 Interprocess Communication

## 독립 프로세스와 협력 프로세스

동시에 실행되는 프로세스는 다른 프로세스와의 관계에 따라 독립 프로세스와 협력 프로세스로 구분할 수 있다.

### Independent Process

다른 프로세스와 데이터를 공유하지 않고, 다른 프로세스의 실행에 영향을 주거나 받지 않는 프로세스다.

```text
Process A          Process B
독립된 주소 공간   독립된 주소 공간
```

### Cooperating Process

다른 프로세스에 영향을 주거나 다른 프로세스의 영향을 받을 수 있는 프로세스다.

특히 데이터를 공유하는 프로세스는 협력 프로세스에 해당한다.

```text
Process A ←── 데이터 교환 ──→ Process B
```

---

## 프로세스 협력이 필요한 이유

### Information Sharing

여러 프로세스가 같은 정보를 사용해야 할 수 있다.

예를 들어 브라우저에서 복사한 텍스트를 코드 편집기에 붙여넣으려면 서로 다른 프로세스 사이에서 클립보드 데이터를 전달해야 한다.

```text
Browser Process
      │
      │ 복사
      ▼
Clipboard
      │
      │ 붙여넣기
      ▼
Editor Process
```

---

### Computation Speedup

하나의 큰 작업을 여러 하위 작업으로 분리하여 병렬로 처리하면 실행 시간을 줄일 수 있다.

```text
전체 이미지 처리
├── Process A: 상단 영역 처리
├── Process B: 중앙 영역 처리
└── Process C: 하단 영역 처리
```

다만 실제로 실행 시간이 줄어들려면 여러 CPU 코어에서 작업을 병렬로 실행할 수 있어야 한다.

---

### Modularity

시스템을 기능별 프로세스로 나누면 각 구성 요소의 역할을 분리할 수 있다.

```text
Web Service
├── Web Server Process
├── Database Process
├── Logging Process
└── Worker Process
```

모듈 간에는 IPC를 통해 필요한 정보만 교환한다.

---

## IPC의 개념

**Interprocess Communication, IPC**는 프로세스들이 데이터를 주고받고 실행을 조정할 수 있도록 운영체제가 제공하는 통신 메커니즘이다.

IPC는 다음 용도로 사용된다.

- 데이터 전달
- 작업 요청
- 처리 결과 반환
- 이벤트 알림
- 실행 순서 조정

일반적으로 각 프로세스는 서로 분리된 주소 공간을 가진다. 한 프로세스가 다른 프로세스의 메모리에 직접 접근할 수 없기 때문에 운영체제가 허용하는 별도의 통신 방법이 필요하다.

교재에서는 IPC의 기본 모델을 다음 두 가지로 구분한다.

```text
Interprocess Communication
├── Shared Memory
└── Message Passing
```

---

## Shared-Memory Model

### 개념

공유 메모리 방식에서는 운영체제가 여러 프로세스가 함께 접근할 수 있는 메모리 영역을 만든다.

```text
Process A ─┐
           ├── Shared Memory
Process B ─┘
```

프로세스들은 공유 영역에 데이터를 기록하거나 읽으면서 통신한다.

```text
Process A
   │
   │ 데이터 기록
   ▼
Shared Memory
   │
   │ 데이터 읽기
   ▼
Process B
```

---

### 동작 방식

1. 프로세스가 운영체제에 공유 메모리 생성을 요청한다.
2. 다른 프로세스가 해당 공유 메모리를 자신의 주소 공간에 연결한다.
3. 프로세스들이 공유 영역을 읽고 쓰면서 데이터를 교환한다.
4. 통신이 끝나면 공유 메모리 연결을 해제한다.

공유 메모리 영역을 생성하고 연결하는 초기 단계에는 운영체제의 개입이 필요하다. 그러나 영역이 설정된 후의 데이터 접근은 일반 메모리 읽기와 쓰기처럼 수행된다.

---

### 장점

공유 메모리가 설정된 후에는 프로세스가 직접 메모리를 읽고 쓸 수 있다. 매번 커널을 거쳐 데이터를 전달할 필요가 없으므로 대량의 데이터를 빠르게 교환하는 데 적합하다.

---

### 문제점

여러 프로세스가 같은 위치를 동시에 읽거나 수정하면 데이터 불일치가 발생할 수 있다.

예를 들어 두 프로세스가 동시에 같은 값을 증가시킨다고 가정한다.

```c
count = count + 1;
```

두 프로세스가 모두 기존 값 `10`을 읽은 뒤 각각 `11`을 기록하면, 두 번 증가했음에도 최종 결과가 `11`이 될 수 있다.

따라서 공유 메모리를 사용할 때는 프로세스가 다음과 같은 동기화 문제를 직접 해결해야 한다.

- 어느 프로세스가 먼저 접근할지
- 동시에 쓰는 것을 어떻게 막을지
- 데이터가 준비되었음을 어떻게 알릴지

뮤텍스, 세마포어 등의 동기화 도구는 이후 Chapter 6과 Chapter 7에서 다룬다.

---

## Message-Passing Model

### 개념

메시지 전달 방식에서는 프로세스가 운영체제가 제공하는 통신 기능을 통해 메시지를 주고받는다.

```text
Process A
    │
    │ send(message)
    ▼
Kernel
    │
    │ receive(message)
    ▼
Process B
```

기본적으로 다음과 같은 연산을 사용한다.

```text
send(message)
receive(message)
```

프로세스가 동일한 메모리 공간을 직접 공유하지 않아도 통신할 수 있다.

---

### 장점

- 공유 데이터에 대한 직접적인 충돌을 줄일 수 있다.
- 구조가 비교적 명확하다.
- 적은 양의 데이터를 전달하기에 적합하다.
- 서로 다른 컴퓨터에서 실행되는 프로세스 사이에도 적용하기 쉽다.
- 분산 시스템에 적합하다.

---

### 단점

메시지를 전송하거나 받을 때 시스템 콜과 커널 개입이 필요할 수 있다.

```text
송신 프로세스
    │
    │ 시스템 콜
    ▼
커널 메시지 영역
    │
    │ 전달 또는 복사
    ▼
수신 프로세스
```

이 과정에서 다음 비용이 발생할 수 있다.

- 사용자 모드와 커널 모드 전환
- 데이터 복사
- 메시지 큐 관리
- 송신자와 수신자 스케줄링

따라서 일반적으로 대용량 데이터 전달에서는 공유 메모리보다 느릴 수 있다.

---

## Shared Memory와 Message Passing 비교

| 구분             | Shared Memory                | Message Passing                  |
| ---------------- | ---------------------------- | -------------------------------- |
| 통신 방식        | 공통 메모리 영역을 읽고 씀   | 메시지를 송수신                  |
| 커널 개입        | 초기 설정에 주로 필요        | 메시지 송수신마다 필요할 수 있음 |
| 데이터 전달 성능 | 일반적으로 빠름              | 상대적으로 추가 비용이 있음      |
| 동기화           | 프로세스가 직접 해결         | 통신 연산에 일부 포함 가능       |
| 데이터 충돌      | 발생 가능                    | 직접적인 메모리 충돌이 적음      |
| 적합한 데이터    | 대용량 데이터                | 비교적 작은 메시지               |
| 분산 환경        | 일반적으로 구현이 어려움     | 구현하기 쉬움                    |
| 구현 복잡도      | 동기화 때문에 복잡할 수 있음 | 상대적으로 명확함                |

공유 메모리는 설정 이후 일반 메모리 접근으로 통신하므로 빠를 수 있다. 반면 메시지 전달은 작은 양의 데이터를 교환하거나 분산 시스템에서 통신할 때 유리하다. 많은 운영체제는 두 방식을 모두 지원한다.

---

## Chrome의 다중 프로세스 구조

교재는 프로세스 협력의 예시로 Chrome 브라우저의 다중 프로세스 구조를 소개한다.

하나의 브라우저 프로세스가 모든 탭을 처리하면 특정 탭의 웹 애플리케이션이 충돌했을 때 브라우저 전체가 종료될 수 있다.

Chrome은 이를 줄이기 위해 기능을 여러 프로세스로 분리한다.

```text
Chrome
├── Browser Process
├── Renderer Process: Tab A
├── Renderer Process: Tab B
├── Renderer Process: Tab C
└── Plug-in Process
```

### Browser Process

- 사용자 인터페이스 관리
- 디스크 I/O 관리
- 네트워크 I/O 관리

일반적으로 Chrome 실행 시 하나의 Browser Process가 생성된다.

### Renderer Process

- HTML 처리
- JavaScript 실행
- 이미지 렌더링
- 웹 페이지 화면 구성

일반적으로 서로 다른 사이트나 탭에 별도의 Renderer Process가 사용될 수 있다.

### Plug-in Process

특정 플러그인을 실행하기 위한 프로세스다.

---

### 다중 프로세스 구조의 효과

특정 탭의 Renderer Process가 충돌해도 다른 탭과 Browser Process가 반드시 함께 종료되는 것은 아니다.

```text
Tab B Renderer 충돌
        │
        ├── Tab B만 영향
        ├── Tab A는 계속 실행
        └── Browser Process도 계속 실행 가능
```

프로세스를 분리하면 다음 장점이 있다.

- 장애 격리
- 보안 격리
- 멀티코어 활용
- 탭별 자원 관리

반면 프로세스 수가 증가하므로 다음 비용도 발생한다.

- 프로세스별 독립 주소 공간
- 추가 메모리 사용
- 프로세스 간 통신 비용
- Context Switch 증가 가능성

Chrome의 프로세스들은 완전히 독립적으로만 동작하는 것이 아니라, 브라우저 기능을 제공하기 위해 IPC를 통해 서로 통신한다.

---

# 핵심 요약

1. **프로세스는 실행 중인 프로그램**이며, 코드뿐 아니라 실행 상태와 할당된 자원을 포함한다.

2. 프로세스 주소 공간은 일반적으로 Text, Data, Heap, Stack 영역으로 구성된다.

3. 프로세스는 New, Ready, Running, Waiting, Terminated 상태를 이동한다.

4. Ready 상태는 CPU만 기다리는 상태이고, Waiting 상태는 I/O나 이벤트 완료를 기다리는 상태다.

5. 운영체제는 프로세스를 PCB로 표현하며, PCB에는 프로그램 카운터, CPU 레지스터, 상태, 메모리 정보 등이 저장된다.

6. CPU 스케줄러는 Ready Queue에서 다음에 실행할 프로세스를 선택한다.

7. Context Switch는 현재 프로세스의 상태를 저장하고 다른 프로세스의 상태를 복원하는 과정이며, 실제 사용자 작업이 수행되지 않는 오버헤드다.

8. UNIX에서는 `fork()`로 자식 프로세스를 생성하고, `exec()`로 현재 프로세스의 프로그램을 교체하며, `wait()`로 자식 종료를 기다린다.

9. Zombie는 이미 종료되었지만 부모가 종료 정보를 수거하지 않은 프로세스다.

10. Orphan은 실행 중 부모가 먼저 종료된 자식 프로세스다.

11. Android는 메모리 부족 시 Empty, Background 등 중요도가 낮은 프로세스부터 종료한다.

12. 프로세스 간 통신은 크게 Shared Memory와 Message Passing 방식으로 구분된다.

13. Shared Memory는 빠르지만 동기화가 필요하고, Message Passing은 구조가 명확하고 분산 환경에 적합하지만 커널 개입 비용이 발생할 수 있다.

# 면접 포인트

## 프로그램과 프로세스의 차이는 무엇인가요?

프로그램은 저장장치에 존재하는 정적인 명령어와 데이터의 집합이고, 프로세스는 해당 프로그램이 메모리에 적재되어 실행 중인 동적인 인스턴스입니다. 프로세스는 프로그램 코드 외에도 프로그램 카운터, CPU 레지스터, 스택, 힙, 열린 파일 등의 실행 상태를 가집니다.

---

## Ready 상태와 Waiting 상태의 차이는 무엇인가요?

Ready 상태는 CPU만 할당되면 즉시 실행할 수 있는 상태입니다. Waiting 상태는 I/O 완료나 특정 이벤트 발생을 기다리는 상태이므로 CPU를 할당해도 바로 실행할 수 없습니다. 기다리던 이벤트가 완료되면 Waiting에서 Ready 상태로 이동합니다.

---

## PCB란 무엇인가요?

PCB는 운영체제가 프로세스를 표현하고 관리하기 위해 사용하는 커널 자료구조입니다. 프로세스 상태, 프로그램 카운터, CPU 레지스터, 스케줄링 정보, 메모리 정보, 열린 파일 등의 정보를 저장합니다. Context Switch가 발생하면 현재 프로세스의 실행 상태를 PCB에 저장하고, 다음 프로세스의 PCB에서 상태를 복원합니다.

---

## Context Switch는 왜 오버헤드인가요?

Context Switch 중에는 현재 프로세스의 CPU 상태를 저장하고 다른 프로세스의 상태를 복원합니다. 이 시간에는 사용자 프로세스의 실제 작업이 진행되지 않으므로 오버헤드입니다. 또한 새로운 프로세스가 실행되면서 캐시와 TLB의 적중률이 낮아질 수 있어 간접적인 성능 비용도 발생할 수 있습니다.

---

## 인터럽트가 발생하면 항상 Context Switch가 발생하나요?

아닙니다. 인터럽트 처리 후 원래 실행하던 프로세스로 돌아가면 프로세스 간 Context Switch는 발생하지 않을 수 있습니다. 인터럽트 처리 후 스케줄러가 다른 프로세스를 선택할 때 프로세스 간 Context Switch가 발생합니다.

---

## `fork()`와 `exec()`의 차이는 무엇인가요?

`fork()`는 현재 프로세스를 복제하여 새로운 자식 프로세스를 생성합니다. `exec()`는 새로운 프로세스를 만드는 것이 아니라 현재 프로세스의 주소 공간을 새로운 프로그램으로 교체합니다. UNIX에서는 일반적으로 `fork()`로 자식 프로세스를 만든 뒤 자식이 `exec()`를 호출하여 다른 프로그램을 실행합니다.

---

## Zombie Process와 Orphan Process의 차이는 무엇인가요?

Zombie Process는 자식이 이미 종료되었지만 부모가 `wait()`를 호출하지 않아 종료 정보가 남아 있는 상태입니다. Orphan Process는 자식이 실행 중인 상태에서 부모가 먼저 종료된 경우입니다. Zombie는 부모가 종료 정보를 수거해야 제거되며, Orphan은 `systemd` 등의 프로세스가 새로운 부모 역할을 맡습니다.

---

## Shared Memory와 Message Passing의 차이는 무엇인가요?

Shared Memory는 여러 프로세스가 동일한 메모리 영역을 직접 읽고 쓰는 방식입니다. 공유 영역 설정 이후에는 빠르게 데이터를 교환할 수 있지만 동시 접근을 제어하기 위한 별도의 동기화가 필요합니다.

Message Passing은 운영체제가 제공하는 `send()`와 `receive()` 등의 기능으로 메시지를 주고받는 방식입니다. 구조가 명확하고 분산 환경에 적합하지만, 시스템 콜과 커널 개입으로 인해 추가 비용이 발생할 수 있습니다.
